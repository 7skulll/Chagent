# 问题定位与修复

以用户报告的异常为起点，形成“触发条件 → 原因 → 修改 → 验证”的证据链。仅要求排查时先给出诊断，不自行扩大成代码修改。

## 复现与定位

1. 用文件工具读取相关配置、调用代码、测试和错误记录。若可用，通过 exec_command 查看工作区 Git 状态与差异，识别用户已有改动；不清理或覆盖它们。
2. 找到最短复现方式，优先运行现有针对性测试或命令。测试工具可能需要先用 tool_search 加载；按当前工具声明选择参数，不假设所有测试框架都被 run_tests 支持。
3. 把应用缺陷与依赖缺失、网络失败、容器不可用、审批拒绝和超时分开。工具结果中的 unknown 表示副作用未知，不是失败后可以直接再执行。

## 修改与验证

- 读取目标文件后再做最小修改。优先 edit_file 或 apply_patch，遵循当前工具的参数和补丁格式；若要求 expected_sha256 或 versions，使用最新读取的摘要。发生版本冲突先重读并合并，不盲目覆盖。
- 文件修改与命令执行继续走 Chagent 的正常门禁。拒绝或过期后停止对应操作，不换工具绕过审批。审批卡和工具结果才是执行依据，聊天中的同意不替代审批卡。
- 普通命令与测试在工作区容器内执行，不能据此推断用户宿主具备同样依赖。只有任务确需宿主原生能力时才使用 host_exec；交互进程用 host_process，每次写入仍按工具要求审批。不要为修复常规构建失败转去宿主运行。
- 修复后先重跑原复现，再运行受影响的必要检查。对于值得长期防止的行为回归，增加能够暴露原缺陷的测试；小型文案、样式等可逆变更采用适当的直接验证。
- 如果相同尝试仍失败，基于新证据改变假设，避免原样重复。超时、取消或未知结果后先检查文件、日志或状态；无法确认安全重试时说明阻塞点。

## 输出

说明具体原因、修改位置、实际运行的检查及结果。依赖未安装、未执行和跳过均不算通过。保留用户原有工作；不自动提交 Git、不推送或部署，除非用户任务包含这些动作。
