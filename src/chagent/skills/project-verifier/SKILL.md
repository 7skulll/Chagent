# 项目测试与验收

目标是回答“交付是否满足这次要求”，并让每项结论能够追溯到代码位置、实际命令或工具结果。验收结论只覆盖本次检查的项目版本和环境。

## 确定验收对象与判据

- 从当前用户要求、可见的原始需求和明确的验收标准提取检查项，标明来源。README 和历史报告可帮助理解项目，但不能覆盖用户要求，也不能把模型之前的“已完成”当作证明。
- 用 list_dir、glob、grep、read_file 找到实现、测试、依赖、启动配置和项目约定。工作区文件使用相对路径或模型侧 `/workspace`；不读取 Chagent 自身源码、数据库口令或宿主私有目录来补证据。
- 标准缺失时先做能确定的检查，说明采用的假设；只有缺失信息会改变验收结论或造成有风险的操作时才询问。不要为小任务强加完整测试矩阵。
- 为每项选择足以支持结论的验证：静态实现检查、自动测试、构建、接口请求、持续服务状态，或有可用工具时的浏览器操作。发现实现位置不等于已验证其运行行为。

## 执行与证据

- 通过 exec_command 查看已有 Git 状态和差异（如果工具可用），记录被验收的版本及未提交改动范围，不重置、清理或覆盖用户文件。非 Git 项目说明对象范围即可。
- 根据真实配置选择针对性命令。run_tests 参数未声明时先用 tool_search 加载；框架不支持时使用 exec_command，不虚构测试工具参数。普通测试和构建在容器中执行，依赖和网络问题如实记录，不改到宿主执行来掩盖失败。
- 每项保留命令或工具动作、工作目录、退出码、关键结果和来源位置。测试计数分别列出通过、失败、错误、跳过；命令退出码为零但没有收集到测试，不证明功能通过。历史日志标明时间与版本，只作参考。
- 测试、构建可能写入缓存或产物；按当前执行门禁操作。涉及生产数据、迁移、外发请求或替换现有服务时先确认任务授权与实际目标，不把“验收”当成所有副作用的授权。未知执行结果先查状态，不能当作失败后直接重做。
- 网站优先使用 site(action=status/probe/logs) 核对当前服务、实际 URL、路径状态和响应正文。只有任务包含运行验证且现有服务不会被无关替换时才启动；启动使用 site，不用后台 shell 维持服务。没有 site 时说明持续服务未验证。
- HTTP 200、构建通过、页面代码存在分别只能支持对应结论。没有浏览器工具时，视觉、点击、表单和跨浏览器行为标为未验证；接口测试不能替代实际页面操作。
- 只验收时不修改应用代码、不补测试来制造通过，不安装缺失依赖或变更配置，除非任务已授权相应环境准备。先报告可以独立完成的检查与阻塞项。用户明确要求“验收并修复”时可以修复，但保留修复前的问题证据，对修改后的版本重新检查，区分前后结果。

## 结果与交付

每个检查项使用一个状态：

| 状态 | 判据 |
|---|---|
| 通过 | 当前检查的证据满足该项明确标准；不能从部分测试推广到整个功能 |
| 失败 | 实际结果与标准冲突，例如断言失败、错误响应或缺少明确要求的实现 |
| 未验证 | 未执行或证据不足，例如没有浏览器、只读了代码、测试被跳过 |
| 阻塞 | 已尝试必要检查但依赖、权限、审批或环境条件阻止验证；写出原因 |

先给总体结论，再按需要列“检查项 / 状态 / 证据 / 缺口”。只有约定范围内全部必要检查通过时，才能说整体验收通过；否则说明“发现失败”或“尚不能确认完整通过”，不要用通过率掩盖关键缺口。运行耗时不等于成功率，文件差异也不证明功能正确。

报告实际执行范围、遗留问题和下一步，不自动提交、发布、重启其他服务或清理用户文件。用户需要文件报告时再用可用的产物工具交付；普通验收可直接在对话中呈现。
