# 关键路径优化：记忆提取与上下文构建

日期：2026-10-28。状态：已实现，154 项测试通过；真实供应商链路 8/9（唯一失败项为改动前即存在的 `/remember` 冗余文件写入）。同日修复了审查发现的一批队列与配置缺陷，见第 6 节。

对应[主链路诊断与优化方案](主链路诊断与优化方案.md)的第一阶段 A 与第二阶段 E、F。诊断基线曾指出两个把工作串进用户等待时间的位置：`AgentRunner.run` 在保存最终回答**之前**调用记忆提取模型；`ContextManager.prepare` 在每轮工具循环重新投影并重复计数整段历史。

## 1. 记忆提取：从运行内移出

### 改动前

```text
模型给出最终回答
  → prepare_completed()：再发一次模型请求做提取（同一总超时内）
  → 与回答一起在 run 完成事务里写候选
  → runs.finish(completed)
```

问题不只是慢：注入 2 秒提取、0.5 秒运行超时时，回答已经落库，运行终态却是 `failed`（诊断 F1）。提取模型不可用会让用户已经看到的内容变成"失败"。

### 改动后

```text
模型给出最终回答
  → runs.finish 事务内 on_completed()：
       · 显式 /remember → 确定性写入（无模型调用）
       · 其余满足条件 → 只插入 memory_jobs 一行
       · 发出 memory_job_queued，随后 run_completed
  → MemoryWorker（有界并发）先回收过期租约，再用 SKIP LOCKED 领取
  → 独立超时内调用模型 → 候选与 job 终态同事务提交
```

| 文件 | 职责 |
|---|---|
| `storage/migrations/0009_memory_jobs.sql` | 队列表：`run_id` 唯一、状态机、`attempts`、`available_at`、`lease_expires_at` |
| `storage/memory_jobs.py` | 入队、领取、完成、失败重试、回收过期租约 |
| `memory/worker.py` | 轮询与唤醒、租约、取消归队、`drain()` |
| `memory/service.py` | `on_completed`（入队）与 `run_job`（提取）分离 |

### 语义约定

- **入队与运行完成同事务。** job 只可能随 `run_completed` 一起出现，不存在"运行完成但任务丢失"或"任务存在但运行未完成"。
- **一个 run 一个 job。** `run_id` 唯一键防止重复提取；重复输入的去重仍由记忆仓库的 key/hash 判定，不依赖队列。
- **提取失败只影响 job。** 失败计入 `attempts`，未达上限则按 `retry_delay` 重新可用；达上限为 `failed`。运行终态永不被 worker 修改。
- **租约回收计一次尝试。** worker 崩溃（被 kill、OOM、网络分区）时行停留在 `running`，`fail()` 根本没机会执行。`reap_expired()` 在租约到期后回收：`attempts + 1`，未达上限回到 `queued`，达上限直接 `failed` 并补发 `memory_job_failed`，同时把该次尝试遗留的 `memory_extractions` 行标记为失败。若不计数，崩溃型失败可无限重试，`max_attempts` 只对抛异常的失败有效。
- **取消与崩溃必须分开。** 主动取消（关停或外部取消）走 `requeue`，不消耗次数；租约过期则一定计数——前者我们知道发生了什么，后者只知道进程没回来。
- **取消已完成任务不会改回运行状态。** 提取启动时运行早已终结。
- **记忆可用时间晚于回答。** 这是刻意取舍：网页后台 worker 立即接手；单次 CLI 在打印结果后 `drain`，超时则保留待下次处理；`--demo` 同样适用。
- **`drain()` 只推进"现在能跑"的任务。** 处于退避等待（`available_at > now()`）的任务不会被等待，因此 CLI 在 `drain` 之后用 `unfinished()` 判断，并明确打印"仍有 N 个任务会在下次运行继续"，不再假装队列已清空。
- **worker 并发受连接池约束。** 每个 worker 在读写时占用一个连接，`CHAGENT_MEMORY_WORKER_CONCURRENCY` 至多为 `CHAGENT_DB_POOL_MAX_SIZE - 1`（单连接池除外），以免 worker 占满连接池、让并发运行在 `db_timeout` 后失败。该组合在启动时校验，而不是留到运行期超时。
- **工具主动停止的运行不提取记忆。** `end_reason=tool_requested_stop` 没有最终回答可供比对，`on_completed` 以 `has_answer=False` 跳过入队；显式 `/remember` 仍照常确定性写入。这类运行的输入若含长期偏好，需要用户显式记住一次。
- **一次运行内召回结果复用。** 同一 run 内反复进入工具循环不再重复检索；**运行期间对记忆的编辑/删除在下一轮运行生效**，每次请求仍记录实际注入的版本与 revision。

### 超时的两种含义必须分开

`_extract` 内部的 `asyncio.timeout(policy.timeout)` 若直接向外抛 `CancelledError`，worker 会把它误判为"进程正在关闭"并把 job 塞回队列——不消耗次数，于是无限重排。当前实现把这个预算超时转换成普通失败（消耗一次尝试），只有外部取消才归队。这条是调试中真实踩到的坑，单独记录以免回退。

## 2. 上下文构建：投影一次，按累计成本选择

### 改动前

每次 `build()` 对每个已选消息 `deepcopy` + 序列化计数，且**每个候选轮次再整段重算一次**：200 条消息时一次构建序列化 10,602 条消息（近似二次），400 条时 41,202 条。压缩的二分试探又会多次调用 builder。

### 改动后

- `context/projection.py`：按**持久消息 ID** 缓存"模型可见投影 + 单条成本"。投影是存储消息的纯函数（去 `details`/`usage`/`duration_ms`、产物正文替换），消息行不变则成本不变。缓存有上限，超出整体清空，不做复杂淘汰。
- `ContextManager` 按 run 持有 `ProjectionCache`，`release(run_id)` 时丢弃；同一 run 内新增的已提交消息只投影一次。
- 轮次选择改为**累计成本**：固定开销（系统指令 + 摘要）+ 各轮成本求和，O(n) 而非 O(n²)。
- 最终请求仍做一次完整 `count(messages)` 作为权威值，累计值只用于选择。

### 计数器契约

`TokenCounter.additive = True` 是**显式承诺**：`count(messages)` 等于各条 `count([message])` 之和。`ByteTokenCounter` 满足（每条 JSON 字节 + 固定 8 字节开销，消息之间不交互）。

未声明该属性的计数器一律走原来的精确重算路径，不会因为"看起来可加"而算错。新增计数器若模仿真实分词器的跨消息行为（如合并 token），必须保持不声明。

## 4. 真实链路验证（付费供应商）

离线诊断用的是脚本化客户端。隔离这条性质还需要在真实供应商上验证，因此用[真实链路脚本](../scripts/test_live_chain.py)跑完整 9 个场景（`deepseek-v4-flash`，`--max-calls 26`）：

```sh
env -u CHAGENT_API_KEY PYTHONPATH="$PWD/src" uv run --env-file .env python scripts/test_live_chain.py \
  --case all --max-calls 26 --output docs/diagnostics/live-chain-step4-2026-10-28.json
```

原始结果见[live-chain-step4-2026-10-28.json](diagnostics/live-chain-step4-2026-10-28.json)，共 17 次供应商请求、19,553 tokens。

8/9 通过。`automatic_memory_candidate` 直接证实了隔离性质：

| 证据 | 值 |
|---|---|
| 事件顺序 | `run_completed` → `memory_extraction_started` → `memory_saved` |
| `memory_job_queued` | 出现在完成事务内、`run_completed` 之前 |
| job 终态 | `status=completed`，`attempts=0` |
| 供应商请求 | 两次独立请求：`purpose=task`（3 条消息）与 `purpose=memory`（2 条消息） |
| 时间 | 运行 1227ms，提取 751.71ms **发生在运行结束之后** |
| 候选 | 模型给出的称呼偏好被写入为 `candidate`，经仓库 API 审核后成为可用记忆 |

唯一失败项 `explicit_memory` 是**既有缺陷，与本次改动无关**：模型在 `/remember` 之后仍自行调用 `list_dir`/`read_file`/`write_file` 写了一份 `memory.json`（4 次请求），而确定性路径早已把记忆写入数据库。同日上午改动前的记录（[explicit-retest](diagnostics/live-chain-2026-10-28-explicit-retest.json)）是同样的失败形态。修复方向见[真实链路测试与 Claude 参考设计](真实链路测试与Claude参考设计.md)第 6 节：让 `/remember` 走确定性短路、完全不调用供应商，属于独立改动，未包含在本次范围内。

顺带修正了脚本自身对终态位置的假设：提取事件会追加在 `run_completed` 之后，因此 `terminal_event` 改为"终态之后只允许出现 `memory_*` 记账事件"，而不是"最后一个事件必须是终态"。

## 5. 边界

- worker 是**进程内**的：`create_runner` 为每个 runner 建一个，网页在 lifespan 启停，CLI 在结束时 `drain`。没有独立队列服务，也没有跨进程调度；同一 job 的并发安全依赖 `SKIP LOCKED` 与租约，而不是进程内锁。
- **租约必须长于一次提取的预算超时。** 否则一个仍然健康、只是慢的尝试会被当成崩溃回收（现在还会扣掉一次尝试），两个 worker 同时处理同一 job。`bootstrap` 用 `max(60s, 3 × policy.timeout)` 保证这一点，调整超时配置时不能破坏该关系。
- **"事件流以终态结尾"不再是全局不变量。** 提取事件（`memory_job_queued`、`memory_extraction_started`、`memory_saved`、`memory_job_failed`）会追加在 `run_completed` 之后。消费方应等待终态事件，而不是认为读到末尾就没有后续。`tests/test_web.py` 里"两次回放文本完全相等"的断言目前成立，是因为该测试的提示太短、不会入队；若将来加入长提示的网页用例，该断言需要改成"回放是先前流的超集"。
- 提取仍然是一次完整模型调用，未做批量合并或结果缓存；同一内容在不同 run 中仍会各提取一次（候选去重发生在写入阶段）。
- 投影缓存假设"消息行创建后不再变化"。当前实现符合这一点；若将来支持编辑历史消息，必须以内容版本参与缓存键。
- `render()` 仍对选中的消息 `deepcopy`，保证调用方修改请求不会污染缓存。这一步是 O(选中数)，未消除。
- 未实施诊断文档中的 B（运行所有权与失联恢复）、C（失败运行的事实恢复）、D（增量合并）、G（工具阻塞隔离）、H（进程会话与重试）。

## 6. 审查修复

对已实现部分做了一轮代码审查，修掉的是"边界条件没走到"的缺陷，不改变主链路结构：

| 问题 | 后果 | 修法 |
|---|---|---|
| `claim()` 回收过期租约时不计数 | 让进程崩溃的 job 可无限重试；`max_attempts` 只约束抛异常的失败 | 新增 `reap_expired()`：`attempts + 1`、达上限 `failed`、补发 `memory_job_failed`、关闭遗留的 `memory_extractions` 行；`claim()` 只看 `queued` |
| worker 并发可与连接池上限相等 | worker 占满连接池，并发运行在 `db_timeout` 后失败 | `Settings` 校验 `memory_worker_concurrency <= max(1, db_pool_max_size - 1)` |
| 非可加计数器仍为每条消息计算成本 | 该成本在精确路径下无人读取，白做一次序列化 | 只有声明 `additive` 的计数器才在投影时计价，其余记 0 |
| `drain()` 在退避等待期返回，CLI 静默退出 | 用户以为提取完成，实际任务还挂着 | 写明 `drain` 只推进"现在能跑"的任务；CLI 用 `unfinished()` 判断并打印剩余数量 |
| `runs.finish()` 清理 `memory_extractions` 的分支 | 提取只在运行终结后发生，该语句永不命中；将来若把提取挪回运行内会静默误伤 | 删除，并留注释说明前提 |
| `tool_requested_stop` 的运行不提取 | 有意的取舍，但此前只体现在代码里 | 写入上面的语义约定，明确需要用户显式记住 |

顺带删掉从未被调用的 `ProjectionCache.retain()` 与 `MemoryWorker.wait_idle()`，并把 `bootstrap` 里重复创建的两个 `MemoryJobRepository` 合成一个。

已知未处理：`memory_jobs.status` 的 `'cancelled'` 取值没有任何代码写入。删除它需要新增一条迁移（迁移带校验和，不能改已应用的 0009），收益不足，暂留。

新增测试：过期租约计一次尝试、崩溃循环到上限即 `failed`、worker 上报崩溃耗尽的任务、非可加计数器不逐条计价、并发与连接池的组合校验。

## 7. 回退

两项改动互相独立：

- 记忆提取可退回到"运行内提取"：让 `on_completed` 直接调用 `run_job` 的提取部分并在同一事务写入，`memory_jobs` 表可保留不用。
- 上下文选择可退回精确路径：把 `ByteTokenCounter.additive` 去掉即可让所有构建走原来的逐轮重算，行为不变、性能回到基线。
