# 容器生命周期与产物交付方案

2026-11-05 立项；2026-11-06 更新。**状态：实现已交付，剩余端到端场景见验收记录。** 本文回答三个互相纠缠的问题：一次 run 结束后容器里的环境怎么处置、容器里的产物怎么正确地落到宿主、以及什么工作该进容器什么不该。它改的是执行契约（容器生命周期、`TMPDIR` 语义、产物交付路径），所以按[文档维护规则](README.md#文档维护规则)先立一篇，实施后把契约并进[统一可编程执行契约](统一可编程执行契约.md)、证据并进[验收记录汇总](验收记录汇总.md)。

## 1. 问题

工作区是宿主目录的 bind 挂载（`tools/sandbox.py:150`），于是三个问题被同一个事实搅在一起：**容器往工作区写的字节，落的就是宿主的同一份文件**。所以「产物输出到宿主」不是一个搬运步骤，而是一次语义澄清；而「环境怎么处置」只发生在挂载之外；「该不该进容器」则完全由「要不要执行不可信代码」决定，与文件是不是产物无关。

立项时的后果已经出现在本机：`release()` 与 `close()` 都是空函数，容器建了不删，14 小时内堆了 16 个 `chagent-ws-*`；`/tmp` 是容器级共享的 tmpfs，两个并发 run 会互相覆盖同名临时文件；站点状态文件也放在那里，容器一重启就既丢了进程也丢了「它死没死」的证据。2026-11-06 已接入 run 私有 scratch、站点状态持久化、空闲回收、受限产物导出与显式重建。

## 3. 目标与非目标

**目标**：容器有明确的生命周期与回收判据；每个 run 有私有 scratch，run 结束即消失；产物分三类各有交付路径，第四类（挂载外）有显式且受限的通道；站点状态在容器重启后可判定；「该不该进容器」有一张写下来的判据表。

**非目标**：不追求容器强隔离（rootless/userns 是另一件事）；不自动更新镜像（会中断网站）；不把 `/cache` 变成可交付目录；不为每次 run 新建容器。

## 4. 设计

### 4.1 容器生命周期：常驻 + 空闲回收 + 显式重建

容器**不在 run 结束时回收**。理由是冷启动成本：Maven 依赖冷拉一次是分钟级，而 run 的预算讨论过一次又一次（[实施记录第 37 节](实施记录.md)）。代价是闲置资源，所以补一条回收规则：

| 状态 | 进入条件 | 离开 |
|---|---|---|
| `absent` | 没有容器 | `ensure_container` 创建 → `ready` |
| `ready` | 创建或校验通过 | 每次 `docker exec` 前刷新 `last_used_at` |
| `running` | 有活动 run 或网站 `running` | 两者都结束 → `ready` |
| `idle` | `now - last_used_at > TTL` 且无活动保护 | GC → `reaped` |
| `reaped` | 被 GC 或人工删除 | 下次需要时重建 → `ready` |
| `stale_image` | 容器镜像 ID ≠ 当前镜像 ID | 显式重建 → `ready` |

- **TTL**：`CHAGENT_CONTAINER_IDLE_SECONDS`，默认 1800，`0` 表示永不回收。和 `CHAGENT_APPROVAL_UNWATCHED_GRACE` 一样是显式配置并在 `/api/config` 显示，不藏常量。
- **保护条件**（任一成立就不回收）：有该工作区的活动 run/命令租约；经容器进程及 HTTP 核实的网站仍在运行；`last_used_at` 在 TTL 内。容器使用者从检查到 `docker exec` 启动必须持有租约；GC 在同一协调机制下复查，不能只依赖数据库中的旧 `running` 值。
- **驱动者**：单进程主控里一个惰性任务，每 300 秒扫一次。首轮只显示 `/api/containers` 中的孤儿候选，下一周期才逐个核对名称、label、挂载、活动进程和 run 目录后删除；绑定缺失或 `rebind_required` 本身不足以证明容器可删除。
- **不自动重建镜像**：`ensure_container` 现在校验 `Config.Image`（tag 名），同一 tag 被重建后旧容器不会更新。改为记录容器镜像 ID，与当前镜像 ID 比较，不一致只标记 `stale_image` 并在 `/api/config` 与 `site(status)` 提示；**重建是显式动作**（`POST /api/workspaces/{id}/container/rebuild`）。活动 run 或网站会被拒绝；用户先停止网站，再显式重建，避免一键中断服务。

### 4.2 run 私有 scratch

立项时两个并发 run 共享同一个 `/tmp`（容器级 tmpfs），同名临时文件会互相覆盖。设计如下：

- 容器命令的 `docker exec` 覆盖创建时的默认环境，注入 `TMPDIR=/tmp/chagent-run-<run_id>`、`HOME=/tmp/chagent-run-<run_id>`；目录由第一条命令**幂等创建**（`mkdir -p` 后 `exec`）。容器自身的默认 `HOME/TMPDIR=/tmp` 暂留给非 run 进程。
- run 结束时由主控异步删除 `/tmp/chagent-run-<run_id>`；`sandbox.release(run_id)` 与 Runner 调用点改为可等待的操作。主控崩溃后的遗留目录在启动或定期扫描时按已终结 run 清理。
- 失败或取消同样删除。**不保留**：要交付的东西必须由模型在 run 内显式带出来（4.3），保留 scratch 只会让 tmpfs 涨到 512m 上限。
- 缓存仍然是卷：`/cache/m2`、`/cache/pip`、`/cache/npm`，跨 run、跨容器重建保留。

### 4.3 产物：三类已有，第四类补通道

| 类别 | 交付方式 | 判据 |
|---|---|---|
| **工作区文件** | 挂载即宿主；`workspace_manifest_*` 与 `file_diff` 证明改了什么 | 模型说改了 A ⇔ 磁盘上 A 的 SHA-256 变了 |
| **构建缓存** | `/cache` 卷，不进工作区 | 只加速，不交付 |
| **要给人拿走的文件** | `file_outputs`：stage → 撞名确认 → 单次 token → 24h；下载走 API，20 MiB 上限 | 未经确认不覆盖任何已有文件 |
| **挂载外的容器产物** | **新增 `collect_file`** | 见下 |

`collect_file(container_path, workspace_path=None)`：

- 方向固定：**容器 → 工作区**。不是通用双路径拷贝，因为那等于给容器开一条往宿主任意目录写的路。
- 允许的容器路径前缀：`/tmp/chagent-run-<本 run>`（自己的 scratch）、`/cache`（只读复制，用于把缓存里的构建产物搬出来）。`/proc`、`/sys`、`/dev`、工作区本身一律拒绝（工作区本来就直通宿主，走这条路只会给自己的写入门禁开后门）。
- 实现用容器内 Python 逐级 `O_NOFOLLOW` 打开源文件，再通过 `docker exec` 传回二进制字节，拒绝符号链接；校验大小（≤ 20 MiB）、SHA-256，然后走 `OutputService.submit`——和上传/另存为**同一条撞名确认链**，`file_outputs` 里留来源 `container:<path>`。
- 审计区分 `pending` 与 `committed`：只有实际写盘后才写 `file_collected`，待确认时返回输出 ID 与待确认状态；用户确认后记录最终路径。`details` 回给模型同一状态，不把待确认称为已交付。
- 工具描述里写明：**「产出必须写在工作区内；`/tmp` 与 `/cache` 不会被交付——要交付就用 collect_file 带出来。」** 现在没有任何地方说这句话，模型会在回答里声称交付了 `/tmp` 里的东西。

### 4.4 站点状态与重启

立项时站点进程与状态文件都在 tmpfs，容器重启后两者一起消失，`workspace_services` 要等下一次 `site(status)` 才被改成 `unknown`——这期间 DB 说 running、事实是 dead。

改为：`/tmp/chagent-site.json` 与 `/tmp/chagent-site.log` 移到 `/cache/site/`。这样容器重启后：

- 状态文件还在（卷），`site(status)` 读到上次的 `worker_pid`；
- 已记录进程的 `/proc` 启动时间；读取时若 PID 消失或启动时间不符，判作 `stopped`，避免 PID 复用误判。HTTP 可用性由显式 `site(probe)` 验证；容器启动标识未单独入库。
- 模型拿到的是「上次的服务已停止，需要 `site(start)` 重启」，而不是「不知道」。

`unknown` 保留给「状态文件都读不到」的情况。

### 4.5 判定：什么进容器，什么不进

| 工作 | 跑在哪 | 判据 |
|---|---|---|
| 读/写/编辑/打补丁/检索工作区文件 | **主控进程** | 文件本来就是宿主文件；进容器只多一次挂载往返，边界不变 |
| 安装依赖、构建、测试、一次性命令 | **容器** | 要执行不可信代码，要限 CPU/内存/PID，要能观测出网 |
| 长期服务（网站） | **容器**（`site`） | 必须跨 run 存活且能被本机 HTTP 探测 |
| macOS 系统能力（钥匙串、系统 API、GUI、GPU） | **宿主原生 + 逐次审批** | 容器里没有这些 |
| 模型 API、`web_search` / `web_fetch` | **主控进程** | 不经过容器，容器网络审计看不见；已在[验收第 22 节](验收记录汇总.md#22-命令联网观测与撤销边界2026-11-05)写明 |

一句话：**要不要执行不可信代码**决定容器，**要不要碰 macOS** 决定宿主原生，**文件操作两个都不需要**。注意「不需要容器」不等于「不需要审查」：写入仍然过 `WriteGate` 的分级。

这张表要同步进[基础工具设计](基础工具设计.md)的工具描述，让模型读到的说明和这里的口径一致。

## 5. 数据与接口

**迁移 `0025_workspace_containers.sql`**（新表，不改旧表）：

```sql
CREATE TABLE workspace_containers (
    workspace_id uuid PRIMARY KEY REFERENCES workspaces(id),
    container_name text NOT NULL,
    image_id text NOT NULL,
    state text NOT NULL CHECK (state IN ('ready','running','idle','reaped','stale_image')),
    last_used_at timestamptz NOT NULL DEFAULT now(),
    created_at timestamptz NOT NULL DEFAULT now()
);
```

`workspace_bindings` 保持只描述身份（宿主路径/device/inode），运行态放新表——两件事不该挤在一行。

2026-11-06 P0-b 已建立该表；当前写入 `ready`/`reaped` 与 `last_used_at`。`running`/`idle` 由活动租约、run、站点及 TTL 现场推导；镜像 ID 不同会写 `stale_image`，不会自动重建。

**接口**：

| 方法与路径 | 用途 |
|---|---|
| `GET /api/workspaces/{id}/container` | 状态、容器名、镜像、空闲秒数、上次使用 |
| `POST /api/workspaces/{id}/container/rebuild` | 显式重建；活动 run/网站返回 409，必须先停止网站 |
| `GET /api/containers` | 诊断视图：本机所有带 `chagent.workspace=` 标签的容器与它们的归属（含孤儿） |
| `GET /api/config?workspace_id=…` 增加 | `container_idle_seconds`、所选工作区的 `container_state`、`image_stale` |

前端配置面板显示 TTL、容器状态与镜像是否过期；网站入口在 `unknown`/`stopped` 时显示「重启」，镜像过期时显示「重建容器」。重启使用数据库中已保存的命令和端口，并优先使用持久状态中的原工作目录。

## 6. 失败、恢复与边界

- **容器被外部删除**：`ensure_container` 重建并写 `container_recreated` 事件；模型侧看到的是正常的工具结果，不因基础设施抖动而失败。
- **容器配置漂移**（挂载/限额/镜像 tag 不符）：现在直接报错。保留这个行为——静默重建会把一个被改过的容器当成正常的。
- **GC 与 run 抢跑**：回收前在同一把 `ensure_container` 的锁下复查活动 run 与 `workspace_services`；抢到了就跳过，下次再试。
- **`collect_file` 失败**：容器读取失败、路径不合规或超限 → 工具失败且不写盘。撞名返回 `pending` 与输出 ID；该状态不是失败，也不是已交付，确认后才写盘并记 `file_collected`。
- **磁盘满**：`OutputService.submit` 已有的 ENOSPC 路径不变；`collect_file` 复用同一条路径，因此不需要第二套错误处理。
- **不做**：不删 `/cache` 卷（删了等于丢依赖缓存）；不在 run 结束时杀网站（那是 `site` 的语义）；不把 scratch 内容做成可交付的隐式通道。

## 7. 验收判据

| # | 判据 | 怎么测 |
|---|---|---|
| 1 | 两个并发 run 的 `$TMPDIR` 不同，同名文件不互相覆盖 | 两个 run 各跑 `sh -c 'echo $$ > $TMPDIR/pid; sleep 1; cat $TMPDIR/pid'`，断言各自读回自己的值 |
| 2 | run 结束 scratch 消失 | run 后 `docker exec <name> ls /tmp/chagent-run-<id>` 返回非 0 |
| 3 | 空闲回收生效且不碰活跃容器 | TTL 设 1 秒：run 后等待 → 容器消失、DB `state=reaped`；同时有 `site` 在跑的工作区容器仍在 |
| 4 | 孤儿容器首轮展示、次轮清理 | 手工建一个带标签、但 workspace 行不存在的容器 → 首轮列为候选，下一周期核验无活动保护后消失 |
| 5 | `collect_file` 带出 `/tmp` 产物 | 容器内写 `/tmp/chagent-run-<id>/out.txt` → `collect_file` → 工作区出现同名文件、SHA-256 一致 |
| 6 | `collect_file` 拒绝越界 | 目标是工作区外 / 源是 `/proc` / 超过 20 MiB → 拒绝且不写盘 |
| 7 | 站点状态跨容器重启可判定 | `site(start)` → `docker restart` → `site(status)` 返回 `stopped` 并建议重启，不是 `unknown` |
| 8 | 镜像更新只提示不重建 | 重建镜像 tag 后 `site(status)` / `/api/config` 显示 `stale_image`，容器仍运行 |
| 9 | 真实建站一轮 | 真实模型建站 → run 结束 → 产物在工作区、站点仍在线、`file_diff` 与收尾记录一致 |

## 8. 实施顺序与回退

### 2026-11-06 实施进度

- P0-a 已接入：宿主主控的容器命令按 run 注入独立 `HOME`/`TMPDIR`，首条命令创建目录，Runner 收尾异步删除；启动后周期扫描仅清理数据库已终结、且本进程未持有的 run 目录。两个并发命令在真实 Docker 中各自读回私有目录，收尾后两目录消失；模拟崩溃残留的真实容器回放只删终态 run，活动和未知 run 均保留。尚未做真实主控 `kill -9` 和取消/失败整链，故不宣称 P0-a 全部验收完成。

- P1-b 已交付 `collect_file`，二进制、符号链接拒绝、撞名待确认与确认后审计已在真实 Docker + 临时数据库验证。P2 已交付容器详情、镜像过期提示、显式重建及页面入口。活动 run/网站须先结束或停止，重建不自动打断服务。

### 实施批次与验收门槛（历史）

## 9. 取舍记录

- **为什么常驻而不是每次 run 新建**：冷启动依赖安装是分钟级，run 预算与用户等待都不允许；容器重建会丢掉热缓存（卷保住了依赖，但进程状态与镜像层缓存没有）。代价用 TTL 与孤儿清理抵。
- **为什么 scratch 不保留**：保留就必须给它配额、清理策略和「哪些算产物」的判断，而这三件事 `collect_file` 已经用显式动作回答了。默认丢弃比默认保留更安全。
- **为什么不自动重建镜像**：重建会杀掉正在服务的网站，而镜像更新往往是用户在做别的实验。把「要不要中断」交给显式动作。
- **为什么 `collect_file` 只回工作区**：工作区是唯一被准入、被清单、被门禁覆盖的落点。给容器一条往宿主任意目录写的路，等于绕过 `boundaries.py` 与 `WriteGate` 两层。
