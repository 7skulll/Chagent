> **论证卷。** 落地顺序、能力清单与验收口径已并入[执行能力改造总方案](执行能力改造总方案.md)；本文保留证据、代码细节与否决理由。两者冲突时以总方案为准。

## 0. 一句话

**把边界从「进程内的策略」换成「进程所在的位置」。**

Chagent 现在试图用 seatbelt 在进程内给自己上锁；pi 不做这件事——它把整个进程放进容器，并明确声明"没有内建沙箱"。

---

## 1. 这次重读了什么

读的是项目里自带的 `pi-main1.4.0/`，并用线上 main 交叉核对了一处：`examples/extensions/` 下**没有** `sandbox` 目录（1.4.0 与线上一致）。pi 早期版本曾有一个 `sandbox/index.ts` 示例，现已不存在——这不是遗漏，是第 1 条决定的执行结果。

### 1.1 pi 的六个设计决定

| # | 决定 | 证据 |
|---|---|---|
| 1 | **不做应用内沙箱**，且写进安全策略的免责范围 | `docs/security.md`："lack of a built-in sandbox … are generally outside the security boundary" |
| 2 | 边界只有三种位置：OS 用户 / 整进程容器 / 工具级隔离，并排序 | `docs/security.md`：整进程容器 "usually the strongest practical option"；工具级是 "a narrower form of isolation" |
| 3 | 隔离方案全部是**外部运行时**，共四种 | `docs/containerization.md`：Plain Docker / Docker Sandboxes / OpenShell / Gondolin micro-VM |
| 4 | 执行位置是一等抽象：`ExecutionEnv extends FileSystem, Shell` | `packages/durable/src/env/index.ts:374`；两实现 `LocalExecutionEnv` / `RemoteExecutionEnv` |
| 5 | 每个工具都可替换后端，所以"整体搬进 VM"是一个扩展而非核心改造 | `tools/bash.ts:80` 的 `BashOperations`；`gondolin/index.ts` 覆盖 read/write/edit/bash/grep/find/ls 七个 `*Operations` |
| 6 | 信任是显式事件，且**只管加载、不管行动** | `docs/security.md`：`project_trust` "does not limit what tool calls can access or affect" |

第 6 条最值得抄：pi 把"我信任这个目录"和"这个目录里的操作是安全的"明确拆开，并写进文档。Chagent 现在是反的——`execution_profile=trusted-development` 一个词同时表达了两件事。

### 1.2 pi 明确不做的三件事

| 不做什么 | 原因 |
|---|---|
| 不做启动探针 | 它的隔离不在进程内，失败模式是"容器起不来"，本身就是硬的 |
| 不做命令白名单 | 容器里默认放行，不需要知道 `mvn` 是否存在 |
| 不做读路径白名单 | 容器文件系统就是边界，`/usr/lib/jvm` 天然可读 |

**这三条恰好是 Chagent 现在 `sandbox.py` 442 行里最复杂的部分。**

### 1.3 一处必须承认的不对称

pi 能轻松换执行位置，是因为它从第一天就把工具写成 `Operations` 注入形式。Chagent 的 `tools/workspace.py` 把 inode 校验、不跟随符号链接、版本哈希都编在文件工具内部，没有注入点。

**这不是疏忽，是当时的合理选择**——它换来的是 Chagent 在宿主文件系统上的精细保护。代价是：Chagent 换不了执行位置，只能整体搬。

## 2. 结构差异

| 维度 | pi 1.4.0 | Chagent 现状 |
|---|---|---|
| 边界位置 | 进程外 | 进程内（`sandbox.py:411` SBPL） |
| 执行抽象 | `ExecutionEnv`（FS + Shell 一体） | `Sandbox.wrap(argv)` 与 `WorkspaceFS` 两套，互不知道 |
| 工具后端 | 注入 `*Operations` | 直连宿主 |
| 信任 | 运行时事件 + `trust.json` | 启动期 7 条件布尔断言（`config/__init__.py:83`、`web/policy.py:7` 各一份，逐字符相同） |
| 策略方向 | 容器内默认放行 + 定向拒绝 | `deny default` + 读白名单 + 全断网 |
| 失败模式 | 容器起不来 | 14 项探针任一失败 → 503 |
| 平台 | 任意 | macOS only（`isolated` 只认 SeatbeltBackend） |
| 模型是否知道边界 | 系统提示含环境 | **不知道**（`context/environment.py:259` 只有目录树和 git） |

## 3. 诊断

上一轮已经确认：`配置 Spring Boot 并跑起来` 在现有架构下**不可能**，四条路全断：

1. JDK 不在 `boundaries.py:44` 的 `runtime_roots()`
2. `/opt/homebrew/bin` 不在 isolated 的固定 PATH（`sandbox.py:400`）
3. `sandbox_network=False` 被硬约束（`sandbox.py:56`），拉不到 Maven 依赖
4. `detect_suite` 没有 `pom.xml` 分支，兜底 `return "pytest"`（`tests_runner.py:61`）

但真正的病根不是这四条，是：

> **`deny default` 的白名单必须随生态线性增长，而每增长一次都要重跑一次 14 项探针。**

Python → Node → Go → Rust → JDK → Gradle → Kotlin……每加一个工具链，`runtime_roots()` 加路径、`isolated_environment()` 加 PATH 条目、探针加一条、验收加一轮。这是**结构性的**，不是漏配。

容器把这条曲线换成常数：换镜像。

## 4. 方案

### 4.1 三轴分离

现在三个概念被压在一个 `execution_profile` 里。拆开：

| 轴 | 取值 | 回答的问题 |
|---|---|---|
| `boundary` | `container` / `none` | 进程跑在哪 |
| `capability` | `full` / `read-only` | 能不能执行宿主命令 |
| `gate` | `none` / `approval` | 命令要不要人批 |

**刻意只保留三个合法组合：**

| 组合 | boundary | capability | gate | 用途 |
|---|---|---|---|---|
| A | `container` | `full` | `none` | 唯一能执行代码的生产形态 |
| B | `container` | `read-only` | `none` | 只读会话（可选） |
| C | `none` | `read-only` | `none` | 没有容器时的降级：能读写文件、能联网搜索，**不能执行命令** |

**`container + full` 之外的任何组合都不提供代码执行。** 理由：没有容器就没有边界，此时提供代码执行等于把"假装有边界"制度化——这正是当前 `trusted-development` 的病。

组合 C 是刻意的降级，不是例外路径：没装 Docker 的人仍然能用 Chagent 读代码、改文件、写文档、查资料，只是不能用它跑程序。想在本机执行，用 Podman / Colima / OrbStack，都是 Docker 兼容运行时。组合数 3，且每一格的语义都能一句话说清。

### 4.2 P0 — 声明与自证（约 80 行）

去掉 `sandbox` 三档的语义，只留一个声明：

```python
# config/__init__.py
boundary: str = "container"          # container | none
boundary_acked: bool = False          # none 必须显式确认

if self.boundary not in {"container", "none"}:
    raise ValueError("CHAGENT_BOUNDARY must be container or none")
if self.boundary == "none" and not (self.boundary_acked and not self.allow_host_commands):
    # 无边界 + 可执行 = 拒绝启动。两个条件同时满足才允许，且此时也不执行命令。
    raise ValueError("CHAGENT_BOUNDARY=none 只允许在不可执行时使用；"
                     "代码执行必须提供容器边界")
```

三处冗余显示（沿用 `能力审计与融合决策.md:218` 的设计），理由相同：让"我在什么边界下"无法从任何单一页面被遗忘。

```
Behavior: boundary=container (外置; 进程内无隔离) | capability=full | gate=none | tools=13
```

- 启动横幅（`web/__main__.py:143`）
- `GET /api/info` 新增 `boundary` 字段
- `GET /api/config` 新增 `boundary` 字段

**替代 14 项探针。** 探针回答的是"我的策略生效了吗"；声明回答的是"我在哪"。前者可以被策略 bug 骗过，后者不能——容器里就是容器里。

**P0 必须连带改的三处断言**，否则 P1 的容器根本起不来（它们现在硬要求 `sandbox == "isolated"`）：

| 位置 | 现在的条件 | 改为 |
|---|---|---|
| `config/__init__.py:83` | `trusted_development` 要求 isolated | `containerized` 要求 `boundary=container` + 可写 + `approval=never` |
| `web/policy.py:7` | 同上，逐字符重复 | 改为调用同一函数，删掉重复 |
| `bootstrap.py:58`、`builtin.py:60` | `unified` 要求 `sandbox.mode == "isolated"` | 要求 `boundary == "container"` 且工作区可写 |

这四处是同一个判断写了四遍。P0 顺带合并成一个 `boundary_allows_execution(settings)`。

### 4.3 P1 — 容器（1 个 Dockerfile + 1 个 compose + 约 120 行）

**镜像**

```dockerfile
FROM python:3.13-slim

RUN apt-get update && apt-get install -y --no-install-recommends \
      git curl ca-certificates ripgrep \
      openjdk-21-jdk-headless maven \
      nodejs npm \
    && rm -rf /var/lib/apt/lists/*

WORKDIR /app
COPY pyproject.toml uv.lock ./
RUN pip install --no-cache-dir uv && uv sync --frozen --no-dev
COPY src ./src

ENV CHAGENT_BOUNDARY=container \
    CHAGENT_EXECUTION_PROFILE=containerized \
    CHAGENT_WORKSPACE_ROOT=/workspaces \
    CHAGENT_SANDBOX=off \
    CHAGENT_SANDBOX_NETWORK=true \
    CHAGENT_DATABASE_URL=postgresql://chagent:chagent@db:5432/chagent

EXPOSE 8765
CMD ["uv", "run", "chagent", "--no-open", "--host", "0.0.0.0"]
```

**三处必须改的代码**

| 位置 | 现状 | 改为 |
|---|---|---|
| `web/__main__.py:30` | `HOST = "127.0.0.1"` 硬编码 | `--host` 参数，默认仍 `127.0.0.1` |
| `boundaries.py:18` | `validate_workspace` 只校验"不是程序目录" | 额外要求：落在 `CHAGENT_WORKSPACE_ROOT` 内（未设置时不检查） |
| `web/app.py:75,105` | 硬编码 `"code_mode": False`、`"default_mode": "work"` | 由 settings 推导 |

`validate_workspace` 加的这条是**容器化后唯一的新约束**：工作区必须是被挂载进来的目录，否则容器里看到的空目录会让模型"读写成功但文件消失"。

**挂载**

```yaml
services:
  db:
    image: postgres:16
    environment: { POSTGRES_DB: chagent, POSTGRES_USER: chagent, POSTGRES_PASSWORD: chagent }
    volumes: [ "chagent-db:/var/lib/postgresql/data" ]
  chagent:
    build: .
    ports: [ "8765:8765" ]
    volumes: [ "${CHAGENT_WORKSPACES:-./workspaces}:/workspaces" ]
    depends_on: [ db ]
```

不挂 `~/.ssh`、`~/.aws`、`~/.gitconfig`、宿主 `~/.m2`。凭证只通过 `--env-file` 传入模型 API key，且该 key 用只做推理的独立密钥。

### 4.4 P2 — 删（−450 源码 / −508 脚本 / −398 测试）

| 删除对象 | 行数 |
|---|---|
| `sandbox.py` 的 SBPL 生成（`_sbpl`、`profile`、`isolated_profile`）、`SeatbeltBackend`、isolated 分支的 policy/environment/probe/record | ~250 |
| `tools/isolation_probe.py` | 105 |
| `boundaries.py` 的 `runtime_roots()` 及其引用 | ~15 |
| 4 个配置字段（`sandbox`、`sandbox_network`、`sandbox_deny_read`、`sandbox_writable_tmp`） | ~30 |
| `scripts/probe_code_isolation.py`、`probe_sandbox_profile.py`、`probe_readonly_acceptance.py` | 508 |
| `tests/test_sandbox.py`（249）、`test_code_isolation.py`（112）、`test_workspace_boundary.py`（37） | 398 |

**保留**（这几样与 seatbelt 无关，是独立价值）：

- `WorkspaceFS`（inode 校验、不跟随符号链接、版本哈希）——容器里同样需要，防止符号链接把写入引出挂载点
- `Sandbox.wrap(argv)` 接口本身——退化为恒等函数，但保留调用点，未来换执行后端不用改工具
- `tool_calls.details.sandbox` 审计字段——改名为 `details.boundary`，记录 `{boundary, network, workspace_writable, image}`

### 4.5 P3 — 能力补齐（约 110 行）

| 项 | 改动 | 行数 |
|---|---|---|
| Maven / Gradle 识别 | `detect_suite` 加 `pom.xml → maven`、`build.gradle → gradle`；`build_command` 加 `["mvn","-q","-B","test"]` / `["./gradlew","test"]` | 40 |
| Maven 输出摘要 | `mvn -q` 的 `Tests run: X, Failures: Y` 行需要单独解析，否则走"tail 8 行"兜底 | 30 |
| 边界注入系统提示 | `context/environment.py:259` 的 sections 增加 `Boundary:` 段：可用语言运行时、网络开/关、工作区绝对路径、不可访问的宿主路径 | 25 |
| 概念收敛 | 删 `default_mode`、`enabled_modes`、`readonly_code_available`、`code_workspace_writes`，清 `SessionCreate/Edit` 悬空注释 | 30 |

边界注入那条最便宜、收益最高：现在模型不知道边界，撞上 `deny` 会换个命令重试，`ProgressGuard` 三次后终止 run。有了这段，它第一次就会说"无法访问，需要宿主机执行"。

## 5. 做完能实现什么能力

按"能否用一条命令验证"排序。

| # | 能力 | 阶段 | 验证方式 |
|---|---|---|---|
| 1 | 配置并启动 Spring Boot 项目 | P1+P3 | 说"建一个 Spring Boot 服务并跑起来"，容器内 `mvn spring-boot:run` 成功，`curl localhost:8080` 有响应 |
| 2 | 安装任意依赖 | P1 | `pip install`、`npm i`、`mvn dependency:resolve`、`cargo build` 都成功 |
| 3 | 编译运行 Java / Kotlin / Scala | P1 | 容器内有 JDK 21 + Maven，无白名单 |
| 4 | `run_tests` 识别 Java 项目 | P3 | 工作区有 `pom.xml` 时返回 `Suite: maven`，而不是静默跑 pytest 报"找不到测试" |
| 5 | 模型第一次就正确判断可行性 | P3 | 系统提示含边界；问"能不能访问 /Users/xxx"时直接回答不能，不重试 |
| 6 | 在 Linux 服务器上运行 | P1 | 同一镜像在 Linux 起服务，无需改代码 |
| 7 | 新增工具链只需改一行 | P1 | 在 Dockerfile 加 `golang`，重建镜像，无需改 Python 代码、无需重跑探针 |
| 8 | 审计能说清"当时在什么边界下跑的" | P0+P2 | `tool_calls.details.boundary` 记录 image、network、writable |
| 9 | 换运行时（Podman / Colima / 远程 Docker） | P1 | 只改 `DOCKER_HOST` |

**第 1 条是这个方案存在的理由。** 其余八条是它的副产品。

## 6. 预期效果

| 指标 | 现在 | 之后 | 说明 |
|---|---|---|---|
| 可执行语言 | Python/Node/Go/Rust（依赖必须预置） | 任意（缺什么装什么） | |
| 依赖安装 | 不可能 | 可以 | |
| 平台 | macOS only | 任意（Docker） | |
| 隔离代码 | ~1,150 行（含 398 行测试）+ 508 行脚本 | ~120 行 | −93% |
| 合法组合 | 1（7 条件布尔断言） | 3（每格一句话说清） | 增加的是语义，不是分支 |
| 新工具链成本 | 改 3 处 + 重跑 14 项探针 + 一轮验收 | 改 Dockerfile 一行 | 从"每次"到"常数" |
| 启动自证 | 14 项探针，任一失败 503 | 1 条声明，不存在"探针骗过" | |
| 模型撞墙重试 | 3 次后 ProgressGuard 终止 | 提示里写明，第一次就绕开 | |
| Docker 不可用 | — | 启动失败（fail-closed） | 新增的失败模式，可用 |

**代价（必须写清楚）**

1. **隔离强度实际下降**。容器不是安全边界，Docker daemon 以 root 运行、默认共享内核。真正的强隔离要 rootless + userns-remap + seccomp，本方案不含。
2. **macOS 上 bind mount 慢**。virtiofs 下大量小文件 IO 比原生慢 2–10 倍，`mvn` 编译感知明显。
3. **容器内起服务，端口要额外暴露**。用户说"跑起来"时，8080 在容器内，宿主要 `-p` 映射或 `docker exec` 验证。这是行为变更。
4. **失去"本机直跑"**。没有 Docker 就不能执行代码。

## 7. 达不到

- **不是零信任**。容器能联网就能外泄数据；模型 API key 在进程内存里。
- **不防容器逃逸**。内核漏洞、`--privileged`、挂载 `/var/run/docker.sock` 都会击穿。
- **不回滚**。取消 run 后文件改动仍在。
- **无 PTY**。`process_stdin` 仍禁用，交互式命令跑不了。
- **不跨项目读文件**。工作区外仍不可达（容器里也一样，除非额外挂载）。

最后一条要特别说明：这不是退步。现在"读不到工作区外"是靠 seatbelt 白名单实现的，之后是靠"没挂载进来"。**保证的来源变了，结论没变**——而且更硬，因为白名单会配错，没挂载不会。

## 8. 风险与回滚

| 风险 | 触发条件 | 处置 |
|---|---|---|
| Docker 未运行 | 用户首次启动 | 启动即报错，提示 `docker info`；不降级 |
| Postgres 跨容器 | compose 未起 db | `depends_on` + 健康检查重试 |
| 工作区路径不在挂载根内 | 用户用 `--workspace ~/foo` | 启动报错，提示 `CHAGENT_WORKSPACES` |
| 挂载点权限 | Linux 上 uid 不匹配 | 镜像内固定 uid 1000，文档写明 `--user` |
| 回滚 | P2 删除后想退回 | P0/P1 与 P2 分开提交，P2 单独一个 commit 可 revert；P0/P1 不依赖 P2 |

**顺序上 P0/P1 先于 P2**：前两步让新路径跑起来，P2 才拆旧的。P2 之前回归必须是绿的，且第 4 步（容器内真实链路）必须已通过。

## 10. 验收口径

P0：
- `CHAGENT_BOUNDARY=none` 且 `allow_host_commands=true` → 拒绝启动
- `/api/info` 返回 `boundary`，与启动横幅一致

P1：
- `docker compose up` 后 `curl localhost:8765/api/info` 返回 `boundary=container`
- 容器内 `java -version`、`mvn -v`、`node -v` 都有输出
- 浏览器能对话，能读写 `/workspaces` 下的文件，宿主能看到改动

P2：
- `grep -r "sandbox-exec" src/` 无结果
- 全量回归绿，跳过数 0
