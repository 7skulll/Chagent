# 用户技能生成与管理方案

> **状态：契约草案，未实施（2026-11-13）。**
>
> 本次只形成方案，不新增用户技能数据库、生成服务、管理界面或动态加载能力。现有八个打包技能、长期记忆、任务经历与运行诊断为可复用资产，不能据此宣称用户技能已可生成或启用。当前行为以代码和 [README](../README.md) 为准。

## 1. 产品定位与用户决定

Chagent 根据用户选择的记忆、任务材料和要求，帮助生成可编辑的工作流程；技能是否生成、何时启用，均由用户决定。首版不是后台观察到习惯后自行写技能，也不是自动改写系统提示或自身源码。

四条固定约定：

1. 现有八个内置技能归为系统技能，随程序发布；用户不能修改、删除，也不能通过同名用户技能替换。产品内的不可变性由 API 和装配逻辑执行，不仅靠提示词；不承诺防止操作系统文件所有者直接修改安装文件。
2. 用户可选择是否生成用户技能，也可直接手工创建。选择生成只授权生成草稿，不代表启用；生成结果默认关闭。
3. 用户技能只有在用户显式开启具体版本后，才进入模型可见目录。模型可在任务匹配时按需调用，开启不等于每轮加载。
4. 用户可编辑、关闭和删除自己的技能。生成、编辑、开启和删除不增加命令、网络、文件、宿主操作或跨会话查询权限。

不把用户沉默、记忆被注入、run_completed、一次审批同意或单次“提交并推送”学习成持续授权。当前用户要求优先于历史习惯；系统技能中的平台能力和工具边界不能被用户技能改写。

## 2. 与记忆、任务经历和现有技能的关系

| 信息类型 | 首选承载方式 | 示例 |
|---|---|---|
| 稳定偏好或项目事实 | 长期记忆 | 默认中文、项目使用 PostgreSQL |
| 任务进行中的状态 | 当前任务状态/交接材料 | 哪些文件已改，哪项测试尚未执行 |
| 对已有流程的个性化要求 | 独立用户技能，标明适用的基础流程 | 审查时先列问题，再列证据与未验证范围 |
| 稳定的多步工作方法 | 独立用户技能 | 按指定口径比较材料、列冲突、核对来源后生成报告 |

首版不实现复杂的技能继承和自动合并：用户技能保存必要的个性化步骤，可以关联系统技能的 ID 和版本供兼容性检查；需要系统流程时显式加载对应系统技能。禁止直接复制完整系统技能再去掉边界描述。单句偏好若长期记忆已足够，先说明无需新技能，但用户仍可决定创建。

记忆提供有来源的素材，不直接变成指令。自动提取的 candidate/rejected/deleted 记忆不作为已确认习惯；首版生成器使用用户所选、当前可访问的 active 记忆和用户明确给出的材料。用户可显式引用一段尚未保存为记忆的要求，按本次输入处理，不借此自动激活记忆。

现有任务摘要标记的是 answer_recorded，不证明完成成功。需要复用操作流程时再核对可访问的实际工具结果或用户纠正。任务经历允许同工作区范围内检索，但完整运行诊断仍限当前会话；生成器不能凭另一个会话的 run_id 绕过限制。

## 3. 用户操作流程

### 3.1 生成入口

首版提供三个入口：

- 从长期记忆管理中选择条目，点击“生成技能”。
- 在当前任务结束后，由用户选择“将这套流程整理成技能”，再选择可用证据。
- 在用户技能页手工创建，或提供任务描述并选择生成。

生成请求前展示用途、所选来源和作用域，避免默认扫描所有历史。根据项目经验生成时默认当前工作区；跨工作区使用需用户明确选择用户级。资料含其他人的信息、密钥或私有路径时，先过滤或提示不可作为素材，不把原始完整对话复制进技能。

首版不做常驻自动推荐。后续可单独提供“是否接收技能建议”的设置；建议只显示候选线索，不等于开始生成，用户拒绝后对相同来源/主题抑制重复建议。

### 3.2 生成、预览与启用

用户确认生成 → 后台生成草稿 → 校验 → 展示正文、适用/不适用范围、来源与限制 → 用户编辑或保留 → 用户显式开启选定版本。

草稿生成失败不创建可加载技能，不改变任何已有启用版本。界面应清楚显示“已生成，未开启”，不预勾选开启，不把关闭技能藏在模型目录中。用户明确的开启请求必须能够定位到已经生成的具体版本；含糊的“以后这样做”不由模型猜测为技能开启请求。

模型生成器没有技能管理写入工具，不能替用户调用开启 API。首版管理动作由网页交互入口承接；聊天可协助准备草稿或打开对应管理项，但不能把普通对话文本伪造为已发生的 UI 决定。

### 3.3 编辑与版本

正文版本不可原地覆盖，编辑总是产生新 revision。关闭技能编辑后仍关闭；已开启技能编辑时，旧 active_revision 继续生效，新版先是草稿。

保存时可显式选择“仅保存草稿”或“保存并应用此版本”；关闭技能的对应操作应明确标为“保存并开启”，不能以普通保存隐式启用。用户开启或回退旧版本也要指向准确 revision。操作使用 expected_revision，冲突时重新加载差异，不静默覆盖另一个页面的改动。

### 3.4 关闭、删除与运行中撤销

关闭后保留正文，不能再被自动或显式加载；点名关闭的技能也只返回“未开启”，不暗中开启。删除后从管理列表的正常视图和模型目录中移除，不因来源记忆仍存在而自动重建。后续手工重新创建属于新的用户决定。

开启和应用新版本从下一次 run 生效，已运行任务固定所用版本。关闭或删除属于撤销：立即阻止新读取，并请求取消实际引用该用户技能的活动 run；执行中已发生的文件、请求或命令副作用不能回滚，界面说明取消是否收敛。未使用该技能的 run 不受影响。

历史原文仍按运行审计策略保存；后续模型上下文投影不应再次注入已关闭/删除技能的完整正文，而用不可用标记替代。否则技能即使已退出目录，仍会从历史工具结果中继续起作用。原始审计记录不改写，取消和历史投影需单独测试。

## 4. 来源选择与生成质量

### 4.1 证据清单

每个生成任务保存所选 memory_id/revision、可见消息/任务记录引用、来源范围、生成器/模型版本和输入摘要哈希。只保存解释来源所需的最小摘录；不复制整份原始对话、私有推理或环境变量。

区分用户明确要求、反复纠正、用户采纳与工具执行结果。多次检索同一记忆不算多份独立证据；同一结果的多次转述不算重复成功。推断的频次仅用于建议，不替代用户选择，也不设置“重复三次就自动启用”的规则。

生成前做重叠检查：若与系统技能或已有用户技能类似，展示复用/编辑已有技能或新建的区别，不自动修改它们。适用范围有矛盾时保留冲突供用户决定，不把项目习惯泛化为所有任务的默认要求。

### 4.2 首版生成限制

只生成说明型 SKILL.md：名称、简明 description、触发/不触发条件、步骤、工具前提、结果验证和输出约定。正文优先写能改变决策的内容，不堆通用提示。

- 核对当前真实工具名与参数，延迟工具说明先经 tool_search 加载；没有工具则说明降级范围。
- 不虚构 OCR、公式重算、原生 Office 排版、浏览器控制或跨会话运行读取。
- 将宿主私有路径、旧 PID、一次性容器端口、临时凭据与当次审批从可复用流程中剥离。
- 不生成自动发消息、提交/推送、发布、恢复未知操作或放宽审批的持续授权。
- 首版不生成/执行辅助脚本，不安装依赖、不设置自动化任务、不接受任意文件夹扫描或附件执行。

格式/schema、长度、敏感内容、工具兼容性与来源归属校验通过后才可开启。静态校验通过只说明可加载，不代表已证明技能有效；UI 区分“格式/兼容检查通过”与“行为已验证”。用户确认也不能绕过程序强制的权限限制。

## 5. 技能存储与身份

保留包内八个系统技能的现有名单和读取行为；用户技能由数据库与管理服务保存，不写入 src/chagent/skills，不修改系统文件，也不依赖工作区中未经登记的 SKILL.md 自动生效。

建议的逻辑实体（具体迁移编号在实施时按现有迁移最大号追加）：

| 实体 | 主要字段与约束 |
|---|---|
| user_skills | UUID、名称、description、scope(user/workspace)、workspace_id、head_revision、active_revision、enabled、deleted_at、更新时间；工作区级必须绑定当前有效工作区 |
| user_skill_revisions | skill_id/revision、正文、哈希、来源摘要、创建方式与时间、生成器版本；正文版本不可变 |
| skill_sources | 对应 revision 的记忆/消息/任务引用与版本，来源是否已变更或不可访问；引用不赋予新的读取权限 |
| skill_generation_jobs | 用户请求标识、来源快照、状态、预算、claim_token/租约、attempt、输出 revision 或安全错误；生成完成只能写草稿 |
| skill_audit / run_skill_references | 用户管理操作及本轮实际加载的类型、ID、revision、hash、作用域；不把仅进入目录当成实际使用 |

当前为单用户本机项目，不凭空加入多用户 RBAC；user 作用域代表此本地用户跨工作区可见，workspace 作用域按真实绑定隔离。系统/用户身份用独立 type + ID 表达：显示名可类似，但不能覆盖同名系统技能，也不让模型依靠名字猜测来源。

enabled 与版本状态分开：draft 仅表示有待发布内容，active_revision 指向用户选定版本，deleted_at 表示已删除。兼容检查失败可以标记 blocked_reason，使版本暂不可加载，但不假装用户主动关闭或自动改写其内容。

后台 job 可以复用 memory_jobs 的租约/幂等/独立超时模式，不混用其提取语义。相同请求重试不重复创建技能；用户删除目标、取消 job 或来源发生竞争变化时，旧领取者不得把技能复活或重新开启。

## 6. 管理接口与运行时加载

### 6.1 拟新增接口

| 入口 | 约束 |
|---|---|
| GET /api/skills | 返回系统只读目录和当前作用域用户技能，标记类型、版本、开启与兼容状态 |
| POST /api/user-skills | 手工创建关闭的草稿 |
| POST /api/user-skill-generations | 显式提交生成请求，限定已选来源/作用域，返回 job 状态 |
| GET /api/user-skill-generations/{id} | 查看生成进度、失败或结果；不泄漏模型凭据和未授权来源 |
| POST /api/user-skill-generations/{id}/cancel | 用户取消生成，领取者随后不得提交草稿或恢复任务 |
| PATCH /api/user-skills/{id} | 带 expected_revision 保存新的正文/元数据版本，默认不发布 |
| POST /api/user-skills/{id}/activate | 明确开启或应用指定 revision；校验用户操作、作用域、版本和兼容性 |
| POST /api/user-skills/{id}/disable | 关闭、撤销后续读取，按引用请求取消活动 run |
| DELETE /api/user-skills/{id} | 用户删除，并处理关联 job、活动引用与目录失效 |

接口复用现有本机请求认证、跨源/请求边界及工作区身份检查；不能只隐藏 UI 按钮。所有用户管理写入入口拒绝系统技能 ID。生成器与普通任务模型只获读取能力，不获得这些管理接口的通用调用凭据。后续自然语言管理如要加入，必须另定可信用户意图绑定机制，首版不实现。

### 6.2 发现与加载

现有 read_skill(name) 保持只解析内置系统技能，避免升级后原调用被同名用户内容接管。用户技能通过明确的 skill_id/type 加载，调用时基于 ToolContext 校验可见性、enabled、deleted_at、active_revision 和兼容性；元数据目录不是授权依据。

首版明确采用兼容扩展：read_skill 参数二选一，原 name 仍限定系统技能枚举，新 skill_id 为用户技能 UUID；两者同传或都不传均拒绝。新增 search_user_skills(query) 只检索本轮可见、已开启的用户技能，最多返回 8 个有稳定 ID 的名称/简介候选，按已登记作用域过滤，不开放任意文件路径。查询/读取需要 runner 提供会话上下文，不能由模型指定 workspace_id。模型无权枚举未开启或其他工作区用户技能。显式点名也不能绕过关闭状态。

每个 run 固定可见目录及实际加载的 revision/hash；普通开启/编辑不在中途切换版本，关闭/删除走撤销检查。控制用户目录和正文预算，按任务与作用域提供有限候选；工具声明、目录或正文被省略时记录原因，不能丢失当前用户要求来容纳技能。

规则冲突时，当前用户要求优先于历史偏好，平台/工具权限不受技能改变；系统流程的可选做法可按本次用户目标调整，强制执行边界不可取消。用户技能之间冲突不采用“谁最后加载谁赢”，应选择更具体作用域、排除无关技能，不能消解时说明冲突。

## 7. 记忆变化、删除与用户技能维护

来源记忆更新、删除、作用域变化或系统基础技能升级时，只标记相关用户技能需要复核并展示差异；不自动重写或删除用户内容。若工具/工作区身份已不兼容，阻止新的加载并说明 blocked_reason，用户更新后显式应用新版本。

用户技能是独立保存的流程，不是记忆的隐藏副本。创建时说明：后来删除原记忆，不等于删除已经写入用户技能的衍生内容。记忆删除界面列出关联技能并提供一并关闭/删除的明确选项；没有选定时不悄悄级联改写。用户明确要求忘记相关信息时，清理流程必须覆盖这些衍生内容，不能只删 memories 行就声称已忘记。

技能删除的首版产品语义是逻辑删除、不可加载、不可被同一 job 自动复活。历史运行和最小审计仍按留存规则存在，不声称彻底物理擦除；彻底删除敏感信息需单独定义历史记录和导出的清理范围。导出 SKILL.md 只在用户要求时进行，不导出隐含的全部来源资料。

## 8. 效果验证

主要对照是“相同记忆 + 系统技能”与“相同记忆 + 系统技能 + 用户技能”，不能把记忆收益误算成技能生成收益。保持模型、工具、任务预算与初始夹具一致，分别记录人工编辑前后的技能版本。

开发样本用于生成，未参与生成的任务和相邻负例用于验证。按[测评方案](智能体测评与自我迭代方案.md)记录版本、trial、outcome、判据和不确定性；当前评测 P0 清单仍需扩展到数据库用户技能的有效 revision/hash，不能只计算包内技能文件。P1–P5 尚未全部实现，不依赖一个不存在的完整门禁作为首版前提。

验证维度：用户重复纠正次数、实际交付质量、误触发、相邻任务不触发、项目范围迁移、用户偏好更新、关闭/删除后不再使用、上下文/时延/模型费用。用户不反对不是满意反馈，技能被读取不等于有益；真实用户采纳与人工复核结果单独保存，不由生成模型自评决定。

## 9. 实施顺序与交付判据

| 阶段 | 交付 | 必须验证 |
|---|---|---|
| U0 | 系统/用户身份、用户技能版本、管理 API 与目录装配 | 系统写入/删除被服务端拒绝；默认关闭、显式开启；跨工作区隔离、版本冲突、同名不覆盖；无模型管理写权限 |
| U1 | 记忆/当前任务来源选择、手动生成 job、预览与编辑 UI | 未选不生成；失败/重试仅草稿；来源精确可追溯、候选记忆不伪装已确认偏好；用户编辑保留；生成后目录仍不可见 |
| U2 | 运行引用、目录预算、动态读取、撤销及记忆关联维护 | 固定版本、关闭/删除阻止新读并收敛活动 run；历史正文不重新激活；旧 job 不复活；来源变化提示、关联清理、无授权升级 |
| U3 | 行为对照与真实模型验收 | 与相同记忆基线比较，包含误触发、负例、偏好更改、作用域和注入样本；静态格式通过不冒充效果已验证 |

U0 先交付手工创建/编辑的说明型用户技能；U1 再接入基于选择素材的生成；U2 的撤销与历史投影必须完成后，才把动态技能运行能力作为完整产品开放。U3 不强求每个用户技能上线前跑昂贵全量评测，但功能交付必须有代表性真实模型与确定性契约测试，日常 UI 如实显示个体技能的验证状态。

当前不做：后台自主生成或启用、自动脚本学习、修改/删除系统技能、绕过执行审批、自动替换用户已编辑版本、多用户协作和技能市场。后续用户需要自动推荐时另定范围，不隐含在本次方案内。
