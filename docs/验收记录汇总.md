**对象与方法**：本机 macOS，用户 8765 宿主主控实例（`CHAGENT_HOST_DB_COMPOSE=true`，工作区 `/Users/macbook/Desktop/测试用`）与其 Compose PostgreSQL。主控两次以 `kill -9` 终止后带迁移 `0022` 重启；交互输入与审批决策由真实 DeepSeek 驱动的 HTTP 脚本发起（脚本只在本文件注明「agent-driven」的场合代替点按，审批事件与工具结果全部落库）。模型自述不作为证据，所有结论以 `approval_requests`、`native_executions`、`native_stdin_writes`、`tool_calls` 与实际进程状态为准。

## 18. 模型侧审批反馈（2026-11-05）

**要修的问题**：C5（[第 10 节](#10-c5-审批真实网页2026-11-05)）里每一轮都有真实审批卡、已消费的授权和落地的文件结果，而模型最终回答仍称"没有出现审批提示"。机制成因不在模型：审批在工具**执行前**由 `_ask` 阻塞完成，结果里只有命令输出，模型没有任何渠道知道页面答过什么，只能按"我看不到审批"作答。

**对象与方法**：独立实例 `127.0.0.1:18770`，`CHAGENT_APPROVAL=untrusted`，`--host-controller`，工作区 `/tmp/chagent-c5-feedback`（页面显示规范化后的 `/private/tmp/chagent-c5-feedback`），共用本机 Compose PostgreSQL 与真实 `deepseek-flash`。`/api/info` 确认 `boundary=container capability=full gate=approval`。审批决策由脚本调用页面同一 `POST /api/approvals/{id}/decide`（带 note），**未在浏览器 DOM 里点按**。结论以 `tool_calls.result`、`approval_requests` 与磁盘字节为准，不以模型自述为唯一证据——这一点与 C5 的方法一致，正是本次要修的对象。

**实现**：审批答案随工具结果回到模型，共四处接线，无迁移。

| 环节 | 改动 |
|---|---|
| `ApprovalOutcome` | 新增 `note`：`approved` 与 `denied` 两条分支都带上用户写的备注 |
| `public_note()` | 过滤 `local prompt` / `no viewer` / `no interactive approver` 这类"谁答的"审计标记，它们不是用户的话，不当作备注传给模型 |
| `GateDecision` → `Grant` | 门禁把 `approval_id` 与 `note` 一起交给调度器；`execute_batch` 在结果提交前调用 `with_approval()` |
| `with_approval()` | 在结果 `content` 首位插入一行「Approval: the user approved this … call in the page before it ran (approval …)… do not report that no approval was requested」，`details` 记 `approval=approved`、`approval_id`、`approval_note`；备注在模型侧截到 500 字符，`details` 保留全文 |

拒绝路径同样补上：`The user's note: …` 追加在固定的拒绝文案之后。原文案只说"不要重发"，用户的理由才说明"该改成什么"。

**备注的两个边界**：网页 `ApprovalDecision.note` 的上限是 2000 字符，比许多工具结果本身还长；把全文塞进模型上下文，在小窗口下会挤掉它注释的那条结果。所以模型侧截到 500 字符并加省略号，`details.approval_note` 保留全文。备注内容不转义——它与用户消息同源，是用户自己写的话，不是外部数据。

**闭环一：批准。** run `3a6eb959-be93-4009-84a4-eaf1e0572abc`，模型先 `read_file` 取哈希，再 `write_file` 覆盖 `existing.txt`；审批 `210b4561-4957-4e37-87dc-5babbfd2ddee` 状态 `approved`、已消费，note 为「只允许这一版」。

| 事实 | 证据 |
|---|---|
| 被批准的调用带审批行 | `write_file` 结果首块以 `Approval: the user approved this write_file call in the page before it ran (approval 210b4561)` 开头，第二行为 `The user added with the approval: 只允许这一版` |
| 结构化字段 | 同一行 `details.approval=approved`、`approval_id`、`approval_note=只允许这一版` |
| 未审批的调用不带 | 同 run 的 `read_file` 首块是 `File: existing.txt / SHA256 …`，`details` 无 `approval` 键 |
| 模型回答与数据库一致 | 「是。工具返回中明确说明该次 `write_file` 调用在页面中经过了用户审批（approval 210b4561）……结果是**用户批准了**」，并照抄审批行与用户备注 |
| 磁盘 | `existing.txt` 变为 `c5-approved-by-page` |

**闭环二：拒绝（含用户理由）。** run `b8053ba3-884e-470f-8ef4-de07f6edbe8b`，审批 `2d919f5e-8a52-4307-ad35-0c3885f9498f` 状态 `denied`、未消费，note 为「内容不对，先别改」。

| 事实 | 证据 |
|---|---|
| 拒绝原因到达模型 | 工具结果文本为固定拒绝文案 + `The user's note: 内容不对，先别改` |

## 21. run 工作区文件差异（2026-11-05）

**实现**：run 进入模型与工具循环前将工作区普通文件的相对路径、字节数和 SHA-256 记录为 `workspace_manifest_before`；终态提交前记录 `workspace_manifest_after`，并由两次清单计算 `added/modified/deleted` 与数量。成功、失败、取消均走结束清单路径；事件顺序保证结束清单在 `run_completed/run_failed/run_cancelled` 之前。`/api/runs/{id}.file_diff` 直接从持久化结束事件读取，网页运行提示也按该事件展示实际文件路径和数量，不依赖模型复述。

**边界**：不跟随符号链接；权限错误、扫描中变化、文件数量超过 5 万或哈希总量超过 2 GiB 时，清单标记 `complete=false` 并记录原因，不把差异当成完整事实。run 在装载工作区状态前失败，或进程硬崩溃时，可能没有两份清单，API 返回 `null`，不伪造差异。此记录只证明两次扫描时的文件内容，不提供自动回滚，也不包含工作区外副作用。

**自动验证**：独立目录的新增、修改、删除及外部符号链接；另测扫描上限不能声称差异完整。真实数据库 run 使用 `write_file` 写出 `site.txt`，核对磁盘、两份事件及 API 投影同一 SHA-256 差异；网页 run 详情返回差异；JS reducer 以事件中的数量和路径生成确定性提示。事件提交失败的故障注入仍按原存储错误关闭 run，不让结束扫描异常覆盖原始故障。全量回归 **653 项通过、0 跳过、69.5 秒**，新加的扫描上限用例随后单独通过；JS 纯函数测试 **22 项通过**。

**回放发现并修掉的一个真缺陷**：收尾提示会**丢**。`workspace_manifest_after` 与 `network_observed` 是 run 结束前最后两条事件，页面按帧合并重绘，而 SSE `end` 处理器先 `reset` 再重读会话——排队的最后一帧被取消，两条提示从未画出来。离线回放测试看不到（它们按状态绘制，不经过 `end`），只有真实浏览器 + 真实 run 会暴露。修法不是改帧策略，而是把"收尾记录"变成持久事实：新增 `render/run-summary.js` 与 `core/format.js` 的 `diffSummary`/`networkSummary`，`openSession` 在终态 run 上读回 `/api/runs/{id}` 追加一块 `.run-summary`。实时提示保留（run 进行中可见），收尾块负责刷新后仍可核对。

**仍未验收**：一条完整的"一句话建站"run 把这套差异摘要写进最终回答（归实施计划第 5 项的真实项目验收）。

## 22. 命令联网观测与撤销边界（2026-11-05）

宿主主控在每个 run 的模型/工具循环前启动独立网络采集容器，它只共享工作区容器的网络空间，拥有 `NET_RAW`，不挂载工作区或 Docker socket。采集器读取 `eth0` 发出的 IP 包头，不记录内容，终态前写入 `network_observed`：每个目标的 IP、端口、发出字节数及总量。`/api/runs/{id}.network_observation` 和网页结束提示读取同一事件。采集器未就绪时拒绝宿主主控 run，避免一边联网一边宣称已观测。其他运行模式没有此承诺。

真实 Docker 探针：在现有工作区容器的网络空间启动采集器，执行 `curl https://example.com` 后得到 `104.20.23.154:443` 发出 2457 字节、Docker DNS `192.168.65.7:53` 发出 114 字节；随后用临时 PostgreSQL schema 跑完整 Chagent `exec_command` run，`network_monitor_started` 和 `network_observed` 均已持久化，观测到 HTTPS 目标与 DNS 目标、合计 2723 字节、15 个包，run 为 `completed`。临时 schema、探针容器与缓存卷已清理。此数值是当次包级观察，不是供应商计费或可跨机器比较的基准。

撤销语义：用户取消 run 时，现有执行器终止正在运行的命令进程组，后续工具不再启动；采集器在终态前停止并记录截至停止时的观测。已经发出的网络请求及远端副作用无法撤回。网络空间与持续运行的网站服务由工作区共享，因此包级目标和字节数属于该 run 时间窗口内的**工作区容器观察值**，可能包含同时运行的网站流量；采集器异常终止或内核丢包时不能声称绝对完整，也不识别域名或 HTTP 路径。当前没有用网络隔离断开一个已持续运行的网站。

**自动验证（2026-11-05 补齐）**：新增 `tests/test_network_audit.py` 20 项。包解析：IPv4/TCP、VLAN 标签、UDP 端口、无端口协议（ICMP 记 0）、IPv6、以太网填充不计入而截断帧只报已捕获长度、非 IP 与短包拒绝。sidecar 生命周期：等 `READY` 才放行、`docker run` 失败即清理、`READY` 不到即失败、未启动时 `monitor_unavailable`、`stop` 幂等且只删一次容器、`truncated` 不报完整、`docker logs` 失败与非法 JSON 都变成 `complete: false` 而不是抛错。runner 路径：完成、取消、失败三条各只落一条 `network_observed`；观测器不可用时 run 以 `execution_error` 拒绝并落 `complete: false, reason=monitor_unavailable`；没有宿主 sandbox 的 run 不启动观测器。

**真实浏览器 + 真实模型（2026-11-05）**：独立实例 `127.0.0.1:18772`、临时数据库、`CHAGENT_APPROVAL=untrusted`、宿主主控。真实 DeepSeek 在 run `52e3e417-98b6-43e5-8c43-33649e95c233` 里先后执行 `exec_command curl https://example.com` 与 `write_file net-check.txt`：`network_observation` 为 `sent_bytes=2571`、`packets=13`、目标 `104.20.23.154:443` 与 `192.168.65.7:53`（Docker DNS）；页面收尾记录与 `/api/runs/{id}` 一致，刷新后逐字不变。

**一条容易误读的事实**：模型 API 的 HTTPS 流量发生在**宿主主控进程**里，不经过工作区容器，因此一个只做 `write_file` 的 run 观测到 0 字节是正确结果，不是采集失败（本批第一轮实测就是 0，被误当成缺陷查了一轮）。观测值只覆盖容器网络空间内的流量。

## 23. 批量写审批（1A，2026-11-05）

**要解决的问题**：一次轮次改三个文件要出三张卡，用户要在三次点击里确认同一件事；而第 33 节的「写入纳入审批门禁」本来就是为了让人看见改动，不是让人点三次。

**实现**（迁移 `0023`，无数据改写）：

| 环节 | 做法 |
|---|---|
| 批次身份 | 同一模型轮次的写审批共享一个 `batch_id`，`batch_index` 保留模型给出的顺序；单条提问（宿主命令、单个写入）`batch_id` 为 `NULL`，旧路径不变 |
| 每调用一行 | 每次工具调用仍有自己的行：`tool_record_id`、参数指纹、`expires_at`、`consumed_at` |
| 页面决策 | `POST /api/approvals/{id}/decide` 命中批次时，一条条件 UPDATE 覆盖该批次所有 `pending` 且未过期的行；已经过期或已答的行不会被复活 |
| 逐调用核销 | 调度器仍用每行的批准 id 执行 `consume()`，一次授权不能用于另一次调用 |
| 提问时机 | 批次在**第一个并行组之前**发出：写工具是顺序的，按组提问仍会是三张卡 |
| 页面 | 一张卡列出每个文件，按钮写「批准这 N 处」；批次只发一条 `approval_requested`，页面不会画三张 |

`WriteGate` 拆出三个可复用片段（`intent` 只判定不提问、`grant`／`refusal` 把结果映射成决定），调度器据此先收集整轮写入再一次提问。

**自动验证**（`tests/test_approval_batch.py`，9 项）：三文件同批（一个 `batch_id`、顺序、三条 `approval_requested` 变一条、三行都 consumed）；整批拒绝（磁盘不变、三行 `denied`、未消费、模型拿到「was not declined…not a tool failure」的逐调用拒绝语）；重复决策与另一行再决策都返回 `conflict`；两页并发决策一个成功一个 `conflict`；**部分过期**（手工让一行过期后，决策只覆盖活着的行，过期行不写盘）；取消 run 整批转 `cancelled` 且零消费；**授权不能被另一个调用消费**（用 A 的批准 id 消费 B 的 tool record 失败）；单个写入与新建文件行为不变。

**真实浏览器 + 真实模型（2026-11-05）**：独立实例 `127.0.0.1:18773`、临时库、宿主主控、`CHAGENT_APPROVAL=untrusted`。真实 DeepSeek 在 run `3113f610-a4cb-47b8-aca8-3555078ee59b` 里先读三个文件拿到 SHA256，然后在同一条消息里发出三个 `write_file`。页面只出现一张卡：

```
需要确认：3 处文件改动
overwrite a.txt (existing 4 B file)
overwrite b.txt (existing 4 B file)
overwrite c.txt (existing 4 B file)
目录 /private/tmp/chagent-batch-ws，21:57:46 前有效；批准会一次作用于这 3 次调用，每次仍然独立核销
[批准这 3 处] [拒绝]
```

点一次「批准这 3 处」后：run `completed`、`pending` 归零、磁盘 `a=A b=B c=C`、`file_diff` 为 3 个 modified、数据库三行 `approved` 且各有 `consumed_at`。控制台零错误。

**本批发现并修掉的一个真缺陷**：批次的第一版给每行都发一条 `approval_requested`。页面按事件建卡片，于是同一批次画出三张卡：一张有内容、两张永久停在「正在读取…」（也解释了为什么 `getElementById("approval")` 读到的是空的那张）。改为批次只发一条事件，并在 reducer 里加「已有待答卡片就不再追加」的防御。离线测试看不到，因为它们不经过 SSE。

**未验证**：`apply_patch` 与 `edit_file` 的批内组合只有同一条分级路径覆盖，没有单独出卡；跨模型轮次的合并（现在按轮次分批，两轮就是两张卡）不在本项范围。

## 24. 失败分类与重试语义（1B，2026-11-05）

**要解决的问题**：一次调用没拿到结果时，模型只看到一句错误文本。于是被拒绝的写入被换个参数再发一遍，超时（结果未知）的调用被当成没发生直接重试——后者可能把已经在磁盘上发生过的副作用再做一次。1B 给每种结局一个名字、一个「能不能再试」的答案，并把重试变成可审计的 attempt。

**实现**（迁移 `0024`，无数据改写）：

| 环节 | 做法 |
|---|---|
| attempt | `tool_calls.attempt` = 同一 run 内同一 `name` + 同一 arguments 的第 N 次执行，入队时在同一事务里计数。重试因此是新行、新 `tool_record_id`、新票据 |
| 分类 | `tools/retry.py` 一张表八种结局：`denied`／`unwatched`／`expired`／`cancelled`／`unavailable`／`stale`／`execution_failed`／`outcome_unknown`，各带 `retryable` 与一句给模型的说明 |
| 结果字段 | 拒绝与执行失败都在 `details` 里带 `failure_class`、`retryable`、`attempt`；批准仍带 `approval`／`approval_id`／`approval_note` |
| 未知结果 | `outcome_unknown` 把一段话写进结果的**正文首块**（不是 details）：「Result unknown… do not retry this call as if nothing happened」——详情模型可以不读，正文不行 |
| 自动重试 | 没有。测试断言未知结果之后 `tool_started` 只有一次：脚手架不会自己重放，重试只能来自模型的新调用，而那会重新走审批 |

`retryable` 的口径是「再跑一次是不是合理的下一步」，不是「谁的责任」：`expired` 与 `execution_failed` 为真（前者开新问题、后者读错误改输入），其余为假。这张表有守卫测试：改动 `retryable` 集合会失败并提示同步文档。

**自动验证**（`tests/test_retry_attempt.py`，11 项）：八种结局都有名字与说明、`retryable` 集合与文档一致、未知名字不会默认可重试；同一调用两次是 attempt 1/2、换参数是新 run 的 attempt 1；**拒绝后重试会再问一次**（两行审批、第一行 `denied` 未消费、第二行 `approved` 已消费）；**旧票据不能用于新 attempt**（用第一次的批准 id 消费第二次的 tool record 失败）；执行失败标 `execution_failed` + `retryable=True`；超时标 `outcome_unknown` + `retryable=False` 且正文以 `Result unknown:` 开头；拒绝的拒绝语带 `failure_class=denied`。

**写测试时踩到的一处**：`ToolExecutor` 的生效超时是 `max(默认, 工具请求)`，所以「工具请求 0.2 秒」在默认 35 秒的 harness 里仍是 35 秒——hang 用例直接把 run 预算耗光（`run_timeout`）。要测挂起必须把 executor 的默认也调小。记在这里，免得下一个人以为是 `outcome_unknown` 没生效。

**未验证**：真实模型读到不同分类后是否**改变**行为（同一被拒写入不再换个参数重发、未知结果先检查）。这需要真实供应商的对照观察，本轮只保证脚手架给出的信息是明确且不互相矛盾的；`apply_patch` 的失败分类与写入共用同一条路径，未单独验证。

**回退**：删除 `tests/test_retry_attempt.py` 与 `tools/retry.py`；`approval_result`／`with_failure` 的字段与未知结果正文前缀去掉；`DROP COLUMN attempt`。

## 25. 跨进程审批唤醒（1C，2026-11-05）

**要解决的问题**：等待批准的人只在自己进程里被唤醒。另一个进程（第二个主控、脚本、CLI）做出的决定要等到下一个轮询 tick 才被看到，所以那个 0.25 秒的轮询既不能删、也掩盖了「跨进程决策慢」这个事实。

**实现**：

| 环节 | 做法 |
|---|---|
| 门铃 | PostgreSQL `LISTEN chagent_run_wakeup` / `pg_notify`，载荷是 run id。一个频道服务所有 run：每 run 一个频道要反复 LISTEN/UNLISTEN，取消的等待者还会留下频道 |
| 事务性 | `pg_notify` 写在审批变更的同一个事务里，提交时才投递。回滚的决定不会叫醒任何人；被叫醒的人一定能读到已提交的行 |
| 连接 | 监听器用**池外**的专用连接：监听要占住连接，从池里拿会悄悄缩小查询用的池 |
| 断线 | 连接断开就重连并重新 `LISTEN`。断开期间的通知 PostgreSQL 不会补发，所以超时重读必须保留 |
| 兜底 | `POLL_SECONDS` 从 0.25 秒改为 **1 秒**，含义也从「轮询机制」变成「丢失通知的恢复上界」。单进程内仍然是立即唤醒 |

**自动验证**（`tests/test_cross_process_wakeups.py`，4 项）：

1. **另一个进程收到决定**：真子进程 `LISTEN` 后在就绪行上阻塞，主测试进程通过 `ApprovalRepository.decide` 做决定，子进程收到同 payload，端到端 < 2 秒。
2. **跨连接决策唤醒等待者**：决定用裸 SQL + `pg_notify` 发出（绕开进程内广播），订阅者在 **< 1 秒**内醒来——只有通知路径能做到这一点。
3. **通知丢失由超时兜底**：没有任何通知时，`wait` 在超时上界返回而不是永久挂住。
4. **断线重连后继续投递**：监听器连接被主动掐断，`reconnects` 增加、重新 `LISTEN`，下一条通知仍然收到。

**真实产品路径（2026-11-05）**：独立实例 `127.0.0.1:18774`、临时库、宿主主控、`CHAGENT_APPROVAL=untrusted`、真实 DeepSeek。真实模型发起覆盖 `existing.txt` 的写审批后，**由另一个进程**（`decide_elsewhere.py`，独立 `Database` + `ApprovalRepository`）批准：

```
decide 耗时            7 ms
approval_decided       22:21:25.930112
tool_started           22:21:25.943613     → 13.5 ms
tool_completed         22:21:25.949226
磁盘                   existing.txt = "new"
```

13.5 毫秒远低于 1 秒的兜底上界，说明唤醒走的是通知而不是轮询。

**一处被测试逼出来的修正**：把 `POLL_SECONDS` 从 0.25 调到 1.0 之后，`test_a_reconnecting_page_clears_the_unwatched_clock` 变红——它用「audience 被调用几次」模拟轮询节奏，节奏变了假设就不成立。修法不是把产品改回去，而是让该用例显式设 `broker.poll = 0.1`：它测的是宽限逻辑，不该依赖产品默认的恢复间隔。

**未验证**：`pg_notify` 在连接重建窗口内丢失通知的情形（PostgreSQL 不补发）只由「超时兜底」覆盖，没有做真实的断网演练；多主控同时等待同一个 run 的竞争没有被专门测试（决策本身是条件更新，重复决策返回 `conflict`）。

**回退**：删 `events/notify.py` 与 `tests/test_cross_process_wakeups.py`；`RunNotifications.attach` 与 `_ensure_listener` 去掉；审批变更里的 `_wake` 去掉；`POLL_SECONDS` 改回 0.25。

## 26. 出口保护专项验收：site、宿主原生与记忆（2026-11-05）

一场会话三个回合（run id 全部在库中）：

| 回合 | 做了什么 | 结果 |
|---|---|---|
| 宿主原生 | `exec_command pwd` → `host_exec pwd`（同页批准 `fcf7e05b`） | 两次工具结果都含 `/private/tmp/chagent-egress-ws`；run `3e330f07` completed，3 次模型调用 |
| `site` | `site(action=status)` | 工具结果 `{"url": "http://127.0.0.1:60226", "service": null}` 出现在下一次请求里；run `85c42180` completed |

## 27. 压缩失败根因：投影边界漏掉 JSON 转义换行（2026-11-05）

**现象**：小上下文窗口（9000）下压缩反复失败，`compaction_failed` 的原因是 `Summary must be a completed text response without tools`，而 `compaction_calls.response` 里记着的是 `stop_reason="error"`、`error_message="deepseek: Invalid provider response (ProtectedPathError)"`。

**根因不是模型，也不是 thinking**：压缩器把历史轮次用 `json.dumps` 序列化成**一个字符串**再放进摘要请求。工具结果 `Exit code: 0\n/private/tmp/<ws>\n` 在这个字符串里，换行是**两个字符** `\` + `n`，于是工作区路径后面紧跟的是**反斜杠**。`models/outbound.py` 的 `PATH_END` 边界集合里有空白、引号、标点，**没有反斜杠**，所以投影没命中；随后守卫（正确地）认定「请求里还有未映射的工作区路径」并拒绝发送。也就是说：**任何以工作区绝对路径结尾的工具输出，都会让压缩失败**，与 thinking 无关——第 26 节第一次把它归因成 thinking，是错的。

**修复**（`models/outbound.py`）：

- `PATH_END` 的备选里加一条**字面反斜杠**（`[class]|\\|…`）。反斜杠不是 POSIX 路径的合法字符，把它当边界不会误伤真实路径；而 `"` / `\t` / `\u` 这些转义形式也因此一并覆盖。
- 拒绝信息带上**命中的文本片段**（不超过 24 字符）。原来的消息只说「检查失败」，定位要靠临时打补丁打印 payload——这次就是这么查的，不该让下一个人再走一遍。

**自动验证**（`tests/test_model_outbound.py` 新增 3 项）：`json.dumps` 出来的 `Exit code: 0\n<ws>\n` 被投影成 `/workspace`；同名兄弟目录（`<ws>-other/x`）**不**被投影且仍然拒绝（防止把前缀匹配当成路径匹配）；拒绝消息包含命中文本。

**真实复验**：同一场景（窗口 9000、阈值 0.4、thinking on、真实 DeepSeek）重跑，`compaction_calls` 连续两条 `completed`，`compaction_completed` revision 1、`tokens_before` 4418 → `tokens_after` 420；代理同时记到两条 `purpose=summary` 请求，含 `/workspace`、不含宿主路径。

**未验证**：`to_host`（把 `/workspace` 还原成宿主路径）也用了同一个 `PATH_END`，本轮只验了 `to_model` 方向。理论上工具参数里出现 `/workspace\` 这种形态没有实际意义，但仍是一处未被覆盖的组合。

**回退**：还原 `PATH_END` 的一条备选与 `_excerpt`；删掉新增的三个用例。行为退回「带 JSON 转义换行的路径不投影」，压缩会再次失败——所以回退只在确认要放弃压缩时才有意义。

### 37.6 现场发现（已修）

**模型被 `tool_search` 误导，报告了一个其实已经声明的工具不存在。** run `692c6815` 里模型想调 `host_process`，却先用 `tool_search` 去「找」它；查询 `host_process write stdin to native process` 命中了 `host_exec`（两个描述里都有 `native`），返回的是 `host_exec` 的声明。模型据此认为 `host_process` 没有参数定义，最终回答里说「write 从未发出」，而请求快照里 `host_process` 一直在 `tools_added` 中。

修法（本批提交）：`ToolSearchTool` 在匹配前先看查询是否**点名了一个已经声明的工具**——是就直接回答「它已经在当前请求里，参数就在工具列表，无需加载」，不再返回一个只共享某个词的无关工具。新增 1 项回归（`test_a_query_naming_an_already_declared_tool_loads_nothing`）。
