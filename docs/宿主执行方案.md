## 1. 目标和成功定义

用户选定一个已存在的本机工作区，提出“写一个 Python 或 Java 网站”。Chagent 应能读取现状，创建或修改项目，在受限环境安装依赖、构建、测试、根据错误修复，持续启动服务，并从本机验证 HTTP 页面。最后交付工作区文件、可访问地址、测试与运行证据、启动和停止方法。

“在本机可用”默认指网站进程在本机 Docker 执行环境中运行，用户可用本机浏览器访问。只有用户明确要求 macOS 原生进程，或任务确实依赖宿主资源时，才申请宿主原生执行。后一种操作必须等待用户在 Chagent 网页审核并批准。因此普通建站可以连续自主推进；原生宿主操作不能同时承诺零确认。

成功必须由实际文件、命令退出码、测试结果、持续进程状态和本机 HTTP 请求共同证明。模型文字、单元测试数量、工具健康探针均不能单独证明建站成功。任意需求和外部依赖不能保证百分之百成功；失败时要准确报告阻碍、保留可继续的状态。

## 2. 旧架构根因与当前实施

下表记录实施前的故障根因；表内“当前事实”是旧容器主控的历史状态，不是新入口的现状。

| 方面 | 当前事实 | 对目标的影响 |
|---|---|---|
| 主控位置 | Chagent 整个进程在容器中，命令在该进程中就地执行；compose 只挂一个宿主目录到 /workspaces | 运行中不能直接接入任意新宿主目录，切换被迫重启 |
| 工作区身份 | 数据库以容器内 root_path 区分工作区和会话 | 两个宿主目录依次挂到 /workspaces 会被当作同一工作区；旧会话可能访问新目录 |
| 容器边界 | 工作区是 bind mount；容器命令可联网，当前容器并非强隔离 | 容器内写文件就是改宿主文件，不能把“在容器里”当作无副作用 |
| 审批 | 容器命令、部分覆盖写入与方案 A 的宿主终端各有确认路径 | 正常编码被多次打断；用户在聊天里回答无法批准终端请求 |
| 宿主执行 | A 原型只支持经终端确认的一次性命令；未完成真实模型闭环 | 无法可靠运行持续的宿主服务，未形成同一网页内的审批体验 |
| 运行与预览 | 容器固定映射 8080；会话进程只属于一个 run | 任意项目端口、长时间运行、断连后的恢复没有统一契约 |
| 验证 | 已有大量组件测试和部分真实项目记录，但缺少固定的一句话建站验收集 | “测试通过”不能外推为 Python/Java 网站均可自主交付 |

2026-11-05 已备份原 Compose 数据库，在同一数据库上应用工作区身份迁移。无法证明原宿主目录的 `/workspaces` 旧工作区标为 `rebind_required`，历史会话可通过只读审计接口查看、不能执行；新工作区按规范化宿主路径建立独立身份并记录设备号、inode。工作区容器按路径哈希命名，切换目录无需重启主控。宿主主控网页需要本机浏览器登录令牌，数据库口令已轮换；工作区容器不能读取两者。容器仍能联网、能写其 bind mount 的用户工作区，所以用户应只选择允许 Chagent 修改的目录；这不构成对工作区文件的回滚保证。

当前工具面：普通文件工具、`exec_command`、`run_tests` 在工作区容器执行；`site(start/status/probe/logs/stop)` 管理跨 run 网站与本机回环地址；`host_exec` 只在宿主主控中注册，且需要同页一次性审批和更早轮次成功的容器命令或测试证据。宿主执行独立核验已消费的匹配批准，记录启动与终态；拒绝或无人查看时不执行。`host_exec` 带 `yield_time_ms` 时以交互方式启动，进程留在本 run 内，用 `host_process` 读取、写入 stdin 或停止；每次写入（含 EOF）都是一张只覆盖该次输入的新审批卡，不沿用启动批准，写入结果逐条落 `native_stdin_writes` 审计。没有 PTY：原生宿主进程是管道语义，终端类交互交还用户。容器命令也没有通用跨 run 的交互 stdin/PTY；网站服务使用独立 `site` 生命周期。

## 3. 确定的架构

采用“宿主主控 + 每工作区独立容器执行后端”。不继续扩展方案 A 的宿主终端代理。

- **宿主主控**：FastAPI 网页、模型循环、PostgreSQL、稳定工作区身份、审批、执行调度、服务入口和运行状态。主控保存模型凭据；项目命令和容器不能继承这些凭据。
- **工作区容器**：每个活动工作区拥有明确的容器实例和仅属于该工作区的挂载。模型生成的普通安装、构建、测试、应用启动命令在这里执行。容器有资源限制、最小权限、明确网络策略及可复用依赖缓存。
- **宿主执行器**：与模型调用隔离的窄接口。只有准确命令、目录、环境、超时及本次批准均匹配时才启动宿主进程；没有免审批模式。它记录实际启动、退出和未知结果。
- **服务入口**：宿主代理本机端口到相应容器内实际监听端口，提供稳定的本机访问地址。Docker Desktop 下不假设宿主能直接访问容器 IP；端口映射不能在运行中的容器上临时新增，须通过预设入口代理或等效通道解决。

模型只看到可申请的工具；执行位置由工具和主控策略决定，不由模型文字声明决定。宿主主控虽运行在本机，也不得把任意模型参数直接拼成宿主 shell 命令。

## 4. 工作区和数据契约

1. 数据库为每个宿主工作区建立稳定 UUID，保存规范化宿主路径、可选文件系统身份和当前容器映射。会话、记忆、产物和运行记录均引用 UUID；容器路径不充当主键。
2. 每次使用前在宿主重新检查目录存在、身份、符号链接和准入规则。目录移动或身份变化时停用该映射，要求显式重新绑定，绝不自动指向另一个目录。
3. 为一个工作区创建或恢复其执行容器，不重启整个 Chagent。多个工作区可以轮换或并存，资源配额由主控控制。
4. 迁移旧数据前备份数据库。能证明原宿主路径的旧 /workspaces 记录才映射到新 UUID；无法证明的旧会话标为“待重新绑定”，保持可查看审计但禁止工具执行。迁移后会话、记忆和文件输出隔离已有针对性回归，见[验收第 19 节](验收记录汇总.md#19-迁移后工作区隔离2026-11-05)。
5. 保留用户现有未提交改动。A 原型逐项迁移或撤除，不以整包覆盖工作区 UI、数据库或历史记录（现状：`hostexec/service.py` 保留、默认关闭，`实施记录` 第 36 节与 `设计总览` 记为「历史兼容」——撤除还是改写本条，需要一次明确决定）。

## 5. 执行、审批和风险边界

默认允许在所选工作区内正常创建和修改项目，并在工作区容器内运行构建、测试和服务。风险不能只靠命令前缀或模型“自审”判定；容器必须实际限制路径、凭据、网络与资源。容器对 bind mount 的写入会改变宿主文件，因此 run 进入模型与工具循环前和终态提交前会记录工作区普通文件的相对路径、大小与 SHA-256 清单，并以两次清单计算新增、修改、删除；工作区外写入不得由容器完成。扫描不跟随符号链接，遇到权限、并发修改或上限会标记不完整，不把不完整差异当作确定结论。

以下请求在同一 Chagent 网页暂停并显示准确参数：宿主原生命令、工作区外读写、访问本机凭据或其他额外权限。用户看到命令、真实 cwd、用途、预期影响及容器验证证据。批准只对该请求一次有效，不覆盖后续 stdin、改动后的命令或另一个工作区。拒绝、超时、无人查看、取消均不执行；请求已发出但结果不明时标记 outcome_unknown，不自动重试。

审批结果、实际工具结果和最终回答使用同一条持久化记录。模型可引用批准事实，但“模型说已批准”不是批准证据。宿主执行器必须独立验证批准状态，不能接受来自容器的“用户已同意”标志。

## 6. 一次建站任务的闭环

1. 主控锁定工作区 UUID 和容器身份，读取目录与已有改动；保护用户预存文件。
2. 模型制定短计划，使用文件和命令工具创建项目、安装依赖、构建及运行定向测试；失败后读取实际输出并修复。
3. 将服务作为受管理的长进程启动。记录进程标识、实际监听端口、日志位置、超时与停止方法；运行结束、崩溃或容器重建时明确状态。
4. 入口代理提供本机地址。主控发出真实 HTTP 请求，检查状态码和关键内容。涉及前端 JS、页面布局或交互时增加浏览器验证；仅 HTTP 200 不等于页面可用。
5. 主控比对最终文件、测试、服务和 HTTP 证据，交给模型生成总结。最终回答分别列出已验证、未验证、失败或需要用户批准的部分（**未实现**：提示词只有「不要编造工具输出与测试结果」的通则，见第 8.1 节）。
6. 如果必须原生运行，先展示容器验证结果，再走网页审批；批准后宿主执行、读回结果、按同样标准验证。用户拒绝时继续容器内可行工作或准确停下。

任务可以跨多次模型调用、用户审批和断线继续。预算是单次活动限制，不应以一个固定 run 超时否定整个项目。重启后能恢复的进程继续跟踪，不能确认的外部副作用标记未知，禁止盲目重复。

## 7. 终端、工具链和性能

普通 Python/Java 网站不要求用户打开 Terminal。容器执行器提供非交互命令、持续进程、日志、停止和 stdin；宿主原生进程的交互输入另行审批，不沿用启动批准。登录、验证码或必须由用户输入的凭据明确交还用户。

**PTY 不做（2026-11-05 决定）。** 理由有四：一是逐次审批 stdin 已经覆盖需要喂输入的场景，构建、测试、服务和 REPL 用管道足够；二是 PTY 不是「多一个参数」，它带来行缓冲与回显、窗口尺寸、`SIGWINCH`，以及 Ctrl-C 变成字节而非信号的一整套新契约，容器与宿主两侧都要实现和测试；三是它服务的是全屏 TUI 与密码输入，而这些按本节第一段本就该交还用户，做 PTY 等于在网页里重造终端，与「原生操作不承诺零确认」的定位冲突；四是当前没有真实需求证据。第二交付的措辞里不再保留 PTY；将来若出现必须交互的构建工具，按[文档维护规则](README.md#文档维护规则)先立方案篇再实施。

基础镜像提供 Python、JDK、Maven/Gradle、Node 与常见构建工具；按项目识别实际工具链。依赖缓存持久化，镜像可预热。首次下载、外部仓库故障、模型能力和用户需求不完整仍可能延迟或阻止交付，系统必须给出可操作的失败说明。

## 9. 发布、回退与不变约束

先备份数据库和现有部署配置，在隔离环境演练迁移；随后用新主控读取旧历史，确认工作区映射，再逐步启用执行。旧容器部署保持可回退，但回退后不得把新工作区身份重新解释为旧 /workspaces 路径。A 原型（宿主终端代理）仍是默认关闭的历史原型，不得作为正式能力宣传；跨宿主目录切换已是宿主主控的正式能力（第 14 节验收），容器主控档的跨根切换仍返回 503，两者不要混说。

需要保持的约束是：用户选择哪个真实目录，任务就只对该工作区生效；普通建站在受限环境自主推进；确需宿主原生执行时由用户在同一网页确认；最终成品与验证证据都能在用户工作区和会话中检查。后续实现选择可以调整，但不能放松这四条，也不能用新增功能掩盖未通过的整链验收。


## 10. 容器边界 A 批补强（2026-11-17）

- 工作区容器创建与复用共用 `ContainerPolicy`（当前版本 1）。复用核对工作区标签与挂载、预期缓存卷、镜像引用、启动命令/用户、根只读、capability/安全选项、namespace、CPU/内存/PID、tmpfs 与 loopback 端口；不符返回差异名称，需先停止活动任务/网站再显式重建。固定资源仍为 2 CPU、2 GiB、256 PID、512 MiB tmpfs。
- 每次命令/测试绑定实际容器 ID、镜像 ID、可取得的 RepoDigests、创建时间、策略版本/哈希、实际资源/挂载/网络和镜像过期标记；`boundary.environment` 随工具证据保存。宿主主控另将每次调用与环境 JSON 存入 `container_invocations`，在创建容器内进程之前登记。
- `exec_command` / `run_tests` 在执行容器中启动标准库 Python 监督器，使用 Linux subreaper 回收派生和脱离原进程组的后代。取消后通过独立 Docker 调用请求容器内收尾，并核对监督器 PID/start time 与最终状态；正常命令退出也清理后台后代。监督器源码由主控传入，已有执行镜像无需为该模块重建。
- `cleanup_pending` 或终态 run 的未确认调用会阻止新任务复用容器；状态持久化于迁移 `0030_container_cleanup.sql`，不会因主控内存清空而被遗忘。未确认调用的临时目录不由恢复扫描删除，保留排查依据。显式重建在确认活动任务/网站已停止并删除旧容器后解除标记。网站 stop 通道仍可在 pending 状态核验策略后停止服务，普通新命令仍被阻止。
- 未确认收尾返回错误并标记 outcome_unknown，不宣称副作用已停止。监督器与候选命令运行于同一容器/用户，进程监督不是对抗同权限恶意进程的独立安全边界；控制文件篡改、监督器被强杀等无法确认的状态进入待清理。文件和外部网络副作用不回滚。
- 本批只补强宿主主控的现有执行路径；持续工作区、现有审批、网站生命周期与默认联网行为继续沿用原契约。没有引入独立任务副本、独立验证容器或外部 Benchmark 后端。


## 11. 独立任务环境 B 批（2026-11-17）

`TaskEnvironment` 提供独立环境后端，入口为 `python -m eval.cli task-env run`。由控制器对已授权工作区制作完整快照，或读取前次保存的 snapshot.tar；镜像引用解析为实际 ID 后固定执行。容器以任务 UUID 命名并标记 `chagent.task`，工作目录 `/workspace` 与 `/cache` 均使用本任务独享 Docker 卷，没有源目录或结果目录的宿主 bind 挂载。保持 A 批 2 CPU/2 GiB/256 PID、根只读、cap-drop ALL、no-new-privileges、512 MiB tmpfs。默认 `--network none`，需要出网时明确选择 bridge；不发布宿主端口。持续工作区与网站路径不改动。

控制器结果目录必须新建且位于源目录之外，保存 `environment.json`、`snapshot.tar`、命令证据、`artifacts.tar` 与采集目录。环境文件记录准备/就绪/执行/采集/清理阶段，真实容器/镜像身份、资源与挂载、快照哈希、逐文件哈希、声明产物及清理结果；同一路径禁止重复创建。初始化后每次执行/采集重新核对实际容器身份及基础执行策略。命令复用 A 批监督器，取消和超时进行容器内收尾；中断状态不允许自动续跑命令。

快照最多 100 MiB、10000 个文件/目录；支持普通文件、目录与执行权限，拒绝符号链接、硬链接、特殊文件、非规范相对路径。归档内容是后续复跑的固定输入，不承诺对正在并发修改的源目录取得事务性快照；应使用静止夹具。没有自动忽略规则，所有合法输入都纳入快照和记录。独立缓存默认不共享，复跑从同一快照创建新容器和新卷。

产物必须用重复的 `--artifact` 明确声明相对路径（支持文件、目录），不允许重叠声明；默认总计 20 MiB、10000 条。采集在命令收尾之后执行，通过目录描述符及 no-follow 打开每个路径，不跟随候选链接。控制器再次验证归档路径、类型、范围、重复成员和总量，通过后在临时目录提取并发布 artifacts 目录。缺失、链接、超限等写为 collection_failed，不判绿，也不会发布部分产物目录。产物采集不是最终任务判分。

清理只操作本任务固定命名且 ownership label 匹配的资源；资源类型和身份不符则拒绝删除。CLI run 在成功/失败后均尝试清理；容器或卷删除不能确认时保留 cleanup=pending。控制器中断后可从结果目录重新加载并显式 cleanup，不自动重跑；清理幂等，快照和产物保留。Docker daemon 本身不可访问时不把查询失败当作资源已不存在。该后端当前面向顺序控制器调用，没有接产品 Agent/Web、实验槽位调度、独立验证器或 Terminal-Bench；使用带 `/app/.venv/bin/python` 的 Chagent 执行镜像。命令时限 .1–600 秒，既有产品权限和审批仍由原运行路径负责。

```sh
# 输出目录需在输入目录之外且尚不存在；执行后自动采集并清理。
PYTHONPATH=src:. .venv/bin/python -m eval.cli task-env run \
  --workspace /absolute/fixture --out /absolute/evidence/task-001 \
  --cmd 'python3 main.py > answer.txt' --artifact answer.txt
# 使用同一份固定输入创建第二个独立尝试。
PYTHONPATH=src:. .venv/bin/python -m eval.cli task-env run \
  --snapshot /absolute/evidence/task-001/snapshot.tar --out /absolute/evidence/task-002 \
  --cmd 'python3 main.py > answer.txt' --artifact answer.txt
# 主控中断后只恢复清理，不重放任务。
PYTHONPATH=src:. .venv/bin/python -m eval.cli task-env cleanup --out /absolute/evidence/task-001
```


2026-11-17 A/B 联合复核补修：独立任务的控制端证据目录允许位于仓库内 `eval/results`，命令路径映射所需的空本地目录改用独立临时目录，并遵守配置的 CHAGENT_WORKSPACE_ROOT。证据目录不再作为 WorkspaceFS 用户工作区，因此不触发程序目录保护；输入工作区的原有程序目录保护继续生效。新增仓库内证据路径与“失败→修复→测试通过→产物哈希→原快照重现失败”回归。


## 12. 独立验证环境 C 批（2026-11-17）

`eval.verification` 提供冻结验证方案、独立验证和恢复清理。`task-env run --verifier <目录>` 在候选执行前固定验证代码快照、实际验证镜像 ID、协议/驱动版本与超时，留存在任务结果的 verifier-plan/。任务完成声明产物采集并确认其执行容器/卷清理后，验证器才可消费 artifacts.tar；验证前重新计算归档哈希及文件清单，与任务记录逐项核对。验证代码归档也重新核对，任何不符均记 infra_error，不运行判分代码。

验证使用独立 UUID 容器/卷，先由临时初始化容器装载数据，移除初始化容器后启动正式验证容器。`/verifier` 与 `/artifacts` 分别只读挂载两个私有卷，根文件系统只读，默认且当前固定 network=none、不发布端口，cap-drop ALL、no-new-privileges，资源沿用 2 CPU/2 GiB/256 PID/512 MiB tmpfs。没有宿主 bind 挂载，不共享执行阶段的进程、缓存、可写工作区；验证镜像须预装依赖，验证时不安装软件。每次执行前核对容器 ID、镜像、挂载、网络及基础资源/权限配置。

验证协议为 verify-function-v1：控制器指定目录必须包含 check.py，定义 `verify(artifacts: pathlib.Path)`，返回 bool 或 `{'passed': bool, 'details': JSON对象}`，details 最多 32 KiB（连同结果协议），不接受 NaN/Infinity。预期错误产物应返回 False；函数异常、非法返回、超时、缺结果、结果/退出状态绑定不符及清理异常记 infra_error，不能当成普通零分。验证进程输出仅作诊断，结构化结果由驱动独立写文件，核对本次 token 和退出码；控制端读取有大小/常规文件/no-follow 限制。pass/fail 分别附 score=1/0，infra_error/inconclusive 的 score=null，保留既有 GraderResult 四态契约。

验证器是可信控制代码，应先使用正确/错误产物校准。需要运行候选程序时，使用有超时及输出限制的子进程；同解释器直接 import 候选可能改变验证器自身行为，本协议不承诺抗同权限恶意代码的完整评分隔离。只读卷防止常规文件篡改，Docker 资源/网络限制约束执行副作用，不能替代验证规则本身的正确性。语义模型判据仍未启用。

每次验证使用新的输出目录，保存 verification.json（阶段/真实环境/清理状态）、冻结代码/产物归档、verifier.log（最多 64 KiB，truncated 字段单列）、raw-result.json（如存在）、result.json（grader/score/证据绑定）。原始结构化结果与归档保留，重复使用输出目录被拒绝。清理仅操作名称/owner label/已知容器身份匹配的资源；cleanup_pending 立即使公开判定无有效 pass。主控中断后使用 verify-cleanup，只回收资源、不重跑；未完成验证不因资源清理成功而变成通过。

```python
# 控制器目录内的 check.py；该目录不会进入候选任务容器。
def verify(artifacts):
    answer = artifacts / 'answer.txt'
    return {'passed': answer.is_file() and answer.read_bytes().strip() == b'42',
            'details': {'check': 'expected answer'}}
```

```sh
# 执行前冻结验证器，随后执行、采集、清理、独立验证并清理。
PYTHONPATH=src:. .venv/bin/python -m eval.cli task-env run \
  --workspace /absolute/fixture --out /absolute/evidence/task-001 \
  --cmd 'python3 main.py > answer.txt' --artifact answer.txt \
  --verifier /absolute/controller-checks --verifier-timeout 120
# 对已有已采集且已清理的任务进行一次新的后验验证（不冒充原实验预登记）。
PYTHONPATH=src:. .venv/bin/python -m eval.cli task-env verify \
  --task-out /absolute/evidence/task-001 --verifier /absolute/controller-checks \
  --out /absolute/evidence/verification-002
# 验证主控中断后单独恢复清理。
PYTHONPATH=src:. .venv/bin/python -m eval.cli task-env verify-cleanup \
  --out /absolute/evidence/task-001/verification
```

CLI 返回码：0 为执行与验证成功，1 为执行失败或明确判据失败，2 为配置/基础设施/验证异常；判据的结果与候选命令退出状态分别保留。独立 verify 返回 0/1/2 对应 pass/fail/其他。当前是控制器后端及 CLI，尚未接入产品 Agent/Web、既有 trial 槽位或 Benchmark 官方验证器，也未引入多服务/GPU 或自由文本语义判分。


## 13. 资源、网络与多服务 D 批（2026-11-17）

独立任务增加 `--environment-spec <JSON>`。配置只由控制器提供，支持版本 1、任务镜像/已固定镜像 ID、主执行资源、验证资源、网络模式与最多 8 个服务。拒绝未知字段，不能通过配置传入宿主挂载、Docker socket、privileged、cap_add 或任意 Compose 选项。所有镜像先解析/验证为本机已有的实际 ID，再创建资源；服务依赖图先检查未知依赖、重复名称与环并拓扑排序。实际冻结配置保存在 environment-spec.json，哈希与服务/网络身份纳入 environment.json。冻结配置可连同原 snapshot.tar 直接用于新任务复跑，已固定 ID 优先于原镜像引用，不随标签漂移。

资源单位与边界：cpus 为 .1–16；memory_mb 为整数 128–32768；pids 为整数 16–4096；tmpfs_mb 为整数 16–1024。默认值仍为 2 CPU/2048 MiB/256 PID/512 MiB tmpfs。主容器加服务的 CPU/内存配置总量上限 16 CPU/32 GiB，验证资源单独固定。所有执行/采集前核对实际配额；不提供硬盘卷容量配额或 GPU 声明，不承诺超出节点能力的资源可用。持续工作区产品路径仍使用 A 批原策略，D 的可配资源作用于独立任务与验证后端。

网络模式：none 为单容器断网（有服务时拒绝）；internal 为 Docker 内网；bridge 保留外联能力。有服务或选择 internal 时，创建任务专属 bridge 网络，服务名作为专属网络 DNS 别名，不发布宿主端口；无服务的 bridge 沿用 B 批原模式。internal 不等于宿主/内网目标的细粒度地址 ACL。不同任务使用不同网络与资源 ID，准入检查网络标签/ID/Internal、未知端点和每个容器的实际连接；外来端点会阻止新命令，清理时保留外来容器并让本网络进入 cleanup_pending，而不是强删其他资源。

服务配置包含 name、image（可附 image_id 固定）、command argv、显式字面量 env、resources、depends_on、healthcheck argv 与 startup_timeout（1–120 秒）。启动时为每服务创建独享 /data 卷，根只读、cap-drop ALL、no-new-privileges；按依赖顺序等待健康检查。健康检查通过才启动依赖方及主任务，运行前继续核对健康和资源身份；退出/健康超时属于准备失败，会回滚整个已创建拓扑。服务环境变量不会从宿主自动继承；显式配置值作为冻结配置留证。服务镜像需兼容只读根和该健康检查机制，不自动安装依赖或放宽权限。

清理顺序为主任务 → 逆依赖服务 → 私有工作区/缓存/服务数据卷 → 任务网络，保存最终服务状态和健康检查信息。控制器被强杀后，新进程从同一结果目录恢复整个拓扑的清理，不重放任务。Docker 对不存在网络使用 network ... not found 的回复，专门识别这一幂等成功条件；daemon 不可访问仍为待清理。

```json
{
  "version": 1,
  "network": "internal",
  "resources": {"cpus": 1, "memory_mb": 512, "pids": 128, "tmpfs_mb": 64},
  "verifier_resources": {"cpus": 1, "memory_mb": 512, "pids": 128, "tmpfs_mb": 64},
  "services": [{
    "name": "api",
    "image": "chagent:local",
    "command": ["/bin/sh", "-c", "printf 42 > /data/answer.txt; exec python3 -m http.server 8080 --directory /data"],
    "resources": {"cpus": 0.5, "memory_mb": 256, "pids": 64, "tmpfs_mb": 64},
    "healthcheck": ["python3", "-c", "import urllib.request; assert urllib.request.urlopen('http://127.0.0.1:8080/answer.txt',timeout=1).read()==b'42'"],
    "startup_timeout": 30
  }]
}
```

`--network` 可选 none/bridge/internal，与配置文件冲突时拒绝；不指定时保留默认断网。独立 `task-env verify` 可通过 `--verifier-resources <JSON>` 固定验证限额。验证容器继续断网且只消费声明产物，服务在验证前已清理；多服务任务应由主任务通过允许的服务接口生成交付物。保留后端数据库/服务状态给官方验证器、任意 Compose/GPU/GUI、产品 Agent/Web 与 Terminal-Bench/SWE-bench 适配均不在本批交付范围。
