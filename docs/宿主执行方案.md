# 宿主执行方案（A/B 两案，待决策）

**状态**：方案未决，代码未动。本文只描述目标、缺口与两条可选路径，不改变任何现有行为。
**问题来源**：2026-11-05 提出——Chagent 接到"写一个 Python 项目并在本机运行"这类任务时，应当能在选定工作区建文件、在容器内跑高危操作、自己审核结果、再**在用户本机**执行必要操作；宿主操作必须人工审核，确认后才执行；成品落在用户工作区。
**相关文档**：[统一可编程执行契约](统一可编程执行契约.md)（当前三轴）、[历史决策档案](历史决策档案.md)（为什么走到容器）、[实施计划](实施计划.md)（顺序）。

## 1. 目标流程与现状核对

| # | 要求 | 现状 | 结论 |
|---|---|---|---|
| 1 | 在选定工作区创建文件 | `write_file` / `edit_file` / `apply_patch` / `create_directory`，写入经 `WriteGate` 按不可逆性分级审批 | 已具备 |
| 2 | 在容器内执行高危操作 | `exec_command` / `run_tests` 就地跑在容器内（进程本身在容器里），`gate=approval` 时逐次询问 | 已具备 |
| 3 | 自己审核容器内执行结果 | 多轮循环读回 tool result、`run_tests` 定向验证；真实项目上出现过"2 失败 → 修复 → 5 通过" | 已具备（有 1 个已定位缺陷，见第 8 节） |
| 4 | 在用户本机执行操作 | 不存在任何宿主执行路径 | **缺失** |
| 5 | 宿主操作人工审核后才执行 | 审批 broker 只能管容器内的调用 | **缺失** |
| 6 | 成品输出到用户工作区 | 工作区是宿主目录的 bind mount，容器内写入即宿主写入 | 已具备 |

4/6。第 4、5 项是同一件事：没有宿主执行通道。

## 2. 当前为什么做不到

三条事实，缺一不可：

1. **Chagent 整个进程在容器里。** `compose.yaml` 的 `chagent` 服务就是它，`CHAGENT_WORKSPACE_ROOT=/workspaces` 是 bind mount 的挂载点；端口只映射 `127.0.0.1:8765` 与 `127.0.0.1:8080`。
2. **命令执行没有转交层。** `src/chagent/tools/sandbox.py` 的 `wrap()` 只做断言，不做搬运：边界不是 `container` 就抛 `PermissionError`，是就原样返回 `argv`，由本进程就地 `create_subprocess_exec`。容器是"进程所在的位置"，不是"命令被送去的后端"。
3. **"宿主可执行"这一档在类型层面不存在。** `src/chagent/execution.py:117`：

   ```python
   if axes.boundary == NONE and axes.capability == FULL:
       raise ValueError("Host commands require the container boundary; "
                        "set CHAGENT_EXECUTION_PROFILE=containerized")
   ```

   这行拦截的动机是防误配（有人只开了 `ALLOW_HOST_COMMANDS` 却没给容器），副作用是同时封死了一条正当的产品路径。

另有两条与方案无关、但会直接影响体验的已知取舍：容器不是强安全边界（root、无 userns）；取消 run 不回滚已写的文件。

## 3. 术语与边界

**宿主操作**：以运行 Chagent 的那个操作系统用户的权限、在容器之外执行的命令，或对该用户可见路径的读写。典型例子：`python3 -m venv`、`pip install`、`brew`、启动并访问本机服务、打开浏览器、改工作区以外的文件。

**容器操作**：模型生成的、可在镜像内完成的命令，例如 `pytest`、`npm ci`、`mvn test`、`git diff`。

**判定原则**：模型不能自己决定"这条去哪儿跑"就完事——位置由**工具参数**指定，权限由**策略**决定。宿主位置的授权强度恒高于容器位置，不允许配置成"宿主也免问"。

## 4. 方案 A：宿主执行代理（容器主控 + 一条窄通道）

### 4.1 结构

容器内的 Chagent 一个字都不搬。宿主上另起常驻进程 `chagent-hostexec`，它是**唯一持有宿主执行权的组件**。容器的工具面多一个 `host_exec`，但它只有"提出申请"的能力，没有执行能力。

```
容器: 模型 → host_exec 工具 → 静态审查 → TCP 请求
                                      ↓
宿主:                    HostRunner 收单 → 人工确认 → 受限执行 → 流式回传
                                      ↑                    ↓
宿主:                            审计日志 JSONL        工作区（同一份 bind mount）
```

### 4.2 一次调用的时序

1. 模型调用 `host_exec(command="python3 -m venv .venv && .venv/bin/pip install -r requirements.txt", cwd="myproj", purpose="准备本机运行环境")`。
2. 容器侧 `HostExecTool` 做本地静态审查：`cwd` 经 `WorkspaceFS.parts()` 逐级解析、不得越界；命令长度上限；单轮调用配额。**这一步只过滤坏请求，不构成授权。**
3. 请求经容器到宿主的固定端口发出（`host.docker.internal:8766`，宿主侧只绑定 loopback）。
4. 宿主进程弹确认：首版为终端 prompt，可选 `--ui web` 由宿主自己服务 `127.0.0.1:8766` 页面（**不是**容器的 8080）。显示命令原文、`cwd` 绝对路径、来源 run id、模型自述的 `purpose`。
5. 人批准 → 宿主任进程：`asyncio.create_subprocess_exec`，环境变量只给 `PATH/HOME/LANG/SHELL`，`start_new_session=True`，超时 `killpg`，输出按 4KB 块流式回传。
6. 输出与退出码回到容器，作为 tool result 交给模型。模型据此决定下一步：回容器重跑测试，或宣告完成。

### 4.3 授权模型（本方案的核心约束）

**确认必须在宿主侧完成，不能由容器转发。** 若容器侧网页弹卡、再把"已批准"带回宿主，等于让容器告诉宿主"人点过了"。容器一旦被 prompt injection 或依赖 RCE 攻破，就能伪造批准。因此：宿主进程自己收集点击、自己执行；容器全程不持有任何可直接触发的凭据。

容器环境里的 token 只用于挡本机其他进程乱连，**不承担授权作用**。授权只有一条：人在宿主侧点的那一下。

### 4.4 强制约束

- 无 `--yes` 自动批准模式。allowlist 默认空；显式开启后也只对**不含 shell 元字符**的前缀生效，判定复用 `policy.allowlisted()`。
- 请求不复用：一次申请一次确认，不缓存票据。
- 速率限制：默认 20 次/分钟，超限直接拒绝并记日志，防止模型刷屏逼人连点。
- `cwd` 必须落在 `CHAGENT_HOST_WORKSPACES` 内，且不跟随符号链接。
- 审计写到宿主的 `~/Library/Logs/chagent/hostexec.jsonl`（Linux 为 `~/.local/state/chagent/`），容器不可写。
- 最坏后果写清楚：容器被攻破后能发起任意申请、会在宿主日志留痕、**没人点就不会发生任何事**。

### 4.5 平台细节

**不要用 Unix domain socket。** Docker Desktop 的容器跑在 Linux 虚拟机里，宿主 macOS 的 socket 文件 bind 进去后连不上（inode 属于 macOS，不在 VM 命名空间内）。必须走 TCP + `host.docker.internal`（compose 需 `extra_hosts: ["host.docker.internal:host-gateway"]`）。仅在 Linux 原生 Docker 下才考虑 `$XDG_RUNTIME_DIR/chagent/host.sock`。

### 4.6 改动清单

| 位置 | 内容 |
|---|---|
| `src/chagent/hostexec/`（新） | `service.py` 服务端与生命周期、`protocol.py` 请求/响应与版本号、`confirm.py` 确认界面、`runner.py` 受限执行与输出回传 |
| `src/chagent/tools/host.py`（新） | `HostExecTool`，工具名 `host_exec` |
| `src/chagent/tools/builtin.py` | 仅当 `CHAGENT_HOST_EXEC=approval` 且 probe 通过时注册；探测不到则模型看不到这个工具（注册表即边界） |
| `src/chagent/execution.py` | 增加第四轴 `host_exec: off / approval`，同步 `describe()`、`/api/info`、启动横幅，保持"三处口径一致"的既有约束 |
| `src/chagent/tools/policy.py` | `host_exec` 的容器侧策略：不做逐次询问（真正的门在宿主），但记录 `purpose` 供确认界面使用 |
| `compose.yaml` | `extra_hosts`、`CHAGENT_HOST_EXEC`、`CHAGENT_HOST_ENDPOINT`、`CHAGENT_HOST_TOKEN` |
| `docs/统一可编程执行契约.md` | 新增第四轴与宿主通道的约束、失败措辞、退路 |

### 4.7 长进程

`host_exec` 支持 `yield_ms`。给出时走 `start` 模式：返回 `{status: "running", pid, log_path}`，日志写在工作区内 `.chagent/logs/<call_id>.log`，模型用现有 `read_file` 读取。这样既不必给容器开第二条读日志的通道，也不会让宿主长跑进程占死一次工具调用。

### 4.8 失败模式

| 情况 | 表现 |
|---|---|
| 宿主进程没起 | 工具不注册，模型没有这个能力 |
| 人拒绝 | 返回"这是对这次宿主执行的决定，容器内可继续"，不复用命令类拒绝措辞 |
| 超时 | `killpg` + `outcome_unknown=execution_started`，与一次性命令一致 |
| 宿主进程崩溃 | 容器侧请求超时失败，run 继续，模型收到"宿主执行器不可用" |
| 速率超限 | 直接拒绝并提示"稍后再试"，不排队 |

### 4.9 成本与风险

约 700–800 行新增代码、25–30 项测试，一天量级。风险集中在一个点：**宿主端口是新的攻击面**。缓解手段是第 4.3 与 4.4 两条——端口只是"申请的入口"，不是"执行的通路"。

## 5. 方案 B：主控搬到宿主，容器降级为执行后端

### 5.1 结构

`chagent` 服务从容器里搬出来，跑在宿主（`uv run chagent web`）。容器只留一个常驻的 `chagent-sandbox`，通过 `docker exec` 执行高危命令。宿主执行就是本地子进程——它本来就在自己家里。

```
宿主: Chagent 主控（模型循环、工具面、审批 broker、文件工具直接写工作区）
        ├─ target=host      → HostGate（强制审批）→ 原生 subprocess
        └─ target=container → 现有审批链        → docker exec chagent-sandbox
工作区: 宿主真实目录，无 mount 间接层
```

### 5.2 一次调用的时序

1. `exec_command(target="container")`（默认）→ 现有审批链 → `docker exec -i -w /workspaces/myproj chagent-sandbox /bin/sh -c "pytest"`。
2. 模型读回结果、自审、改代码（文件工具原生写宿主工作区，仍过 `WriteGate`）。
3. 需要本机运行时：`exec_command(target="host", command="python3 -m venv .venv && ...")`。
4. `HostGate` 拦截：强制审批，不可被 `never` 或 allowlist 降级；卡片标题固定为 `on your machine: …`。
5. 批准 → 宿主原生子进程，复用现有 `ProcessManager`（长进程、`process(write)`、`killpg` 全部可用）→ 结果回模型。
6. 成品直接在宿主工作区，无 mount 间接层。

### 5.3 改动清单

| 位置 | 内容 |
|---|---|
| `src/chagent/execution.py` | `BOUNDARIES` 加 `host`；`PUBLISHED` 加 `(host, full, approval)`；**硬拒** `(host, full, none)`；`executable` 从"进程级单值"改为"按目标判断" |
| `src/chagent/tools/command.py` | `exec_command` 增加 `target` 参数，默认 `container` |
| `src/chagent/tools/container.py`（新） | `ContainerRuntime`：`docker exec` 封装、宿主路径到 `/workspaces/<name>` 的映射、启动前健康检查、容器内环境变量白名单 |
| `src/chagent/tools/policy.py` | 新增 `HostGate`：`target=host` 恒返回需要审批，且不参与 allowlist 判定 |
| `src/chagent/tools/sandbox.py` | `wrap()` 从"原样返回"改为"包成 `docker exec`"，`record()` 增加 `target` 字段 |
| `compose.yaml` | `chagent` 服务移出；`chagent-sandbox` 常驻（`entrypoint: sleep infinity`），工作区仍 bind mount |
| 配置与迁移 | `CHAGENT_WORKSPACE_ROOT` 语义从容器内路径改为宿主真实根；`config show` 增加一致性校验；迁移说明 |

### 5.4 代价（必须记录的取舍）

这是对 2026-11-04 那次容器化改造的**部分回退**。那次把整个进程放进容器，是为了让"模型生成的命令"和"Chagent 本体"共用同一道边界。方案 B 之后，Chagent 本体以用户权限跑在宿主——只要代码里有一个路径校验漏洞，它就能读 `~/.ssh`。

换句话说：**A 保护"agent 本体被攻破"，B 只保护"模型生成的命令"**。B 的信任链更短、实现更直，但换掉的是当初那道理由。

另外：11-04 的容器执行验收证据需要重做，`docs/验收记录汇总.md` 第 6 节的结论会变成"针对旧部署形态"。

### 5.5 成本

约 900–1200 行改动、30–40 项测试、compose 与文档重写，2–3 天，含一次完整验收重跑。

## 6. 对照与推荐

| 维度 | 方案 A | 方案 B |
|---|---|---|
| 需求 1/2/3/6 | 不变，已具备 | 不变（写文件变原生，少一层间接） |
| 需求 4/5 | 新增受控通道 | 本地子进程 + `HostGate` |
| agent 本体被攻破 | 仍在容器内 | 获得用户权限 |
| 新增攻击面 | 一个宿主端口 + 一条协议 | 无新增，但 `docker exec` 参数拼接要防注入 |
| 实现量 | 一天 | 2–3 天 |
| 已验收资产 | 全部保留 | 容器验收需重做 |
| 长期形态 | 双组件 | 单组件 |

**推荐先做 A。** 理由不是工作量，而是 A 不推翻已验收的边界，只加一条"人点一下才通电"的线。B 的模型更干净，但它把刚建好的墙自己拆了一半；如果这台机器长期只做单人本地开发、且接受 agent 与用户同权限，再迁 B 不迟。

A 中的 `HostExecTool` 抽象层可按后端参数化（本地 / 远程 / VM），迁到 B 时可以直接复用为 `NativeRunner`，不会白写。

## 8. 无论选哪个，都该先补的三件事

这三件与宿主执行正交，但会直接影响方案落地后的验收可信度：

1. **批准证据回写**。`tools/scheduler.py` 的 `_ask()` 只在拒绝时写 `approval_result`，批准路径只把 `approval_id` 存进 `grants`，模型上下文里没有任何"有人批准过"的痕迹。C5 验收中模型因此断言"没有出现审批提示"——不是幻觉，是链路缺证据。修法：批准时也给工具结果附一条文本 + `details.approval="approved"`。
2. **`terminate` 语义**。参考 pi 的做法：拒绝后若整批工具结果都要求终止，则结束当前 run，避免模型在"这条路已封"时反复试。
3. **审批异常三路径**：浏览器断连超过 grace、审批到期、应用重启后的挂起恢复。三条都只有自动测试，没有真实网页证据。

## 9. 交付判据（两案通用）

这条能力算交付，需要同时满足：

- 真实模型在空工作区里从零建一个 Python 项目：容器内建虚拟环境受限 → 触发宿主执行 → 确认卡显示命令原文与 cwd。
- **拒绝一次**：模型收到"未执行、容器内可继续"，且不原样重试同一条命令。
- **批准一次**：宿主执行成功，输出回到模型，模型据此继续或收尾；成品文件出现在用户工作区。
- **无人值守**：没有页面/终端在等时，宿主请求必须失败，不得自动执行。
- **伪造无效**：绕过容器侧直接打宿主端口，无 token 得 401，有 token 但没人点则不执行。
- **可审计**：容器侧 tool record 与宿主侧 JSONL 都能查到同一次申请。
- 全量回归 0 失败，0 跳过；真实网页流程单独记录，不以自动测试替代。
