# F2 实施与审计：一次写入只付一次所有权校验

日期：2026-10-29。范围：`RunRepository`、`SummaryRepository`。无新迁移，无表结构变更。

## 1. 目标

B1 给每条受保护写入加了所有权校验：`SELECT ... FOR UPDATE` 确认 token、状态与租约，再写业务行，最后写事件。问题在于事件插入前又取了一次 `FOR UPDATE`——同一个事务、同一行、同一件事做了两遍。F2 的目标是把"每次写入一次校验"变成"每个事务一次校验"，并在能用条件更新表达的地方，让写入本身承担校验。

## 2. 改了什么

### 2.1 一个事务只有一道门

`check_owner()` 仍是唯一入口，现在它返回被锁定的运行行（`id`、`session_id`、`status`），并且明确写了一件事：它拿到的行锁同时是 `MAX(sequence) + 1` 分配序号的依据。因此同一事务内后续写入的每个事件都传 `locked=True`，只付一次 `INSERT`。

`_insert_events()` 不再接受 `locked` 参数，改为在 docstring 里写明前置条件：调用者必须已经持有运行行锁。原来那个参数给了"锁两次"一个合法的外表——默认值就是再锁一次，于是每条事件多出一条 SQL，而代码看上去毫无问题。

`_event(..., locked=False)` 保留"没有锁就自己取"的分支，专供不拥有该运行的写入者：记忆 worker 的 `audit_event`、重建恢复扫描的接班人。默认值仍是"自己取锁"，因为漏传只会多一条 SQL，不会写错顺序；漏传 `locked=True` 的代价由测试兜住。

### 2.2 终态写入自己就是门

`finish()` 原来先 `check_owner` 再 `UPDATE runs ... WHERE status = 'running'`，两条语句判断同一件事。现在合并为一条：

```sql
UPDATE runs SET status = %s, error = %s, end_reason = %s, ended_at = now()
WHERE id = %s AND status = 'running' AND owner_token = %s
  AND lease_expires_at > clock_timestamp()
RETURNING id
```

受影响 0 行时才多花一条 `SELECT` 说明原因，区分"运行已终态"（`RuntimeError`，与原来一致）与"失去所有权"（`RunOwnershipLost`）。错误路径才付这笔钱。

### 2.3 压缩调用改成条件写入

- `start_call()`：`INSERT INTO compaction_calls ... SELECT ... FROM runs WHERE ... owner_token = %s AND 租约有效`，`rowcount == 0` 即失联。写入前不再有探测查询。
- `finish_call()`：`UPDATE compaction_calls c ... FROM runs r WHERE r.id = c.run_id AND ...`，同样以运行行条件为准；0 行时再查一次，区分"调用已结束"与"失去所有权"。
- `save()`：复用 `check_owner()` 返回的行做会话归属检查，删掉后面那次 `SELECT session_id, status FROM runs ... FOR UPDATE`——同一事务里第二次读同一行没有任何收益。附带的行为变化：运行在检查点提交前一刻失去所有权或已终态，现在抛 `RunOwnershipLost`（归类为 `storage_error`），原来是 `StateConflictError`（归类为 `execution_error`）。两者都拒绝写入，新分类更贴近事实。

## 3. 实测

`scripts/bench_write_path.py --repeats 5`，临时 schema、离线模型、中位数：

| 场景 | SQL（F1 → F2） | 事务 | WAL | 墙钟 |
|---|---|---:|---:|---:|
| 两轮模型 + 一次工具 | 56 → **46**（−18%） | 11 | 20KB → 21KB | 10.4ms → 10.7ms |
| 1.6 秒流式回答（150 片 @10ms） | 64 → **59**（−8%） | 21 | 32KB → 33KB | 1690ms → 1628ms |

事务数不变是设计使然：F2 去掉的是事务内的重复语句，不改变提交边界。普通运行省 10 条、流式回答省 5 条，正好是各自的事务内业务写入数。

## 4. 与方案的偏差

**没有做到"每条写入 3 条 SQL 降到 2 条"。** 方案的原话如此，但一次业务写入的构成是"校验 + 业务行 + 事件"，其中校验语句同时是序号分配的锁，删不掉；能删的只是它后面那次重复加锁。所以实际是每条写入 4 → 3 条、每个事件批次 3 → 2 条。

要让业务写入本身降到 2 条，只有一条路：把序号分配并进校验语句，即给 `runs` 加 `event_sequence` 计数列，用

```sql
UPDATE runs SET event_sequence = event_sequence + %s WHERE ... RETURNING event_sequence - %s
```

同时完成"校验 + 加锁 + 发号"。评估后不采用：

- 它把序号从 `run_events` 的派生值变成 `runs` 上的独立状态，必须由**每一个**事件写入者维护——包括重建扫描的接班人（它不拥有运行，条件更新不适用）和压缩检查点里那条直接 `INSERT ... MAX(sequence) + 1`。任何一处漏掉都会撞 `(run_id, sequence)` 主键，而这是审计主键。
- 换来的是每批少一条 `MAX(sequence)`：那是主键索引上的取最大，不是当前成本。当前成本在提交与 fsync，F1 已经把 81 个事务压到 21。
- 需要新迁移与存量回填，收益与风险不成比例。

**校验频率没有降低。** 每个事务仍然校验一次。方案标题写的是"降频"，落地的其实是"去重"：B1 的边界（旧 owner 不能回写、租约过期即失联）没有一丝放松，只是不再重复问同一个问题。真正降低频率（每 N 批一次）会削弱 B1，仍然不做。

## 5. 没动的部分

- 租约 30 秒、心跳 5 秒，`heartbeat()` 仍是条件更新。
- `begin()`、`finish()`、工具结果提交、压缩调用仍要求 owner 匹配。
- "租约过期不等于旧进程已死"的边界不变：拒绝写入，但不代替扫描器判定运行终态。
- 事件批量事务仍每批校验一次（F1 的 21 个事务里，校验次数等于批次数）。

## 6. 验收

新增 `tests/test_write_gate.py` 8 项，全量 **208 项通过**：

| 用例 | 钉住的形状 |
|---|---|
| 单条事件 | 2 条 SQL（门 + 插入），不是 3 |
| 模型调用开始 | 3 条 SQL（门 + 插入调用 + 插入事件） |
| 终态写入 | 6 条 SQL，且不包含独立的所有权探测 |
| 失权后写入 | 抛 `RunOwnershipLost`，运行仍为 `running`，事件表没有新增行 |
| 租约过期 | 抛 `RunOwnershipLost`，不误记为 `cancelled` |
| 重复终态写入 | 抛 `RuntimeError` 而不是所有权错误 |
| 压缩调用 | `start_call` 1 条、`finish_call` 2 条；失权后两条都拒绝 |
| 检查点保存 | 失权时由门直接拒绝，且不落任何行 |

这些用例同时是护栏：谁把 `locked=True` 漏掉、或者把独立的所有权探测加回来，SQL 条数断言会先失败。
