## 2. 成本方程

一次运行的总时长 ≈ **轮次 ×（首字延迟 + 生成长度／速率 + 框架开销）+ 工具耗时**。探针实测把这一项拆开：

| 分项 | 实测 | 占比 | 还能优化多少 |
|---|---|---|---|
| 首字延迟（供应商） | 570ms/轮 | 40% | 不在我们手里 |
| 模型生成 + 工具执行 | ≈ 860ms/轮 | 59% | 只能靠"少说话、少来回" |
| 框架（上下文构建、调度、事件） | **7ms/轮** | **0.5%** | 已到顶，继续压没有意义 |
| 提示缓存 | 83.4%（H 批后复测；P1 样本为 87.1%，两者不可直接比较） | — | 前缀断裂 **0** 次，已到理论上限 |

**推论**：把 SQL 从 46 条压到 20 条，省不出一轮；把编辑成功率从 2/3 提到 1，直接省一轮。因此下一阶段的每个批次都必须回答同一个问题：**它减少了几轮，或者减少了几次无效调用。** 答不出来的不做。

## 4. 目标形态

一次 run 的形态固定为四段，任一段的超额都算缺陷：

```
定点（0 轮）→ 读（1 轮，可并行多文件）→ 改（1 轮，可并行多文件）→ 验（1 轮）
```

对应三条硬约束：

1. **定点不花轮次**：cwd、目录树、AGENTS.md、git 状态在 system 里，模型不必先 `list_dir`。
2. **改要一次成**：编辑的失败代价是整轮，所以宁可工具侧宽容（归一化匹配、参数修复），也不让模型重试。
3. **工具面封顶 12 个**：现在 10 个，schema 合计约 2.8KB／轮。新增一个必须删一个，或证明它省下的轮次值得。

## 5. 批次

顺序即优先级。每批独立提交、独立验收、独立可回退。十个批次均已交付，此后新增工作仍按同一口径验收。

### M 批（第 0 步）· 让"轮次"成为可回归的指标

**动机**：现在所有报告都报毫秒，没有任何一处报轮次，因此 G–J 全部无法验收。

- `scripts/test_live_chain.py` 的每用例结果增加 `model_calls`、`tool_calls`、`repeated_tool_calls`，失败时打印工具序列。
- 新增 `scripts/probe_task.py`：固定 fixture 仓库，跑一次真实供应商任务，输出 `{turns, tool_calls, elapsed_s, correct, tool_sequence}` 到 `docs/diagnostics/`。
- 归档一套四场景探针，作为后续每批的对照：

| 场景 | 形态 | 现状 | 目标 |
|---|---|---|---|
| `fix` | 3 文件仓库 + 单行 bug + 2 失败用例 | 6 轮 / 8 调用 / 8.6s | 4 / 6 / 6.5s |
| `edit` | 同文件 3 处不连续修改，且源码含尾随空格与弯引号 | 未测（预期易失败） | 1 次 edit 调用成功 |
| `multifile` | 改函数签名，两个调用点需同步 | 未测 | ≤5 轮 |
| `long` | 需要一条 45 秒的命令 | **必然失败**（`exec_command` 硬上限 30s） | J 批后成功 |

**验收**：`probe_task.py` 一条命令复现四场景；`fix` 场景多次运行波动 ≤1 轮。

**2026-10-29 实施结果**：已交付。四场景基线与 `fix` 的波动数据见[实施记录](实施记录.md)第 10 节。

### G 批 · 让一次编辑就成功

**动机**：P0 开发期三次跑探针，两次 `apply_patch` 拒绝了本可应用的补丁（表头行数与 `*** End Patch` 标记）；模型随后重试或改用 `write_file`，各花掉一整轮。这不是模型笨，是我们在要求它手写 unified diff。

两套候选形态，**用 `edit` 与 `multifile` 两个场景实测后再选**，不先下结论：

- **G1（Pi 形态）**：`edit_file` 接受 `edits[]`，全部对原文件匹配；精确匹配失败后按 Pi 的归一化阶梯重试；同一段出现多次则报错；参数做 `prepareEditArguments` 式修复。
- **G2（收敛形态）**：`edit_file` 仍是单处，但新增 `delete_file`，`apply_patch` 从默认声明中摘除（保留在注册表，开关启用），编辑面变成 `edit_file + write_file + delete_file`。

共同要求：编辑失败的结果必须写清"哪一处、为什么、文件当前实际内容的前后 3 行"，让模型不必先 `read_file` 再改（现在失败后几乎必然多一轮读）。

**验收**：`edit` 场景 1 次调用成功；`multifile` 场景 ≤5 轮且不出现整文件 `write_file` 覆盖；连续 3 次跑不出现补丁解析失败。

**回退**：两个新工具都只被 `builtin.py` 引用，撤回注册即回到 P0 行为。

**2026-10-29 实施结果**：已交付，选 G1（Pi 形态）。为什么没有同时实测 G2、四次运行的轮次与调用数、`apply_patch` 归零的证据，见[实施记录](实施记录.md)第 11 节。

### H 批 · 开局零成本

**动机**：`fix` 场景 8 次调用里 2 次是定向（`list_dir .`、`list_dir app`），占 2/8 的调用与 1–2 轮。

在 system 里加一段**run 内静态**的环境事实（P1 的不变量仍然成立，因为它每 run 只算一次）：

- `cwd`、当前分支与 `status --short` 摘要（无仓库则省略该行）
- 两层目录树，每目录最多列 8 个文件名加该目录的文件总数；预算取窗口／16（上限 4KB），条目上限 200
- 仓库根与 cwd 之间各级 `AGENTS.md` 内容（按 Codex 的作用域规则拼接，深层在前）
- 明确一句"这些是启动时的快照，之后的变化用工具查"

**验收**：`fix` 场景不再出现开局 `list_dir`；轮次 6→4、调用 8→6、墙钟 ≤7s。前缀在一个 run 的所有轮次里逐字节相等（复用护栏测试 `test_each_turn_extends_the_previous_request_without_rewriting_it`）。

**风险与回退**：目录树可能撑大前缀（上限 4KB，约 1.3K token），若 `cache_read` 比例下降或 TTFT 变差，关掉这一段即可。

**2026-10-29 实施结果**：已交付。`list_dir` 归零（0/10），`fix` 轮次中位 **7 → 6**、墙钟中位 9.4s → 8.4s，但 **4 轮目标未达到**——10 次里 8 次仍先跑测试再改，两次改措辞都没拿掉；两处设计被实测推翻（只给目录名与文件数不够，许可式措辞会让模型照旧列目录）。数据与边界见[实施记录](实施记录.md)第 12 节。

### M2 批 · 度量闭环（S 批发现的口径漏洞）

**动机**：S 批的链路报告报了 **52.1% 缓存命中**，但这个数字**无法归因**。`scripts/report_prompt_cache.py` 硬编码 `postgresql:///chagent`，而 `test_live_chain.py` 为每个用例建一次性 schema 并在结束时 `DROP SCHEMA`——事后审计的工具读不到链路样本。于是「沙箱／上下文改动有没有弄断缓存」目前没有任何回归口径，而它恰好是 P1 不变量的唯一验收手段；L 批要改 system 段结构与压缩保留策略，没有它就无法验证。

**交付**：

- 链路用例复用 `report_prompt_cache.py` 里的 `payload_of()`／`sections()`，对每个 case 的每个 turn 算出 `reusable` 与 `breaks` 并写进报告（纯本地计算，**不额外请求**）。
- `--keep-schema DIR`：失败时保留 schema 名与还原脚本到 `docs/diagnostics/`，日常仍默认清理。
- `Resolved:` 行扩到行为相关配置（`sandbox`／`allow_host_commands`／`compaction`），或新增 `python -m chagent.config show`：本轮两次遇到「shell 环境变量静默盖掉 `.env`」（`CHAGENT_API_KEY` 导致 401、`CHAGENT_MODEL` 导致报告与文件不一致），目前只有 key 路径有提示。

**验收**：任取一份 `--case all` 报告，每个 case 都带 `cache: {hit, reusable, breaks}`，且 `hit` 与 provider usage 一致；人为把某一轮的 system 段改一个字节，报告必须指出 `breaks` 落在哪个 section。本批不减少轮次，按能力边界验收（同 S 批的例外条款）。

**2026-10-29 实施结果**：已交付，314 项测试全过。纯本地计算（零额外请求）：`chagent/diagnostics/cache.py` 从落库请求重建载荷，`report_prompt_cache.py` 与链路脚本共用同一实现。`--case all` **10/10 通过**，10 个 case 全部带 `cache`，根汇总 `hit=61.4%`／`reusable=93.5%`／`breaks=0`（12 次 task 调用）。断点验收在**真库**上做：保留一次失败运行的 schema，审计得 `reusable=92.7%`、`breaks=0`；把某一轮 system 段改一个字节后，同一命令输出 `reusable=0.0%`、`break at system`，并点名 `iteration 1 section system (6383 bytes not reusable)`。`--keep-schema` 只在失败时保留，产物写入失败则退回删除，不会泄漏 schema。同时修了一个旧缺陷：此前一律用 chat-completions 载荷审计，Anthropic 运行的字节会算错。详见[实施记录](实施记录.md)第 16 节。

### I 批 · 无进展检测

**动机**：同一套测试跑两遍、同一文件读两遍，在历史运行里反复出现；`max_turns=32` 是唯一的闸，太靠后。

同 run 内对 `(工具名, 规范化参数)` 计数：第 3 次相同调用不再执行，直接返回错误结果并附"你上次得到的是这份结果，请换策略"（带上次结果摘要，不带全文）。读类工具额外按 `(path, offset, limit)` 判定。

**验收**：构造夹具模型重复调用同一工具，run 以 `repeated_tool_call` 结束原因收敛，而不是耗尽轮次；真实探针不误伤（`edit` 场景里同一文件多次编辑参数不同，不应触发）。

**回退**：一个阈值常量置 0 即关闭。

**2026-10-29 实施结果**：已交付，324 项测试全过。语义按“一次尝试”定义：成功的 `write_file`／`edit_file`／`apply_patch` 开启新尝试，因此“改前跑一次、改后跑一次同一套测试”不会被判重复——这正是 H 批实测提出的要求。集成用例：同一调用每轮重复 → 2 执行、2 拒绝、4 轮后以 `repeated_tool_call` 结束（`max_turns=12`）。真实探针：`edit` 4/4 调用、0 重复；`fix` 两次各 1 次重复但 **`blocked=0`**（一次是改前改后跑测试，一次是补丁后重读），两个场景均正确。轮次未降低（`fix` 5–7，与 H 批同级）：该批买的是“不再无限重复”而不是“更快”。（第 13 节记录的是 G2，即 G 批编辑失败路径的性能修复，与本批无关。）详见[实施记录](实施记录.md)第 17 节。

### N 批 · `/remember` 本地路由（小而确定）✅ 已交付

**动机**：唯一已知的"按设计浪费轮次"——明确命令却进了模型循环，4 次请求、4.7 秒、5 次多余文件操作，且写入位置与数据库分叉。三次复测同一形态。

在输入进入模型循环前解析本地命令，复用现有校验与事务写入，返回真实的命令结果；不能用 `model_stop` 假装发生过模型调用。

**验收**：零供应商请求、零文件／命令工具调用；`scope`／`key` 非法时不返回成功；含 `/remember` 字样的普通句子不被误判。

**2026-10-29 实施结果**：命中即短路，新终态 `explicit_memory`，确认文本经 `save_notice()` 落库，记忆写入仍在完成事务内。`explicit_memory` 场景 **4756ms／2 请求／2 工具 → 24ms／0／0**；`explicit_memory_nonsecret` 10.7ms。三条边界各有断言：记忆策略关闭时不短路、被拒绝的命令（坏键名或疑似凭据）交回模型、普通句子不误判。全链路 9/9 通过。详见[实施记录](实施记录.md)第 14 节。

### S 批 · 沙箱（成本最低，先做）✅ 已交付

**动机**：`allow_host_commands` 一旦打开，一次提示注入就是宿主机任意命令、任意文件、任意网络。审批（K）解决「该不该允许」，沙箱解决「允了也做不出格的事」——两者不互相替代，但沙箱便宜十倍。

**2026-10-29 本机实测**（macOS 26.6.2，详见[执行边界设计](执行边界设计.md) §10）：seatbelt 的写隔离、网络关闭、定向禁读、孙进程继承**全部通过**，且能在沙箱内真实跑通项目测试（`Ran 2 tests, OK`）；**白名单式读隔离不可用**（全局 `deny file-read*` → SIGABRT）。`sandbox-exec` 会 exec 替换成子进程，PID 不变，因此现有 `killpg` 取消路径**零改动**。

**交付**：新增 `tools/sandbox.py`（约 150 行：`SandboxPolicy`／`SandboxSupport`／`Backend` 抽象／SBPL 生成／六项探测），`command.py` 与 `tests_runner.py` 两处 `wrap`，四个配置项，14 个测试。测完即止，不改超时、取消、调度、门控。

**验收**：打开 `CHAGENT_SANDBOX=workspace-write` 后，命令写不出工作区、连不上网、读不到 `deny_read` 中的任何一项，且拒绝发生在内核而非路径检查；探测失败时 fail closed，绝不静默降级；`sandbox` 字段如实进入工具结果。**不考核轮次与墙钟**：本批不减少模型往返，它买的是安全边界。

**回退**：`CHAGENT_SANDBOX=off`，无数据或迁移需要撤销。

**2026-10-29 实施结果**：已交付，303 项测试全过。六项探测全过；真机上工作区写入成功、`/private/tmp` 写入被拒、`ls ~/.ssh` 被拒、`curl` `exit=6`；`run_tests` 在沙箱内跑通（`.venv/bin/python` 符号链接可用）。三处设计被实测修正：白名单式读隔离不可用（只能黑名单）；`writable_tmp` 使「只写工作区」变为「工作区 + 私有临时目录」；审计记录必须描述实际权限而非配置。详见[实施记录](实施记录.md)第 15 节。

### L 批 · 上下文的正确性（不是优化）

**动机**：`ByteTokenCounter` 按 UTF-8 字节估算，英文约 4 倍高估、中文接近 1:1。后果不是"数字难看"，是**同一任务在中英文下压缩时机完全不同**：英文过早摘要，白丢刚读过的代码，模型随后重新 `read_file`——又是一轮。

- 换真 tokenizer（tiktoken 或供应商计数接口），保留字节计数器作为无网络回退，两者在 `snapshot` 里分别记录，不混用。
- 压缩改为**保留式**：最近 N 条工具结果原文保留，只摘要中段（Codex `compact_retained_tool_outputs`）。摘要提示词显式要求保留"已确认的文件路径与改动"。
- system 拆成 5 个具名段（`preamble`／`tools`／`rules`／`environment`／`state`），固定顺序拼装，加测试断言"同一 run 内各段字节不变"。

**验收**：同一份中英混合历史在两种计数器下的 `token_estimate` 偏差 < 15%（当前英文方向约 4×）；压缩前后各一次探针，`read_file` 次数不增加。

**2026-10-29 实施结果**：已交付，343 项测试全过。`tiktoken/cl100k_base` 对 5 次真实调用的中位绝对偏差 **2.5%**、均值比 **1.00×**；字节估算 **234.7%**、3.35×——验收线 <15% 达成。关键实现点是按**线上格式**计数（复用适配器的 `openai_message()`／`openai_tools()`），以及每工具 40 token 的声明开销校准常数。system 拆成 5 个具名段后，链路 `prompt_cache.breaks = 0`、`reusable = 93.5%`，说明分段没有弄断前缀。压缩改为保留最新 2 条工具结果原文；探针 `read_file` 次数 4/5 → 3/4（`edit` 2→2），未增加。压缩夹具必须按估算值定窗口：同一历史估算小约 3 倍，硬编码窗口会让压缩静默不再触发。详见[实施记录](实施记录.md)第 18 节。

### K 批 · 审批（执行边界的第一步）

**动机**：`exec_command` 只约束 cwd，进程不沙箱、无运行中审批。`allow_host_commands` 默认关闭是对的，但一旦打开，一次提示注入即可在宿主机执行任意命令。

- 命令准入：allowlist（可配）+ 每条新命令需一次批准；批准绑定 `(run_id, argv 摘要, cwd)`，不复用给不同命令；会话级"记住此命令"必须显式。
- 等待批准不占执行槽、不占工作区门控、不占数据库连接；取消与心跳在等待期间继续工作。
- 拒绝结果必须让模型看懂"被拒绝"与"执行失败"的区别，避免它换参数重试。

**验收**：注入式测试（模型试图 `curl … | sh`）在不批准时被拒绝且 run 正常收敛；批准一条命令后，另一条不同命令仍需批准；等待期间其他工具调用不阻塞。

**2026-10-29 实施结果**：已交付，368 项测试全过。三条验收都有端到端用例：拒绝路径目标文件不存在、无 `tool_started`、run 以 `model_stop` 收敛（`details.execution_started=false`）；批准 A 后执行 B 仍产生新的 pending；会话 A 等待时同一 runner 的会话 B 正常完成。另外补了两项设计里列为验收但容易漏的：运行预算 1.0s 等待 1.5s 后批准仍正常结束（`RunBudget` 暂停），以及指纹不匹配的陈旧 grant 无法消费。**没有**实现的：权限提升通道（`CHAGENT_ALLOW_UNSANDBOXED`）、`on-failure`、按 attempt 重试、跨进程即时唤醒（250ms 轮询兜底）、独立墙钟上限。详见[实施记录](实施记录.md)第 19 节。

### J 批 · 持久 shell（Codex 能力的关键缺口）✅ 已交付

**动机**：`exec_command` 的 `timeout_ms` 硬上限 **30 秒**，"装依赖／长构建／交互式调试"在当前形态下根本不可能。这是与 Codex 差距最大的一处，比再补两个只读工具重要得多。

最小切片（目标 ≤400 行，不追求 Codex 的 6,915 行）：

- `ProcessManager` 持有子进程，按 run 归属，提供 `start` / `read(since)` / `wait` / `stop`；
- `exec_command` 增加 `yield_time_ms`：到点未结束则返回 `process_id` + 已有输出，不占用整次工具调用的超时预算；
- 新增 `write_stdin(process_id, chars)` 与 `read_process(process_id, since)`；
- 输出走有界内存窗口 + 既有产物机制归档，支持游标；
- run 结束／取消时终止该 run 拥有的进程组；不跨 run 遗留服务；重启后不凭旧 PID 宣称接管。

**前置**：K 批必须先上线。持久 shell 把"一次性执行"变成"长期存在的写权限"，没有审批就是扩大了漏洞面。

**验收**：`long` 场景（45 秒命令）成功并分两次读回输出；取消后进程组确实回收；活动进程数有上限。

**2026-10-29 实施结果**：已交付，383 项测试全过（新增 15 项）。`long` 场景真实供应商 **3 轮／2 次工具调用／47.7 秒**：`exec_command(yield 30000)` 拿到 `SLOW_JOB_STARTED` 与句柄，`process(read, since=17, wait_ms=30000)` 一次取回剩余输出与退出码，结果文件生成。取消与 run 结束都 `killpg` 整个进程组，1 个 run 最多 4 个活进程。三个缺陷是真命令才暴露的：陈旧事件让 `wait_ms` 立即返回、退出码比末行输出晚到（多吃一轮）、单个超大 chunk 让有界窗口失效。边界：不跨进程接管、窗口有界、工作区门锁不覆盖进程、没有 PTY。详见[实施记录](实施记录.md)第 20 节。

## 6. 明确不做

| 不做 | 理由 |
|---|---|
| 继续压 SQL／事件路径 | 单轮 7ms，全压掉也省不出一次首字延迟 |
| Codex 的 `world_state` 哈希增量 | 为 100+ 工具、200KB 前缀设计；我们前缀几 KB 且缓存已到顶 |
| `spec_plan`／`tool_search` 动态工具加载 | 阈值未到：工具 >20 个或 schema >30KB 再议 |
| 把 per-run 数据挪出 system 去救缓存 | P1 已证：run 内是常量，挪了没有收益，尾部 user 消息还会让模型该停不停 |
| 多 Agent／子 Agent 委派 | 一次委派至少 +2 轮串行；在轮次还贵的时候是负收益 |
| 把 `exec_command` 上限简单调到 10 分钟 | 治不了"拿不到中间输出"，只会让一次卡死更贵；J 批才是解法 |
| 新增只读工具 | 工具面已 10 个，边际收益被 `grep`／`glob` 吃掉 |
| 把文件工具也塞进 OS 沙箱 | `WorkspaceFS` 的 dirfd + `O_NOFOLLOW` 已守住路径边界；子进程化换来的只是同一件事的内核版本，成本高一个量级 |
| 用 Docker 当沙箱 | 双命名空间路径翻译、`.venv` 符号链接跨不了容器、UID 映射与 bind mount 性能未知；Docker 的独占价值是「装依赖」，那属于 J |

统一验收口径：**每个批次都给出"轮次／工具调用／墙钟"三项前后对照**，并注明样本数；只有墙钟改善而轮次不变的批次不算完成——那说明省下的是常数项。

唯一例外是纯安全批次（S 沙箱）：它不减少模型往返，也不买任意一项常数项，买的是「允了也做不出格的事」。这类批次按**能力边界**验收——列出哪些动作被内核拒绝、哪些没有被拒绝，并如实写进能力表；不能用「测试全绿」代替「限制确实生效」。

必须保持的边界（沿用前版，未变）：PostgreSQL 保存审计事实、RunState 只是活动视图；状态与关键事件同事务提交，通知在提交后发送；文本、工具结果、终态不因客户端变慢而被丢弃；单次运行只有一个推进模型循环的任务；`unknown` 不等于未执行，租约到期不等于旧进程已死；宿主决定最大能力，模型只能提出请求；等待审批不占执行资源；沙箱、审批、恢复解决三个不同问题，任一通过都不能替代其余。

新增一条：**提示词里的每条指令都要有测试或探针兜底**。本次发现一个具体回归——P0 加进 `BasicContextBuilder` 的默认指令（"用 grep/glob 定位、一次 apply_patch、用 run_tests 验证"）在 P1 回退 `builder.py` 时被 `git checkout` 一并撤掉，没有任何测试发现。G 批已把默认指令改成"一次 `edit_file` 携带全部改动"并补了断言测试；H 批把它迁进具名 section 时沿用该断言，不要另起一份文案。
