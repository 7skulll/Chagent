# 下一阶段统一实施方案：事件、恢复、执行边界与长任务

状态：A 批已实施并通过核心验收，其他批次待实施；已与[执行边界设计](执行边界设计.md)合并。依据：当前工作区源码与本地 Pi、Codex 快照。本文是统一路线与验收计划；执行边界文档规定策略／沙箱／审批的详细契约。A 批实现与测量见[事件链路 A 批验收](事件链路A批验收.md)；其他章节仍为设计目标。

## 1. 目标与现状

目标是逐步达到 Codex 对编码任务的控制与执行能力，同时以 Pi 的短调用路径、直接事件传递和清晰状态所有权为性能参考。使用当前 Python、PostgreSQL、单进程本地应用结构，不引入额外消息服务。

当前已具备：提交后推进的 RunState、有界工具并发与工作区屏障、后台记忆提取、上下文投影与成本缓存、持久化事件和断线回放。

主要缺口：

| 当前行为 | 影响 | 本方案对应改造 |
|---|---|---|
| `_response()` 对每个文本增量等待一次事件事务 | 消费模型流被数据库延迟拖慢 | A：文本合并与提交后通知 |
| SSE 每 150ms 查询运行及事件 | 可见延迟和空查询增加 | A：通知唤醒，低频查询兜底 |
| 主运行所有权仅在内存 `_tasks` 中 | 强杀后运行不收敛，会话一直繁忙 | B：租约与写入所有权检查 |
| 失败运行整体不进入正常历史 | 下一次任务不知道已经发生的修改 | B：恢复已确认事实，保留未知提示 |
| 命令只有启用／关闭、没有受限执行与审批 | 真实仓库执行缺少可审计的权限边界 | E：策略、沙箱与审批 |
| 运行时只能拒绝新输入或取消 | 无法自然补充指令、排后续任务 | C：会话输入队列 |
| 命令一次性等待、无持续进程句柄 | 长测试、构建和服务启动受限 | D：可持续命令会话 |

`/remember` 的确定性短路作为独立小修复：明确命令不经过任务模型，避免额外文件操作。它不依赖 A–D，可以单独验收和提交。

## 2. 必须保持的边界

1. PostgreSQL 保存审计事实；RunState 是活动视图，不是第二份可独立修改的真相。
2. 状态变化与对应关键事件同事务提交；通知只在事务提交后发送。
3. 文本、工具结果、终态不因客户端变慢而被静默丢弃。预览可以合并，真实结果不能丢弃。
4. 单次运行仍只有一个推进模型循环的任务；工具并发、事件写入和记忆 worker 都有明确所有者与关闭流程。
5. `unknown` 不代表未执行，租约到期不代表旧进程已经死亡；修改工具与命令不得据此自动重放。
6. 每批独立验证和提交。先记录基线，再评价收益，避免把所有改动合成一个难以定位回归的大提交。
7. 宿主配置决定可申请的最大能力，模型只能提出请求；批准绑定具体调用，不能直接覆盖全局策略或扩大工作区根。
8. 等待审批不占执行槽、工作区门控或数据库连接；暂停活动预算时，心跳与取消继续工作。
9. 沙箱、审批与恢复分别解决限制、授权和失联收敛问题。任意一项通过都不能替代另外两项。

## 3. A 批：事件合并与提交后通知

已实施，核心验收通过。目标是缩短文本传递路径，保持原有工具循环、结果顺序和事务语义。具体结果、真实链路与尚未测量的浏览器绘制延迟见[验收报告](事件链路A批验收.md)。

### A1. 最小模块划分

| 模块 | 职责 |
|---|---|
| 新增 `agent/stream_writer.py`：`TextStreamWriter` | 单次模型响应的文本合并、定时刷新、容量限制、错误传播与关闭 |
| 新增 `events/notifications.py`：`RunNotifications` | 进程内按 run 唤醒订阅者，只保存版本与同步原语 |
| `storage/repositories.py` | 保留事件分配序号与事务写入；外层事务成功后通知 |
| `agent/runner.py` | 为每次模型流创建 writer，结束前排空，接收写入错误 |
| `web/app.py` | 先订阅再追赶数据库事件，随后等待通知；保持游标回放 |

不增加通用事件分发框架。writer 仅处理文本流，工具及状态事件继续由原有事务方法保存。

### A2. 文本合并规则

```text
供应商事件
  → 协议校验
  → 有界文本缓冲
  → 首个非空片段优先提交
  → 后续按 20ms 或 4KiB 刷新
  → 数据库提交成功
  → 通知 SSE 读取已提交序号
```

- 单次模型流一个后台 writer；容量初始设为 64KiB，按 UTF-8 字节统计，最终参数由基准决定。
- 缓冲计入正在写库的文本；单个超大片段按字符边界分段入队。容量耗尽时生产方等待，不持续创建任务、不静默丢文本。
- 定时器独立于新片段到达：供应商停止输出但尚未终结时，已有文本也会到期刷新。
- `flush()` 要等待调用时已接受的文本全部提交，不只是发一个唤醒信号。
- 模型正常终结后，先排空文本，再保存模型响应、完成事件，最后才可能调度工具。
- writer 写库失败要立即让模型消费方停止，关闭响应流，按存储错误收敛。不能等缓冲满了才发现失败。
- 用户取消或模型报错时，停止继续接受文本，对已接收文本做有上限的清理刷新；数据库不可用时不承诺保存全部尾部，也不能返回成功。
- 模型响应正文仍是最终回答依据，增量事件用于流式呈现。不可把未提交文本先发送给客户端，再假设将来能落库。

20ms 是合并阈值，不是持久化延迟上限。数据库繁忙会增加等待；强杀时可能丢失尚未提交的缓冲文本。工具意图、工具结果及已提交消息不受文本缓冲影响。正常结束必须保证增量拼接与最终正文一致。

### A3. 关键事件与通知

保留 `tool_queued`、`tool_started`、工具结果、模型响应、运行终态与状态的事务关联，不放进文本合并队列。

`RunRepository._event(connection, ...)` 处于其他方法的事务内，不能在这里直接发通知。通知应由真正拥有事务的方法在退出事务后发出。显式记忆写入、后台记忆完成等嵌套事务同样遵守此规则；需要检查所有外层提交入口。

通知不存正文、不分配事件序号，也不为每个订阅者保存事件列表。通知失败或遗漏只影响及时性，客户端仍能通过数据库补齐。

### A4. SSE 等待协议

1. 建立订阅，持有该 run 的通知版本。
2. 捕获版本，查询并发送 `sequence > cursor` 的持久事件；有整页积压就立即继续追赶。
3. 无积压时等待版本变化；等待前重新检查版本，避免查询与等待之间漏通知。
4. 无通知也定期重查，初始兜底间隔 1 秒，兼容通知丢失和其他进程写入；不是多进程即时推送承诺。
5. 断线以最后的持久序号恢复；客户端如需处理重复交付，按事件 ID 去重。
6. 订阅结束释放引用，不保留无限增长的 run 通知字典。

运行流在对应终态事件处结束，而不是要求“整个审计流最后一个事件永远是 run_completed”。后台记忆可能继续追加事件。记忆 job 通过独立状态查询显示，不能让回答 SSE 为等待提取一直不结束。游标已超过终态时也应立即结束。现有终态之后的记忆审计事件保留在库里。

### A5. 验收门槛

| 验收 | 通过条件 |
|---|---|
| 文本正确性 | 正常结束时，持久增量拼接等于最终回答，含中文、空片段和超大片段 |
| 时间阈值 | 供应商暂停时，未满 4KiB 的已有文本仍自动刷新 |
| 顺序与原子性 | 文本提交在模型完成及工具执行之前；事务回滚不发布相应事件通知 |
| 失败收敛 | 注入 COMMIT 失败，模型消费停止，无后台 writer 泄漏，无成功终态 |
| 取消与关闭 | 在排队、写库、等待通知时分别取消；状态正确且所有子任务退出 |
| 回放 | 连接中断重连无缺片；查询与等待交界的通知不会造成长时间挂起 |
| 背压 | 慢 SSE 客户端不拖住模型消费；慢数据库下缓冲达到容量后背压，内存不持续增长 |
| 后台记忆 | 回答流及时结束；job 可继续处理且状态可独立获取 |

性能验收采用单独 A/B 基准，至少 30 次测量，记录中位数和 P95。复用相同 PostgreSQL、固定响应大小和增量节奏；分别测快速突发和慢速持续输出。

- 快速突发 128 个小增量场景，文本事件事务数目标减少至少 80%；不要求慢速逐片到达场景也有此收益。
- 空闲 SSE 数据库查询频率目标从约每秒 6.7 轮降到不高于每秒 1 轮／连接。
- 单进程轻负载下，提交完成到 SSE 生成数据的 P95 目标低于 30ms；首个可见片段的 P95 不应明显回退。
- ASGI 传输延迟与浏览器可见首字分别测量，模型网络耗时单列，不能混成“框架速度”。

这批不需要新增数据库表或迁移。保留现有序号分配锁，只有基准证明它成为瓶颈时再优化。

## 4. B 批：运行所有权与失败事实恢复

分 B1、B2 两次交付，先解除永久繁忙，再让续聊理解已发生的事实。

### B1. 所有权与失联收敛

给主运行增加执行所有权 token、租约截止时间和必要索引。一个运行的一次执行使用一个不可复用 token；第一版不接管同一个 run 继续执行，失联后标为 interrupted，续聊创建新 run。

- 租约使用数据库时间；初始参考心跳 5 秒、租约 30 秒，部署前结合事件循环阻塞测量调整。
- 心跳续租必须同时满足 token 匹配、运行活动、租约尚未过期；过期所有者不能自行复活。
- 模型／工具状态提交、消息和关键事件提交都在事务内校验并锁定对应所有权。后台记忆事件属于已结束运行的审计，走自己的 job 所有权，不能被主运行的活动检查误伤。
- owner 检查必须在实际事务内完成，不能先查询通过、稍后再无条件提交。锁顺序统一，避免与工具行更新产生死锁。
- 启动及定期扫描过期运行：同事务标记 `interrupted/owner_lost`，排队工具 cancelled，未确认执行 unknown，关闭遗留调用并写终态事件，解除会话占用。
- 心跳失败或 owner 校验失败时，旧进程停止接受新操作、取消本地执行并清理资源；不得覆盖已由恢复流程写入的终态。
- 执行工具前检查所有权，但明确它与文件系统操作之间不是原子事务。失联后的外部副作用仍可能不确定，不承诺 exactly-once。

同时审查 memory job 的领取与完成是否绑定该次领取 token，避免将来旧 worker 在租约回收后覆盖新尝试。

验收使用两个真实进程与隔离 schema：强杀执行进程、到期收敛、新输入可运行、暂停后恢复的旧进程不能再提交、心跳与扫描并发、健康长任务不被误回收。补测数据库短暂不可用时的保守停止。

### B2. 失败事实恢复

保持原始历史不变，增加恢复上下文投影，不把整个失败模型交换直接塞回正常历史。

- 读取上次失败／取消／失联运行中已提交的工具结果及相关产物。
- 对确认成功的修改提供事实引用；对 unknown 调用列出执行意图与未确认状态，不宣称成功。
- 已确认事实优先由结构化记录生成，不额外请求模型总结，不增加续聊的模型前置调用。
- 恢复信息包含源 run、tool record、artifact ID，并作为参考数据注入，不能成为新授权。
- 避免生成孤立的 tool result 或缺结果的 assistant tool-call 批次；不改变供应商协议要求。
- 以最新恢复边界去重并纳入上下文预算；不能每次续聊重复注入整个失败历史。

核心场景：写文件成功但结果提交失败、取消时已有一部分工具完成、命令超时可能产生副作用、失败前已有大产物。新运行先确认实际文件状态，不自动重做未知修改。

## 5. E 批：执行策略、沙箱与审批

这是合并后新增的优先里程碑，移到运行中输入和持续进程之前。原路线把权限策略放在较后位置；若目标是在真实仓库执行编码任务，应在扩大命令能力前具备受限执行与授权。具体规则见[执行边界设计](执行边界设计.md)。

### E1. 策略与受限执行

- Executor 是策略的统一收口，保留参数校验与宿主命令开关。默认不因沙箱探测成功自动注册命令。
- 默认文件权限、宿主可申请范围、本次授权分开；文件写、网络、无沙箱执行分别控制。
- read-only 要拒绝工作区内写入；untrusted 在 full 下仍需逐次确认，不能因模式变大而失效。
- 文件工具继续使用 WorkspaceFS，只支持工作区内路径；第一版区外写直接拒绝，不承诺批准后绕过当前路径边界。
- 沙箱后端需要实际验证允许写、拒绝写、网络限制等行为；不可用时关闭受限命令能力。只有宿主明确允许且符合审批策略时，才可使用如实标记的无沙箱执行。
- 进程权限配置包含读取／写入范围、受保护路径、环境与网络，profile 缓存覆盖完整权限指纹。
- 第一小步可先交付 never 策略和拒绝路径；审批入口未实现时不接受会无限等待的配置。

验收先验证策略与实际 OS 边界，再跑真实模型语义场景；不能靠工具自述或模拟测试证明沙箱可用。

### E2. 审批与执行准入

依赖 A 的提交后通知、B1 的所有权清理与 E1 的权限判定，不新增重复的事件总线或恢复扫描器。

```text
准备调用／策略判定
  → 必要时创建审批并等待（不持有执行资源）
  → 重新取得工作区门控与并发额度
  → 校验 owner、grant、参数及文件版本
  → tool_started → 实际执行 → 原顺序提交结果
```

采用 `Executor.prepare`／`execute_prepared` 的小拆分。审批等待由 Scheduler 在到达该独立分组时完成；分类可保守串行，但不能只在现有 slot 内增加一次 await。

- 新增 ApprovalBroker 与审批表，使用调用指纹、attempt、owner、期限和策略版本绑定本次授权。
- 通知只用于唤醒，审批结论必须读库；批准／过期／取消通过条件更新竞争，防止快速批准丢信号和重复授权。
- 保留 RunStatus，运行仍为 running；API 依据 pending 审批显示 waiting_for=approval。避免为了等待原因扩展所有状态判断。
- 活动预算在等待前暂停，等待结束恢复剩余时间；工具预算从实际执行开始。等待期间保留独立审批期限、可选墙钟上限和持续心跳。
- CLI 交互与 Web 都能显示具体操作、路径和权限差异；非交互模式不自动批准、不无限等待。审批接口检查受信请求来源。
- 第一版关闭 on-failure。普通非零退出码、超时和网络错误不能证明命令尚未产生副作用。
- 审批拒绝返回明确的“未执行”结果；取消、进程关闭或失联则收敛 pending 审批，不复活旧运行。

验收特别加入：等待时其他会话可使用同工作区；0.5 秒活动预算等待 2 秒审批后可继续；取消后再批准不得执行；旧 owner 与过期 grant 不可使用；审批之后文件变化不得静默覆盖。

### 合并时明确舍弃的旧做法

- 不按 started_at 批量终结旧运行，只处理租约确认失效的 owner。
- 不用每 run 单队列向多个 SSE 连接分发事件，统一复用版本通知与数据库游标。
- 不在等待完成后才补 deadline，也不让人工等待占用 ToolExecutor 的执行超时。
- 不自动无沙箱重跑已经启动过的命令，不把网络请求升级成 full 文件权限。
- 不预先固定“0010 同时实现全部审批状态迁移”；迁移按各批实际落地顺序追加。

## 6. C 批：运行中输入队列

保留每个会话单一模型循环所有者，增加顺序明确的用户输入：

| 输入 | 第一版语义 |
|---|---|
| steer：补充指令 | 持久化接收，在完整工具批次结束或下一次模型请求前消费 |
| follow-up：后续任务 | 当前运行收敛后，按接收顺序启动后续运行 |
| cancel | 取消活动任务，等待清理；不自动删除排队任务 |

初版不在半个工具批次中间更改任务。等待模型输出时收到 steer 会明确显示“已排队”；若要立即中断，用户可取消。避免对已发出的请求悄悄假定它已经收到新指令。

输入需要唯一请求 ID、接收序号和消费状态；在事务中处理重复提交与消费。持久记录不等于所有消息都已执行：重启后排队输入应可查询，能否自动启动必须遵守运行恢复规则。

`RunState.current_input` 当前指向原始用户输入。增加 steer 后必须明确原始目标、已消费补充输入与记忆召回查询的区别，不能让记忆提取和上下文构建继续误认只有一条用户消息。

验收：连续补充、排队后取消、重复网络提交、运行完成与新输入同时发生、重启后恢复队列，以及任何时刻每个会话只有一个模型循环。

## 7. D 批：可持续命令会话与编码闭环

在 E 批通过后，先支持非交互进程，复用同一策略、沙箱、审批、进程组与产物机制。ProcessManager 不成为绕过 Executor 的第二个执行入口。

- 一个 `ProcessManager` 拥有子进程，提供启动、读取新输出、等待、停止；后续有真实交互需求时再加 stdin／PTY。
- 命令工具短时间等待后可返回稳定 process ID，不让长构建占住一次工具调用的超时预算。
- 明确“启动工具调用已完成”与“子进程已经结束”的区别，运行停止也不等于所有子进程自然完成。
- 输出采用有界内存窗口与产物归档，支持游标读取；限制活动进程数量、输出量和保留时间。
- 进程关联工作区、会话与创建运行。默认停止／取消时终止该运行拥有的进程；需要跨运行保留时必须有显式持有策略，不默认遗留服务。
- 沿用受控命令开关；进程会话本身不提供操作系统沙箱。进程重启后不凭旧 PID 宣称已重新接管子进程。

验收：长测试运行、逐步读取输出、输出截断与完整归档、取消进程树、停止后回收、服务关停清理与启动期间取消。

随后补代码搜索、多文件补丁、turn diff 与变更回退，建立真实编码任务集：定位问题→修改→运行测试→根据失败修复→交付。供应商重试另作独立改造，至少区分请求尚未产生输出、已产生部分输出、工具已经执行，不能统一重试整轮。

## 8. `/remember` 小修复

在用户输入进入模型循环前解析明确的本地命令；复用现有记忆校验、来源记录与事务写入，返回真实命令处理结果。

需要定义本地命令的完成原因和返回字段，并同步 CLI、API 与网页。不能用 `model_stop` 假装发生过模型调用；也不能破坏工具正常停止时 `message=None` 的现有契约。

验收包括零供应商请求、零文件／命令工具调用、scope／key 校验、写入失败不返回成功、关闭记忆时行为明确、普通包含 `/remember` 字样的句子不被误判成命令。
