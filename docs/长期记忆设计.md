# 长期记忆

在会话摘要、运行内压缩和工具产物之上，增加用户与工作区的长期记忆。采用 PostgreSQL、关键词检索和有版本的记忆记录，复用现有模型适配器，不增加向量数据库、合并代理或独立调度服务。记忆与会话摘要分开：摘要帮助继续原任务，记忆供新会话复用稳定偏好与事实。

自动提取最初发生在运行完成事务里，后来改成 `memory_jobs` 队列加进程内 worker：运行只负责入队，回答不必等待第二次模型调用。

工作区身份（2026-11-08 合并后口径）：记忆挂在 `workspaces` 行上，而工作区的身份由 `workspace_bindings`（宿主路径 + `device` + `inode`）证明。无法证明宿主来源的旧 `/workspaces` 行标记为 `rebind_required`：会话与记忆仍在库里、可通过只读审计接口查看，但不会被注入当前工作区的检索结果，也不能在其上执行。**没有单独的“隔离状态”字段**——可见性由读时按绑定过滤决定，因此不存在“记忆状态是 quarantined 所以不可见”与“绑定不可用所以不可见”两套口径并存的情况。旧记录不会仅凭相同的 `/workspaces` 路径自动绑定；目录身份变化（设备号或 inode 变了）时要求显式重新绑定，见[验收第 19 节](验收记录汇总.md#19-迁移后工作区隔离2026-11-05)与[数据库配置](数据库配置.md)。

## 分层与主链路

| 模块 | 职责 |
| --- | --- |
| `domain/memories.py` | Memory、MemoryProposal、MemoryPolicy，以及内容与作用范围校验 |
| `storage/memories.py:MemoryRepository` | 作用范围、检索、去重、冲突、乐观版本、版本审计与删除状态 |
| `storage/memory_jobs.py:MemoryJobRepository` | 提取队列：入队、领取、租约回收、重试与终态 |
| `memory/service.py:MemoryService` | 按预算注入、显式记忆指令、提取调用与候选校验 |
| `memory/worker.py:MemoryWorker` | 进程内后台 worker：领取 job、独立超时、失败重试 |
| `memory/__main__.py` | 无需模型 Key 的本地记忆管理 CLI |
| `web/app.py` 和网页记忆弹窗 | 创建、编辑、候选审核、冲突替换、删除、来源与版本查看 |

```text
每次任务模型请求：
  ContextManager → 系统／任务状态＋摘要＋近期完整交换
  MemoryService.enrich → 检索已生效记忆 → 按剩余预算加入参考资料
  ModelRequest + 带记忆 ID／revision 的 ContextSnapshot

任务已得到最终回答，runs.finish 事务内：
  显式 /remember → 程序解析并直接写入（整条运行不进模型循环，终态 explicit_memory）
  其他情况       → worth_extracting 判断后只插入 memory_jobs 一行
  → 发出 memory_job_queued，随后 run_completed

运行结束之后（MemoryWorker）：
  SKIP LOCKED 领取 job → 独立超时内调用模型 → 校验候选
  → 候选写入与 job 终态同事务提交
```

记忆不会伪装成当前系统指令或用户授权。注入使用独立的 UserMessage，标记为检索到的历史参考资料，明确当前用户输入和显式 TaskState 优先；不修改原始 messages。候选、已拒绝和已删除的内容均不进入检索。

## 作用范围与检索

- `user`：本地单用户的偏好，在各工作区共享，没有多人账户体系。
- `workspace`：项目事实，按数据库 workspace_id 隔离。网页按当前选中的已打开工作区过滤，模型不能自行选择任意未授权工作区读取。

同一个 key 在同一作用范围至多一条 active 记录；工作区记录会覆盖相同 key 的用户默认值，其他工作区仍使用用户默认值。

查询取自当前运行的原始用户输入。英文按词提取，中文按相邻双字提取，最多 32 项；使用参数化的 PostgreSQL strpos 匹配 key 与 content。匹配的工作区事实优先，并为匹配的用户偏好预留候选位置；无关 pinned 记录排在相关记录之后。用户级资料可作为通用偏好参与检索；工作区事实需要命中关键词、被用户标为 pinned，或覆盖同键的活动用户默认值。

默认最多注入 8 条；检索最多读取 4 倍的候选，以便前面的较长记录放不进预算时仍能尝试后面的记录。记忆整体预算为 `min(2048, 输入预算的 10%)`，并且不能让最终请求超过现有输入预算。预算不足时跳过记忆，不挤掉原始用户输入、任务状态或当前保留交换。pinned 允许无关键词匹配，不代表可以绕过预算或压过相关工作区事实。

快照新增：

```text
memory_references: [{id, revision, key, scope}]
memory_token_estimate
memory_omitted
```

这些字段用于解释本轮到底使用了哪些记忆；实际正文保存在模型请求审计中。计费使用与主上下文相同的估算器（`wire_tokens_ascii4_wide1`），并从供应商锚点中扣除，避免同一段记忆每轮被重复计入。

记忆管理页可按需查看每条记忆的注入轮数、最近注入时间和显式修正次数。注入统计直接从每个 run 的首个模型请求快照计算，不在请求主链路额外写库；它表示该记忆进入过请求，不证明它帮助了回答。

## 三种写入方式

**手动管理**：网页或 CLI 显式创建的内容直接生效，origin 为 manual。同键已有不同的活动内容时返回冲突，要求编辑当前版本。

**格式明确的记住指令**：在聊天里发送：

```text
/remember user response.language = 用中文简洁回答
/remember workspace project.database = 使用 PostgreSQL
记住用户：回答尽量简洁
记住项目：本项目使用 PostgreSQL
记住：这是一条当前工作区笔记
```

这些指令由程序解析，成功完成该轮任务后提交，origin 为 explicit_user。用户级显式笔记默认 pinned；没有指定键的笔记使用内容哈希生成 note 键。它们仍会作为本轮普通聊天输入交给任务模型，不是独立的聊天路由。

相同键与内容会去重；同键内容不同则产生候选供审核，不覆盖已有记录。明确指令与一个无冲突候选的内容完全相同时，可以直接激活该候选。格式不匹配的普通自然语言走候选提取规则，不猜测写入指令。

**模型候选**：默认对长度至少 80 字符，或含偏好／习惯／记住等中英文提示词的已完成任务，额外调用一次模型——由完成事务判断"值不值得提取"并入队，实际的模型调用发生在运行结束之后。可通过配置关闭。模型不提供工具，只返回严格 JSON，最多 5 条：

```json
{"memories":[{"key":"response.language","scope":"user","content":"用中文简洁回答","evidence":"偏好中文"}]}
```

每条 evidence 必须是本次用户原文的非空精确子串；来源消息 ID 由程序绑定，模型不能指定来源、状态、pinned 或审批结果。提取只使用有边界的当前用户输入和最终回答，不扫描所有历史，不把工具输出中的文本当成用户声明。推断结果始终是 candidate，审核前不会进入上下文。

默认提取超时 20 秒，输出上限不超过当前模型的 1200 tokens。输入根据模型窗口缩小并标记截断；无预算、断流、非法 JSON、来源不匹配、工具调用、空白条目或明显凭据内容都会被拒绝。没有可记忆内容时允许空列表。

## 冲突与版本

每条记录保存 key、content、scope、pinned、status、revision、origin、源会话／运行／消息、evidence、conflict_with 与时间。origin 记录生成来源；用户后续编辑、采纳或替换可以在版本动作中追溯。

活动记录与同键新候选并存。网页展示当前活动内容和 revision 后才提供替换操作；采纳时必须提交候选 revision，以及要替换的活动记录 ID 和 revision。任何一方已变化都返回 409，避免旧页面覆盖新状态。

所有编辑、采纳、拒绝和删除都会递增 revision，并向 memory_revisions 追加快照。按作用范围与 key 使用事务级锁；批量提案按稳定顺序获取锁，避免不同会话交叉更新同组记忆。去重依据同范围、同键和内容哈希，不进行语义相似度合并。

删除将状态改为 deleted，立即停止后续检索。同键、同内容的自动提取不会重新加入已删除或已拒绝的记录；用户明确再次保存则可以重新建立。删除不是历史擦除：原始聊天、已有请求快照、摘要和版本审计仍保留，过去的回答中也可能已经引用过该事实。

## 完成、取消与故障

显式指令在运行完成事务内直接写入，不经过队列；它与运行终态同事务提交，写入失败会回滚这一批记忆，只保留任务终态并记录 `memory_write_failed`。

**整条运行也不进模型循环。** 命令在 `_load_state()` 之后、第一次构建上下文之前被识别，命中即以 `explicit_memory` 结束：零供应商请求、零工具调用、不构建模型上下文；当前普通运行也不再自动采集环境快照。确认文本由 `RunRepository.save_notice()` 作为一条没有 `model_calls` 行可挂的 assistant 消息落库，CLI、网页与事件重放看到的是同一条。

这样做的理由不是省一次调用，而是**避免重复写入**：命令同时作为普通消息进入模型时，模型会按"用户要我记住"再写一个 `MEMORY.md`，未经验证的副本可能在后续文件读取中被当作另一份事实，与数据库记录并存。早期 AGENTS.md 自动注入路径已移除。

三条边界：

- 记忆策略关闭时不短路——此时完成事务什么也不写，给"已记住"就是撒谎，运行仍走模型。
- 命令被拒绝时不短路——键名不合法或内容像凭据（`validate_memory` 拒绝）时交回模型解释原因；两条路都不写库，但用户拿到的是理由而不是假确认。
- 只有整条输入就是命令才命中（`fullmatch`），"请说明 /remember 怎么用"这类句子照常走模型。

自动提取走队列：

- 完成事务只插入 `memory_jobs` 一行（`run_id` 唯一键，天然幂等），发出 `memory_job_queued`，随后 `run_completed`。整个事务不发起模型调用。
- `MemoryWorker` 用 `FOR UPDATE SKIP LOCKED` 领取任务，带租约、领取令牌（`claim_token`）与 `attempts` 计数；`attempts` 达 `max_attempts` 后置为 `failed`。
- 候选写入与 job 终态在同一事务提交，因此不会出现"记忆写了但任务仍待处理"或反过来的不一致。
- 完成、失败与归队都要求令牌匹配：租约被回收后，旧领取者的写入被拒绝并抛 `MemoryJobClaimLost`；由于它在候选写入的同一事务内抛出，候选一并回滚，不会留下重复记忆。旧尝试此时静默退出，不把已由新尝试接管的 job 报成失败。
- 提取失败只改 job：按 `retry_delay` 重新可用并发 `memory_job_failed`，运行终态保持 `completed`。用户已看到的回答不会被提取失败改写。
- 取消与崩溃必须分开：主动取消（关停或外部取消）走 `requeue`，不消耗次数；租约过期由 `reap_expired()` 回收并计一次尝试，同时把该次尝试遗留的 `memory_extractions` 行标记为失败。
- 提取预算超时被转换成普通失败（消耗一次尝试），只有进程真正停止才会归队。

提取请求使用独立的 `memory_extractions` 表，保存 `prompt_version`、`purpose=memory` 的请求、响应、状态与耗时，不混入任务 `model_calls`，也不把提取文本流到聊天中。

代价：记忆可见时间晚于回答。网页由进程内 worker 立即接手；单次 CLI 在打印结果后 `drain` 一次，仍在退避或超时的任务留到下次启动并明确提示。没有独立队列服务，同一 job 的并发安全依赖 `SKIP LOCKED`、租约与领取令牌，而不是进程内锁。隔离性与边界见[实施记录](实施记录.md) 第 1、3 节。

## 网页、API 与 CLI

网页输入框旁的“长期记忆”可切换已生效、待审核、已删除和已拒绝列表。可创建、编辑、采纳／拒绝候选、删除，以及查看来源与版本记录。上下文面板显示本轮实际注入的记忆键、版本与用量。

| 方法 | 接口 | 用途 |
| --- | --- | --- |
| GET / POST | `/api/memories` | 分页列表或手动创建；列表支持 status、limit、before |
| GET | `/api/memories/<UUID>` | 记录与当前同键冲突内容 |
| PATCH | `/api/memories/<UUID>` | 修改 content／pinned，必须带 expected_revision |
| DELETE | `/api/memories/<UUID>` | 标为 deleted，必须带 expected_revision |
| POST | `/api/memories/<UUID>/accept` | 采纳；冲突时还需 replace_id 和 replace_revision |
| POST | `/api/memories/<UUID>/reject` | 拒绝候选，必须带 expected_revision |
| GET | `/api/memories/<UUID>/revisions` | 最近 100 个版本快照 |

列表每页最多 100 条，编辑正文最多 2000 字符；键为不超过 80 个小写英文字母、数字、点、短横线或下划线。未知 ID 和其他工作区记录返回 404，格式错误返回 400，版本冲突返回 409。沿用现有回环地址、Host 和 Origin 边界。

```sh
uv run --env-file .env python -m chagent.memory list
uv run --env-file .env python -m chagent.memory list --status candidate
uv run --env-file .env python -m chagent.memory create project.database "使用 PostgreSQL" --scope workspace
uv run --env-file .env python -m chagent.memory show <记忆UUID>
uv run --env-file .env python -m chagent.memory edit <记忆UUID> "使用 PostgreSQL 16" --expected-revision 1
uv run --env-file .env python -m chagent.memory accept <候选UUID> --expected-revision 1
uv run --env-file .env python -m chagent.memory revisions <记忆UUID>
```

CLI 的 `--workspace /absolute/path` 放在子命令之前，不配置模型 Key 也能管理记忆。

## 配置与迁移

- `0006_memories.sql`：memories、memory_revisions、memory_extractions。
- `0009_memory_jobs.sql`：`memory_jobs` 队列表，`run_id` 唯一，含 `attempts`、`max_attempts`、`available_at`、`lease_expires_at`。
- `0011_memory_job_claims.sql`：`claim_token` 与"运行中必须有租约和令牌"的约束。

启动入口自动应用迁移，见[数据库配置](数据库配置.md)。

```dotenv
CHAGENT_MEMORY_ENABLED=true
CHAGENT_MEMORY_EXTRACT=true
CHAGENT_MEMORY_TOKENS=2048
CHAGENT_MEMORY_ITEMS=8
CHAGENT_MEMORY_TIMEOUT=20
# 单个 job 的最大尝试次数（含租约过期回收），1–10
CHAGENT_MEMORY_ATTEMPTS=3
# 一个进程内的并发 worker 数，1–4，必须小于连接池上限
CHAGENT_MEMORY_WORKER_CONCURRENCY=1
```

`MEMORY_ENABLED=false` 停用检索与写入，保留数据库与管理界面；`MEMORY_EXTRACT=false` 只关闭自动提取，显式记住指令与手动管理仍可用。`MEMORY_TIMEOUT` 同时是单次提取的预算和 worker 租约的基准（租约取 `max(60s, 3 × timeout)`），调整时不能破坏"租约长于一次提取"的关系。配置重启后生效。

## 验证与范围

完整回归 208 项，包含跨会话与重启读取、工作区隔离、用户默认值覆盖、中文关键词、候选不注入、提取去重、精确来源、冲突版本检查、删除后不自动复活、预算不足跳过，以及异步提取后的这些性质：主运行不等待提取、提取事件出现在 `run_completed` 之后、租约过期计一次尝试、崩溃循环到上限即 `failed`、取消只归队、worker 失败只改 job 不改运行、租约回收后旧领取者的完成／失败／归队全部被拒且候选回滚。

浏览器使用离线模型完成创建、编辑、同键候选审核、版本查看和新会话注入验证。真实供应商上的提取语义质量只在真实链路脚本中抽查，没有长期评估。

不包含向量／语义检索、自动可信度判定、自动语义合并、过期清理与多用户权限；"后台"只是一次性的提取队列，没有周期性整理或跨进程调度。关键词可能漏召回，用户级资料可能包含本轮无关内容；条数与预算限制控制注入量。候选审核、作用范围和显式修订负责保证用户可纠正记忆。
