# 边界与门禁重构方案

2026-11-04。状态：**未实施**。

本文只描述改动方案。当前生效行为见[执行边界契约](执行边界设计.md)，当前路线图见[实施计划](实施计划.md)。方案交付后按第 9 节把结论迁回专题，本文转为历史。

## 1. 问题陈述

三个互相独立的问题，现在被 `CHAGENT_EXECUTION_PROFILE=trusted-development` 一个开关绑定：

| 事实 | 来源 | 后果 |
|---|---|---|
| 网页入口强制 `CHAGENT_APPROVAL=never` | `config/__init__.py:83`、`web/policy.py:6`、`web/policy.py:27` | 审批链、端点、前端卡片全部不可达 |
| `isolated` 与 `network=true` 在构造时互斥 | `tools/sandbox.py:56` | 网页无法安装依赖、无法访问任何网络 |
| 可信开发要求六项同时成立 | `config/__init__.py:83` | 无法表达「已在容器内」这种组合 |
| 审批系统约 970 行 | 见第 3 节盘点 | 代码不白写，但接在了必然不成立的分支上 |

实测：`Settings.from_env()` 解析结果为 `isolated / writable / network=false / approval=never / trusted=True`，与门禁完全一致；审批链在任何网页 run 中都不会被调用一次。

结论：问题不是「审批该不该有」，而是**边界、能力、门禁三件事被焊成了一个开关**。

## 2. 原则

| 轴 | 何时决定 | 由谁决定 | 取值 |
|---|---|---|---|
| 边界 | 部署时 | 运行环境 | 本机账号 / `workspace-write` / `isolated` / `container` |
| 能力 | 构造时 | `ToolRegistry` 是否注册 | 注册即存在，未注册即不可调用 |
| 门禁 | 运行时 | 显式装配的 gate 链 | 空链 / 人工确认 / 规则拦截 |

三条轴必须能独立取值。参考 pi 的分工：边界交给部署（容器、VM、专用账号），能力交给工具注册，审批是可选的扩展而非必经路径（`pi/packages/coding-agent/docs/security.md`）。

## 4. 目标架构

### 4.1 边界四档

| 档位 | 内层隔离 | 网络 | 工作区可写 | 适用场景 |
|---|---|---|---|---|
| `off` | 无 | 可开 | 是 | 仅在容器内使用 |
| `workspace-write` | 定向拒绝 | 可开 | 是 | 容器内的默认档 |
| `isolated` | seatbelt deny-default + 探针 | 强制关闭 | 是 | 本机直跑（当前生产档） |
| `container` | **不做内层隔离** | 可开 | 是 | 显式声明外层已隔离 |

`container` 档的构造条件：

- 必须显式设置 `CHAGENT_SANDBOX=container`，不接受从其他档自动推导
- 必须同时满足 `CHAGENT_CONTAINER_DECLARED=true`，缺失则拒绝启动
- 启动横幅必须打印 `boundary=container (declared; no in-process confinement)`

该档不做仓库外硬链接扫描、不建私有 scratch、不施加 seatbelt。它把安全责任完整交给部署方，因此**自证不可省略**（见第 7 节）。

### 4.2 ToolGate

新增 `tools/gate.py`（约 40 行）：

```python
class ToolGate(Protocol):
    name: str
    async def check(self, call: ToolCall, *, context: ToolContext,
                    signal: asyncio.Event, budget) -> GateDecision: ...

@dataclass(frozen=True, slots=True)
class GateDecision:
    allow: bool
    reason: str = ""      # 原样进入 tool result，模型据此改变策略
    code: str = "denied"  # denied / expired / unwatched / stale / unavailable
```

`scheduler._ask` 改为链式：

```python
for gate in self.gates:            # 默认 ()，等价于 pi 的 never
    decision = await gate.check(call, context=context, signal=signal, budget=budget)
    if not decision.allow:
        refused[index] = approval_result(decision.reason, None, decision.code)
        break
```

三条不变式，均沿用现有实现已有的事实：

1. gate 必须在取并发 slot、工作区 gate、数据库连接之前询问（`scheduler.py:275`）
2. gate 抛异常视为拒绝，并写 `tool_call_refused` 事件，不静默放行
3. `GateDecision.code` 必须区分拒绝性质，沿用现有四段文案

`ApprovalBroker` 只需增加一个 `check()` 适配器转发到现有 `request()`，内部逻辑不动。

### 4.3 能力面

不变。`create_builtin_registry` 的构造期剪裁仍是唯一能力控制方式，本次不改。

## 7. 安全论证

采用 pi 的思路意味着把「命令能否运行」的部分判断从应用内移到部署判断。pi 的文档明确写着工作区不是边界，并让用户自行上容器。Chagent 当前的 `isolated` 比 pi 默认更严，这是优势，不应对齐而丢弃。

因此本方案保留四档并存，按部署选择，而非把 `isolated` 降级。

`container` 档唯一的真实风险是：使用者以为自己在容器里，实际在本机。三种防线：

1. 必须显式声明，不从 `/.dockerenv` 之类自动推导（自动推导会掩盖误判）
2. 启动横幅逐次打印实际档位与「无内层隔离」字样
3. `/api/info` 与 `/api/config` 返回三轴取值，网页可查

禁止的组合：`container` + `approval=never` + 未声明容器。第三条在构造时直接抛错。
