# 统一可编程执行契约

更新：2026-11-05。本文主体记录**旧容器主控部署**的执行契约。当前自主建站入口使用宿主主控：文件与普通命令/测试在选定工作区，命令由独立容器执行；`site` 管理跨 run 网站；`host_exec` 仅在网页审批后执行一次宿主原生命令，带 `yield_time_ms` 时为交互启动，由 `host_process` 读写并逐次审批。旧 `/workspaces` 会话只读隔离，不自动重绑。新架构状态、证据与缺口见[宿主执行方案](宿主执行方案.md)。以下旧 `process` 和门禁细节不能直接外推到宿主主控。

2026-11-06 宿主主控增量：每次容器命令使用 run 私有的 `HOME/TMPDIR=/tmp/chagent-run-<run_id>`，正常收尾时异步清理；主控启动后周期扫描，仅清理数据库已终结且本进程未持有的遗留目录。网站状态和日志保存在 `/cache/site`，状态核对 PID 与进程启动时间；`site(status)` 不隐式启动已停止的容器。验收范围见[容器生命周期方案](容器生命周期与产物交付方案.md#2026-11-06-实施进度)。

同日 P0-b 增量：宿主主控的已登记容器默认闲置 1800 秒后可回收，`CHAGENT_CONTAINER_IDLE_SECONDS=0` 禁用回收。命令 run 与站点操作持有本进程租约，删除前还复核数据库活动 run/站点、宿主目录身份、容器 label/挂载及实际进程。孤儿候选先由 `/api/containers` 只读展示，首轮后台扫描不删除，下一周期再严格核验。自动回收不删 `/cache` 卷。`collect_file` 与显式重建仍未交付。

## 三个轴

执行行为由三个互相独立的轴描述，全部由开关推导，不能直接设置：

| 轴 | 取值 | 回答 | 来源 |
|---|---|---|---|
| `boundary` | `container` / `none` | 进程跑在哪 | `CHAGENT_EXECUTION_PROFILE`（声明值必须与之一致） |
| `capability` | `full` / `read-only` | 有没有命令执行能力 | `CHAGENT_CODE_MODE` 与 `CHAGENT_ALLOW_HOST_COMMANDS` |
| `gate` | `none` / `approval` | 高危动作要不要人批 | `CHAGENT_APPROVAL` |

推导与校验只有一处：`src/chagent/execution.py` 的 `resolve()`。配置、网页门禁、CLI 与工具装配都读 `Settings.axes`，不再各自列举条件。

合法组合四个：

| 组合 | boundary | capability | gate | 用途 |
|---|---|---|---|---|
| A | `container` | `full` | `none` | 可写容器，运行时不逐次审批 |
| B | `container` | `read-only` | `none` | 只读会话 |
| C | `none` | `read-only` | `none` | 没装 Docker 的降级：读写文件、查资料，不能执行命令 |
| D | `container` | `full` | `approval` | 可写容器，命令与覆盖写入经审批 broker |

网页接受 A 和 D。除此之外的组合在启动时被拒绝，例如本机 `configured` 档加 `CHAGENT_ALLOW_HOST_COMMANDS=true` 会报「Host commands require the container boundary」。

**宿主通道有两套，不要混为一谈。** 三轴仍只描述 Chagent 主进程的容器执行位置；`boundary=none` + `capability=full` 仍被拒绝。

| 通道 | 开启条件 | 行为 |
|---|---|---|
| 方案 A 宿主终端代理（历史原型，默认关闭） | `CHAGENT_HOST_EXEC=approval` + 端点与随机 token + 宿主健康探针报告交互终端可用 | 由**宿主终端**逐次输入当次申请 ID 确认一次性命令；要求同一 run 更早轮次有成功的容器命令或测试；不改变三轴，不支持持续宿主服务，未通过真实模型端到端验收 |
| 宿主主控档的原生工具 `host_exec`（当前入口） | 启动档为 `host-controller` | 在**同一网页**逐次审批的宿主命令；同样要求更早轮次有成功的容器命令或测试；审计写入 `native_executions`。带 `yield_time_ms` 时交互启动并返回 `process_id`，由 `host_process` list/read/write/stop 管理：读与停不询问，**每次 stdin 写入（含 EOF）各需一张只覆盖该次输入的新审批卡**，写入逐条落 `native_stdin_writes`。主控重启把在跑执行标 `unknown`，不接管、不重试；进程 ID 不跨 run、不跨重启 |

宿主原生进程是**管道语义**，不是终端：没有 PTY、窗口尺寸与信号键，需要终端的交互按方案第 7 节交还用户。

2026-11-05 已交付：交互式宿主 stdin（`host_process` + 迁移 `0022`）与逐次写入审批，证据见[验收第 16 节](验收记录汇总.md#16-宿主原生交互-stdin-与重启未知演练2026-11-05)。目标与门槛见[自主建站整体方案](宿主执行方案.md)，顺序见[实施计划](实施计划.md)。

B 与 C 没有网页入口。C 就是本机默认档：`configured` + 无宿主命令，能读写工作区文件、查资料，不能执行命令；本机 CLI 的真实模型运行也走这一档，装配时不用统一工具面，保留 work/code 两个都不含命令工具的旧面，因此不会因为缺少命令能力而启动失败。

## 启动条件

网页要求组合 A 或 D，并且实际位于容器内：`CHAGENT_EXECUTION_PROFILE=containerized`、`CHAGENT_BOUNDARY=container`、`CHAGENT_CONTAINER_DECLARED=true`、`CHAGENT_SANDBOX=off`、`CHAGENT_SANDBOX_NETWORK=true`、可写工作区、命令开启；`CHAGENT_APPROVAL` 可为 `never`、`on-request` 或 `untrusted`，启动同时检查容器标记。工作区必须位于 `CHAGENT_WORKSPACE_ROOT` 内。Compose 覆盖 `.env` 的执行档设置；模型密钥仍由 `.env` 提供。容器内命令可联网，子进程环境不继承模型密钥和数据库连接串。显式声明和标记检查用于防止普通宿主误启，不证明容器提供强隔离。

`configured` 在本机保留配置诊断，但不能执行命令，也不能启动生产网页。旧 `trusted-development`、`isolated`、`workspace-write` 配置与 `CHAGENT_DEFAULT_MODE` 会被拒绝。`--demo` 是单独的无真实模型诊断入口。当前网页允许对 `yield_time_ms` 启动的本 run 长进程写入最多 8192 字符或关闭 stdin（容器主控档用 `process`，宿主主控档用 `host_process`，后者每次写入另需一张同页审批）；不支持 PTY，一次性命令不接收输入。

容器主控档的工作区来自启动时的单个宿主 bind mount：不同宿主目录若都映射成 `/workspaces`，`workspaces.root_path` 会错误复用工作区和会话身份，因此该档的 `POST /api/workspaces/switch-host` 返回 503，只能在同一个挂载根内打开子目录。宿主主控档不需要重挂载：同一接口按规范化宿主路径建立独立工作区身份，并按需为该目录建立独立执行容器，网页可切换到任意已存在宿主目录。两个档位都不能把旧会话静默用于新的宿主根。

## 接口字段

`/api/info` 与 `/api/config` 都返回 `boundary`、`capability`、`gate` 三个值，与启动横幅 `Execution:` 行同源。`programmable` 表示生产统一工具面是否启用（组合 A 或 D），`boundary` 只报告位置，不再兼任能力标志。`code_mode=false` 是保留给旧前端的「不可选择 code 标签」；`default_mode`、`execution_profile` 与 `sandbox` 已从响应中移除，`CHAGENT_DEFAULT_MODE` 在启动时明确报错而不是被忽略。`/api/config` 仍返回 `sandbox_network` 与 `host_commands` 这两个原始开关，它们只是三轴的输入，不能当成独立能力：能力一律看 `capability`。

`/api/config.host_execution` 单独报告实验性 `host_exec` 是否实际注册；`host_workspace_path` 报告 Compose 配置的宿主挂载路径，供界面识别，不是新的权限轴。不要把 `host_commands=true` 误读成宿主原生命令已获授权：旧字段指容器内命令开关。

## 实际能力核对

启动时同时检查配置、Runner 的显式 `unified` 标记、两种旧会话值是否映射到同一 executor、文件与执行工具是否齐备、命令工具是否共用实际执行配置、实际审批策略与 broker，以及 `process` 是否具备 list/read/write/stop。运行时的 `SandboxSettings.allows_execution` 是同一判定的运行侧一半，工具装配与网页门禁都用它，不另写条件串。

容器命令使用容器可见的文件系统和网络。网页搜索工具和模型请求独立于命令执行。`ToolGate` 在取得执行并发位之前处理可选门禁，异常按拒绝记录。审批配置的 `process(write)` 每次都询问，命令 allowlist 不放行 stdin；问题显示进程 ID、原文、UTF-8 字节数和 EOF 标志。批准绑定 run、工具调用记录、参数指纹和 cwd，只能消费一次；进程归属仍由 `ProcessTool` 核对。拒绝、超时与取消不写入；已退出进程不会收到输入。文件修改与命令副作用在取消时不自动回滚。**审批结果随工具结果回到模型**：被批准的调用在结果首行写明「用户已在页面批准」及审批号，附用户备注（模型侧最长 500 字符，`details.approval` 记全文），拒绝文案附用户填写的理由。模型看不到页面，工具结果是它唯一能知道这次决定的地方（[验收第 18 节](验收记录汇总.md#18-模型侧审批反馈2026-11-05)）。容器路径的实际验收见[容器执行阶段验收](验收记录汇总.md#6-容器执行2026-11-04)。

## 审批覆盖的动作

`gate=approval` 管两类动作，两者都是「先问人、再占执行资源」：

| 类别 | 工具 | 何时问 |
|---|---|---|
| 执行 | `exec_command`、`run_tests`、`process(write)` | 按 `never` / `on-request` / `untrusted` 判定；`process(write)` 永远问 |
| 写入 | `write_file`、`edit_file`、`apply_patch` | 按**不可逆性**分级，见下 |

写入分级（`tools/gate.py` 的 `grade_write`，纯判定加一次存在性探测）：

- 新建普通文件 → **不问**，可逆且代价为零；
- 覆盖已有文件 → **问**，问题里带路径和当前大小，例如 `overwrite src/app.py (existing 12.4 KB file)`；
- `apply_patch` → **问**，问题里列出涉及的文件数与文件名；
- 新建 `.git/`、`.github/`、`.husky/`、`.vscode/`、`.env*`、`.npmrc`、`.bashrc` 等钩子与配置路径的文件 → **问**，因为它们之后会在没人重读的情况下被执行；
- 路径逃出工作区或经过符号链接 → **问**（执行层仍会拒绝这种调用，这里只是不静默）。

`create_directory` 不问：空目录可逆。`create_file` 走自己的工作区落盘确认，不重复问。

**适用范围（2026-11-05 修复）**：该分级现在两个档都生效。宿主主控档过去只装 `HumanGate`（其 subject 只描述宿主原生命令），`WriteGate` 未接线，覆盖写入不经审批；现已改为 `(HumanGate, WriteGate)`，真实模型复验覆盖出卡并核销、拒绝不改盘、新建不出卡，证据见[验收第 17 节](验收记录汇总.md#17-宿主主控档写入审批2026-11-05)。

之所以把写入并入审批：工作区是宿主目录的 bind 挂载，容器只是进程的位置。一次覆盖写入不经过任何命令，却直接改用户机器上的真实文件；只审命令等于放行了更短的那条路径。
