# 会话与上下文

会话保存原始记录，上下文只决定"这一次请求看什么"。裁剪、压缩、产物替换都不修改已保存的消息。

2026-11-05 边界补注：下面的“保存规范化工作区路径”指当前进程可见路径。容器部署将宿主目录挂到 `/workspaces`，不同宿主根重挂载后不能凭该路径恢复旧会话的真实归属；跨宿主切换已关闭。稳定宿主路径与工作区 UUID 的迁移方案见[自主建站整体方案](宿主执行方案.md)。

## 现状

| 模块 | 职责 |
|---|---|
| `sessions/manager.py:SessionManager` | 创建、分页、重命名、归档与恢复 |
| `storage/repositories.py:ConversationRepository` | 会话、消息、任务状态、历史分页 |
| `domain/sessions.py:TaskState` | 显式目标、约束、决定、待办、来源与 revision |
| `context/builder.py:BasicContextBuilder` | 预算选择、完整轮次裁剪、工具配对检查、元数据隔离 |
| `context/projection.py:ProjectionCache` | 按持久消息 ID 缓存"模型可见投影 + 单条成本" |
| `context/manager.py:ContextManager` | 摘要触发、切点选择、保存与失败回退 |
| `context/compactor.py:ContextCompactor` | 历史序列化、分批摘要、响应校验与调用审计 |
| `context/environment.py` | 保留的历史环境采集辅助模块；Runner 当前不自动调用或注入 |
| `context/tokens.py` | 两种计数器：BPE（可选依赖）与字节回退，都按线上格式计数 |
| `domain/context.py:ContextSnapshot` | 选中来源、每条消息的选择理由、预算与估算方式 |

```text
CLI / 本地网页
  → SessionManager → ConversationRepository → sessions / task_states / messages

AgentRunner 每轮模型请求前
  → ContextManager.prepare
      → 读取可重放历史、任务状态、最新有效摘要（run 内复用 RunState）
      → BasicContextBuilder.build：投影 + 累计成本选择完整轮次
      → 超过触发阈值：ContextCompactor 生成新检查点
      → 返回 ModelRequest + ContextSnapshot
  → 保存请求与快照（model_calls）
```

`ContextBuilder` 只处理传入数据，不查数据库、不改历史、不写任务状态。

## 会话管理规则

- 创建会话时验证工作区确实为目录并保存规范化路径；继续会话一律使用已保存的工作区。
- 列表按创建时间与 ID 倒序，用 `next_cursor` 稳定分页；重命名不改变排序。
- 默认不列出归档会话；归档保留消息与运行记录，但不能启动新运行，恢复后可继续。
- 活动运行期间可以重命名，但不能归档或修改任务状态；三者共享会话行锁。
- 不提供清空或永久删除。

历史分页从最新消息向前读取，页内按时间顺序排列，下一页用 `next_before`。分页是检查原始记录的接口，不把任意一页当作模型上下文。

## 显式任务状态

```text
TaskState
  goal / constraints / decisions / pending    目标、约束、决定、待办
  source_message_ids                          本会话原始消息引用
  revision                                    乐观更新版本号
```

状态由用户或调用方显式维护，不根据模型回答自动更新；来源必须属于同一会话。更新需要提供 `expected_revision`，冲突返回 `StateConflictError`，调用方重新读取后决定，不盲目覆盖。

Runner 在运行开始时读取状态，运行期间禁止修改，因此一次运行使用固定版本。快照记录该版本号，历史请求保存当时的状态文本。

普通历史中未登记为任务状态的要求仍是普通历史，会受裁剪影响——当前没有自动识别早期约束的能力。

## 预算、投影与裁剪

```text
input_budget = model.context_window - output_reserved - safety_reserved
```

`ContextPolicy` 的输出预留默认是 `min(model.max_tokens, 8192)`，安全余量 256，历史消息软上限 200，单条工具结果 2000。`model.max_tokens`（`CHAGENT_MAX_TOKENS`）从此只当**上限**用：它仍然是模型允许的最大输出，但不再决定窗口预留多少。

chat-completions 强制 `input + output <= window`，所以预留量必须等于请求里的 `max_tokens`——不存在"要 16k、按 4k 规划"。8192 的取值来自 319 次真实调用的分布（p50 98、p90 579、p99 3054、最大 5140，且在 16384 预留下 `output_limit` 失败次数为 **0**）：对观测到的最长回答仍有 1.6 倍余量，却把窗口的 25% 预留降到 12.5%。猜低的代价是一轮显式失败（`output_limit`），不是截断产物。

选择顺序：

1. 保留系统指令、工具声明与显式任务状态。
2. 保留当前运行：原始用户输入与最新完整交换不被压缩。
3. 从新到旧加入完整用户轮次，直到达到预算或历史条数上限。
4. 一旦某个轮次放不下就停止，保持连续的近期历史。

一轮由用户消息开始，包含它引发的模型请求、工具调用与结果。不会只留下孤立工具结果，也不靠删单条消息凑预算。工具配对完整性优先于 200 条软上限。

### 投影缓存与累计成本

每条消息的"模型可见投影"是纯函数：去掉 `details`／`usage`／`duration_ms`，把 artifact 正文换成摘要摘录，把超上限的工具结果截中间。重复计算它曾是 200 条消息 48ms 的来源。

- `ProjectionCache` 以 `消息 ID + 计数器名 + PROJECTION_VERSION` 为键，缓存在一次 run 内复用，run 结束丢弃；超过上限整体清空，不做复杂淘汰。
- `TokenCounter.additive = True` 是显式承诺：`count(messages)` 等于各条 `count([message])` 之和。声明了才按累计成本选择，未声明的一律走精确重算，行为不变。
- 最终请求的**权威值**：有供应商锚点时是 `observed_prompt_tokens + 尾部估算`，否则是完整 `count(messages)`。累计值只用于选择。
- 缓存正确性依赖"消息行创建后不再变化"；若将来支持编辑历史消息，必须把内容版本并入缓存键。

效果：200 条消息 48.4ms → 7.1ms（序列化 10,602 → 402 条），400 条 188.2ms → 10.5ms。实现细节与边界见[实施记录](实施记录.md) 第 1 节。

### 工具声明：延迟加载

固定前缀里最大的一块不是指令，而是工具声明。实测一次全量 face 是 **3352 token / 16 个工具**，占固定前缀的 8 成以上；这些字节每个请求都要重发。

`CHAGENT_DEFERRED_TOOLS=true`（默认）把"晚用或不用"的那一组（`web_search`、`web_fetch`、`run_tests`、`process`、`create_file`、`host_exec`）从声明里拿走：

```
system 段 tools        ← 仍是 JSON Schema，但只含核心面
system 段 tool_index   ← 一行一个名字： "- run_tests: Run the project's test suite once and …"
model 调 tool_search   ← 返回完整 schema（文本），并记进本次 run
下一轮请求             ← 该工具出现在 tools_added 里，模型可以直接调用
```

实测 **3352 → 2273 token**（省 32%），代价是某个工具第一次真正被需要时多一轮。

四条设计约束：

- **索引与"已加载"无关**。`tool_index` 在一次 run 内字节不变；加载只增加声明，不移动索引。否则一次加载会破两次前缀。
- **名字在索引里，参数在 `tool_search` 的结果里**。chat-completions 不能在会话中途加工具，所以"加载"必须同时做两件事：把那轮的文字给模型看，并在下一轮真的声明它。
- **不足 3 个可延迟工具就不延迟**。`tool_search` 自己的声明约 180 token，索引一行约 20；低于这个数量它是纯亏，于是整张 face 原样声明。
- **核心面不动**：读写、编辑、补丁、目录、glob、grep、命令执行、artifact 分页。这些是每个会话前三轮就要用的，多一轮加载比它的声明更贵。

`CHAGENT_DEFERRED_TOOLS=false` 回到全量声明，`tool_search` 不注册。

### 单条工具结果上限

选择只能整轮丢弃，因为留下工具调用却删掉它的结果不是供应商接受的上下文。于是单条结果成了“一整轮是否存活”的决定因素，这一段把它单独封顶。

- `ContextPolicy.max_tool_result_tokens` 默认 2000 token。超限时 `context/truncate.py:truncate_middle()` 保头保尾、切点对齐到行边界，中间写入标记：省略了多少字符、原文未改、如何按更窄的范围重新取。
- 计量口径是 token 而不是字节：同样 8000 字节的结果，英文约 2000 token、中文约 2666 token，按字节封顶会让中文结果更早挤掉整轮。
- 存储层独立在 8000 字节处把结果换成 artifact 引用（带摘录 + `read_artifact` 分页），投影层不会重复截断一个已有的引用。
- 这是**投影**上的截断，`messages` 与 `tool_calls.result` 原文不变；`ContextSnapshot.truncated_tool_results` 记录本轮被模型看到时共省略了多少字符。

### token 估算

一个计数器，加一个来自供应商的锚点。没有 tokenizer：真实编码器要额外依赖（容器镜像不装 extras）、无网络时可能加载不了词表，而且各供应商词表本就不同。

| 数字 | 来源 | 用途 |
|---|---|---|
| `wire_tokens_ascii4_wide1` | `context/tokens.py:estimate_tokens` | 首次请求、尾部增量、轮次之间的相对比较 |
| `observed_prompt_tokens` | 供应商 `usage.total_tokens` | 上一次请求的真实大小（`ObservedUsage`） |

- 启发式按**线上格式**计数：`wire_text()` 复用 `models/transcript.py` 的 `openai_message()`／`openai_tools()`，所以 thinking、`timestamp` 这类不会发给供应商的内容不计费，工具声明的 `{"type":"function"}` 包装会计入。ASCII 每 4 字节 1 token、非 ASCII 每字符 1 token、每条消息 10 token 固定开销。
- 系数是标定值，不是猜的（2026-11-06，6 个样本）：英文散文 4.48 B/token、Python 代码 4.70、密集 JSON 3.02；中文散文 cl100k 1.22 token/字、o200k 0.75、中文代码注释 1.44。把字节数当 token 数会高估 3.35×，那是被替换掉的口径。
- **锚定**：`RunState.observed` 记录上一次响应携带的 `usage.total_tokens` 与其所在消息的 `sequence`；下一轮只估算 `sequence` 之后新增的消息。误差因此不跨轮累积，这正是整段重估做不到的。
- 锚点在结构性变化时作废，而不是做修正：工具声明变化（`state.tool_revision`）、新摘要装入、响应没有 `usage`、或该摘要已覆盖锚点位置。作废后回落到整段估算。
- 记忆引用块从锚点中扣除。它每轮由 `MemoryService.enrich` 重新加入并重新计费，留在锚点里会每轮重复计算同一段。
- `estimate_source` 有三种取值：`observed`（供应商真值 + 尾部估算）、`scaled`（锚点覆盖的消息后来被裁掉了，退回“估算 × 实测比例”）、`coarse`（本轮没有锚点）。`tail_token_estimate` 记录尾部那一截；`coarse_token_estimate` 记录同一请求的纯估算值，两者之差就是比例。
- **比例校正也作用于选择**：`observed.input_tokens / coarse_prompt_tokens` 是本内容上启发式的实测偏差，`_select()` 用它把候选成本换算成供应商单位再比预算。否则选择按低估的估算放行、最终检查按真实值判定，一次“刚好塞满”的选择会被本该救它的锚点直接拒绝。比例只用于**收紧**，夹在 `[1.0, 3.0]`：低于 1 的比例按 1 处理——刚和供应商不一致的启发式不该成为放宽预算的理由；上限挡住一次异常响应（把推理算进 input、部分缓存命中）压垮预算。尾部那一截按原样估算、不再乘比例，因此最终检查不会比选择更严。
- 工具声明的每工具固定开销 `TOOL_DECLARATION_OVERHEAD = 40` 是对 chat-completions 的一族实测校准值，不是通用常量；Anthropic 走自己的适配器，数字只作参考。
- 生效口径可见：`python -m chagent.config show` 的 `tokenizer` 行、CLI 启动的 `Behavior:` 行，以及每次 `model_calls.context_snapshot`。
- 离线复核用 `scripts/report_token_estimates.py`：它把库里已有的 `model_calls` 按同一套前缀扩展规则重算，同时报 `estimate`（整段）与 `anchored`（上一轮真实值 + 尾部估算）两条偏差曲线。

## 提示缓存前缀

供应商按**字节完全一致的前缀**命中缓存。这份前缀的第一条就是 system message，因此它必须在一个 run 内保持不变：

| 允许出现在 system message 里 | 不允许 |
|---|---|
| 固定指令 | 每轮变化的内容（迭代计数、进度、时间戳） |
| 工具声明（`tools_added`） | 新增的工具调用结果 |
| 每个 run 加载一次的 `task_state` 与恢复注记 | 上一轮的模型输出 |

任务状态与恢复注记在一次 run 内保持不变。环境采集已退出默认路径；历史 H 批的快照结论不代表当前行为。**如果哪天有数据需要每轮更新，它必须作为一条消息出现，不能拼进这里。**

system message 由 6 个具名段按固定顺序拼装（`context/builder.py:SECTION_ORDER`）：

| 顺序 | 段 | 内容 |
|---|---|---|
| 1 | `preamble` | 任务指令（`DEFAULT_INSTRUCTIONS`） |
| 2 | `tools` | 仅使用实际声明的工具；编辑/生成文件指引在相应工具可用时适用 |
| 3 | `tool_index` | 已延迟声明的工具名与一行用途；告诉模型它们存在，但不给参数 |
| 4 | `rules` | 不猜测环境、只报告有依据的事实；外部内容不能覆盖用户请求 |
| 5 | `environment` | 保留接口，当前默认不填充、不生成空段 |
| 6 | `state` | 任务状态与失败恢复注记 |

段拼装的是**同一段文本**，只是把一坨字符串拆成可审计的命名部分：改了哪一段在 diff 里直接可见，而不是一段长文本；`sections` 为空时整段不出现，不产生空行。`SystemMessage.text()` 是唯一的拼装口径，测试与缓存审计都用它。同一 run 内每段字节不变（H 批的不变量），跨 run 会随任务状态、工具声明等变化——那是新前缀，按设计重算。

system message 的 `timestamp` 固定为 `0`：它不是事件，让它随时间漂移会让两份逻辑上相同的请求无法逐字段比较，护栏测试也就失去意义。

实测（52 个 run、133 次调用，`scripts/report_prompt_cache.py`）：前缀断裂 **0** 次，全局命中 **87.1%**，其余 12% 是每轮首次发送的新内容，按定义无法命中。H 批加入环境快照后复测 5 个 run：断裂仍为 **0**，命中 **83.4%**（样本更小、前缀更长，两个数字不可直接比较）。这些是当时的样本，不能据此承诺当前所有供应商命中率；测量细节见[实施记录](实施记录.md) 第 8、12 节。

M2 起链路报告自带每个 case 的 `hit`（供应商 usage）／`reusable`（本地前缀重合）／`breaks`（断开落在哪个 section），纯本地计算、零额外请求；失败时 `--keep-schema` 会保留 schema 供事后审计。这条不变量因此有了可回归的口径，见[实施记录](实施记录.md) 第 16 节。

护栏（`tests/test_context.py`）：

- 同一份历史与同一份 per-run 状态构建两次，整份请求逐字段相等；
- 第 N 轮的请求必须是第 N+1 轮请求的字节级前缀。

**不要**把 per-run 数据挪到请求尾部的消息里。它看起来能省掉"改一次状态破一次缓存"，但一个 run 内这些数据本就是常量，挪动带不来命中；而尾部多出的 user 消息会被模型读成"用户刚说了话"，在本该停止时继续动作（离线夹具上立刻复现；真实链路没有做这项对比实验，因此按更保守的一侧取舍）。

## 环境信息的当前策略

Runner 不再调用 `build_environment`，系统提示不自动附加真实 cwd、目录树、Git 分支/状态或 AGENTS.md，也不产生 `environment_projected` 事件。`RunState.environment` 和构建器的可选环境段仍保留供显式调用，但不能据此说默认路径会采集。

模型需要文件事实时通过实际可用工具读取，不能靠提示词获得未注册能力。旧消息、记忆、摘要和工具结果仍可能含有路径；移除自动注入不等于旧资料已清除，也不构成请求出口保护。后续目标见[源码保护方案](历史决策档案.md#7-仍未交付源码保护)。

H 批的缓存/轮次测量是当时启用环境快照的样本，保留在[实施记录](实施记录.md)第 12 节；当前不可直接沿用“list_dir 归零”等结论。

## 自动摘要

```text
触发 = 完整投影达到输入预算的 80%，或有未摘要历史被预算／条数限制排除
近期目标 = 输入预算的 50%
摘要空间 = min(2048, 输入预算的 25%)
```

只按已完成的完整用户轮次选择连续前缀，不在工具调用与结果之间切割；系统消息独立保留；当前运行、当前用户轮次不进入压缩来源。切点用边界二分查找，避免逐个旧轮次重建上下文。

### 投机压缩（异步预压缩）

摘要原本是一段同步停顿，卡在"工具结果返回"与"下一次模型请求"之间：最多 8 次调用、60 秒超时、每次运行最多 4 次。投机把它挪到模型正在跑工具的时间里去。

```text
projected ≥ 输入预算 × 0.6（speculative_trigger）  → 后台起一个候选摘要
下一轮 projected < 0.75（trigger）                 → 什么都不做；候选继续保持待用
下一轮 projected ≥ 0.75                            → 采纳候选（必要时等它）；不再重算
```

**规则：投机只改变"何时付费"，不改变"是否采纳"。** 采纳条件与同步路径完全一致（`_should_compact`）。早期实现让候选一就绪就采纳，结果是每轮都在阈值上方反复压缩，把每次运行的 4 次预算烧光——这条不做就会有。

三个不变量：

| 不变量 | 做法 |
|---|---|
| 后台不写数据库 | 摘要调用记在 `MemoryCalls`（内存）里；采纳时由前台一次性 `record_calls` 写入，再 `save` 检查点 |
| 只产候选、不产检查点 | 候选的 `revision` 是占位 0，真正的 revision 在采纳时从数据库取；`id` 也在那时才定 |
| 运行结束即取消 | `release()` 取消在飞任务并限时等待（`speculative_shutdown_timeout`），它没有任何数据库状态可回滚 |

失效条件只与"提示词的形状"有关，与历史增长无关——历史只追加，候选覆盖的是一个前缀，覆盖少一点是常态：

- 模型或供应商变了
- 工具声明变了（`state.tool_revision`）
- 候选所基于的上一份摘要变了（id 或 revision）

采纳时还要**重新校验**：候选是对着当时的历史验证的，而后续轮次已经追加，所以最终请求要重新构建并过一遍 `_checked` 与 `_verify_reduction`。不通过就丢弃，退回同步压缩。

被丢弃的候选会写一条 `compaction_discarded` 事件，带上 `speculative_calls` 与 `speculative_tokens`——那是已经花掉的钱。运行终态之后才被丢弃的候选不再有机会写事件（`run_events` 的门禁随运行关闭），这类浪费只体现在供应商账单上，不在库里。

代价与边界：

- 被丢弃的候选照样产生费用；`max_compactions_per_run` 对投机同样计数，被丢弃的那次也算。
- 等到预算真的不够时，等待被限制在摘要自己的超时（`CHAGENT_COMPACTION_TIMEOUT`）内；换来的是一次同步压缩的兜底，而不是让挂死的请求吃掉整个 run 预算。
- 投机期间内存里多一份历史列表（消息对象共享，只有列表被复制）。

### 运行结束后压缩（post-turn）

投机压缩挪走的是"工具执行期间"的等待；还有一段在用户侧——下一次运行的第一条请求要等摘要跑完才发得出去。post-turn 把这段也挪走：答案已经提交、run 已经终结，此时再压一次，代价不在任何人的等待路径上。

两个约束决定了它不是"在 `finish` 后面加一行"：

- **写入闸门**。`SummaryRepository.save` 走 `check_owner`，要求 run 仍在运行且租约有效。终结后的压缩用 `post_run_token` 通过 `check_finished_owner`：条件是 `runs.status='completed' AND owner_token=<本进程持有的 token>`，并锁住 run 行。只有刚终结这次运行的进程能写；别的进程知道 run id 也写不进去。
- **审计不断档**。`compaction_calls` 同样由 post-turn token 写入，所以"答案交付后才花掉的钱"仍然出现在库里，而不是只出现在供应商账单上。失败也写，状态为 `failed`。

其余规则：

- 只在 `end_reason=model_stop` 且有最终答复时调度；工具请求停止、显式记忆都不算。
- 触发线 `post_turn_trigger`（默认 0.6，不得高于 `trigger`）：低于它说明下一次请求还有余量，压了只是提前花掉本来不必花的钱。
- 一个会话同时只跑一个 pass；第二个 run 结束得更早时跳过，新的范围由下一次 pass 覆盖。
- 校验与同步路径同源：以"下一次请求"（`current_run_id=None`）为基线重建，检查确实变小、剩余消息放得下；不通过就丢弃。
- 最新一轮答复连同它的问题留在摘要之外——检查点不该把刚刚交付的那一轮吞掉。
- 事件 `compaction_completed` 带 `post_turn: true`，写入时间在 `run_completed` 之后；实时流可能已经结束，重开会话仍能看到。
- 进程退出前 `drain_post_turn` 给它在连接池关闭前落库的机会（Web 关闭、CLI 单次运行都会等）；等不到就丢，下一次运行按需再压。

默认关闭（`CHAGENT_COMPACTION_POST_TURN=false`）：它花的是用户没有要求的调用，付不付这笔钱是部署决策，不是库的默认值。本仓库的 `.env` 显式打开。

### 两种压缩实现

摘要不是唯一办法。有时这段历史本身没什么值得保留的语义（大量工具输出、失败的尝试、探索性试错），花 8 次调用换 2k token 摘要不如直接丢掉并说清楚丢了什么。实现上两者共用同一套生命周期——校验、保存、事件、状态更新完全一致，事件里用 `implementation` 区分：

| `implementation` | 做什么 | 模型调用 |
|---|---|---|
| `summary` | 模型把这段历史压成摘要（保留式证据） | 1–8 次 |
| `fresh_window` | 丢掉这段历史，宿主写一份"它是什么"的重述 | 0 次 |

`CHAGENT_COMPACTION_FRESH_WINDOW` 取三个值：

- `fallback`（默认）：只用摘要；摘要失败时退到 fresh window。这是把一个死路变成活路——此前"预算已经不够 + 摘要失败"等于 `context_rejected` 让 run 失败。
- `always`：完全不做摘要，每次压缩都是 fresh window。
- `off`：只有摘要，失败就按原样回退（`test_compaction.py` 用这个值钉住摘要实现的失败语义）。

fresh window 的正文由三部分组成，按价值排序：**丢弃声明**（"这段历史没有被摘要，也没有工具能读回它，不要假设它说了什么"）、**被丢弃轮次里的用户请求**（原件截断到 300 字符，最多 3 条——丢掉用户自己的措辞是 fresh window 最贵的部分）、**最新工具结果原文**（复用摘要那条保留式证据的机制，因为它正是让模型重新读文件的东西）。正文受摘要预算约束，放不下就报错而不是悄悄变长。

两条诚实性要求：

- `session_summaries` 的 `model`／`provider` 写 `host`，`prompt_version` 写 `fresh-window-v1`，`usage` 为 NULL——没有模型写过这份检查点，字段不能暗示有。
- 正文里不出现 `Goal:`／`Progress:`／`Decisions:` 这类摘要小节标题。重述不能长得像摘要，否则模型会把"丢了"读成"总结过了"。

`fresh_window=always` 时不会启动投机压缩：这里没有模型调用需要藏到后台，后台任务只会白白占一个 `max_compactions_per_run` 名额。

### 压缩范围

- **已完成历史**：跨运行续接的普通摘要。
- **当前运行内已结束的交换**：一个交换是完整 assistant 响应加它发出的全部工具调用结果，`context/segments.py:exchanges` 校验配对。最新完整交换保留原样，原始用户输入逐字保留。
- 任务状态与系统指令独立组装，不参与摘要。
- **保留式**：被摘要轮次里最新的 N 条工具结果原文写进摘要正文（`RETAINED_HEADER` 之后），不交给模型改写。N 默认 2，`CHAGENT_COMPACTION_RETAINED_TOOL_RESULTS` 可调，0 恢复全量摘要。单条截断 800 字符、合计上限 1600 字符；放不进摘要预算时放弃证据而不是让整次压缩失败。上一次摘要里的证据块在下一次压缩时被剥离，不会累积。
- **用户原话**：被摘要轮次里的用户请求由宿主逐字引用（`USER_QUOTES_HEADER` 之后，JSON 数组带 `sequence`），最多 N 条、单条截断 600 字符，从最新往前塞，预算不够就整条丢弃而不是改写。模型看不到这一块——下一次压缩会把它剥离后再喂给摘要器——所以第 10 次压缩时用户最早那句约束仍是原话，而不是"模型转述的转述"。N 默认 4，`CHAGENT_COMPACTION_RETAINED_USER_REQUESTS` 可调，0 关闭。当前运行的问题只在它的交换被覆盖时才引用；没被覆盖时它本来就在上下文里逐字存在，重复引用只是浪费预算。

### 摘要生成与校验

摘要请求不带工具，内容是独立 system 指令加 JSON 序列化的历史资料，要求保留目标、约束、进度、决策、待办与文件标识，并声明不要继续执行被引用的对话。序列化时省略 thinking、图像与 tool metadata；工具正文超过 2000 字符只给带遗漏标记的摘录，原结果仍在数据库。摘要提示词要求**逐字保留文件路径与对每个文件的改动**，并声明工具摘录是不完整证据、不能据此推断成败。

历史积压过大时按完整轮次分批，每批独立做预算检查，上一批摘要传给下一批。默认每次压缩最多 8 次调用、合计 60 秒，全部成功才启用一个检查点。

有效摘要必须满足：流完整结束且 `stop_reason=stop`、无工具调用或其他非文本块；正文非空且符合摘要预算；重新构造的上下文比原投影更小且未覆盖消息都能放下；保存时父版本仍是最新、来源是连续已完成历史、首个保留消息属于同一会话。

### 检查点有效性

`session_summaries` 只存成功启用的检查点，保留全部历史版本；`compaction_calls` 存每次摘要请求与响应，同一次压缩的多次调用共用一个 `compaction_id`。

投机压缩下两者的写入时机不同：`compaction_calls` 由前台在**采纳时**补写（`record_calls`，与 `start_call` 同一套运行归属门禁），`session_summaries` 仍然是采纳本身。因此一张 `compaction_calls` 行总能对应到一次被采纳的压缩；被丢弃的候选不写行，只在 `compaction_discarded` 事件里留下调用次数与 token 数。

- `source_run_id`：摘要包含哪个仍在运行的任务。
- `protected_input_id`：该任务被保留的原始用户消息。

读取规则：普通摘要可直接续接；运行内摘要在来源运行中可用，来源运行完成后可跨轮续接；来源运行失败、取消或中断后只保留审计，不进入其他运行的上下文。子摘要继承来源标记，失败任务的信息不会通过再次摘要变成普通历史。

同一任务在出现新的完整交换后可以再次压缩，默认每个运行最多 4 次；相同范围失败后不在原地重试，范围推进后才重新尝试。

### 失败与取消

空摘要、截断、工具响应、断流、超时、超过调用次数或保存冲突都不启用新检查点，发出 `compaction_failed` 并回退到"既有摘要 + 近期完整轮次"。若回退策略仍要排除普通旧历史，快照里会记录原因。取消运行记录 `compaction_cancelled`；已提交的检查点独立有效，即使后续任务失败也保留。

压缩失败不会静默截断用户输入：必需内容仍超预算时记录 `context_rejected` 并使运行失败。

```dotenv
CHAGENT_COMPACTION_ENABLED=true
CHAGENT_COMPACTION_TRIGGER=0.8
CHAGENT_COMPACTION_KEEP_RECENT=0.5
CHAGENT_COMPACTION_SUMMARY_TOKENS=2048
CHAGENT_COMPACTION_MAX_CALLS=8
CHAGENT_COMPACTION_TIMEOUT=60
CHAGENT_COMPACTION_MAX_PER_RUN=4
CHAGENT_COMPACTION_SPECULATIVE=true
CHAGENT_COMPACTION_SPECULATIVE_TRIGGER=0.6
CHAGENT_COMPACTION_SPECULATIVE_TIMEOUT=5
CHAGENT_COMPACTION_FRESH_WINDOW=fallback
CHAGENT_COMPACTION_RETAINED_USER_REQUESTS=4
CHAGENT_COMPACTION_POST_TURN=false
CHAGENT_COMPACTION_POST_TURN_TRIGGER=0.6
```

关闭自动压缩不删除也不忽略已启用的摘要，只停止生成新版本。`speculative_trigger` 必须严格小于 `trigger`，否则同步路径总是先触发，投机不会发生——配置在启动时直接报错而不是静默失效。`post_turn_trigger` 不得高于 `trigger`，同理。

## 大工具输出产物化

工具结果文本超过 8000 个 UTF-8 字节时，保存工具结果的事务同时写入 `tool_artifacts`：

```text
id / session_id / run_id / tool_record_id
content / char_count / byte_count / sha256 / source_truncated
```

- 产物不可变，属于产生它的会话；原始 `messages` 与 `tool_calls.result` 仍保存完整结果，`ToolResultMessage.artifact` 只存紧凑引用。
- 上下文层把大文本替换为产物 ID、长度、摘要校验值、头尾摘录和读取方法，保留原 `tool_call_id`、名称与错误标记。
- 会话历史默认加载用 `project_artifacts=True`，只读引用与图像，不把全文再读一遍；摘要请求同样使用引用。
- 工具 `read_artifact` 只能读本次会话的产物，`offset` 是从 0 开始的字符位置，`limit` 为 1–1000，分页在 PostgreSQL `substring` 完成，返回长度、SHA256、来源截断标记与 `next_offset`。

网页历史接口对带产物的结果返回引用与摘录，展开后可点击"读取产物全文"逐页追加。

## 上下文检查

每次成功构建记录：

- 策略与计数器名称、输入预算、输出预留、安全余量、估算 token。
- 选入的原始消息 ID，以及每条历史消息的选择理由：`system_instruction`、`current_turn`、`recent_complete_turn`、`summarized`、`token_budget`、`history_limit`。
- `TaskState` revision。
- 摘要 ID、revision、覆盖边界、`projected_token_estimate`。
- 注入的记忆 ID、revision、作用范围与用量；候选不会注入。
- `artifact_ids`、`summary_source_run_id`、`protected_input_id`。

预算拒绝发生在模型调用之前，保存拒绝事件与原因，不伪造模型请求记录。

## 使用示例

```sh
# 创建与查看会话
uv run --env-file .env python -m chagent.sessions create --title "项目开发"
uv run --env-file .env python -m chagent.sessions list --limit 20
uv run --env-file .env python -m chagent.sessions show <会话UUID>

# 重命名、归档与恢复
uv run --env-file .env python -m chagent.sessions rename <会话UUID> "新标题"
uv run --env-file .env python -m chagent.sessions archive <会话UUID>
uv run --env-file .env python -m chagent.sessions restore <会话UUID>

# 历史、任务状态、请求选择记录、摘要版本
uv run --env-file .env python -m chagent.sessions history <会话UUID> --limit 20
uv run --env-file .env python -m chagent.sessions state <会话UUID>
uv run --env-file .env python -m chagent.sessions context <会话UUID> --limit 5
uv run --env-file .env python -m chagent.sessions summaries <会话UUID> --limit 10

# 首次状态修订；后续使用读取到的最新 revision
uv run --env-file .env python -m chagent.sessions state <会话UUID> \
  --expected-revision 0 \
  --set-json '{"goal":"完成基础设施","constraints":["不修改现有业务文件"],"pending":["运行验证"]}'
```

## 边界

- 运行开始仍会读取该会话的全部可重放历史再做预算选择；按摘要边界在数据库侧限量加载尚未实现。
- 被替换的记录（`messages.superseded_by` 非空）留在库里可读，但**不进入回放**：重新生成与编辑重发都只追加，旧记录从被替换的那条起整个后缀退休。一个新 run 若没有自己的用户消息（重新生成），当前轮取最近一组用户输入，压缩不得把它吞进摘要。
- 失败、取消与中断运行的原始消息仍不回放给模型；其中已提交的副作用由宿主生成一条恢复注记进入系统指令（见[实施记录](实施记录.md) 第 4 节），不伪造消息、不补齐半个工具批次。
- 摘要质量只按锚点检查，没有语义无损的自动验证。
- 产物没有清理策略，与会话记录一起增长。
