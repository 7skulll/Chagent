## 1. 记忆提取移出运行与上下文投影（2026-10-28）

对应诊断基线里的三项：`AgentRunner.run` 在保存最终回答**之前**调用记忆提取模型；`ContextManager.prepare` 在每轮工具循环里重新投影并重复计数整段历史；同一运行内反复检索记忆。

### 1.1 提取不再排在回答之前

改动前，模型给出回答后还要在同一总超时内再发一次提取请求，然后与回答一起在完成事务里写候选。代价不只是慢：注入 2 秒提取、0.5 秒运行超时时，回答已经落库，运行终态却是 `failed`。

改动后，`runs.finish` 的事务里只做三件事：显式 `/remember` 的确定性写入、插入一行 `memory_jobs`、发 `memory_job_queued`。`MemoryWorker` 在运行之外领取任务，用独立超时调用模型，候选与 job 终态同事务提交。

语义约定（完整表述见[长期记忆设计](长期记忆设计.md)）：

- **入队与运行完成同事务。** 不存在"运行完成但任务丢失"或"任务存在但运行未完成"。
- **一个 run 一个 job。** `run_id` 唯一键防止重复提取；内容去重仍由记忆仓库的 key／hash 判定。
- **提取失败只影响 job。** worker 从不修改运行终态。
- **租约回收计一次尝试。** worker 被 kill 时 `fail()` 没机会执行，行会停在 `running`；`reap_expired()` 到期回收时 `attempts + 1`，并把该次尝试遗留的 `memory_extractions` 行标记为失败。不计数则崩溃型失败可无限重试。
- **取消与崩溃必须分开。** 主动取消走 `requeue`，不消耗次数；租约过期一定计数——前者知道发生了什么，后者只知道进程没回来。
- **工具主动停止的运行不提取。** `end_reason=tool_requested_stop` 没有最终回答可比对，`on_completed` 以 `has_answer=False` 跳过入队。

一个实现上的坑单独记下来：`_extract` 内部的 `asyncio.timeout` 如果直接把 `CancelledError` 抛出去，worker 会误判为"进程正在关闭"并把 job 塞回队列——不消耗次数，于是无限重排。当前实现把这个预算超时转换成普通失败，只有外部取消才归队。

### 1.2 上下文构建：投影一次，按累计成本选择

改动前，每次 `build()` 对每个已选消息 `deepcopy` 并序列化计数，而且**每个候选轮次再整段重算一次**：200 条消息时一次构建序列化 10,602 条消息（近似二次），400 条时 41,202 条；压缩的二分试探又会多次调用 builder。

改动后：

- `context/projection.py` 按**持久消息 ID** 缓存"模型可见投影 + 单条成本"。投影是存储消息的纯函数，消息行不变则成本不变；缓存有上限，超出整体清空，不做复杂淘汰。
- `ContextManager` 按 run 持有缓存，`release(run_id)` 时丢弃；同一 run 内新增的已提交消息只投影一次。
- 轮次选择改为**累计成本**求和，O(n) 而非 O(n²)；最终请求仍做一次完整 `count(messages)` 作为权威值。
- `TokenCounter.additive = True` 是**显式承诺**：`count(messages)` 等于各条 `count([message])` 之和。未声明该属性的计数器一律走精确重算，不会因为"看起来可加"而算错。新增计数器若模仿真实分词器的跨消息行为，必须保持不声明。

| 历史消息数 | 构建耗时（前 → 后） | 序列化消息数 |
|---:|---|---:|
| 40 | 2.759ms → 2.407ms | 522 → 82 |
| 200 | 48.387ms → **7.117ms** | 10,602 → 402 |
| 400 | 188.165ms → **10.472ms** | 41,202 → 802 |

增长曲线由二次变线性：200 → 400 条只增加 3.4ms（改动前增加 140ms）。

隔离性同样有数：注入 50ms 提取的文本回答 56.87ms → 16.38ms；1s 提取 + 0.5s 运行超时，从"运行 failed（回答已落库）"变成"运行 completed，job 先 queued 后 completed"；空记忆库 8 轮工具 45.29ms → 37.30ms（召回复用）。

### 1.3 真实链路

`deepseek-v4-flash` 跑 9 个场景，8/9 通过。`automatic_memory_candidate` 直接证实隔离：事件顺序 `run_completed` → `memory_extraction_started` → `memory_saved`，`memory_job_queued` 出现在完成事务内、`run_completed` 之前；运行 1227ms，提取 751.71ms 发生在运行结束之后。

唯一失败项 `explicit_memory` 是既有缺陷，与本批无关：模型在 `/remember` 之后仍自行调用 `list_dir`／`read_file`／`write_file` 写了一份 `memory.json`，而确定性路径早已把记忆写进数据库。修复方向见[下一阶段实施方案](下一阶段实施方案.md) 的 N 批。

顺带修正了脚本对终态位置的假设：提取事件会追加在 `run_completed` 之后，因此 `terminal_event` 改为"终态之后只允许出现 `memory_*` 记账事件"。

## 2. A 批：文本合并、提交后通知与 SSE（2026-10-28）

目标是缩短文本传递路径，工具循环、结果顺序与事务边界都不变。

| 文件 | 改动 |
|---|---|
| `agent/stream_writer.py`（新） | 每次模型响应一个 `TextStreamWriter`：首片优先、20ms／4KiB 合并、64KiB 容量、flush／close 与故障传播 |
| `agent/runner.py` | 消费供应商流与写库分开；同时监控 writer，写库失败能打断等待中的供应商；模型完成前排空文本 |
| `events/notifications.py`（新） | 按 run 的版本广播，不存正文、不给每个订阅者存事件列表；最后一个订阅释放后移除条目 |
| `storage/database.py` | 同一个 Database 实例持有一份进程内通知服务，供仓储与 Web 共享 |
| `storage/repositories.py` | 关键事务提交后通知；增加终态事件序号查询 |
| `storage/summaries.py`、`memory/worker.py` | 摘要事务、后台记忆外层事务成功后通知，避免在嵌套事务内提前发布 |
| `web/app.py` | 先订阅再追赶持久事件、版本检查防止漏唤醒、1 秒无通知兜底；终态事件处关闭回答流 |
| `web/schemas.py`、`web/static/app.js` | 独立的 memory-job 状态接口与后台状态展示，回答流不等待记忆提取 |

```text
供应商文本 → 有界缓冲 → 合并事务提交 → 版本通知
                                        ↓
                         SSE 按已提交 sequence 查询／发送
```

实际保证：

- 首个非空片段不等待合并定时器；定时器独立运行，供应商暂停输出时也会刷新已有文本。
- 超大增量先按字符分片再编码；64KiB 额度包含正在写库的内容，慢数据库对生产方形成有界背压。
- 单次响应一个 writer、一个流消费任务，不按增量创建任务；数据库等待不持有 Condition 锁。
- 非文本事件到达时排空已有文本；模型完成与后续工具调度之前，必须确认已接收文本全部提交。
- 写库失败立即让消费方停止并关闭供应商流，不等下一个 token 或缓冲耗尽；取消／模型异常时最多给 writer 2 秒清理预算，无法保存的尾部不伪装成成功。
- 只有事务成功才发通知，通知不保存正文；断线补齐仍依赖 PostgreSQL，通知遗漏与跨进程写入由兜底查询恢复。
- 多个 SSE 订阅者收到同一份持久事件，不竞争消费；慢客户端不持有连接、不阻塞生产者。
- 回答 SSE 截止于该 run 的首个终态事件，重连游标已越过终态时也立即结束；后台记忆事件仍留在审计表，但不越过回答终态发送。

合并事件增加 `count` 元数据，表示合并的内部文本片段数（超大供应商片段可能被拆分），不当作供应商 token 数。

实测（`scripts/benchmark_event_path.py`，改动前后各 30 次，P95 用 nearest-rank）：

| 场景／指标 | 改动前 | 改动后 |
|---|---:|---:|
| 快速突发 128 片：文本事务中位数 | 128 | **2** |
| 同上：完整窗口 SQL 中位数 | 286 | 43 |
| 同上：首片提交 P95 | 0.815ms | 0.751ms |
| 同上：首片 SSE 生成 P95 | 151.351ms | 1.213ms |
| 同上：提交完成 → SSE 生成 P95 | 147.402ms | **0.429ms** |
| 每片等待 5ms、32 片：文本事务中位数 | 32 | 9 |
| 同上：提交完成 → SSE 生成 P95 | 144.211ms | 1.320ms |
| 写库注入 5ms、128 片：模型流消费阶段中位耗时 | 918.027ms | 0.265ms |

最后一行只衡量生产方消费流的时间，不是整次运行耗时；最终文本排空与响应事务仍要等数据库。快速突发场景文本事务减少 **98.4%**，各场景提交到 SSE 生成的 P95 均低于 30ms；慢速流不保证相同合并比例。

真实 DeepSeek 核心与事件场景全部通过（12 次请求、14,367 tokens）：长文本收到 199 个供应商增量、保存 43 条文本事件，重建内容与最终回答逐字一致。浏览器只做了功能检查，没有采集绘制级首字延迟，因此上表的 P95 只对应 SSE 服务端生成。

**后续更正**：本批只合并"同一个 20ms 窗口内的片段"，每 20ms 仍是一个事务。真实供应商是慢速流，一次刷新只产生一片，合并窗口无从发挥——1.6 秒回答仍是 81 个事务，由 F1 解决。

## 3. B1：运行所有权与记忆任务领取令牌

前提：运行状态的写入分布在 Runner、`RunRepository`、`ToolScheduler`、`ContextManager`、`SummaryRepository` 与 `MemoryService`；后台记忆任务还会在运行终态后追加事件，因此不能在所有事件写入处一律要求运行仍为 `running`。锁顺序统一为"先锁运行行并校验所有权，再做其他受保护写入"——只在 `_event` 里补一次校验保护不了先于事件执行的业务写入，所以 `check_owner()` 位于各事务的写入之前。

`0010_run_ownership`：新运行分配独立令牌与 30 秒租约，运行期间每 5 秒续租。主运行的事件、模型与工具写入、终态、摘要事务在同一事务内锁定并校验所有权；后台记忆事件走独立审计入口。续租失败时停止本地运行，不写成功或取消终态。

收尾统一走 `AgentRunner._close_if_running`：先读当前状态，非 running 即不动；`finish` 再次校验所有权，失败时转成 `RunFailedError(storage_error)`。这个转换是必须的——`finish` 在 `except` 块内抛出，不会被同级的 `except RunOwnershipLost` 接住，否则会以未分类异常逃出 `run()`，且数据库行与返回结果不一致。放弃收尾的运行保持 `running` 交给扫描器，不谎称 `cancelled`。

失联收敛：网页服务启动后每 5 秒扫描，新运行启动前也扫描；每批 `FOR UPDATE SKIP LOCKED` 锁定已过期且有令牌的运行。运行终态、进行中工具的 `unknown`、排队工具的 `cancelled`、未结束的模型／压缩调用与终态事件在同一事务写入，提交后通知订阅者。已完成的工具记录保持原样。

`0011_memory_job_claims`：`memory_jobs.claim_token`，以及 `status = 'running'` 时必须同时具备租约与令牌的约束（`NOT VALID`，迁移时正在运行的旧 job 保留原租约并照常回收，之后的写入一律受检）。

- `claim()` 在领取事务内生成令牌并返回，令牌只存在于进程内，不从行里反推。
- `complete()`／`fail()`／`requeue()` 都要求 `id + status='running' + claim_token` 同时匹配，否则抛 `MemoryJobClaimLost`。不能只做"尽力更新"：候选与 job 终态同事务提交，`complete` 抛错才能让候选一起回滚，避免旧尝试留下重复候选。
- worker 捕获 `MemoryJobClaimLost` 后静默返回，既不改 job 也不发 `memory_job_failed`——此时 job 属于新尝试，报告失败会把活着的 job 记成失败。
- `reap_expired()` 回收时清空令牌，新领取者拿到新令牌，旧令牌从此无法写入。

残余行为：被回收的旧尝试可能已经花掉一次模型调用，`memory_extractions` 审计行会由新尝试以 `ON CONFLICT (run_id)` 覆盖。只浪费一次调用，不影响候选与终态的原子性。

验收覆盖令牌与过期租约拒绝写入／续租，过期运行收敛为 `interrupted/owner_lost`，真实子进程强杀后由另一进程批量收敛，健康租约与被锁运行不被误收，取消时失权返回 `storage_error` 且运行保持 `running`，旧领取者三种写入全部被拒，失效领取的候选随 `complete` 一起回滚，慢 worker 让位后不写终态、不发失败事件。

迁移把存量运行视为历史遗留：不根据新进程启动时间判断其他进程是否存活，也不自动终止它们。升级时需要停机人工收敛，且不得同时运行不执行所有权校验的旧版本。

## 4. B2：失败运行的事实恢复

不能直接放开历史：`ConversationRepository.messages()` 只为模型加载 `completed` 运行与当前运行的消息，而失败运行可能停在半个工具批次里——助手消息带 tool call、结果没提交，或者反过来。原样放回历史会让 `ContextBuilder._validate` 的配对检查失败，供应商协议也不接受孤立的 tool result。所以恢复只读结构化记录，历史一行不改。

| 位置 | 改动 |
|---|---|
| `domain/recovery.py`（新） | `RecoveryFact`、`RecoveryNote`、`build_recovery_note()`：按（工具，目标）取最新，上限 12 条／2000 字符 |
| `storage/repositories.py` | `recovery_facts()`：只读查询，不写任何行 |
| `agent/runner.py` | 每次运行加载一次事实，有事实时写 `recovery_projected` 审计事件 |
| `agent/types.py` | `RunState.recovery`，同一运行的所有轮次复用一份注记，不重复查询 |
| `context/builder.py` | 作为固定系统开销注入，计入上下文预算 |
| `domain/context.py` | `ContextSnapshot` 增加 `recovery_fact_count` 与 `recovery_source_runs` |

注记永远不是消息：没有 message id、没有 sequence，不会被回放、压缩，也不会被当作 tool_call 的配对结果。

采集口径：

- 只采信 `tool_calls.status = 'completed'`（模型已经看到的确定结果）与 `'unknown'`（已开始但无结果）。`'failed'` 表示工具返回了错误结果、没有留下持久副作用，不投影。
- 只收集有外部副作用的工具：`write_file`、`edit_file`、`exec_command`。读操作不产生事实。
- 每条事实带源运行、工具名、目标、提交状态；有产物时附 artifact 短 id。
- `unknown` 的措辞固定为 "no result was committed, verify before retrying"，不写"已完成"。
- 注记正文声明自己是参考数据，重复执行必须重新确认；它不构成授权，也不写入 task_state。

恢复边界：只读**最近一次 completed 运行之后**的失败。会话一旦有运行正常结束，更早的失败就属于历史，否则每次续聊都会重新注入同一批旧事实。同一条失败链里反复修改同一文件，按（工具，目标）只保留最后一次——这是状态快照，不是操作日志。

实测确认诊断里的 F2 形态已经反转：`write_file` 落盘 → 模型请求失败 → 下一轮的 system 指令里出现"`write_file notes.txt` — committed"，而 `messages` 仍只有 `["system", "user"]`。

未覆盖：注记不持久化，可在 `model_calls.request` 与 `context_snapshot` 中审计但不能回放；若下一次运行正常结束却完全没碰那些文件，再下一次不会知道这些事实（要修需按目标跟踪"最近一次成功写入"）；`exec_command` 的 `unknown` 只说明结果没落库，不能证明子进程已停止。

## 5. F1：事件批量提交

一次 1.6 秒的流式回答产生 76 条 `text_delta`，每条都走同一条路径：开事务 → `check_owner` → 锁 `runs` 行分配序号 → `INSERT` → 提交。76 次 fsync、76 个事务、约 245 条 SQL 全部压在模型流上。A 批的合并只解决了突发（128 片压成 2 个事件），慢速流一次刷新只有一片，窗口无从发挥。

| 位置 | 改动 |
|---|---|
| `storage/event_queue.py`（新） | `EventStream`：每 run 一个有界缓冲（256 条）、一个 `asyncio.Lock` 保证顺序、一个刷盘任务（100ms 或 64 条触发） |
| `storage/repositories.py` | `emit()` 只入队；`flush_events()` 排空；`close_events()` 收尾；`event_failure()` 供模型流等待；`_insert_events()` 一次插入多行 |
| `agent/runner.py` | 文本增量改走 `emit()`；`_response()` 与模型流、文本 writer 一起等待刷盘失败；每个响应结束前排空一次；`finally` 里关闭流 |

序号仍由数据库分配，一条语句给整批编号：

```sql
INSERT INTO run_events (run_id, sequence, type, payload)
SELECT %s,
       (SELECT COALESCE(MAX(sequence), 0) FROM run_events WHERE run_id = %s)
         + row_number() OVER (ORDER BY t.ord),
       t.kind, t.payload::jsonb
FROM unnest(%s::text[], %s::text[]) WITH ORDINALITY AS t(kind, payload, ord)
```

`MAX(sequence)` 读到的是语句开始前的快照，所以一条语句能编号整批；批量事务仍先 `check_owner` 锁住运行行，别的写入者插不进来。

三个必须守住的地方：

- **顺序靠"写前排空"，不靠内存排序。** 任何业务写入（`save_response`、`queue_tool_calls`、`tool_completed`、`finish`、直写 `event`）在开事务前都先 `flush_events()`。缓冲里的增量永远以更小的序号先落库。
- **终态事件仍在 `finish()` 的同一事务里。** 排空发生在终态事务之前而不是之后，回放不会看到"终态之后还有文字"。
- **刷盘失败必须中断模型流。** 只把错误存在缓冲里不够：供应商阻塞时没有下一次 `append` 来暴露它，运行会一直挂着。`_response()` 因此同时等待消费者、文本 writer 与事件流失败，任一先完成就按它处理。

失败与退化：

- 批量被数据库拒绝（例如触发器报错）：`flush` 记下错误并抛出；`finish()` 捕获后丢弃这一批并照常写终态。**终态优先**——事件已经丢了，让运行卡在 `running` 只会更糟。
- 所有权丢失：`finish()` 不吞这个错误，由 runner 归类为 `storage_error`，运行留给扫描器收敛。
- 取消：`close_events()` 排空一次再停任务，排不空就丢；强杀最多丢 100ms 内未提交的增量，消息与工具结果不受影响。
- 缓冲满（256 条）：`emit()` 直接 `flush()`，把"数据库慢"变成对生产方的背压，而不是无界内存。

| 场景 | SQL（前 → 后） | 事务 | 事件 | WAL |
|---|---:|---:|---:|---:|
| 两轮模型 + 一次工具 | 57 → 56 | 11 → 11 | 10 | 20KB |
| 1.6 秒流式回答 | 260 → **64** | 81 → **21** | 80（增量 76） | 38KB → 32KB |

21 个事务 = 建运行、开始模型调用、17 个增量批次、保存响应、收尾。

没到方案预测的"约 45 条 SQL"：每批仍要一次 `check_owner`（校验 + 插入 2 条）。再往下压就得把校验降到"每 N 批一次"，那会削弱 B1 的边界，不做——F2 改为把校验并进业务语句。墙钟没有变快（1666ms → 1690ms，噪声内），这符合预期：1.6 秒由模拟供应商的 150×10ms 决定，F1 的作用是让提交不再串在流上。

遗留边界：刷盘任务在进程内，跨进程的审计事件（记忆 worker 的 `memory_saved`）仍走直写路径，与批量事务靠 `runs` 行锁互斥；100ms 是选定的回放粒度，放宽到 250ms 能再少一半事务但断线补的块更大；批量写失败只能整体丢弃，没有重试一次的策略。

## 6. F2：一个事务一道所有权门

B1 给每条受保护写入加了校验：`SELECT ... FOR UPDATE` 确认 token、状态与租约，再写业务行，最后写事件。问题在事件插入前又取了一次 `FOR UPDATE`——同一事务、同一行、同一件事做了两遍。目标是把"每次写入一次校验"变成"每个事务一次校验"，并在能用条件更新表达的地方让写入本身承担校验。

- **一个事务只有一道门。** `check_owner()` 返回被锁定的运行行，并明确它拿到的行锁同时是 `MAX(sequence) + 1` 分配序号的依据。`_insert_events()` 不再接受 `locked` 参数，改为在 docstring 写明前置条件"调用者必须已持有运行行锁"——原来那个参数的默认值就是"再锁一次"，等于给重复加锁留了一个合法外表。`_event(..., locked=False)` 保留"没锁就自己取"的分支，专供不拥有该运行的写入者（记忆 worker 的 `audit_event`、恢复扫描的接班人）。
- **终态写入自己就是门。** `finish()` 原来是"先校验再 `UPDATE ... WHERE status='running'`"，两条语句判断同一件事，现在合并为一条带 `owner_token` 与租约条件的 `UPDATE ... RETURNING id`。受影响 0 行时才多花一条 `SELECT` 说明原因，区分"运行已终态"（`RuntimeError`）与"失去所有权"（`RunOwnershipLost`）——错误路径才付这笔钱。
- **压缩调用改成条件写入。** `start_call()` 用 `INSERT ... SELECT FROM runs WHERE owner_token = %s AND 租约有效`，`rowcount == 0` 即失联；`finish_call()` 用 `UPDATE ... FROM runs`，0 行时再查一次区分两种原因。
- **检查点不再重读运行。** `save()` 复用 `check_owner()` 返回的行做会话归属检查，删掉同一事务里的第二次 `FOR UPDATE`。附带的行为变化：检查点提交前一刻失权或已终态，现在抛 `RunOwnershipLost`（`storage_error`），原来是 `StateConflictError`（`execution_error`）；两者都拒绝写入，新分类更贴近事实。

| 场景 | SQL（F1 → F2） | 事务 | WAL | 墙钟 |
|---|---:|---:|---:|---:|
| 两轮模型 + 一次工具 | 56 → **46**（−18%） | 11 | 20KB → 21KB | 10.4ms → 10.7ms |
| 1.6 秒流式回答 | 64 → **59**（−8%） | 21 | 32KB → 33KB | 1690ms → 1628ms |

事务数不变是设计使然：去掉的是事务内的重复语句，不改变提交边界。普通运行省 10 条、流式回答省 5 条，正好是各自事务内的业务写入数。

**与方案的偏差**：没有做到"每条写入 3 条 SQL 降到 2 条"。一次业务写入是"校验 + 业务行 + 事件"，校验语句同时是序号分配的锁，删不掉，能删的只是它后面那次重复加锁。实际是每条写入 4 → 3、每个事件批次 3 → 2。

要让业务写入本身降到 2 条，只有给 `runs` 加 `event_sequence` 计数列，用 `UPDATE ... RETURNING` 同时完成校验、加锁与发号。评估后不采用：它把序号从 `run_events` 的派生值变成 `runs` 上的独立状态，必须由**每一个**事件写入者维护——包括不拥有运行的扫描接班人（条件更新不适用）和压缩检查点里那条直接 `INSERT ... MAX(sequence) + 1`，任何一处漏掉都会撞 `(run_id, sequence)` 主键；换来的只是每批少一条主键取最大，而当前成本在提交与 fsync。

**校验频率没有降低**：每个事务仍校验一次。落地的其实是"去重"而不是方案标题里的"降频"，B1 的边界（旧 owner 不能回写、租约过期即失联）没有一丝放松。

没动的部分：租约 30 秒、心跳 5 秒、`heartbeat()` 仍是条件更新；`begin()`、`finish()`、工具结果提交、压缩调用仍要求 owner 匹配；"租约过期不等于旧进程已死"的边界不变。

`tests/test_write_gate.py` 的 8 项同时是护栏，钉住 SQL 条数：单条事件 2 条、模型调用开始 3 条、终态写入 6 条且不含独立探测、压缩调用 1／2 条；谁把 `locked=True` 漏掉或把独立探测加回来，断言会先失败。

## 7. P0：检索、补丁与测试工具（2026-10-29）

前一批把写入路径压到了 46 条 SQL／11 个事务，但端到端没变快：一次真实的三文件单行修复仍然要 15.7 秒。原因是那一轮跑了 **10 次模型调用、14 次工具调用**，而框架自身每轮只占 7–9ms（`main-path-2026-10-29.json`）。瓶颈是轮次，不是 I/O。这一批只补工具面，不动运行循环。

### 7.1 三个工具与一条提示

| 工具 | 替代的旧做法 | 省下的轮次 |
|---|---|---|
| `grep` | `exec_command` 跑 `find`／`grep`，拿回一坨文本再读 | 定位与读取合并 |
| `glob` | `list_dir` 逐层翻 | 一次拿到候选文件 |
| `apply_patch` | 每个文件一次 `edit_file` | N 个文件 1 次调用 |
| `run_tests` | 同一套测试反复 `exec_command`，全量输出进上下文 | 一次调用一份摘要 |

`BasicContextBuilder` 的默认指令同步改成"用 grep／glob 定位、只读需要的文件、已知全部改动时一次 apply_patch、用 run_tests 验证"，否则新工具只是躺在 schema 里。规则与边界写进[基础工具设计](基础工具设计.md)。

### 7.2 实测

同一探针（3 文件 + 单行缺陷 + 2 个失败用例，`/tmp/chagent-probe2`），同一提示词，deepseek-flash，改动前后各跑：

| | 墙钟 | 模型调用 | 工具调用 | input | output |
|---|---:|---:|---:|---:|---:|
| 改动前 | 15.74s | 10 | 14 | 4,297 | 1,594 |
| 改动后样本 1 | 8.73s | 6 | 8 | 1,849 | 704 |
| 改动后样本 2 | 9.03s | 6 | 8 | 1,920 | 850 |
| 改动后样本 3 | 11.62s | 8 | 10 | 2,352 | 997 |
| 中位数 | **9.03s（−43%）** | **6（−40%）** | **8（−43%）** | **−55%** | **−48%** |

三次都改对了源码、都没碰测试文件，测试从 2 失败变成全绿。token 降幅主要来自 `run_tests` 的摘要化：改动前模型把完整 unittest 输出读进上下文，改动后只有计数与前几条失败。

**没达到预设验收线。** 开工前定的是 ≤5 轮／≤7 次调用／≤8 秒，实际中位数 6／8／9.0s。差距来源固定且可复现：每一轮首步仍是 `list_dir`，随后还有一次 `glob app/**/*.py`——而 `list_dir` 已经把 `app/` 列出来了。这是模型在缺少仓库索引时的定位习惯，不是工具缺失。要么加仓库地图，要么接受这 1–2 轮。

### 7.3 验收过程中改掉的两个自身缺陷

- **`run_tests` 的 unittest 命令曾带 `-t .`。** 带 top-level 目录时 `unittest discover` 要求测试目录是可导入包，裸 `tests/`（无 `__init__.py`）直接 `ImportError: Start directory is not importable`。第一次复测就踩中：工具在第 1.2 秒失败，模型转去写 `importlib` 临时脚本，整轮退化到 26 秒。现在只用 `discover -s <目录>`，`python -m` 本身已把工作区放进 `sys.path`。
- **`apply_patch` 曾因表头计数与 `*** End Patch` 拒绝合法补丁。** 模型给出 `@@ -5,9 +5,10 @@` 但正文是 6 行，并习惯性地加了 Codex 风格的结束标记。行数在 unified diff 里只是提示，定位靠的是上下文内容，因此改为忽略行数、忽略 `***` 标记，只保留"上下文必须唯一匹配"这一条硬约束；匹配到多处且等距时仍然拒绝。

同批修好并归档：`diagnose_main_path.py` 在 F1 之后必定崩在 `first_text_committed is None`（文本增量改走 `emit`，脚本只插桩了 `event`）。现在插桩 `emit`（`first_text_queued`）与 `flush_events`（`first_text_committed`），两个时间戳都进报告并做 `None` 兜底。该脚本仍无回归测试兜底。

### 7.4 边界

- 检索工具只读、可与其它只读工具并行；`apply_patch` 是写工具，走独占屏障。`run_tests` 与 `exec_command` 共用 `CHAGENT_ALLOW_HOST_COMMANDS` 开关。
- `apply_patch` 承诺"全量校验后再写"，**不承诺跨文件回滚**：写阶段失败时错误信息列出已提交的文件。POSIX 上没有更便宜的做法。
- 补丁只支持 unified diff 子集，不支持重命名；`*** Update File:` 语法未移植。
- 新增 27 项测试（检索 9、补丁 9、测试工具 9），全量 **235 项通过**。`test_runner.py` 里"第一个工具必须是 echo"的断言改为"工具集按名称排序且包含 echo"。

## 8. P1：提示缓存实测与护栏（2026-10-29）

P0 把轮次从 10 压到 6，剩下的每轮成本里最大的一项是首字延迟（实测 495–751ms，均值 570ms）。原本的判断是：`task_state` 与恢复注记拼在 system message 里，两者每轮可能变，一变前缀缓存整段失效，把它们挪到消息尾部就能救回 TTFT。

### 8.1 先量，再改

新增 `scripts/report_prompt_cache.py`：从 `model_calls` 还原每次请求的真实载荷（`domain.codec` 还原消息 → `transcript.openai_payload`），按 **prompt 顺序**切成"system 文本／工具声明／逐条消息"，逐轮比对相邻请求的共同前缀，再与供应商回报的 `cache_read` 对照。按 prompt 顺序切分是必须的——直接比对整个 JSON 会因为键排序把 `tools` 排到 `messages` 之后，把可复用比例算成个位数。

全库 52 个 run、133 次调用（样本归档 `docs/diagnostics/prompt-cache-2026-10-29.json`）：

| 指标 | 实测 |
|---|---|
| 前缀断裂的轮次 | **0**（52/52 个 run 每一轮都完整复用了上一轮前缀） |
| 全局命中率 | **87.1%**（189,443 prompt token 中 164,989 命中） |
| 单 run 命中率 | 中位约 90%，随上下文变长单调上升 |

**原假设不成立。** `task_state` 与恢复注记确实写在 system message 里，但 `AgentRunner._load_state()` 每个 run 只执行一次，两者在一个 run 内都是常量，前缀因此从来不会在同一 run 内改变。剩下的 12% 未命中就是每轮首次发送的新内容（模型输出与工具结果），按定义不可能命中：这个维度已经到顶。

单 run 明细（`74f52049`，6 轮，命中 89.3%）：

| 轮次 | prompt | cached | 命中 | 可复用占比 |
|---:|---:|---:|---:|---:|
| 0 | 1,868 | 1,664 | 89.1% | — |
| 1 | 2,329 | 1,920 | 82.4% | 74.7% |
| 2 | 2,775 | 2,304 | 83.0% | 84.8% |
| 3 | 3,243 | 2,816 | 86.8% | 86.7% |
| 4 | 3,508 | 3,328 | 94.9% | 92.3% |
| 5 | 3,614 | 3,456 | 95.6% | 96.6% |

命中率与可复用占比逐轮贴合，差额来自供应商的块粒度（cache 以 64 token 为单位匹配，报告里约为 1k token 一处）。

### 8.2 试过的方案与放弃理由

改法直接：system 只留指令与工具声明，`task_state` + 恢复注记合并成一条尾部 user 消息。改完测试立刻炸——`FakeModelClient` 按"最后一条消息是 user 还是 toolResult"决定行为，尾部多出的 user 消息让它在拿到工具结果后又发了一次工具调用，探针从 6 轮退化到 8 轮、5 次调用变 7 次。

这不是测试夹具的怪癖，而是本机 agent 的停止语义：**"最后一条是用户消息"等价于"用户刚说了话，继续说下去"**。把宿主数据伪装成新一轮输入，会让模型在该停时不停。收益一侧同样站不住：数据在一个 run 内是常量，挪位置带不来任何命中。

因此保留"per-run 常量放 system"的设计，改为把它写成不变量并加护栏：

- `test_identical_state_builds_an_identical_request`：同一份历史、同一份 per-run 状态构建两次，整份请求逐字段相等（system 的 `timestamp` 也固定为 0，否则这一条断言不成立）。
- `test_each_turn_extends_the_previous_request_without_rewriting_it`：第 N 轮的请求必须是第 N+1 轮请求的字节级前缀。

任何把逐轮数据塞回前缀的改动都会让这两条失败。

### 8.3 顺带修掉的一个 P0 遗留

`SIDE_EFFECT_TOOLS` 漏了 `apply_patch`：崩溃的 run 即使真的改了文件，下一轮的恢复注记也不会提，模型会以为工作区还是原样。补进集合，目标改从 `result.details.files[].path` 取（补丁没有单一 `path` 参数），一次改多个文件时按逗号列出。新增一项测试；回退 `SIDE_EFFECT_TOOLS` 后确认该测试确实失败。

### 8.4 边界

- 命中率上限由"每轮新内容"决定，不是优化空间。要继续降只能降轮次或降单轮输出。
- 冷启动的第一个请求命中率为 0：system + 工具声明约 1.8k token 要重写一遍缓存。TTL 内连续运行不会有这一笔（实测第二次运行首轮即 89.1%）。
- 一个 run 内工具集变化（`tool_revision` 变化）会改 `tools_added`，该轮前缀必然失效。这是必要失效。
- 缓存只影响 prompt 计价与 prefill，**不影响 TTFT 的主要成分**（排队与首 token 生成）。这条把"靠缓存救 TTFT"的路线关掉了：速度的下一步只能是减轮次。

## 9. 全链路复测与方案重估（2026-10-29）

三层同时跑：单元 239 项全过（30.1s）、真实供应商 8/9（17 次请求，input 7,419／output 847／cache_read 19,072）、多步修复探针 8.6s／6 轮／8 次工具调用。唯一失败仍是 `/remember` 的多余文件操作，与 10-28 两次同形。

### 9.1 成本构成

| 分项 | 实测 | 占比 |
|---|---|---|
| 首字延迟（供应商，6 轮均摊） | 570ms/轮 | 40% |
| 模型生成 + 工具执行 | ≈860ms/轮 | 59% |
| 框架（上下文、调度、事件） | 7ms/轮 | 0.5% |

P0 把探针从 10 轮／14 调用压到 6 轮／8 调用，墙钟 15.7s→8.6s，全部收益来自轮次，没有一毫秒来自框架优化。这与 P1 的结论一致：缓存已到上限，速度的下一步只能是继续减轮次。

### 9.2 两个新事实

- **探针仍有 2 次纯定向调用**：`list_dir .` 开局，`list_dir app` 在上一步已证明可达之后。这与工具无关，是"模型不知道工作区长什么样"的固定成本。
- **P0 的默认指令丢了**：P1 回退 `builder.py` 时 `git checkout` 把 P0 同时加进去的指令文本（"用 grep/glob 定位、一次 apply_patch、用 run_tests 验证"）一并撤掉，239 项测试无一发现。探针行为没有回退（6 轮／8 调用不变），说明那句话当时也没真正改变模型行为——但"测试不覆盖提示词"这个口子要堵上。

### 9.3 参考实现的结论

读完 Pi 1.4.0 与 Codex main 后，采纳与拒绝的比例大约是 1:1，见[下一阶段实施方案](下一阶段实施方案.md) 第 3 节。最有价值的一条是编辑形态：Pi **没有** `apply_patch`，只有 `{path, edits[]}` + 归一化匹配 + 重复匹配拒绝。我们恰好相反——最脆弱的那条路径（手写 unified diff）被写进了默认指令，而它在三次探针里失败了两次。

### 9.4 边界

- 本轮没有改任何生产代码（除文档与诊断归档），数字只用于判断方向。
- 探针是单任务单样本，波动约 ±0.5s；用它比较批次差异时看轮次，不看毫秒。

## 12. H 批：开局零成本（2026-10-29）

**动机**：`fix` 场景 8 次调用里有 2 次是纯定向（`list_dir .`、`list_dir app`）。工作目录、目录结构、分支状态、项目约定本来都是启动时就知道的事实，却让模型花一整轮去问。

### 12.1 交付

- `context/environment.py`（新增，254 行）：工作目录、两层目录树（每目录带文件总数与最多 8 个文件名）、git 分支与 `status --short` 摘要、仓库根到工作区各级 `AGENTS.md`（深层在前）。树 200 条目 / 4 KB、AGENTS 4 份 / 每份 2 KB / 合计 4 KB，git 1.5 秒超时。
- 接入点是 `AgentRunner._load_state()`：每个 run 计算一次，存入 `RunState.environment`，由 `BasicContextBuilder.build(environment=...)` 拼进 system message，`ContextManager` 原样透传。之所以不是每轮算，是因为它属于提示缓存前缀（[会话与上下文设计](会话与上下文设计.md)「运行级环境快照」）。
- 审计事件 `environment_projected`（字符数、条目数、是否截断、是否有仓库、读到的 AGENTS.md），用来回答"这次前缀为什么变长"。
- 任何一项失败都只让对应的行缺失：工作区不存在、git 未安装或超时、目录不可读，都不影响 run。

### 12.2 两次被实测否掉的设计

这两条都不是从文档推导出来的，是跑出来才发现的，留在这里避免下次重犯。

1. **只给目录名和文件数不够。** 第一版严格按方案写"仅目录名 + 文件数"，结果模型仍然开局 `list_dir .`：它需要知道 `app/` 里有哪些文件，而树只告诉它有 3 个。加上每目录最多 8 个文件名后，`list_dir` 调用在后续 10 次运行里降到 0 次。
2. **"需要时用工具查"这种许可式措辞会反向授权。** 第一版文案写的是"这是启动时的快照，运行中变化过的用工具查"，模型读成"那就查一下"，开局照样列目录。改成"以它为准、不要再列这些目录、只有树里没出现的目录才用 list_dir"之后才消失。**提示词里的许可句会被当成待办。**

### 12.3 实测（deepseek-flash，固定 fixture，真实测试判定正确性）

`fix` 场景 10 次（定稿版本，`--repeats 5` 两组）：

| 指标 | 批次前（M 批 2 次 + G 批 2 次，n=4） | 批次后（n=10） | 方案目标 |
|---|---|---|---|
| `list_dir` 调用 | 每次运行 1–3 次 | **0 次（10/10）** | 不再出现 ✅ |
| 轮次 | 8、6、6、9（中位 7） | 4、5、5、6、6、6、6、7、7、7（中位 **6**，均值 5.9） | 4 ❌ |
| 工具调用 | 11、8、8、13（中位 9.5） | 6、6、7、7、7、7、7、8、11、11（中位 **7**） | 6 ❌ |

正确性 10/10。同批回归：`edit` 5 轮／4 调用，`multifile` **4 轮／6 调用**（G 批为 5 轮／9–10 调用），两个场景都吃到这一批的收益，虽然方案没把它们列为验收对象。

**结论：只兑现了一半。** 10 次运行里一次 `list_dir` 都没有，说明"把定点事放进提示词"这条机制成立且稳定；但轮次只从 7 降到 6，没有到 4，墙钟中位基本没动。

**为什么没到 4 轮**：10 次里 8 次仍在第一次编辑之前跑了一遍测试，尽管任务文本已经写明有 2 个失败用例、默认指令也写了"先改再验证一次"。试过把措辞改硬（"不要在第一次编辑前运行测试"），连续三次 6／5／5 轮，没有改善反而多出一次 6 轮，于是退回温和措辞。**这一轮不是提示词能拿掉的**：`run_tests` 在模型眼里是"先看看失败长什么样"的信息获取，而不是重复劳动。要动它得靠 I 批的重复调用语义——把"同一命令在改动前后各跑一次"和"同一命令原地重跑"区分开，前者合法、后者拦截。

**墙钟为什么没改善**：轮次少 1，但每次请求的首字延迟不变，而快照让前缀长了 0.5–3 KB（fixture 约 0.5 KB，真实仓库 1–3 KB）。轮次收益被前缀成本吃掉了一部分，这正是方案里写的"若 TTFT 变差就关掉这一段"的临界区。当前判断是保留：它把 `list_dir` 这一整类调用清零，代价可测且可关。

`repeated_tool_calls` 在 10 次里出现 6 次，全部是"改前一次 `run_tests`、改后又一次"，参数完全相同。当前的重复计数分不开这两类，I 批必须先把语义定清楚，否则会把合法验证误判成无进展。

## 13. 编辑失败路径：二次方搜索与事件循环阻塞（2026-10-29）

**动机**：G 批把 `edit_file` 从"严格一次匹配"换成"相似窗口搜索"，换来一次编辑就成功，但没有给搜索定预算，也没有检查它在哪个线程里跑。两个问题叠在一起，变成一个能把 run 打死的组合。

### 13.1 三个被证实的事实

1. **相似度搜索对 `old_text` 是二次方、对文件是线性。** `SequenceMatcher.ratio()` 比较的是字符，每个窗口的代价是 `旧文本长度²`，而窗口数等于文件行数。合成样本（400 行，old_text 全部失配）：

   | `old_text` 行数 | 3 | 10 | 20 | 40 |
   |---|---|---|---|---|
   | 耗时 | 0.14s | 1.43s | 5.19s | 19.37s |

   真实文件更难看：本仓库 `storage/repositories.py`（700 行）配 30 行漂移块要 **81.6s**，60 行块要 **318s**。这些不是最坏构造——它们只是"模型抄错了 3 行"。

2. **`locate()` 在失配路径上把搜索算了两遍。** 一次在 `locate` 里判断是否达到 0.97，一次在 `_miss()` 里为了写诊断信息重算，连 `_normalized_lines()` 也重算。上面所有耗时因此已经是翻倍后的数字。

3. **写类文件工具在事件循环上同步执行。** `FileTool.execute()` 当时写的是 `if not self.read_only: return self.handle(...)`，只有只读工具走 `to_thread`。于是 81 秒的搜索期间：`AgentRunner` 的心跳协程（5 秒间隔，租约 30 秒）拿不到执行权 → 租约在库里到期 → 该 run 之后第一次写入抛 `RunOwnershipLost` → 以 `storage_error` 结束，而磁盘上的文件其实已经改好了。同一进程里其它会话的 SSE 也一起停摆。`ToolExecutor` 的 `asyncio.timeout(35)` 救不了：超时靠 `call_later` 投递取消，只在 `await` 点生效，同步调用之间没有 `await` 点。

   这条不是纯推理：往一个写工具里塞 33 秒同步阻塞复现过，run 以
   `RunFailedError storage_error | Run ownership lost or lease expired` 结束，
   而 `runs` 行仍是 `running`——收尾同样要过所有权门，所以它连"我失败了"都写不进去，只能等后续 `reap_expired` 标成 `interrupted`/`owner_lost`。

### 13.2 交付

- `FileTool.execute()`：所有文件工具一律 `asyncio.to_thread` + `shield`，取消时先把线程排空再释放调度槽。写之间的串行不靠事件循环，靠调度器的工作区门（`_WorkspaceGate` 同一时刻只放一个写者），所以移出线程不改变顺序语义。
- `edit_diff.py`：`near_match()` 用**字符比较预算**约束两条分支——窗口数 × 目标长度² 在 `SIMILARITY_WORK_LIMIT`（3000 万，实测约 0.6s 上限）以内就逐窗扫描，超出则只给"锚点投票"选出的候选窗口打分。候选数同样按剩余预算截断，因此无论文件多大、`old_text` 多长，这个函数比较的字符数都不超过预算。
- 锚点投票：目标里唯一且长度 ≥ 8 的行各投一票给它出现的行号减自身位置，票数最高的偏移就是候选窗口起点。一次线性扫描，之后只算个位数个 `ratio()`。
- `_miss()` 不再重算：`locate()` 把已经算出的 `near`、行表一起传下去。
- 失败信息保持"最接近区域 + 行号 + 原文"，只在**完全不像**（没有任何一行能投票）时改为"没有足够接近的区域可供引用"——这条路径上原来的相似度数字本来就接近 0，没有信息量。

### 13.3 实测（同一批样本，本仓库真实文件）

| 文件 | 行数 | `old_text` 行数 | 改造前 | 改造后 | 定位结果 |
|---|---|---|---|---|---|
| `storage/repositories.py` | 700 | 30 | 81.6s | **0.43s** | 第 101 行，0.98（正确） |
| `web/app.py` | 517 | 30 | 39.4s | **0.16s** | 第 101 行，0.97（正确） |
| `storage/repositories.py` | 700 | 60 | 318s | **0.34s** | 第 101 行，0.98（正确） |

锚点路径的准确性单独验过：400 行／20 行漂移块上，锚点结果与暴力扫描**窗口起点和相似度完全相同**（0.9513，第 101 行），耗时 0.015s 对 1.66s。

### 13.4 四条断言

都在 `tests/test_edit_tool.py`，跑全量时共耗时约 0.1s：

1. `test_write_tools_do_not_hold_the_event_loop`：一个 `sleep(0.2)` 的写工具执行期间，10ms 心跳必须走到 ≥5 次（老实现是 0 次）。这条断言的是**机制**，不依赖 `edit_file` 恰好很慢。
2. `test_a_miss_on_a_large_file_stays_bounded`：400 行／40 行失配必须 <1s（老实现约 19s），且信息里仍有"Closest region"。
3. `test_anchored_search_agrees_with_the_exhaustive_one`：把预算压到 0 强制走锚点，结果必须与暴力扫描一致。
4. `test_unrelated_text_is_reported_without_a_similarity_claim`：完全不相关时不再编造相似度。

全量 **279 项通过**（36.4s）。真实供应商回归：`edit` 4 轮／3 调用，`multifile` 4 轮／8 调用，与改造前同值（样本 [`probe-g2-edit.json`](diagnostics/probe-g2-edit.json)、[`probe-g2-multifile.json`](diagnostics/probe-g2-multifile.json)）。

### 13.5 已知取舍

- 候选窗口上限意味着大文件上报的是"候选里最接近的一个"，不是全局最优。这个阶段要么低于 0.97 只用于诊断，要么直接编辑——后者仍有一个前提：目标里至少有一行是精确的。**如果模型把整块缩进都改了**，大文件上不再自动编辑，而是报"没有足够接近的区域"，让模型重读一次。这是有意的：宁可多一轮，也不按错位缩进写盘。
- 搜索预算与 `SIMILARITY_MAX_CANDIDATES`（8）都是实测值，不是推导值。若将来 `old_text` 常态超过 100 行，需要重新标定。
- 线程化没有解决"写操作本身很慢"：`fold_text` 对 1 MiB 文件逐字符折叠约 0.3s，仍在同一条路径上，只是不再阻塞事件循环。
- **未修、但已经看见**：所有权丢失后 `_close_if_running()` 自己也要过所有权门，因此 run 行停在 `running`，要等下一次 `reap_expired()` 才变成 `interrupted`/`owner_lost`。调用方拿到的是 `storage_error`，数据库在两者之间说谎。这是 B1 的既有行为，与本次搜索无关；要修得让收尾路径带一条"我确定自己丢权"的免检收尾写，属于独立决定，这里不动。

## 14. 全链路测试与 `/remember` 短路（N 批，2026-10-29）

### 14.1 范围

真实供应商（deepseek-flash）、真实 PostgreSQL 临时 schema，四组链路共 18 个用例：

| 组 | 用例 | 覆盖 |
|---|---|---|
| `all` | 9 | 文本、文件读写链、跨会话历史、显式记忆、跨会话记忆、自动抽取候选、审查后召回、真实压缩、Web SSE 与重放 |
| `core` | 6 | 上述前四项 + 真实压缩 + 工具请求正常停止 + Web |
| `scheduling` | 1 | 同一响应三路并行读、写后置、结果顺序、worker 回收 |
| `events` | 2 | 流合并可逐字重建、SSE 与重放一致 |

另加两项手工链路：CLI 端到端（读文件→计算→写文件，`sum.txt` = 41）与 CLI 上的 `/remember`，以及一次 Web 端 `/remember`（ASGI，含 SSE 结束与重放）。

**首次运行 8/9 通过，唯一失败项是 `explicit_memory`**，且这项从 10-28 起四次复测全红。

### 14.2 根因：记忆被写了两遍

`/remember` 的写入本来就发生在完成事务里（`MemoryService.on_completed` → `commit`），模型一次调用都不需要。但同一条命令**同时**作为普通用户消息进入模型循环，模型于是按"用户要我记住"的理解去**自己写文件**：

| 时间 | 形态 |
|---|---|
| 10-28 | 新建 `MEMORY.md` |
| 10-29（P0/P1 后） | 新建 `MEMORY.md`，写明键值 |
| 10-29（M 批复测） | `list_dir` → `glob` → `write_file` 建 `MEMORY.md` |
| 10-29（本次，H 批后） | `read_file numbers.json`、`read_file result.json`，然后**拒绝**执行——它发现口令里的十六进制串与 `numbers.json` 的 `marker` 一致，判定为"从工作区数据拼装的凭据" |

最后一种形态尤其说明问题：模型不是照做着玩，它在**推理**，而且推理是对的（测试夹具确实让 nonce 串了两处）。但真正的问题是**这条命令根本不该到模型那里**——数据库那份已经写好了，文件那份是重复且未经审查的第二副本，下一轮还会通过 `AGENTS.md` 重新进入提示词。

### 14.3 修法

- **短路点**在 `AgentRunner.run()`：`_load_state()` 之后判断 `MemoryService.explicit_command(state)`，命中则走 `_explicit_memory()`，不进 `_loop()`。
- **新终态** `explicit_memory`（`completed` 下合法）。不用 `model_stop` 假装发生过模型调用，这正是 N 批验收要求。
- **确认文本落库**：`RunRepository.save_notice()` 写一条没有 `model_calls` 行可挂的 assistant 消息，走同一道所有权门。CLI 与 Web 都能读到，重放一致。
- **事件顺序**：`run_started` → `text_delta`（确认文本）→ `memory_command_resolved`（scope/key）→ `memory_saved`（真实 id/revision）→ `run_completed`。
- **迁移 `0012`** 更新 `runs_end_reason_check`（`0007` 不能改，校验和会拦住）。
- **不采集环境快照**：命令不调模型，没有人读工作区，于是大仓库上不必白扫一遍目录树（`environment_projected` 在这条路径上不再出现）。

三条边界都经测试固定：

1. **记忆策略关闭时不短路**。此时 `on_completed` 什么也不写，给"已记住"就是撒谎；run 仍走模型，`end_reason` 为 `model_stop`。
2. **被拒绝的命令不是命令**。键名不合法或内容像凭据（`validate_memory` 抛 `ValueError`）时短路放弃，交回模型解释为什么不能记；`on_completed` 那边同样失败，所以两条路都不写库，但用户拿到的是理由而不是假确认。
3. **普通句子不误判**。`explicit_memory` 用 `fullmatch`，"请说明 /remember 怎么用"走模型。

### 14.4 结果

| 指标 | 修复前 | 修复后 |
|---|---|---|
| `explicit_memory` 墙钟 | 4756.3ms | **24.3ms**（末次 24.3、前次 43.7） |
| 模型调用 | 2 | **0** |
| 工具调用 | 2（`read_file` ×2） | **0** |
| 事件数 | 70+ | 5 |
| 记忆写入 | 库 1 份 + 文件 1 份 | **库 1 份**（`origin=explicit_user`、`status=active`） |

`explicit_memory_nonsecret` 场景同值：10.7ms、0 请求、0 工具（原先 `list_dir`／`glob`／`write_file` 三次）。全量 **283 项通过**，其中四条新断言固定了"零模型调用 + 零环境快照 + 两条回退路径"。

四组链路复跑全部通过：`all` 9/9、`core` 6/6、`scheduling` 1/1、`events` 2/2。

### 14.5 顺带发现，两件要记下来

1. **`ruff` 从来没真正跑过。** 之前几轮我用 `.venv/bin/python -m ruff`，它报 `No module named ruff`，而这句被 `|| true` 吞掉了——所谓的"静态检查与全量测试"实际上只跑了测试。项目也没有 ruff 配置，`uvx ruff` 的默认规则集给出 133 条（其中 76 条 unsorted-imports 与项目自身的导入分组约定冲突），噪声大于信号。**这次只按精确规则集（`F401,F841,F811`）清掉真问题**：`edit_diff.locate()` 里一个从未使用的 `new` 变量、三处测试未使用的导入。`domain/tools.py` 的 `JsonValue` 是刻意保留（解析递归类型提示），不动。若要长期用 ruff，得先写配置，不能默认全开。
2. **`edit` 场景这次 6 轮（此前 4 轮）。** 多出来的一轮是连续两次 `run_tests`：先 `pytest`、再 `unittest`，参数不同所以不算重复调用。原因是模型不知道夹具用哪个框架，只能逐个试——H 批的环境快照有目录树但没有"测试该怎么跑"。这是新观察项，归属 L/H 之间的"环境事实补一条测试命令"，本批不改。

## 15. 回退参考

| 改动 | 回退方式 |
|---|---|
| 记忆提取移出运行 | 让 `on_completed` 直接调用提取并在同一事务写候选，`memory_jobs` 表可保留不用 |
| 上下文投影缓存 | 去掉 `ByteTokenCounter.additive`（或让缓存不命中），所有构建走逐轮重算，行为不变、性能回到基线 |
