# 当前实施计划

更新：2026-11-03。本文是唯一当前路线图。当前行为见专题文档，已完成的历史证据见实施记录和验收记录；以下计划不代表能力已经开放。

## 目标与顺序调整

优先借鉴 pi 的直接工具循环，让 Chagent 在本地网页完成「读代码 → 创建/修改 → 执行 → 测试 → 修复 → 交付」闭环。先将逐次审批从编码能力的实施依赖中解耦，再完善授权产品。只读模式继续保留，但不再作为编码主线的终点。

本机 pi 默认以启动进程的权限执行工具，没有内置逐次审批。Chagent 借鉴其简单执行方式和按实际工具组织上下文，复用现有 Runner、数据库、网页与工具，不重写一套 Agent。保留已有工作区边界和 isolated 执行；不通过切换 sandbox=off 达成简化。

首个可写版本采用显式启用的可信开发配置：用户在配置中授予工作区写入和命令执行能力，运行时不逐项询问。这里的「可信」表示授权方式，不表示项目内容或模型命令可信。逐次审批是另一种可选策略，现有配置不能被静默覆盖。

## 第一阶段：解耦执行策略与编码能力（已交付）

目的：让编码工具是否可用、命令如何隔离、是否逐次审批分别决定，避免“审批产品尚未完成”成为所有写入能力的门槛。

交付：CHAGENT_EXECUTION_PROFILE=configured|trusted-development；配置冲突拒绝，不改既有审批。code 写入和 process stdin 独立装配，网页核对真实 runner/注册表/审批状态。

工作：

1. 梳理 Settings → bootstrap → registry/executor → ApprovalBroker → 网页门禁的完整路径，列出当前只读、可信开发和既有审批配置的能力矩阵。
2. 在统一装配处定义执行策略，至少区分现有只读配置与显式启用的可信开发配置；具体配置名在实现时确定，不在多处复制判断或增加 demo/single_face 旁路。
3. 可信开发配置使用无需逐次审批的决策；既有审批策略仍走原 broker。冲突配置启动时明确拒绝，不静默将用户策略改成 never，不删除现有审批代码或数据。
4. 网页、CLI、Runner 与工具共用有效能力结果；网页按实际能力展示写入、执行、网络、stdin 与审批状态。默认仍 work，不自动升级旧会话。

完成条件：配置矩阵覆盖只读和开发两条真实模型路径；默认行为不变；可信开发配置不创建或等待逐次审批；旧审批路径仍有效；缺少隔离后端时拒绝执行。该阶段完成不等于可写网页已交付。

## 第二阶段：最小可写编码闭环（限定范围已交付）

依赖：第一阶段。不依赖完整 C3、C4、模型出口保护或五项目回归。

交付：真实模型网页创建 3 个文件、3 项测试通过；追加 divide 后先记录导入失败，再编辑实现，5 项通过；最终移除导入兼容代码后仍通过。刷新/重启恢复、运行中停止与超时已验收，数据库审批记录为 0。修改路径和编辑 diff 由工具结果提供，独立整轮变更列表后续完善。这里只证明合成标准库项目的编码闭环，不替代第三阶段真实项目验证。

工作：

1. 开放可信开发配置下的网页 code：注册既有 write_file/edit_file/apply_patch、exec_command、run_tests 及 process read/stop。文件工具写入与命令工作区可写必须一致，实际 runner 校验不能仅信任 Settings。
2. 继续使用 isolated，工作区可写、命令断网、HOME/tmp 按 run 私有分配；保留源码/运行时目录准入、文件身份检查及失败关闭。只读档继续禁写；本阶段当时 work 工具面未变，后续工作区批次已按用户需求让 work 与可写 code 共用文件工具，见[F1–F4 实施与验收](工作区F1-F4验收-2026-11-03.md)。
3. 首版不提供 process write/EOF，不要求 PTY；普通命令可直接携带输入或使用文件。交互式程序明确列为未支持，避免将交互审批绑定为普通编辑/测试的前置条件。
4. 复用流式、停止、刷新恢复和工具结果展示，提供本轮修改文件及可获取的 diff。Git diff 之外也要检查新建文件；不要求工作区必须是 Git 仓库。
5. 选择现有运行时支持的 Python 标准库项目作为首个端到端样本：网页真实模型从空目录创建代码和 unittest，执行测试；追加需求后修改代码，运行验证，并覆盖一次失败后的修复。

完成条件：真实模型网页完成创建、修改、测试、修复和交付，核对实际文件与测试输出；无逐次审批等待；只读、work、既有审批配置回归通过。验证停止、超时和刷新恢复，说明中断前已写入的内容会保留，不承诺事务回滚。完整自动回归记录通过/跳过/失败；涉及的隔离探针需在可施加 seatbelt 的环境实际通过。

交付范围：本机 macOS、已验证运行时、离线且依赖已具备的编码任务。依赖安装、任意项目构建、命令联网、开发服务器和交互 stdin 不作为首版承诺。

## 第三阶段：真实项目与工具链可用性

依赖：第二阶段。先用 1–2 个真实项目证明可用性，再逐步扩展；不以凑齐五个项目阻塞首版。

- 覆盖真实 Python 项目的多文件修改、已有测试、Git 历史与 diff、失败修复、取消及恢复。
- 按实际需要补充 Node/其他运行时及必要读取白名单；不能为测试通过而放开整个用户目录或 Chagent 源码。
- 分别记录缺依赖、离线安装、构建缓存、开发服务与命令网络需求。支持不了的任务明确失败，不用合成 fixture 冒充真实项目。
- 检查并行文件修改与后台进程的行为；处理用户已有未提交改动，不自动 stash、reset 或覆盖用户文件。

完成条件：每个已声明支持的工具链都有真实项目、真实模型、实际命令与文件结果证据；未支持项可识别且可恢复。Git checkpoint 若另做，只作为文件恢复辅助，不替代隔离或授权，也不保证外部副作用恢复。

## 第四阶段：按需要完善授权、交互与网络

这些工作在可写闭环之后独立推进，不能倒置为第二阶段的总前置条件。

| 批次 | 交付 | 前置条件 |
|---|---|---|
| C3 交互与审批 | 定义可信开发配置和审批配置各自的 stdin 行为；审批配置按进程/run、输入字节与 EOF 绑定单次授权，覆盖拒绝、超时、重复消费、跨 run 和退出 | 执行策略稳定、进程生命周期验证完成 |
| C4 命令网络 | 按真实安装/构建需求定义网络配置、可见提示和撤销；验证新 profile，保持现有 isolated network=true 拒绝直到新实现交付 | 有明确用例与可验证隔离方案；不强制等待不相关的 stdin 功能 |
| 模型可见路径与请求出口 | 统一相对/虚拟路径；主对话、重试、摘要、记忆共用出口检查，处理旧历史阻塞 | 复用已交付统一边界；可并行实施，不阻塞限定范围的开发版 |
| C5 扩展回归与受控开放 | 扩展到五个真实项目；完善审批配置下的网页流程、兼容性和故障恢复 | 对外声明的能力及对应策略已稳定；不作为可信开发首版门槛 |

模型出口保护尚未交付，不能宣传路径隐藏或绝对防外泄；命令断网不限制模型 API 与独立网页工具。路径检测也不保证识别任意编码、图片或源码副本。

## 并行维护与验收规则

- work 补验 Word/Excel、拖拽/粘贴、真实断网重试和跨浏览器；模型语言/格式遵循保留实际偏差记录。
- 当前实现写专题，未来顺序只写本文，证据写实施记录/验收记录；不新增平行路线图。
- 自动测试、合成安全探针、真实工具、真实模型网页和真实项目分别记录；跳过不计通过。
- 隔离缺失/探针失败/源码越界/配置与实际工具面不一致时拒绝对应能力，不回退到 off。
- 开发版有问题时关闭其显式配置并重启，恢复默认 work 或已验证只读配置；保留用户文件和历史，不自动回滚工作区。
- 每阶段独立交付和记录，不设无证据的人日承诺，不在跑通闭环前重写框架或扩张分布式架构。
