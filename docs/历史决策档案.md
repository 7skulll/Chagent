## 1. 演进：边界换过三次位置

| 阶段 | 做法 | 结局 |
|---|---|---|
| 2026-10 至 11-02 | macOS seatbelt 在**进程内**给自己上锁（`isolated`）+ 14 项启动探针 | 已删除 |
| 2026-11-03 | `trusted-development` 档：相信本机账号，可写可执行、命令断网 | 已删除 |
| 2026-11-04 | 整个进程跑进容器，应用内不做隔离 | **当前形态** |

转折点是那句"配置并启动 Spring Boot"：在 `deny default` 的白名单模型下四条路全断——JDK 不在 `runtime_roots()`、`/opt/homebrew/bin` 不在固定 PATH、`sandbox_network=false` 是硬约束拉不到 Maven 依赖、`detect_suite` 没有 `pom.xml` 分支。

真正的病根不是这四条配置，而是：

> **`deny default` 的白名单必须随生态线性增长，而每增长一次都要重跑一次探针。**

Python → Node → Go → Rust → JDK → Gradle → Kotlin，每加一条工具链：加路径、加 PATH 条目、加探针、加一轮验收。这是结构性的，不是漏配。容器把这条曲线换成常数：换工具链 = 改镜像一行。

## 2. 最终决策

| # | 决策 | 理由 | 被否决的替代 |
|---|---|---|---|
| D1 | 边界放**进程外**：整个 Chagent 跑在容器里 | 白名单曲线换成常数 | 继续扩 seatbelt 白名单 |
| D2 | 保留 `WorkspaceFS` | inode 校验、不跟随符号链接，容器里同样需要，防止符号链接把写入引出挂载点 | 全交给容器（挂载点内仍可被击穿） |
| D3 | **不做**工具级隔离（不学 gondolin） | Chagent 是常驻 web 服务，整进程容器天然可行；工具级要重写 317 行保护逻辑，且 `tools/web.py` 在进程内联网，只路由 bash 等于边界开洞 | 把 read/write/edit/bash 路由进 micro-VM |
| D4 | 三轴拆开，只留 3 个合法组合（后加 D 组合共 4 个） | 每个组合一句话能说清；增加的是语义不是分支 | 保留边界四档 |
| D5 | 不做应用内沙箱与启动探针 | 容器标记 + 显式声明能挡普通误配，但声明可伪造，不构成强安全证明 | 继续以探针作为唯一执行边界 |
| D6 | 审批保留为 `gate=approval`，但**不是**执行的前置 | 位置解决了边界；审批留给不可逆的高危动作 | 让审批承担边界职责 |
| D7 | 先建新路径，再拆旧实现 | 删除可单独 revert；先删会让中间态无法验证 | 边删边改 |

三轴：`boundary`（跑在哪）、`capability`（能不能执行）、`gate`（要不要人批），由 `execution.py:resolve()` 一次推导，配置、网页门禁、CLI、工具装配共用同一结果。

## 4. 被否决的替代方案

**边界四档（`off`/`workspace-write`/`isolated`/`container`）**：把"内层隔离强度"当成第一维度，导致 `container` 只是一个"声明自己没有隔离"的档位，仍需维护另外三档。已由三轴模型取代。

**工具级隔离**：为每个工具提供可替换后端（pi 的 `*Operations` 注入）确实更灵活，但 Chagent 的文件保护逻辑编在工具内部，换后端等于重写；且联网工具在 agent 进程内，只隔离命令等于开洞。

**全面融合沉睡能力**：审计发现约 970 行审批链、只读档、`workspace-write`、stdin、模式切换都已实现但入口不可达。全面接回的合法组合会从 2 种膨胀到 12 种以上，按"跳过不计通过"的纪律等于 12 次隔离验收。裁决是只融合 `containerized` 一档，其余**对齐或删除**。

**`TaskState` 开放可写**：它当前位于提示缓存前缀，位置设计假设"run 内不变"；改为模型可写必须移出前缀、降级为消息，否则每次写入都让下一轮缓存全量失效。成本高于收益，未做。

## 5. 审计方法的坑（值得复用）

`2026-11-04` 那次能力审计得出"沉睡能力远多于在用能力"，但过程中踩了四个坑，全部写下来避免下次高估结论：

1. macOS BSD `grep` 不支持 `\b`，用词边界统计会**全部返回 0**。
2. 只匹配双引号会漏掉单引号端点（`file_api.py` 大量用 `'...'`），一次漏了 18 个。
3. 前端 URL 常由 `base(space)+"/text"` 拼接，纯正则扫不到，会误判成孤儿端点。
4. 只扫 `src/` 会漏掉 `tests/` 与 `scripts/` 的引用——曾据此把三个模块判成"469 行死代码"，实际仍在用，已全部恢复。

结论：**任何"未使用"判定都必须再扫一遍 `tests/` 和 `scripts/`，并人工核对字符串拼接。**

## 6. 当时的真问题：能力与入口错位

审计的一句话结论是"Chagent 不缺能力，缺的是能力与入口的对应关系"。三个具体表现与最终处理：

| 表现 | 实例 | 处理 |
|---|---|---|
| 一个词表达三件事 | `trusted-development` 同时表示跑在哪、能不能执行、要不要人批 | 拆成三轴 |
| 同一判定写四遍 | `config/__init__.py`、`web/policy.py`、`bootstrap.py`、`builtin.py` 各写一遍 7 条件 | 收进 `execution.resolve()` |
| 接口与自己矛盾 | `/api/info` 硬编码 `code_mode: false`，而门禁要求 `code_mode=true` 才能启动 | 由 `Settings.axes` 推导 |

还有一个更隐蔽的教训：**测试全绿不代表功能在产品里可用**。审批链 423 行测试真实执行并通过，但它走的是 `configured` + `create_demo_runner`，从未经过 `validate_web_settings`——测试里的活代码，在生产入口是死的。

因此：**不能宣称路径隐藏或绝对防外泄**。系统提示已不再自动注入工作区路径、目录树和 Git 状态，但旧历史、摘要、记忆、上传文件和网页内容仍可能携带真实路径；图片、二进制、任意编码也无法可靠检出。

## 8. 明确的代价与做不到

选择了容器，就必须承认这些，不能靠文档措辞绕过去：

1. **隔离强度实际下降**。容器不是安全边界：daemon 以 root 运行、默认共享内核。强隔离需要 rootless + userns-remap + seccomp，当前镜像不含。
2. **macOS 上 bind mount 慢**，virtiofs 下小文件 IO 慢 2–10 倍，`mvn` 编译可感知。
3. **容器内起服务要额外暴露端口**，用户说"跑起来"时 8080 在容器内，需要 `-p` 映射。
4. **没有 Docker 就不能执行代码**。此时降级为组合 C：能读写文件、查资料，不能跑程序。想在本机执行可用 Podman / Colima / OrbStack，都属于 Docker 兼容运行时。
5. **不防容器逃逸**（内核漏洞、`--privileged`、挂载 `docker.sock`）；**不回滚**取消后的文件副作用；**没有 PTY**；**不跨项目读文件**（靠没挂载，而不是靠白名单——保证来源变了，结论更硬）。
6. 容器标记与显式声明只是**防误配**，不是安全证明。

## 10. 宿主终端代理原型与自主建站架构取舍（2026-11-05）

曾推荐“容器主控 + 宿主代理”（方案 A）：不搬动已验收的容器主控，只加一条经宿主终端逐次确认的一次性命令通道。原型已写入代码但默认关闭，未通过真实模型端到端执行验收；三次真实宿主申请均到期拒绝，说明把确认放在另一终端不能满足网页聊天中的自然交互。

更关键的是工作区身份：数据库用容器路径 `/workspaces` 唯一标识工作区，任意宿主目录若依次挂入该路径，会让旧会话、记忆及文件归属误指向新目录。自动跨根切换已关闭，原挂载已恢复，旧数据未改写。这是原 A 方案作为主架构的否决依据，不应靠继续增加重启逻辑或终端提示掩盖。

目标决定为“宿主主控 + 每工作区独立容器执行后端”：稳定宿主目录身份由主控持有，模型生成的普通命令仍在受限容器执行；确需宿主原生执行时，在同一网页逐次审批。该目标**已于 2026-11-05 实施**（第一交付验收通过，第二交付部分交付，见[验收第 14 节](验收记录汇总.md#14-宿主主控自主建站2026-11-05)）；本文记录的是当时的取舍，不是当前进度。安全边界、旧数据迁移、完整建站闭环和两次真实项目验收统一见[自主建站整体方案](宿主执行方案.md)。本节只记录为什么放弃把 A 当目标，不把未来方案写成当前产品行为。
