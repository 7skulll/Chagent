# 能力审计与融合决策

> 状态：**未实施**。本文只记录审计结论与融合判断，不含代码改动。
> 日期：2026-11-04。审计对象为工作区当前代码（`0019_file_outputs` 之后、统一工具面重构已提交的状态）。

## 1. 结论

一句话：**Chagent 不缺能力，缺的是能力与入口的对应关系。**

三条具体判断：

1. 沉睡能力远多于在用能力，但**绝大多数不该唤醒**。它们不服务于「本机执行代码」这个目标。
2. 真正需要融合的只有一项：`containerized` 档。没有它，`pip install` 永远是死路，目标停在脚本级。
3. 不建议全面融合。合法配置组合会从 2 种膨胀到 12 种以上，每种都要独立验收；本项目的纪律是「跳过不算通过」，这意味着维护成本非线性上升，而收益为零。

除此之外还有一件比融合更紧迫的事：**让接口和文档停止描述不可达的能力**。这不是新增，是对齐。

## 2. 审计方法

四步，均可复现：

| 步骤 | 做法 | 本次产物 |
|---|---|---|
| 配置字段使用面 | 正则匹配 `settings.<field>` 在 `src/`、`tests/`、`scripts/` 的出现位置 | 发现 `default_mode` 在 `src/` 内零引用 |
| 工具面实枚举 | 直接调用 `create_builtin_registry(...)` 取 `definitions()` | 统一面 13 个工具 |
| 端点与前端对照 | 提取 `@api.` / `@router.` 装饰器路径，与 `app.js`、`file-editor.js`、`index.html` 的调用点归一化后比对 | 全部端点在用，无孤儿 |
| 未使用代码 | `uvx vulture --min-confidence 60` | 3 处真实死代码 |

**方法局限，写下来避免下次高估结论**：

- macOS 自带 BSD grep 不支持 `\b`，用 `\b` 的词边界统计会**全部返回 0**。第一次统计就栽在这里。
- 只匹配双引号会漏掉单引号端点（`file_api.py` 大量使用 `'...'`），一次漏了 18 个。
- 前端 URL 常由 `base(space)+"/text"` 拼接，纯正则扫不到，会误判成孤儿端点。
- 静态扫描只看 `src/` 内部会漏掉 `tests/` 与 `scripts/` 的引用。上一轮据此判定 `context/environment.py` 等三模块为「469 行死代码」，实际它们仍被测试与诊断脚本使用，已全部恢复。

结论：**任何「未使用」判定都必须再扫一遍 `tests/` 和 `scripts/`，并人工核对字符串拼接。**

## 3. 三层入口模型

同一份代码，三个入口，能力逐层收窄。这是所有「写了没启用」现象的结构性原因。

| 入口 | 装配参数 | 说明 |
|---|---|---|
| 网页 `create_app` | `unified=True`、`process_stdin=False`、`versioned_files=True`、审批强制 `never`、沙箱强制 `isolated` | 唯一的产品入口，约束最紧 |
| CLI + 真实模型 | `unified=True`、`process_stdin=False`、`versioned_files` 默认 `False` | 审批、沙箱档位可配，但 `unified` 仍要求 `isolated` |
| demo / 测试 `create_demo_runner` | 不强制 `unified`，`single_face` 或 `work_only` 二选一 | 能力最全，`process_stdin` 默认为 `True` |

两个生产入口的工具面相同，均为 **13 个**：

```
read_file  write_file  edit_file  apply_patch  create_directory
list_dir   glob        grep
exec_command  run_tests  process
read_artifact  create_file
```

`web_access=deepseek` 时再增 `web_search`、`web_fetch`（默认 `off`，不注册）。`echo` 只由 demo 路径注册。

## 4. 写好了但没启用

### 4.1 被门禁挡死：代码在，永远走不到

| 能力 | 规模 | 挡点 |
|---|---|---|
| 逐次人工审批全链 | 实现约 **550 行**（`tools/policy.py` 90 + `tools/approvals.py` 143 + `storage/approvals.py` 175 + `migrations/0014` 33 + web 约 60 + 前端约 45）；测试 423 行另计 | `tools/scheduler.py:295` 调用 `requires_approval`，其第一行 `if self.mode == "never": return False`（`tools/policy.py:82`）；网页侧 `config/__init__.py:83`、`web/policy.py:6`、`web/policy.py:27` 三处断言强制 `never` |
| 沙箱 `off` / `workspace-write` | `sandbox.py` 两套策略生成分支 | 网页由 `validate_web_settings` 限死 `isolated`；CLI 真实模型走 `unified=True`，而 `bootstrap.py:58` 要求 unified 必须 `isolated`。两档只剩 demo 与单元测试可达 |
| `execution_profile=configured` | 全部非 trusted 路径 | `web/policy.py:7` 第一个条件即 `settings.trusted_development`，`configured` 直接抛错。对网页**完全不可用**，只对 CLI 有效 |
| 只读代码档 `writable=false` | `tools/builtin.py:69` 的 `readonly_code` 分支、`ProcessTool` 动作裁剪 | 与 `trusted_development` 互斥（后者要求 `sandbox_writable=true`），网页只认 trusted |
| `process_stdin=True` | `ExecCommandTool` 的 stdin 分支、`ProcessTool` 全动作 | 网页与 CLI 真实模型都显式传 `False`，只有 `create_demo_runner` 默认 `True` |

### 4.2 实现完整，但一个入口都没有

**任务状态（`TaskState`）** 是一条完整的链，却没有任何产品入口：

| 环节 | 位置 | 状态 |
|---|---|---|
| 表 | `migrations/0003_sessions.sql`（并在迁移中为既有会话初始化） | 存在 |
| 领域对象 | `domain/sessions.py:56` | 存在 |
| 仓储 | `storage/repositories.py:227`、`:282` | 存在 |
| 加载 | `agent/runner.py:278` | 每个 run 都读 |
| **注入系统提示** | `context/builder.py:233` `_state_section` | **每次模型请求都生效** |
| 网页端点 | 无 | **缺失** |
| 模型工具 | 无 | **缺失** |
| 文档 | `docs/` 零提及 | **缺失** |
| 唯一写入口 | `python -m chagent.sessions state <uuid> --set-json '{...}' --expected-revision N`（`sessions/__main__.py:43`） | 独立 CLI，非产品路径 |

结果是：**每次请求都在读一份用户几乎无法写入的状态**。这是全部发现里最矛盾的一处。

**`SessionManager.set_mode`**（`sessions/manager.py:55`）同理：方法齐全，`src/` 内零调用方；网页 `PATCH /api/sessions/{id}` 只接受 `title` 与 `archived`。

### 4.3 配置被读了，但读到的是死路

| 项 | 实际情况 |
|---|---|
| `default_mode` | `src/` 内**零引用**。`.env.example` 有 `CHAGENT_DEFAULT_MODE=work`，`schemas.py` 有两处，`web/app.py` 硬编码一个 `"work"`，但没有任何逻辑读 `settings.default_mode` |
| `enabled_modes` | 仅被 `domain/sessions.py:11` 的一条注释提到 |
| `code_workspace_writes` | `web/app.py:573` 传入 `configured.trusted_development`，但 `bootstrap.py:75` 的三元分支要求 `mode == "code"`，而 `unified` 下 `modes=("work",)`，条件永不成立 |
| `readonly_code_available` | 只在 `diagnostics/behavior.py:39` 拼一行日志字符串 |
| `approval_allowlist` | 随审批策略一起不可达 |

### 4.4 默认关闭，但一行可开（设计如此，不算遗留）

`web_access=off` → `web_search` / `web_fetch` 不注册。这是有意的静默裁剪，改一行 `.env` 即可。

## 5. 结构冲突

按「是否会导致误解」排序，而非代码量。

**5.1 `/api/info` 与自己矛盾**

`web/app.py:75` 与 `:105` 硬编码 `"code_mode": False`、`"default_mode": "work"`。但 `validate_web_settings` 要求 `code_mode=True` 才能启动。**接口报告的与它刚校验通过的相反。** 前端若据此判断，会隐藏真实可用的能力。

**5.2 文档承诺了三个不可达能力**

| 文档 | 承诺 | 实际 |
|---|---|---|
| `网页对话设计.md:103` | 详细描述 `CHAGENT_APPROVAL` 非 `never` 时的审批卡片、`approval_requested` 事件、`waiting_for=approval` 投影 | 网页启动即拒绝该值 |
| `设计总览.md:9` | 「满足 isolated、工作区禁写…可使用只读代码分析」 | 网页强制 `sandbox_writable=true` |
| `只读模式方案.md` | 整篇描述只读档，并记载「已完成只读验收」 | 当前网页入口取不到这一档 |

**5.3 同一组 7 个条件写了两遍**

`config/__init__.py:83` 与 `web/policy.py:7` 是逐字符相同的布尔表达式。改一处忘一处即不一致；且第一项 `trusted_development` 逻辑上已蕴含其余六项。

**5.4 `mode` 有五个定义源，三个已废**

`SESSION_MODES`（`domain/sessions.py:11`）、`Settings.default_mode`、`Settings.enabled_modes`、`Session.mode`、`SessionDetail.mode`。而 `SessionCreate` / `SessionEdit` 的 mode **字段已删除，注释还留着**：

```python
# web/schemas.py:32
#: Absent means the build's default mode. ``code`` in a work-only build is
#: refused with 409 rather than downgraded: the caller must know what it got.

class SessionEdit(InputModel):   # 下一行就是另一个类
```

这段注释描述的是一个不存在的字段，而这正是它自己反对的错误：「让调用方以为得到了什么」。

**5.5 两套「执行工具」集合**

`WRITE_TOOLS` / `EXECUTION_TOOLS`（`tools/builtin.py:36`、`:40`）管能力边界，`HOST_TOOLS`（`tools/policy.py:30`）管审批边界。`builtin.py:38` 的注释自己承认了这个分裂。审批不可达后，`HOST_TOOLS` 只剩 `policy.py` 内部一处使用。

**5.6 两套产物机制**

`generated_files`（`0017`，`create_file` 工具 + `GET /api/sessions/{id}/files`）与 `file_outputs`（`0019`，编辑器保存 + `/workspaces/{id}/outputs` 决策）。都在用，但「产物」一词指两件不同的事。

**5.7 断网叙事与实际出网并存**

`README.md:63` 已写明：网页工具运行在 agent 进程内，命令沙箱的断网不覆盖它。技术上正确，但若界面只显示「命令断网」，用户会形成「整机不出网」的错误印象。建议在 `/api/config` 的 `behavior` 行显式区分两个概念。

**5.8 真实死代码（3 处）**

| 位置 | 内容 |
|---|---|
| `models/http.py:135` | `raise` 之后的不可达语句 |
| `diagnostics/schema.py:23` | `keep_artifacts` 无调用方 |
| `documents/parsers.py:29` | `SUPPORTED_SUFFIXES` 未被引用 |

## 6. 为什么测试全绿却掩盖了这些

这一点必须单独说，因为它推翻了一个直觉判断。

`tests/test_approval_flow.py:50` 的构造方式：

```python
configured = policy or ApprovalPolicy.from_settings(Settings.from_env(
    {"CHAGENT_EXECUTION_PROFILE": "configured", "CHAGENT_APPROVAL": "untrusted", ...}))
runner = create_demo_runner(..., approval_policy=configured, ...)
```

测试走的是 **`configured` profile + `create_demo_runner`**，从未经过 `validate_web_settings`。所以：

- 审批链在测试里是**活的**，423 行测试真实执行并通过
- 审批链在网页里是**死的**，因为网页门禁是另一条路径

**「测试通过」证明的是「这段代码能工作」，不是「这个功能在产品里可用」。** 同理，`ExecutionProfile` 的 `configured` 分支、沙箱两档、`process_stdin=True` 都在测试与 demo 中被覆盖，但它们在生产入口不可达。

这不是测试写得不好——单测本就该测单元。问题在于**缺少一份「入口 × 能力」的对照表**，导致每次讨论都要重新翻代码。

## 7. 融合裁决

判据三条，不通过即不融合：

1. 是否服务于「本机执行代码闭环」
2. 是否有现存替代品（重叠则该删不该融）
3. 接回成本是否低于它带来的认知负担

| 类别 | 项 | 理由 |
|---|---|---|
| **该融合** | `containerized` 档 | 唯一挡住目标的能力。没有它，装依赖永远是死路 |
| **该对齐，不该融合** | 修 `/api/info`、`/api/config`；收敛 `mode` 五源与 `default_mode` / `enabled_modes` / `code_workspace_writes`；清理悬空注释 | 不增加能力，只让代码与描述一致 |
| **不该融合** | 审批接回网页、只读档接回网页、PTY/stdin、`TaskState` 可写 | 不服务目标；接回只增加配置维度，不增加可完成任务 |
| **该删** | 5.8 列出的三处 | 净负债 |
| **保持** | `web_access`、`TaskState` 只读注入 | 一行配置可开；注入本身没错，错在没入口 |

关于 `TaskState` 需要单独说明：它当前位于**提示缓存前缀**（`context/builder.py:219` 的注释明确要求该消息在一轮内字节一致）。这一位置假设它「run 内不变」。若改为模型可写，必须移出前缀、降级为消息，否则每次写入都会让下一轮全量缓存失效。**位置设计与「可写」存在结构性矛盾**，这也是不建议接可写入口的技术原因，而不只是「用不上」。

## 8. `containerized` 档

不放宽 `trusted-development`，另立 profile，因为两者语义不同：前者是「我相信这个账号」，后者是「我相信外层容器」。

```python
# config/__init__.py
execution_profile ∈ {"configured", "trusted-development", "containerized"}

if self.execution_profile == "containerized" and not (
    self.code_mode and self.allow_host_commands
    and self.sandbox_writable and self.approval == "never"
):
    raise ValueError("containerized 需要 code=on、宿主命令、可写工作区、approval=never；"
                     "网络由外层容器决定")
```

`sandbox` 保持三档不动，`containerized` 允许 `workspace-write` + `sandbox_network=true`。这样 `isolated and network` 互斥的规则完全不用碰，`sandbox.py` 一行不改。

**必须配套的自证**——这一档唯一不能省的东西：

```
Behavior: boundary=containerized (外置边界; 进程内无隔离) | gate=none | tools=13
```

三处冗余：启动横幅、`GET /api/info`、`GET /api/config`。理由：让「我已经离开 seatbelt」这件事无法被忘记。`isolated` 档保持现有的 `behavior=isolated (seatbelt; 14/14 checks passed)`。

**改动量估算**

| 文件 | 行数 |
|---|---|
| `config/__init__.py` | +15 |
| `web/policy.py` | +12 |
| `diagnostics/behavior.py` | +8 |
| `web/app.py` | +6 |
| 文档（本文件 + 执行边界契约） | +50 |
| 合计代码 | **约 90 行** |

比 `边界与门禁重构方案.md` 里的 P0 估算（约 200 行）少，因为不需要动沙箱、不需要动 `_tool_faces`、不需要动隔离探针。

## 9. 效果与边界

**能达成（可验证）**

| 场景 | 现在 | 融合后 |
|---|---|---|
| `pip install -r requirements.txt` | 沙箱拒绝（断网） | 通过外层容器联网成功 |
| `npm install` / `cargo build` | 同上 | 通过外层容器 |
| 完整跑真实项目测试 | 依赖预置齐全才行 | 缺什么装什么 |
| 合法启动组合数 | 1（trusted 的 7 项） | 2 |

**达不到（不会因融合而改变）**

- 仍读不到工作区外的其他项目（除非容器挂载）
- 仍无 PTY / 交互输入
- 取消后仍不回滚文件副作用
- 隔离强度**实际下降**：进程内 `deny default` 改为「靠容器兜底」。这是明确交换，不是免费升级

## 10. 为什么不建议全面融合

举一个数：全面融合后，`execution_profile × sandbox × network × approval × writable` 的合法组合从 2 种变成 12 种以上。

按本项目自己的纪律——「测试跳过不计通过」「合成 fixture 不计真实项目」——12 种组合意味着 12 次隔离验收，且每次都要在真实终端跑 `scripts/probe_code_isolation.py`。维护成本非线性上升，收益为零，因为实际只会用其中一种。

更根本的理由：**当前困境的成因是能力与入口错位，再融合更多能力只会加深错位。** 让「这个开关到底管不管用」更容易判断，比让更多开关能打开更有价值。

## 11. 落地顺序

| 序 | 内容 | 量 | 风险 |
|---|---|---|---|
| 1 | 修 `/api/info` 与 `/api/config` 的硬编码 | 约 10 行 | 无行为变更 |
| 2 | 加 `containerized` profile 与自证横幅 | 约 90 行 | 新增路径，`isolated` 零改动 |
| 3 | 概念收敛：删 `default_mode`、`enabled_modes`、`code_workspace_writes`，清悬空注释 | 约 30 行 | 纯收敛 |
| 4 | 文档补「入口 × 能力」对照表 | 文档 | 无代码风险 |

第 4 项看起来最虚，实际收益最高：它把「为什么这个开关没反应」从每次翻代码，变成查一张表。建议直接以本文第 3、4 节的表格为基础扩写进 `执行边界设计.md`。

## 12. 验收口径

- 第 1 项：`GET /api/info` 的 `code_mode` 必须等于 `Settings.code_mode`；新增断言，不复用硬编码。
- 第 2 项：`isolated` 路径的 `tool_calls` 写入序列与改动前逐条一致；`containerized` 档启动横幅必须出现，缺失即视为未完成。
- 第 3 项：全量回归与改动前基线一致（最近一次为 586 项、15 项环境跳过）；跳过仍不计通过。
- 全部完成后：在本机真实终端跑 `scripts/probe_code_isolation.py`，`isolated` 档须 14/14；`containerized` 档须显式声明「外置边界」，不得伪装成已隔离。

## 13. 与既有文档的关系
