# 第三步：工具批次调度与核心验收

日期：2026-10-28。状态：已实现，核心验收通过。

本批承接结束控制和 RunState，完成工具批次的有界并发、修改屏障、顺序提交及取消清理。仍保留单个 Runner、单个调用执行器和 PostgreSQL 审计链路，没有引入任务服务或通用 DAG 引擎。

## 调用链与职责

```text
AgentRunner：取得完整模型响应，校验调用 ID，保存响应
  → ToolScheduler：整批 queued 意图先提交
  → 连续 parallel 调用分组；其他调用各自形成独占屏障
  → 工作区读／写门控 + Runner 共用并发额度
  → start_tool_call 提交 running 状态
  → ToolExecutor：参数、权限、超时与结果校验
  → 具体工具执行／进度回调
  → 按模型调用顺序保存结果、消息与 tool_completed 事件
  → 提交成功后 append_committed 到 RunState
  → 整批完成，再决定下一轮模型或正常停止
```

`ToolScheduler` 位于 `src/chagent/tools/scheduler.py`。Runner 保留模型循环及结束决策；Executor 只负责单次调用，不承担批次顺序与数据库提交。工具实现仍不直接操作数据库。

### 并发与屏障

- 仅明确声明 `execution_mode="parallel"` 的工具允许重叠。内置 list_dir、read_file、read_artifact 和 echo 开启；write_file、edit_file 与默认未声明工具独占执行。
- `requires_host_execution=True` 一律独占，即使工具误标为 parallel。宿主开关仍由 Executor 检查。
- 按原调用次序分组：`读A、读B、写C、读D、读E` 执行为 `[A∥B] → C → [D∥E]`。写入前等待前组执行和结果提交，写入完成并提交后才开放后组。
- 同一个 Runner 中，所有会话共享并发额度，默认 4；`CHAGENT_MAX_TOOL_CONCURRENCY` 支持整数 1–32，设为 1 可关闭并行。CLI、Web、demo 均已接入。
- 同一规范化工作区的不同会话共享读／写门控：读取可并发，独占调用等待现有读组结束；有写入等待时不再接纳新读组。不同工作区可独立执行，仍受总额度限制。门控覆盖取消清理与结果保存，结束后移除空闲门控。
- worker 数量最多为该组宽度，窗口同时限制执行后尚未提交的结果数量。慢的第一个调用不会让后续整个批次全部启动并积压结果。已提交结果仍保留至批次返回，因此并非整个批次内存占用固定不变。

并发声明代表工具作者保证调用彼此独立。调度器不分析文件依赖或自动推断任意命令的安全性。当前门控只覆盖同一个 Runner、相同规范化根路径，不覆盖多进程、多个 Runner、外部编辑器或根目录不同但范围重叠的工作区。

### 确定的结果与取消语义

实际完成可以乱序，持久化结果、消息序列和 RunState 更新保持模型调用次序。后面的工具即使先完成，`tool_completed` 也可能等待前面的结果提交；这是当前确定性策略。

整批调用意图先在一个事务内保存，新增 `call_index` 表示模型响应中的次序。取消、超时或提交失败时：

| 调用情况 | 保存结果 |
|---|---|
| 已排队，尚未开始 | cancelled，发出 tool_cancelled |
| 已启动，未取得可保存的最终结果 | unknown，发出 tool_interrupted |
| 已取得最终结果，尚未保存 | 清理时尽量提交真实结果 |
| 结果提交正在进行 | 等待该事务结束，不因父任务取消而直接中断 |
| 提交失败或提交结果不确定 | 不重试该次保存、不重跑工具；未确认记录由 finish 标为 unknown |

单工具参数或执行错误仍返回错误结果，不取消其他独立调用。数据库故障与进度持久化故障会停止本批，等待 worker 清理，避免在错误后继续执行后续修改。运行终态沿用前两步的结束原因契约。

已完成的外部副作用不能因数据库回滚而撤销，unknown 也不等于“肯定未执行”。失败运行保持可审计，仍不自动作为正常历史重放。

### 文件读取与进度

只读文件操作移入线程，避免同步 I/O 阻塞事件循环。取消不会强制杀线程：必须等待已开始的读取退出再释放额度和工作区屏障。因此超时能返回错误，但返回时间可能超过配置值；阻塞 50ms、工具超时 10ms 的注入实验约 55.83ms 才完成清理。

修改文件目前继续同步执行，受文件大小上限和独占屏障约束；慢文件系统上的写入、fsync 仍可能阻塞事件循环，这是后续需要进一步隔离的部分。

`signal` 和 `on_update` 已从调度器经 Executor 传到工具。进度采用每次调用容量为 1 的最新预览队列，正文最多 2048 字符，密集更新可合并；最终结果不丢弃。进度协程在调用结束前清理，晚到回调被忽略。自定义工具应在事件循环线程调用回调。

网页显示等待、执行、进度、完成、取消及结果未知。这里只接通工具事件，没有改造逐文本增量写库或 SSE 轮询。

## 核心验收

使用真实 PostgreSQL，每个用例创建并清理临时 schema。完整测试 **140 项全部通过，15.17 秒**；其中本轮新增 17 项调度验收、1 项迁移验收。既有结束控制、RunState、上下文、记忆、工具、Web 等回归保留。

重点验证：

1. 并发实际重叠、额度上限、慢首结果下的窗口限制、原调用顺序回填。
2. 读组与修改屏障、宿主工具强制独占、并发额度跨会话共享。
3. 同工作区跨会话屏障；不同工作区可重叠；取消的读取线程退出前不放行写入。
4. 用户取消、运行总超时、已完成兄弟结果保留、排队调用取消，无遗留 worker。
5. 参数错误不取消其他工具；高频进度合并、晚到回调失效、进度保存失败时收敛。
6. 使用 COMMIT 阶段拒绝事务的 PostgreSQL 约束触发器：排队提交失败时工具不启动；结果提交失败时不重复调用或重试不确定提交。
7. 取消发生在结果提交期间时不丢掉已提交消息、不产生重复结果；并发设为 1 时顺序确定。
8. 迁移保留旧调用顺序并检查非负／非空序号、批次内序号唯一；迁移并发和幂等仍通过。

静态验证：涉及文件的 Ruff E4/E7/E9/F 检查、Python 编译检查、网页 JavaScript 语法检查以及 git diff --check 通过。未做人工浏览器视觉验收。

### 离线耗时对照

固定模型、真实 PostgreSQL、每组 5 次。三个工具各注入 20ms 延迟，两组使用同一份新调度器和持久化逻辑，仅并发额度不同：

| 场景 | 完整运行中位耗时 | 显式 SQL 次数 |
|---|---:|---:|
| 并发额度 1 | 76.31ms | 64 |
| 并发额度 4 | 38.47ms | 64 |

约 **1.98 倍**速度，整条链路耗时减少约 **49.6%**。这是可并行等待场景的控制实验，不代表所有任务或真实模型网络延迟都减半，也没有与 Pi／Codex 做同机比较。

可靠性有成本：新增 queued 意图事件及状态转换后，一次工具循环 SQL 从上轮 40 次增至 44 次，8 轮工具从 138 次增至 163 次。128 个文本增量仍需 281 次 SQL，逐增量持久化瓶颈依然存在，应由第四步事件合并／订阅改造处理。

原始数据：[离线诊断 JSON](diagnostics/main-path-step3-2026-10-28.json)。各场景耗时不宜与同时段的其他机器负载直接比较。
