# 运行与工具调度

一次运行从创建记录开始，到写入终态结束。这个文件说明三件事：运行怎么结束、运行状态怎么推进、一批工具调用怎么执行与提交。三者共享同一条 PostgreSQL 事务边界。

宿主主控入口仍按 run 管理一般工具，但网站由 `site` 独立管理，进程跨 run 存活，状态写入 `workspace_services` 并可重新核对容器内状态。`host_exec` 需同一 run 更早模型轮次的成功容器命令或测试，网页批准按精确参数一次消费，原生执行记录写入 `native_executions`。宿主交互 stdin、每次写入单独审批与重启/未知结果已有真实记录（[验收第 16 节](验收记录汇总.md#16-宿主原生交互-stdin-与重启未知演练2026-11-05)）；审批等待由 PostgreSQL `LISTEN/NOTIFY` 唤醒，跨进程决定实测 13.5 ms 到达，1 秒的重读只是丢失通知时的恢复上界（[第 25 节](验收记录汇总.md#25-跨进程审批唤醒1c2026-11-05)）；被批准的调用在工具结果首行写明审批事实与用户备注，模型据此如实陈述（[验收第 18 节](验收记录汇总.md#18-模型侧审批反馈2026-11-05)）；下文旧 `process` 规则是容器主控历史契约。详见[宿主执行方案](宿主执行方案.md)。

## 1. 结束原因

`runs.end_reason`、终态事件的 `payload.end_reason`、成功返回的 `RunResult.end_reason` 必须是同一个值；失败路径通过 `RunFailedError.end_reason` 暴露。`terminal_reason()` 校验状态与原因匹配，数据库约束再兜一层。

| 情形 | status | end_reason |
|---|---|---|
| 模型正常结束且无工具调用 | completed | `model_stop` |
| 整批工具都要求 terminate | completed | `tool_requested_stop` |
| 本地 `/remember` 命令命中并写入成功 | completed | `explicit_memory` |
| 用户／宿主取消 asyncio Task | cancelled | `user_cancelled` |
| 模型返回 aborted | cancelled | `model_aborted` |
| 达到模型循环上限 | failed | `turn_limit` |
| 同一次尝试内重复被拒绝的调用 | failed | `repeated_tool_call` |
| 全局运行超时 | failed | `run_timeout` |
| 必须保留的上下文超预算 | failed | `context_budget_exhausted` |
| 模型输出截断 | failed | `output_limit` |
| 供应商返回错误 | failed | `model_error` |
| 缺少终结事件等流协议错误 | failed | `model_protocol_error` |
| 可识别的数据库／连接池错误 | failed | `storage_error` |
| 其他未分类执行异常 | failed | `execution_error` |
| 所有者失联，租约被扫描回收 | interrupted | `owner_lost` |
| 迁移前无法追溯的旧记录 | — | `legacy_terminal` |

`completed` 只表示运行正常停止，不代表用户的现实任务已经完成。

**哪些结束进入下一次运行的上下文**：默认只有 `completed`。例外是 `turn_limit` 与 `repeated_tool_call`——两者都在 `execute_batch` 返回之后才抛出，工具结果已提交并与调用配对，没有半个批次，所以可以安全回放。其余失败仍只留在记录里可查、不回放，因为它们可能停在"模型要了工具、结果还没写"的位置（`ConversationRepository.messages`）。

这条例外是补偿性的：触顶后不回放，下一次运行只能看到恢复事实清单（哪些文件改过），读过的内容和做过的判断全部丢失，于是它重读一遍、再撞一次同样的上限。

`explicit_memory` 是唯一不经过模型循环的正常结束：命令在 `_load_state` 之后被识别，确认文本由 `save_notice()` 落库（没有 `model_calls` 行可挂，但仍走同一道所有权门），因此这类运行没有模型调用，也不采集环境快照。判定条件与三条回退路径见[长期记忆设计](长期记忆设计.md)与[实施记录](实施记录.md) 第 14 节。

所有权与收敛：运行带 30 秒租约，执行期间每 5 秒续租；事件、模型与工具写入、终态和摘要都在同一事务内校验令牌。租约过期由常驻进程每 5 秒扫描（新运行启动前也扫一次），把运行置为 `interrupted/owner_lost`，进行中的工具置 `unknown`、排队工具置 `cancelled`。取消时若所有权已经丢失，运行保持 `running` 交给扫描器，不写入 `cancelled`——不能证明所有权就不宣布终态。细节见[实施记录](实施记录.md) 第 3 节。

### 工具正常停止的返回契约

```python
RunResult(
    run_id=...,
    session_id=...,
    message=None,                      # 没有伪造助手消息
    end_reason="tool_requested_stop",
    tool_results=[实际保存的工具结果消息],
)
```

继续沿用 Pi 的规则：整批结果都 `terminate=True` 才正常停止，混合批次继续；单个工具错误仍作为结果交回模型。工具正常停止的运行没有最终回答，因此不会被自动记忆提取入队（显式 `/remember` 照常写入），见[长期记忆设计](长期记忆设计.md)。

## 2. RunState

运行实际持有的是 `RunState`，不是每轮重建的上下文对象：

```text
run_id、session
history（已提交、可进入上下文的消息）
task_state、summary
environment（可选保留字段；当前 Runner 不自动采集或注入）
iteration、active_model_call_id
context_revision
tools、tool_revision
```

- 开始运行时加载一次会话信息、历史、任务状态与可用摘要；下一轮直接用活动视图，不从数据库重读整段会话。
- 模型响应与工具结果用 `INSERT RETURNING` 取得真实消息 ID／sequence，**先提交事务再返回**，Runner 收到后才 `append_committed`。
- 消息内容通过 codec 建立独立快照，不与适配器的可变 partial 对象共享内存。
- 摘要保存成功后更新 `state.summary`；工具集合变化时 `tool_revision` 递增，下一轮重新生成声明。
- 任务状态在运行中禁止修改，因此按运行复用；记忆不缓存，因为用户可能在运行期间审核或编辑。

结束、失败、超时与取消都会清理 `_states`、`_tasks` 与上下文管理器的 run 级缓存；不同会话并发运行各自持有独立 RunState。

### 运行预算与轮次提示

`RunBudget`（`agent/budget.py`）是这次运行唯一的时间闸门，默认 600 秒，只计模型轮次与记账：

- **工具执行期间暂停**。一次 Maven 构建的等待不是模型在思考；旧实现把工具时间也算进 180 秒，一次 129 秒的构建就吃掉七成预算。调度器在每个工具执行前后 `pause`／`resume`。
- **暂停是计数的**。并行批次里多个工具同时在跑，布尔开关会让第一个完成的工具提前恢复计时。人工审批也可以嵌套在同一段暂停里。
- **暂停仍有上限**。单次连续暂停不能超过一个运行预算，超过即按 `run_timeout` 结束——否则一个永不返回的工具会让运行永远挂在"运行中"。审批例外：它已有 `approval_timeout` 兜底，用 `pause(capped=False)` 不受这个上限约束。
- **整轮墙钟上限**。`CHAGENT_RUN_WALL_TIMEOUT` 默认 3600 秒，从 run 开始到结束持续计时，审批等待与工具执行都计入；到期按 `run_timeout` 终止。活动预算仍可暂停。网页配置分别显示“活动时间上限”和“运行墙钟上限”。

轮次上限（`CHAGENT_MAX_TURNS`，默认 32，上限 128）之外，模型每轮还能拿到一条**进度提示**（`agent/turn_note.py`）：

- 形如 `[turn 12/32] Harness progress note, not a new request. 20 turns remain.`，过半追加"用更大步、别重读"，到 80% 追加"停止探索、做完并说清没做完的部分"。
- 它作为尾部的普通 user 消息加入请求，**不进 system**（system 是缓存前缀，每轮改写会让整段缓存失效），也**不落库**（它描述的是本次调度，回放旧计数会变成假的）。
- 若加进去会超过输入预算，这条提示直接丢弃——提示不值得让请求被供应商拒绝。第一轮不发：那时没有可附着的工具结果，模型也还没进入任务。

## 3. 工具批次调度

```text
AgentRunner：取得完整模型响应，校验调用 ID，保存响应
  → ToolScheduler：整批 queued 意图先提交（含 call_index）
  → 连续 parallel 调用分组；其他调用各自形成独占屏障
  → 工作区读／写门控 + Runner 共用并发额度
  → start_tool_call 提交 running
  → ToolExecutor：参数、权限、超时与结果校验
  → 具体工具执行／进度回调
  → 按模型调用顺序保存结果、消息与 tool_completed
  → 提交成功后 append_committed 到 RunState
  → 整批完成，再决定下一轮模型或正常停止
```

`ToolScheduler` 在 `tools/scheduler.py`；Runner 保留模型循环与结束决策，Executor 只负责单次调用，工具实现不直接操作数据库。

### 并发与屏障

- 只有声明 `execution_mode="parallel"` 的工具允许重叠：`list_dir`、`read_file`、`read_artifact`、`grep`、`glob`、`web_search`、`web_fetch`（`echo` 同为并行，但只在演示与探针路径注册）。`write_file`、`edit_file` 与未声明的一律独占。
- `requires_host_execution=True` 强制独占，即使误标为 parallel；宿主开关仍由 Executor 检查。
- `web_search`／`web_fetch` 是第一批**不出进程也不占工作区**的联网工具：不参与工作区门锁，可以和文件读取同批并行；它们自己的边界在 `tools/web.py`（私有地址拒绝、体积上限、超时），不在调度器。
- 按原调用次序分组：`读A、读B、写C、读D、读E` 执行为 `[A∥B] → C → [D∥E]`。写入要等前一组执行并提交完毕，后一组才开放。
- 同一 Runner 的所有会话共享并发额度，默认 4，`CHAGENT_MAX_TOOL_CONCURRENCY` 支持 1–32，设为 1 关闭并行。
- 同一规范化工作区的不同会话共享读／写门控：读并发，独占调用等待现有读组结束；有写入等待时不再接纳新读组。不同工作区可并行，仍受总额度限制。门控覆盖取消清理与结果提交，结束后移除空闲门控。
- 窗口同时限制"执行完但未提交"的结果数量，慢的第一个调用不会让整批结果全部积压。

并发声明是工具作者的承诺：调度器不分析文件依赖，也不推断命令安全性。门控只覆盖同一个 Runner、相同规范化根路径，不覆盖多进程、多个 Runner 或外部编辑器。

### 确定的结果与取消语义

执行可以乱序，持久化结果、消息 sequence 与 RunState 更新一律按模型调用次序。

| 调用情况 | 保存结果 |
|---|---|
| 已排队，尚未开始 | `cancelled`，发 `tool_cancelled` |
| 已启动，未取得可保存的最终结果 | `unknown`，发 `tool_interrupted` |
| 已取得最终结果，尚未保存 | 清理时尽量提交真实结果 |
| 结果提交正在进行 | 等待该事务结束，不因父任务取消而中断 |
| 提交失败或结果不确定 | 不重试保存、不重跑工具；未确认记录由 `finish` 标为 `unknown` |

已完成的外部副作用不会因数据库回滚而撤销，`unknown` 也不等于"肯定没执行"。

### 文件读取与进度

所有文件工具（读、写、编辑）都通过 `asyncio.to_thread` 在线程中执行，避免同步 I/O 和编辑失败时的相似度搜索阻塞事件循环。取消不会强杀线程：必须等已开始的调用退出再释放额度与屏障，因此超时能返回错误，但返回时间可能超过配置值（注入 50ms 阻塞、10ms 超时的实验约 55.8ms 完成清理）。写入之间的串行由工作区门保证，不依赖事件循环的执行顺序。

进度采用每次调用容量为 1 的最新预览队列（正文最多 2048 字符），密集更新可合并，最终结果不丢弃；晚到的回调被忽略。

### 重复调用与无进展

每次尝试内对 `(工具名, 规范化参数)` 计数：第 3 次相同调用不再执行，而是一个普通工具错误，附带上次结果摘要与“换方案”的指令。`read_file` 按 `(path, offset, limit)` 识别，其余工具按全部参数识别，所以同一文件的两处不同编辑是两个调用。

成功的工作区变更会开启新的尝试：`write_file`／`edit_file`／`apply_patch`（声明为 `mutates_workspace`）成功后计数清零。这是 H 批实测要求的区分——“改动前后各跑一次同一套测试”是验证，“原地重跑”才是循环。模型收到拒绝后仍然重复同一调用，运行以 `repeated_tool_call` 结束，而不是耗尽 `max_turns`。

阈值是模块常量 `tools/progress.py:REPEAT_LIMIT`（第 3 次拒绝），置 0 即关闭；拒绝不产生 `tool_started` 事件，工具行直接以 `failed` 收尾，`details.repeated` 记录计数与签名哈希。

### 会话进程与调度的边界

带 `yield_time_ms` 的 `exec_command` 会把子进程交给本 run 的 `ProcessManager`，调用本身随即结束。因此调度器保证的是**调用**的顺序与结果：`process` 与 `exec_command` 都声明 `requires_host_execution`，永远串行，同一批次里不会有两个写 stdin 的调用竞争。它不保证**进程**的生命周期——

- 门锁在调用返回时释放，仍在跑的会话进程可以与后续文件工具重叠，与「终端挂着跑、人继续改文件」一致。
- 进程表按 `run_id` 归属，`process` 只看得见本 run 的 id；另一个 run 的 id 与不存在的 id 返回同一个错误。
- `AgentRunner` 在写终态之前调用 `terminate_run`，正常结束、取消、超时、失败四条路径都会 `killpg` 本 run 的进程组，不遗留服务。
- 进程是否执行完成与工具的 `unknown` 语义无关：`unknown` 描述的是「这次调用有没有拿到可保存的结果」，会话进程的存活状态只由 `process` 的 `read` 报告。

## 4. 事务边界与故障语义

关键提交都在 PostgreSQL 事务内完成，事件与状态同事务：

- 模型响应提交失败：消息与 `model_completed` 回滚，RunState 不前进，下一轮不继续。
- 工具结果提交失败：工具消息、产物与 `tool_completed` 回滚，RunState 不加入不存在的结果，该调用最终为 `unknown`。
- 运行完成提交失败：`run_completed` 回滚，调用方拿不到成功结果，随后以 `storage_error` 写入失败终态。
- 运行失败后，已经提交的工具结果不会随历史回放，但会以宿主注记进入下一次上下文；未确认的调用标为 unknown（见[实施记录](实施记录.md) 第 4 节）。

每个受保护写入在同一事务里只做一次所有权门校验：`check_owner` 校验 token、状态与租约并锁住运行行，同一事务内的事件插入依赖这把锁分配序号，不再重复加锁。终态写入与压缩调用把条件写进语句本身（`UPDATE ... WHERE owner_token = %s`、`INSERT ... SELECT FROM runs`），受影响 0 行即判定失权。见[实施记录](实施记录.md) 第 6 节。

这些分支的回归测试用 `DEFERRABLE INITIALLY DEFERRED` 约束触发器在 COMMIT 阶段拒绝事务，而不是在方法入口抛异常。

## 6. 边界

- 取消不能回滚已发生的文件写入或宿主命令副作用。
- 进程被强杀后，租约到期由扫描器收敛为 `interrupted/owner_lost`，进行中的工具置 `unknown`，新输入随即可用（见[实施记录](实施记录.md) 第 3 节）。迁移前遗留的、没有令牌的 `running` 记录不会被自动接管，升级时需要停机人工收敛。
- 文本按首片优先、20ms／4KiB 合并；64KiB 有界缓冲，取消时最多给 writer 2 秒清理预算，强杀不承诺保留未提交尾部。
- 合并后的事件先进入每运行的有界缓冲，每 100ms 或 64 条提交一次（见[实施记录](实施记录.md) 第 5 节）。任何业务写入与终态事件都会先排空缓冲，因此序号与入队顺序一致；强杀最多丢这 100ms 内未提交的增量。
- SSE 使用同进程提交后版本通知，按数据库游标追赶；通知丢失／跨进程写入由 1 秒查询兜底。详见[实施记录](实施记录.md) 第 2 节。
