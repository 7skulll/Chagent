## 1. 评审结论与合并决策

原方案的核心方向可用：策略由 Executor 收口、沙箱与审批分离、沙箱不可用时明确降级、审批持久化、关键事件先提交后通知。原示例存在下列实现风险，本版以修订规则替换，不能继续按旧伪代码实施。

| 原设计 | 问题 | 合并后采用 |
|---|---|---|
| 工作区内写入一律 allow | read-only 仍可写，违反配置含义 | 先判断写权限，再判断路径与授权 |
| full 下 untrusted 等同 on-request | 本来要逐次审批的操作被放行 | approval 策略独立于沙箱模式 |
| 三档 sandbox 同时当默认权限和绝对上限 | 审批“越过上限”语义矛盾 | 默认权限、宿主允许授予的最大权限分别定义 |
| S1 把区外写变成可读拒绝作为主要收益 | 现有 Executor 已把路径异常转为可读错误；真正缺少的是统一权限规则 | S1 验收只读与有效权限，不把已有错误转换算作新增能力 |
| 工作区外写批准后执行原文件工具 | `WorkspaceFS.parts()` 仍会拒绝；改 root 又可能扩大授权 | 第一版文件工具保持工作区边界，不支持批准后任意区外写 |
| 只按 `(workspace, mode)` 缓存 profile | 不同网络、临时目录或读取权限可能误用旧 profile | 按完整有效权限与后端版本缓存 |
| 审批等待后才延长 timeout | 等待期间原 deadline 已可触发，补时间太晚 | 等待前暂停活动预算，返回后恢复剩余预算 |
| 在现有 execute 内直接等待审批 | Scheduler 外层已持有额度与工作区门控；可能长时间阻塞其他会话 | prepare/审批先完成，再获取执行资源 |
| future 创建晚于审批入库 | 快速批准可能发生在 waiter 注册之前 | 先订阅通知，再查库与等待，数据库为准 |
| 每个 run 一个事件队列 | 多连接会竞争消费，或慢连接反压发布；补历史后再订阅也有窗口 | 提交后版本通知 + 持久游标追赶 |
| 按启动时间终结所有旧运行 | 无法证明其他进程已死亡 | 所有权 token、租约到期与事务内收敛 |
| 任意执行失败后无沙箱重试 | 命令可能先修改文件再失败，重试重复副作用 | 第一版关闭 on-failure；未来按尝试审计、显式确认重试 |
| deny profile 的 true 退出 0 即可宣称支持 | 只能证明能启动，不能证明限制确实生效 | 探测实际允许／拒绝行为，并单独验收目标平台 |
| full + never 等价于所有旧配置 | 还取决于命令注册、网络、路径及环境规则 | 使用明确兼容配置；不宣称单个组合复现全部旧行为 |

原文记录了本机限制性 sandbox-exec profile 失败，当时把它视为「该环境尚未验证可用」的证据。**2026-10-29 复测后更正：失败原因不是平台不可用，而是路径没有 realpath。** macOS 上 `/tmp` 是 `/private/tmp` 的符号链接，SBPL 按内核路径匹配，所以 `(subpath "/tmp/…/ws")` 连它自己允许的目录也放不进去。换成解析后的路径立即正常。这个坑与本节「profile 缓存必须包含实际根路径」是同一条规则的两种表现，§10.2 记录了完整复现。

## 2. 目标与威胁边界

目标是限制模型发起的工具调用，并让超出默认权限的动作有可审计的人工授权。不是隔离恶意 Python 插件，也不把审批当作 OS 沙箱。

- 文件工具在 Python 进程中执行，使用路径与权限检查；命令子进程由平台沙箱约束，两条路径必须遵守同一个有效权限模型。
- 默认不把“能读整个用户目录”当作必须功能。读取范围包含工作区与命令所需的运行时路径；扩展读取范围要明确列出并测试。若兼容模式允许广泛读取，必须明确不提供宿主文件保密性保证。
- 凭证目录、应用自身配置／状态和仓库控制路径需要单独规定读写权限。workspace-write 不自动意味着可以改写所有 `.git`、配置或凭证文件。
- 子进程采用经过筛选的环境，不默认继承模型 API Key、数据库凭证和代理凭证；正常任务需要哪些环境变量由宿主配置。
- 默认关闭命令网络权限。模型请求的是权限，最终执行权限由宿主配置与有效授权决定。
- `full` 或 unsandboxed 表示没有相应内核限制；若无法落实“网络关闭”，结果里必须如实标注，不能只靠配置文字宣称已经隔离。

## 3. 配置与第一版范围

### 3.1 三层权限

1. **默认权限**：`read-only`／`workspace-write`／`full` 是一次调用未经额外授权时的权限配置名称。
2. **可申请范围**：宿主决定能否申请工作区写、网络、受保护路径或无沙箱执行。禁止申请的能力，即使用户对某张审批卡点批准，也不能授予。
3. **本次授权**：绑定一个规范化调用与有限权限增量，不永久修改默认配置，也不赋予任意后续调用同样权限。

网络授权与文件写权限分别表达，不能用“安装依赖需联网”直接请求 full。工具参数中的理由不参与信任判断，只用于向用户说明。

### 3.2 配置建议

| 配置 | 第一版约定 |
|---|---|
| `CHAGENT_SANDBOX` | read-only／workspace-write／full；S 批只实现 off／workspace-write 两档，默认 off（不改变现有行为） |
| `CHAGENT_APPROVAL` | 先实现 never、on-request、untrusted；on-failure 明确拒绝配置，不能悄悄映射到其他模式 |
| `CHAGENT_SANDBOX_NETWORK` | 默认 false，独立于文件写模式 |
| `CHAGENT_ALLOW_HOST_COMMANDS` | 保留已有显式开关，默认仍 false；不因探测通过自动改变用户权限 |
| `CHAGENT_ALLOW_UNSANDBOXED` | 默认 false，表示宿主是否允许无沙箱执行；不等于自动批准某次执行 |
| 审批等待上限 | 初始 300 秒，独立于活动执行时间 |

可以在后续经平台实测后设计“受限命令默认启用”，本批不把沙箱探测结果与默认授权混在一起。

### 3.3 判定原则

| 动作 | never | on-request | untrusted |
|---|---|---|---|
| 在默认读取范围内读取 | allow | allow | allow |
| 默认 workspace-write 下普通工作区写入 | allow | allow | 每次 ask |
| 默认 read-only 下工作区写入 | deny | 显式申请且宿主允许时 ask | 宿主允许时 ask |
| 默认权限内 exec | allow，仍需注册与后端可用 | allow | 每次 ask |
| 超出默认权限但在宿主可申请范围内 | deny | 显式申请、说明理由后 ask | ask |
| 超过宿主硬性范围／无实现支持 | deny | deny | deny |

full 不跳过 untrusted 审批；never 不自动允许越界。普通工作区写入的权限检查要先于放行。

第一版 `read_file/list_dir/write_file/edit_file` 继续限制在会话工作区，路径检查沿用目录描述符与 no-follow 操作。工作区外文件工具请求直接拒绝并说明不支持，不展示“批准后可写”按钮。以后需要区外写入时，再实现限定到具体路径的文件访问能力，不能把 root 改成 `/`。

未知工具默认使用保守策略，不能因为名字像 read 就直接放行。能力类别由宿主注册的工具定义提供，模型不能修改。

## 4. 调用路径与最少新增对象

```text
Runner / Scheduler 到达一个可执行分组
  → Executor.prepare：参数、上下文、宿主开关、策略检查
      → allow：生成 PreparedInvocation
      → deny：生成未执行的错误结果
      → ask：持久化审批并等待（不持有执行槽或工作区门控）
  → Scheduler 获取额度与工作区门控
  → Executor.execute_prepared：重新校验所有权、授权有效期、参数及路径
  → 提交 tool_started，真正执行工具
  → 保存真实结果／产物，按原模型调用顺序推进 RunState
```

新增职责：

| 对象 | 职责 |
|---|---|
| `ExecutionPolicy` | 纯判定，输出 allow／deny／ask，以及请求的精确能力 |
| `PreparedInvocation` | 冻结规范化参数、调用指纹、有效权限与本次 grant 引用 |
| `SandboxBackend` | 能力探测与实际命令包装，报告可落实的限制 |
| `ApprovalBroker` | 创建／读取／决策审批，等待通知；不执行工具 |
| `RunBudget` | Runner 持有，管理活动预算及审批等待暂停 |

第一版可以把相关小数据类型放在 `domain/execution.py`，不需要每个对象拆成多层接口。

策略拒绝和用户拒绝是可交给模型的未执行结果；Broker／存储故障、所有权丢失与协议错误必须传播给 Runner 收敛，不能被 Executor 现有的兜底 except Exception 全部吞成普通工具错误。只有确认没有开始执行时，才能声称“未修改文件”；执行后失败继续沿用未知副作用语义。

### 4.1 与并发调度的关系

- 可能 ask 的调用按原调用次序独立分组；快速分类可保守返回“可能需要审批”，不做 I/O，也不解析 shell 字符串来证明安全。
- 只有实际到达该组时才发起审批，前组先执行并提交；不能提前批准整个批次中尚未到达的修改。
- 同一 run 等待审批时不再派发后面的组。不同 run 的审批分别管理，不能用一个全局审批锁阻塞整个服务。
- 等待不占并发槽、不持有工作区锁、不占数据库连接。lease 心跳与取消继续运行。
- 获批后重新获取资源并复核条件。审批展示写入时应绑定目标的现存版本或“不存在”状态；即使模型没提供 expected_sha256，也不能忽略等待期间的变化。版本冲突返回冲突并重新准备，不能套用旧批准覆盖新内容。文件检查在 Executor 准备阶段完成，纯策略分类本身不做 I/O。
- 工具只有真正开始执行才记 tool_started；等待审批期间保持 queued，并通过审批行解释等待。拒绝可从 queued 直接保存未执行错误结果，结果必须标明 execution_started=false。

现有 Scheduler 在外层获取 gate、worker 在 slot 内调用 Executor，因此不能只给 `_groups()` 加一条 may_ask 就算完成审批支持。

## 5. 沙箱后端与降级

### 5.1 后端契约

后端接收实际 argv、cwd、有效权限、临时目录与环境，输出包装命令及可审计的执行配置。策略只决定允许的能力，不能把任意模型参数直接拼成受信任 profile。

macOS 的 seatbelt、Linux 的 bwrap 是候选后端，本文不提供可直接宣称安全的通用 profile。实现时要按目标系统验证运行所需的读取、进程和网络权限。

探测至少使用合成工作目录与独立的区外临时文件验证：

1. 普通命令能够启动。
2. workspace-write 可以写允许目录，不能写指定禁止路径。
3. read-only 对工作区写入确实拒绝。
4. 需要网络关闭时，用受控本地测试服务验证访问被拒绝，不依赖公网服务。
5. 配置要求的读取与受保护路径限制确实生效。

启动探测要有超时，记录耗时；不能预先承诺“只有 10ms”。探测结果按后端和权限能力记录，而不是一个适用于所有模式的 available 布尔值。

profile／命令模板缓存必须包含实际根路径、模式、读取范围、写入范围、受保护路径、网络、临时目录和后端策略版本；SBPL 与 argv 分别使用正确的编码规则。

2026-10-29 本机实测结论：seatbelt 后端在 macOS 26.6.2 上可用，写隔离、网络关闭、定向禁读、子进程继承全部通过，且能在沙箱内真实跑通项目测试；**白名单式读隔离（全局 `deny file-read*` 加 allow 列表）不可用**，进程在 dyld 阶段 SIGABRT。因此读保护只能做黑名单。完整数据与 profile 形态见 §10。

### 5.2 不可用时

- 受限后端不可用且不允许 unsandboxed：**fail closed** —— 拒绝执行命令，绝不静默降级为无沙箱；文件工具继续按自身策略运行，网页明确显示命令能力不可用。要无沙箱必须是用户显式配置的选择，不能是探测失败的结果。
- 允许 unsandboxed：仍需匹配宿主配置和审批策略；不把用户选择 workspace-write 悄悄变成 full。
- 每次执行记录 backend、实际限制、网络状态、是否无沙箱、批准来源。请求的权限与实际执行的权限分别保留。
- 不回退整个服务，不修改用户全局配置。能力不足的路径要明确报“不支持”，不能用 mock 通过作为平台支持证据。

主进程工具、子进程和未来 ProcessManager 必须复用这些策略；不能让新命令入口绕过 Executor。

## 6. 审批持久化、唤醒与授权消费

### 6.1 记录内容

`approval_requests` 保存 run、tool record、执行 attempt、调用指纹、规范化 cwd／路径、请求权限、理由、策略版本、owner token、期限与决策信息。

第一版状态为 pending／approved／denied／expired／cancelled；增加授权消费时间或等价的消费记录。一个工具尝试最多一个 pending 请求，并对重复创建设置唯一约束。将来若支持重试，通过新的 attempt 区分，不以“允许问两次”为理由移除所有去重约束。

原工具参数的审计沿用 tool_calls；审批展示和普通日志应脱敏，优先引用原记录，避免重复扩散凭证。

### 6.2 无竞争窗口的等待

1. 注册审批通知订阅，再创建审批请求及 approval_requested 事件，提交后通知。
2. 读取持久化状态；pending 才等待版本变化或短周期兜底查询。
3. 批准／拒绝使用条件更新：只允许未到期 pending、匹配的活动 owner；决策与事件同事务，提交后唤醒。
4. Broker 被唤醒后重新读库，不把 future 的 bool 当作最终授权。
5. 过期与批准竞争依靠数据库条件更新决定，不能由两套内存计时器分别覆盖。
6. 执行前按调用指纹、owner、策略版本、grant 期限校验并消费 grant；参数改变、所有权改变或授权失效均不得执行。

重复决策返回冲突；取消后的批准不复活运行。数据库消费 grant 与外部执行不是同一事务：崩溃后可能需要标 unknown，不能因此宣称严格 exactly-once，也不能重放已消费授权。

审批 API 必须确认属于当前本地用户界面与正确工作区，检查 Origin／本地会话令牌等必要的请求来源约束；模型和工具没有自行批准接口。卡片展示实际命令／路径、有效权限差异与风险信息，理由只是说明，不是授权依据。

### 6.3 运行态

第一版保留 `runs.status=running`，API 根据 pending 审批投影 `waiting_for=approval` 与审批 ID，网页显示“等待确认”。这样活动会话索引、终态 CHECK 和现有取消逻辑无需为一个等待原因全部扩展。

不采用原文的 awaiting_approval 状态迁移。如果将来需要多种持久等待态，再统一设计，而不是每增加一种等待就改 RunStatus。

### 6.4 活动预算

审批是在当前 run 已排空前组且无其他本批执行的边界等待，暂停的是整个 run 的活动执行预算。

- 进入等待前记录单调时钟下的剩余预算，并禁用该活动 deadline（使用 reschedule(None) 或等价预算机制）。已过期的预算不能被暂停复活。
- 审批受独立等待期限约束。返回后以“当前时间 + 剩余预算”恢复，不能到 finally 才补已经触发的旧 deadline。
- tool timeout 仅覆盖实际工具执行，不覆盖人工审批、额度和门控等待。模型请求 timeout 保持独立。
- 用户取消、服务关闭与 owner 丢失不被暂停；心跳持续进行。
- 可配置总墙钟上限，防止通过反复审批无限延长运行；墙钟上限不因审批暂停。

### 6.5 重启与失败

审批上线依赖主运行所有权／租约。只清理 owner 已失效的运行及其 pending 审批；禁止按 started_at 或“服务刚启动”批量终结其他进程的运行。

审批拒绝／到期返回未执行的错误结果，模型可选择其他方案。取消或失联则取消 pending 审批并结束运行。第一版不从崩溃前的 pending 审批直接恢复执行，用户新运行重新请求。

## 7. on-failure 与扩大权限重试

第一版不实现 on-failure，配置时明确报暂不支持。

后续只有沙箱包装器能证明“目标命令尚未启动”的失败，才可能作为无副作用的重新发起；普通非零退出码、超时、无网络错误都不足以证明未修改文件。

如果允许用户主动重试已执行命令，必须展示前次结果及可能副作用，创建新的执行 attempt 与授权，保留两次审计；网络授权只增加网络权限，不默认移除文件限制。工具成功与已产生副作用的调用都不能自动重跑。

## 8. 事件通道与迁移

事件合并、首片提交、有界 writer、版本通知与 SSE 等待协议已按 A 批交付，实现与实测见[实施记录 第 2 节](实施记录.md)。不再实现每个 run 一个竞争消费队列。

合并窗口先用 20ms／4KiB，64KiB 缓冲；首片优先，定时刷新独立于新片段。60ms 仅作为性能实验候选，不同时维护两套默认规则。count 可以作为统计元数据，但正文正确性按 delta 拼接验收。

旧文 128 增量的 256 条语句仅描述两条事件 SQL × 128，不代表整条运行总 SQL；未来报告必须区分事件事务、事件 SQL、完整运行 SQL 与 SSE 查询次数。

迁移只追加，不预先固定 0010 的职责。按实际落地顺序先增加 owner／租约，再增加审批表及相关约束。审批第一版不增加 RunStatus，因而不需要重建 runs 状态 CHECK／活动索引。旧版本代码遇到审批表前，必须已停止新授权并清理活动等待，不能只靠批量 UPDATE 声称安全回退。

## 9. 验收矩阵

| 类别 | 核心通过条件 |
|---|---|
| 策略 | 只读拒写；full 不绕过 untrusted；never 不隐式提权；网络与文件权限独立 |
| 路径 | 区外、父路径、符号链接、受保护目录行为明确；审批不扩大 WorkspaceFS 根 |
| 后端 | 真正验证允许与拒绝；后端不可用时 fail closed；未验证平台不标为支持 |
| 沙箱 | 写不出工作区、连不上网、读不到 deny_read 中的任何一项；拒绝来自内核而非路径检查 |
| 沙箱继承 | 孙进程受同一约束；`killpg` 能回收整个进程组且不留孤儿 |
| 配置 | 保留命令显式开关；无沙箱行为可见；拒绝暂未实现的 on-failure |
| 审批 | 刚创建即批准不丢信号；批准／过期竞争；重复 POST；取消后批准；参数改变后不执行 |
| 预算 | 活动预算 0.5 秒、审批等待 2 秒仍可继续；工具预算不消耗在等待上；用户取消立即生效 |
| 资源 | 等待时不占 slot、gate 或数据库连接；另一会话可访问同工作区；授予后重验文件版本 |
| 所有权 | 双进程共享库时不误清理；旧 owner、过期 grant 不可执行或回写 |
| 审计 | 请求、决策、消费和实际执行可追溯；失败不重试未知副作用 |
| 入口 | CLI、Web 和直接工具入口使用同一策略；审批接口不能由非受信请求来源批准 |

CLI 交互模式可以本地询问；非交互模式遇到 ask 应明确返回无法取得批准，不无限等待，也不自动允许。真实链路使用合成临时工作区验证命令受限与模型收到拒绝后的处理；OS 测试与模型语义测试分开报告。

实施切片、统一顺序及性能验收见[下一阶段实施方案](下一阶段实施方案.md)。本轮修订设计与沙箱探测结论，没有执行数据库迁移、代码实现或新的供应商请求。

## 10. S 批实施方案（沙箱最小切片）

状态：2026-10-29 本机实测后定稿并实施。本节的 profile 形态、退出码、信号与回收行为均已在 macOS 26.6.2 上验证，交付结果与三处被实测修正的设计见[实施记录](实施记录.md) 第 15 节。

### 10.1 为什么先做这一批

上一版把沙箱放在审批（K）与持久 shell（J）之后。实测后建议提前，理由有三条：

1. **成本最低**：一个配置开关、约 150 行、两处 `wrap`、14 个测试，约一天。审批与持久 shell 各是数天量级。
2. **不依赖任何人**：沙箱是命令执行的包装层，与审批、与 `ProcessManager` 都不构成前置关系。
3. **做完之后 K 的紧迫性下降**：最坏情况从「宿主机任意执行」降到「能读写工作区、读不到密钥、连不上网、改不了区外」。审批解决的是「该不该允许」，沙箱解决的是「允了也做不出格的事」，两者不互相替代，但便宜的那一个该先上。

K 仍然是 J 的前置（持久 shell 会把「瞬时窗口」变成「常驻窗口 + stdin 通道」），这一点不变。

### 10.2 实测记录

| 探测 | 命令 | 结果 |
|---|---|---|
| 后端存在 | `/usr/bin/sandbox-exec` | 存在（102 KB） |
| `bwrap` | — | 不存在（Linux 专用） |
| Docker | `docker version` | 已安装，daemon 未启动；不作为本批后端 |
| 基线启动 | `(allow default)` + `/bin/sh -c 'echo'` | exit 0 |
| 工作区可写 | 写 `<ws>/.probe` | 成功 |
| 区外不可写 | 写 `$HOME/.probe` | `Operation not permitted` |
| 网络关闭 | `curl https://…` | `exit=6`（解析失败） |
| 网络关闭 | 连本地临时端口 | `exit=7`（连接被拒） |
| 定向禁读 | `ls ~/.ssh` | `Operation not permitted` |
| 孙进程继承 | `sh → sh → sh` 写区外 | 仍被拒 |
| **真实测试执行** | `python -m unittest tests.test_codec` | **Ran 2 tests, OK** |
| **白名单读隔离** | 全局 `(deny file-read*)` + allow 列表 | **SIGABRT，exit 134** |

最后一行是设计约束，不是待修 bug：`(deny file-write*)` 做全局拒绝是好的，唯独读不行，任何全局读拒绝都会让进程在加载器阶段就死掉，连 `/usr/bin/true` 都起不来。

### 10.3 三个已确认的坑

1. **SBPL 字符串必须带引号。** `(subpath /Users/x)` 报 `sandbox-exec: unbound variable: /Users/x`；`(subpath "/Users/x")` 正常。实现里必须有 `_sbpl()` 转义 `\` 与 `"`。中文路径无需特殊处理（已实测）。
2. **路径必须 realpath。** 见 §1 更正后的记录。`WorkspaceFS.__init__` 已经算好了 `self.root = logical_root.resolve(strict=True)`，直接用它生成 profile，不要用 `logical_root`。
3. **读保护只能是黑名单。** 见 §10.2 最后一行。

### 10.4 能力边界（必须如实写进 README，不能称「沙箱隔离」）

| 能做到 | 做不到 |
|---|---|
| 写只落在工作区与用户的私有临时目录 | 默认禁读、只放工作区 |
| 网络全关 | 读任意普通文件（`~/Documents` 里的东西照样能读） |
| 指定路径禁读（密钥目录） | 保护与工作区同树下的兄弟目录 |
| 子进程／孙进程同等继承 | 文件工具（Python 进程内）也进沙箱 |
| 拒绝来自内核，不是路径检查 | Windows／Linux（本机无 `bwrap`） |

准确的威胁模型陈述：**写隔离 + 网络关闭 + 密钥禁读，把「持久化后门」与「数据外泄」两条路径同时堵掉。剩下的最坏情况是「能读到普通文件，但送不出去，也改不了工作区与临时目录以外的任何东西」。** 这比 `allow default` 强很多，但不是「模型看不到你的文件」。

临时目录是一条必须说清的口径：`writable_tmp=true` 时剖面会放行整个 `$TMPDIR`（macOS 为 `/private/var/folders/<hash>/T`，同用户共享），否则大量工具会因无法写临时文件而失败。所以「写只在工作区」应读作「工作区 + 自己的临时目录」，不能写成「只能写工作区」。把 `writable_tmp` 改为 false 可以收紧到只写工作区，代价是部分工具会挂。

测试口径（Z0 起）：`test_sandbox` 在导入时用最小剖面跑一次 `/bin/echo`；跑不起来（例如嵌套沙箱里 `sandbox-exec` 返回 71）就把两个平台类整体 `skipped` 并写明退出码与首行 stderr，而不是留 8 项红让人当成回归。`test_descendants_inherit_the_profile` 先要求同一个剖面下普通命令能跑通，再断言后代写不出去——否则「所有命令都启动失败」会被读成隔离生效。跳过只说明这台机器上无法验证，不说明能力成立：上表才是能力的唯一依据。

### 10.5 profile 形态（实测通过）

```scheme
(version 1)
(allow default)
(deny network-outbound)
(deny file-write*)
(allow file-write*
  (subpath "<workspace realpath>")
  (literal "/dev/null") (literal "/dev/stdout") (literal "/dev/stderr")
  (subpath "/private/var/folders"))
(deny file-read*
  (subpath "<deny_read 每一项>"))
```

三处条件生成：`network=true` 时不输出 `deny network-outbound`；`writable_tmp=false` 时不输出 `/private/var/folders`；`deny_read` 为空时整行省略。

关于临时目录：只放行 `TMPDIR`（`/private/var/folders/**`，macOS 每用户私有），**默认不放行共享的 `/private/tmp`** —— 共享目录里的残留物可能被其他进程利用。这条做成配置项而不是硬编码，因为确有工具硬编码 `/tmp`。

不用临时文件：`sandbox-exec -p <profile>` 内联传递。`create_subprocess_exec` 传的是 argv 列表、不过 shell，因此没有引号注入面，也省掉一个 TOCTOU 窗口和一份清理逻辑。

### 10.6 模块

新增 `src/chagent/tools/sandbox.py`，约 150 行。

```python
@dataclass(frozen=True, slots=True)
class SandboxPolicy:
    workspace: Path                     # 必须是 realpath
    network: bool = False
    deny_read: tuple[Path, ...] = ()
    writable_tmp: bool = True

@dataclass(frozen=True, slots=True)
class SandboxSupport:
    available: bool
    backend: str                        # "seatbelt" | "none"
    checks: dict[str, bool]             # 六项探测各自结果
    detail: str = ""

class SandboxBackend(Protocol):
    name: str
    def wrap(self, argv: Sequence[str], policy: SandboxPolicy) -> list[str]: ...
    async def probe(self, policy: SandboxPolicy) -> SandboxSupport: ...

class DisabledBackend:   # CHAGENT_SANDBOX=off
    name = "none"

class SeatbeltBackend:
    name = "seatbelt"
```

三条实现约束：

- `SandboxPolicy.__post_init__` 必须 resolve 并去重 `deny_read`，并**剔除落在 workspace 子树内的项** —— 否则把 `$HOME` 之类误配进来会把工作区一起锁死。
- `SandboxBackend` 抽象现在就要留。`sandbox-exec` 是 Apple 弃用接口，移除后要换实现（Linux 上 `bwrap`），SBPL 不能写死在 `command.py`。
- profile 按 policy 缓存。workspace root、network、deny_read 都是 run 内常量，一次生成、全 run 复用。它不进提示前缀，因此不影响缓存不变量。

### 10.7 接入点：两处

| 位置 | 改法 |
|---|---|
| `tools/command.py` 的 `create_subprocess_exec` | `*backend.wrap(["/bin/sh", "-c", cmd], policy)` |
| `tools/tests_runner.py` 的 `create_subprocess_exec` | `*backend.wrap(argv, policy)` |

**不需要改的**：超时、取消、`killpg`、输出捕获、产物化、workspace 门控、调度器。理由已实测：`sandbox-exec` 会 **exec 替换**成子进程，PID 不变，`start_new_session=True` 的进程组语义与今天完全一致。

```text
kill 前: ['56914 Ss   /bin/sh', '56915 S    sleep', '56916 S    sleep']
kill 后: ['56914 Z    <defunct>']        ← 子进程立刻死光
wait 后: 空                               ← 由现有 communicate() 回收僵尸
```

这是「一天」而不是「一周」的原因：取消与回收路径零改动。

### 10.8 探测：六项

启动时对当前 policy 探一次，结果按**完整 policy** 缓存（不是一个 `available: bool`）。

```text
1. 普通命令启动        echo alive                 → exit 0
2. 工作区可写          写 <ws>/.chagent_probe     → 成功
3. 区外不可写          写 $HOME/.chagent_probe    → EPERM
4. 网络确实关闭        连本地临时端口              → 连接失败
5. 指定路径禁读        ls <deny_read[0]>          → EPERM
6. 探针清理            删除第 2、3 项产物          → 无残留
```

第 4 项必须用**本地临时端口**而不是公网地址：公网失败可能只是 DNS 问题，没有区分度；本地端口失败才证明 `network-outbound` 真的生效。探测总超时 3 秒（实测全套 < 1 秒）。

### 10.9 两条硬规则

1. **fail closed**：`available=False` 时 `exec_command` 直接返错，不执行。要无沙箱必须显式 `CHAGENT_SANDBOX=off`。
2. **如实记录**：工具 `details` 增加 `sandbox: {backend, network_allowed, denied_reads, unsandboxed}`，并写一条 `sandbox_applied` 事件（policy 摘要 + 探测缓存命中）。理由与 `environment_projected` 相同：将来要能回答「为什么这次能写那个文件」。

### 10.10 配置

| 配置 | 默认 | 说明 |
|---|---|---|
| `CHAGENT_SANDBOX` | `off` | `off`／`workspace-write`；默认 off 保证本批提交不改变任何现有行为 |
| `CHAGENT_SANDBOX_NETWORK` | `false` | 独立于文件写模式 |
| `CHAGENT_SANDBOX_DENY_READ` | `~/.ssh:~/.aws:~/.kube:~/.docker:~/.config/gh:~/.npmrc:~/.pypirc` | 冒号分隔；每项 resolve |
| `CHAGENT_SANDBOX_WRITABLE_TMP` | `true` | 放行 `$TMPDIR`；关掉后只能写工作区，但部分工具会挂 |

### 10.11 测试（`tests/test_sandbox.py` 18 项 + 链路用例 1 项）

纯函数 7 项，不需要真跑沙箱：`_sbpl` 转义 `"` 与 `\`；中文路径原样保留；`deny_read` 剔除 workspace 子树；`deny_read` 去重并 resolve；`network=False` 生成 `deny network-outbound`；`network=True` 不生成；同一 policy 生成的 profile 字节相同。

真实执行 7 项，`skipUnless(sys.platform == "darwin")`：命令能启动；工作区可写；区外不可写；网络关闭（本地端口）；指定路径禁读；孙进程继承；探测失败时工具返错且**没有**声称 `unsandboxed=false`。

最后一条是对 §5.2「不能用 mock 通过作为平台支持证据」的落地：跳过不等于通过。

### 10.12 沙箱与提示缓存

`exec_command` 的 description 随模式变化（实测 152 → 308 字节），而工具声明是提示前缀的一部分。

- **run 内恒定：P1 的不变量不被破坏。** 模式在进程启动时确定，一个 run 的所有轮次看到的 description 逐字节相等。
- **跳配置会换前缀。** 切换 `CHAGENT_SANDBOX` 会让同一个工作区的提示前缀整体变化，供应商侧的缓存对旧前缀失效。这不是缺陷，但要写清：把沙箱开关当成「每任务可切」的旋钮会持续丢掉缓存。
- **沙箱不往上下文里加任何东西。** `sandbox_applied` 是事件，`details.sandbox` 是工具结果元数据，二者都不进提示。

这条目前**只有推理，没有测量**：能算缓存复用的 `scripts/report_prompt_cache.py` 读的是主库，链路测试用一次性 schema，两边对不上，所以本批的 52.1% 无法归因。补测量口径列为 M2 批。

### 10.13 工作量、回退与本批不做

工作量约一天。回退是 `CHAGENT_SANDBOX=off` 一个开关，没有任何数据或迁移需要撤销。

本批明确不做：

- **文件工具进 OS 沙箱**：需要把 `WorkspaceFS` 操作挪进子进程，成本高一个量级，收益只是把已有的路径检查换成内核版本。现有 dirfd + `O_NOFOLLOW` 已经守住边界。
- **Linux 后端**：本机没有 `bwrap`，不写无法验证的实现，也不把未验证平台标为支持。
- **审批**：独立批次（K），不塞进本批。
- **Docker 后端**：`docker run` 约 1 秒启动开销、双命名空间路径翻译、`.venv` 符号链接跨不了容器、UID 映射与 bind mount 性能未知。Docker 的独占价值是「装依赖」，那属于 J，不是沙箱。
- **调高 `exec_command` 的 30 秒上限**：沙箱不解决工具超时，那是 J 的事。

## 11. K 批实施方案（审批最小切片）

状态：2026-10-29 已实施，368 项测试全过；实现、实测与边界见[实施记录](实施记录.md)第 19 节。本节只记录与 §3–§9 契约的对应关系，以及这一版**没有**做什么。

### 11.1 范围

第一版只回答一个问题：**模型要让宿主机执行一条命令时，谁同意。** 不引入新的权限层次，也不改沙箱：

| 契约 | 本版落地 |
|---|---|
| 策略在 Executor 之前判定 | `tools/policy.py:ApprovalPolicy`，纯函数、无 I/O，不解析 shell |
| 三种模式 | `never`（默认，行为不变）／`on-request`／`untrusted`；`on-failure` 直接拒绝配置 |
| `on-request` 的语义 | 只有**沙箱关闭**时才算越出默认权限；`workspace-write` 内不提问 |
| `untrusted` | 每个宿主机命令都问，除非命中 allowlist |
| allowlist | 按 token 前缀匹配；含 `; \| & < > `` ` `` $ ( )` 的命令永不放行 |
| 授权绑定与单次消费 | `(run_id, argv 摘要, cwd)` 指纹 + 状态机；`consume` 是条件更新，第二次必失败 |
| 等待不占资源 | 在获取并发槽、工作区门、数据库连接之前提问；每次轮询开一条短连接 |
| 活动预算 | `agent/budget.py:RunBudget` 在等待期间暂停，返回后按剩余时间恢复；已过期的预算不复活 |
| 运行态 | `runs.status` 不变，`GET /api/runs/<id>` 投影 `waiting_for=approval` |
| 拒绝语义 | 未执行结果标明 `details.execution_started=false`、`approval=denied`，并明确“这是策略而非失败” |
| 入口 | CLI 交互式询问（非 TTY 直接拒绝）；网页 `POST /api/approvals/<id>/decide`；两者都写同一条条件更新 |

### 11.2 审计与事件

`approval_requests` 一行一个尝试（`tool_record_id` 上的部分唯一索引保证最多一个 pending），事件 `approval_requested` → `approval_decided`／`approval_expired`／`approval_cancelled` → `approval_consumed` 与决策同事务提交。被拒绝的调用没有 `tool_started`，`tool_calls.status` 直接以 `failed` 收尾。

### 11.3 本版不做

- **`read-only`／`full` 两档沙箱模式**：S 批只实现 `off`／`workspace-write`，审批不替它补。
- **`CHAGENT_ALLOW_UNSANDBOXED` 与“申请更高权限”**：本版没有权限提升通道，只有“同意执行配置好的那个权限”。
- **文件工具的审批**：文件工具仍在 `WorkspaceFS` 边界内，不存在“批准后越界写”的路径。
- **`on-failure` 重试与 attempt 链**：显式拒绝配置，不悄悄映射。`approval_requests` 已预留 `tool_record_id` 维度，将来的重试以新 attempt 表达。
- **跨进程广播**：等待用同一进程的版本通知 + 250ms 兜底轮询；跨进程决策由轮询覆盖，延迟上限即轮询间隔。
- **独立墙钟上限**：只有会暂停的活动预算，没有“审批也不能拖过 N 分钟”的第二个上限；需要时可加，但本版不引入两套计时器。

### 11.4 验收

| 类别 | 结果 |
|---|---|
| 注入式拒绝 | 模型请求 `printf x > file` 且无人批准：文件不存在、无 `tool_started`、run 以 `model_stop` 正常收敛 |
| 授权不复用 | 批准命令 A 后，命令 B 仍产生新的 pending（`approval_requests` 两行、subject 不同） |
| 等待不阻塞 | 会话 A 等待时，会话 B 用同一 runner 完成 `read_file`；A 一旦批准即执行 |
| 预算暂停 | 运行预算 1.0s、等待 1.5s 后批准：run 以 `model_stop` 结束，不是 `run_timeout` |
| allowlist | `untrusted` + `printf` 前缀：无问题行、无 `approval_requested` 事件 |
| 陈旧授权 | 指纹不匹配的已批准 grant 无法消费，目标文件未生成 |
| 入口边界 | 其它工作区的 runtime 访问该审批得到 404；重复决策得到 409 |

## 12. J 批实施方案（持久 shell 最小切片）

状态：2026-10-29 已实施，全量 383 项测试（新增 15 项）；实现与实测见[实施记录](实施记录.md)第 20 节。本节只记录与 §3–§9 契约的对应关系、能力表，以及这一版**没有**做什么。

### 12.1 缺口

`exec_command` 的 `timeout_ms` 硬上限 30 秒，`ToolExecutor` 另有 35 秒调用上限，两者叠加的效果是：装依赖、长构建、交互式调试在当前形态下**不可能完成**。这不是「上限调小了一点」，而是「拿不到中间输出」——把上限调到 10 分钟只会让一次卡死更贵，所以本批不改上限，改的是「一次调用」这个单位本身。

### 12.2 形态

一次性调用保持原样；需要更久时由模型显式声明 `yield_time_ms`：

```text
exec_command(cmd, yield_time_ms=1000)  →  {process_id, 已有输出, running}
process(action='read', since=0, wait_ms=30000)  →  {新增输出, 下一个 since, 状态}
process(action='write', chars='y\n')  →  写 stdin
process(action='stop')  →  杀进程组
```

| 契约 | 本版落地 |
|---|---|
| 一次调用不再等于一次命令 | `tools/processes.py:ProcessManager` 持有子进程；`ManagedProcess` 是唯一句柄 |
| 归属 | 按 `run_id` 归属，`get(id, run_id)` 对其它 run 与不存在的 id 返回同一个 `None` |
| 上限 | 每个 run 同时 `CHAGENT_MAX_PROCESSES`（默认 4）个活进程；每个进程 `CHAGENT_PROCESS_TIMEOUT`（默认 600s）墙钟 |
| 输出 | 有界窗口（默认 1 MiB，可被 `max_output_chars` 收窄），按绝对游标读；被丢弃的前缀**计数并上报**，`since` 落在窗口之前时报 gap |
| 读取 | `read(since, wait_ms)` 有界等待，最多返回 20 000 字符；游标由调用方带回，因此同一段输出不会被读两次 |
| 写 stdin | 仅会话模式：一次性命令保持 `DEVNULL`，否则 `cat` 会挂死一次不 yield 的调用 |
| 终止 | `stop` 杀**进程组**（`killpg`）；run 结束、取消、超时都在 `AgentRunner` 的 `finally` 里 `terminate_run` |
| 沙箱 | 与 S 批同一层：会话进程跑的就是 `sandbox.wrap()` 之后的 argv，权限在 `spawn` 时确定，之后无法提升 |
| 审计 | `tools[:12]` 上限内新增一个 `process` 工具（当前 12 个），不新增表、不新增迁移 |

### 12.3 四条边界（必须如实写进 README，不能称「后台任务」）

1. **不跨进程、不接管。** 归属表在这个 Python 进程里；重启后旧 `process_id` 一律回答「不存在」，绝不按旧 PID 猜。跨进程接管需要 PID 复用校验与租约，本版不做。
2. **窗口有界。** 只保留最近 `window` 个字符，更早的输出被丢弃且被计数；`read` 会明确报 gap，而不是返回错位的字节。
3. **工作区门锁覆盖调用，不覆盖进程。** `exec_command` 返回后门锁即释放，正在跑的会话进程可以与后续文件工具重叠——和「终端挂着跑、人继续改文件」一样。它保护的是调度期的一致性，不是运行期。
4. **stdin 只在会话模式是管道。** 一次性命令的 stdin 是 `/dev/null`；会话进程的 stdin 是管道，`write` 不重复提问——它是在续写一条已经批准过的命令，不是新命令。

### 12.4 能力表

| 能力 | 现状 |
|---|---|
| 单次调用内的命令 | 与 J 之前完全一致（30s 上限、`killpg` 清理、`on_update` 预览） |
| 超过 30 秒的命令 | 可以：`yield_time_ms` 返回句柄，进程继续跑，分次读回 |
| 分次读输出并接续 | 可以：`since` 游标，最多 20 000 字符/次，gap 明示 |
| 交互式输入 | 可以：`write(chars)`，`close_stdin` 发 EOF |
| 主动终止 | 可以：`stop`，杀整个进程组（含孙进程） |
| 进程数上限 | 可以：每 run 4 个（可配 1..16），超限返回可操作的错误 |
| 墙钟上限 | 可以：`CHAGENT_PROCESS_TIMEOUT`，到时杀组并标注 `timed_out` |
| 重启后接管 | **不可以**：句柄只在启动它的进程里有效 |
| 跨 run 复用 | **不可以**：另一 run 的 id 与不存在的 id 不可区分 |
| PTY / 交互式终端 | **不可以**：没有 `termios`、没有窗口大小，`top`、`vim` 之类不可用 |
| 输出落盘归档 | 不新增：窗口之外的分页由 `read` 游标负责；工具结果层的产物化不变 |
| 后台守护 | **不承诺**：run 结束一律终止，不遗留服务 |
| Windows | **不支持**：`killpg` + `start_new_session` 是 POSIX 语义 |

### 12.5 本版不做

- **`unified_exec` 的完整形态**（Codex 6 915 行）：多终端、`shell_snapshot`、PTY、按需重连都不在本批。目标 ≤400 行，实际 447 行（含工具、注释与边界说明）。
- **跨进程唤醒与租约**：会话进程不写库，因此没有「另一个进程接管」的语义，也就不需要租约。
- **续写时的二次审批**：`write` 复用原命令的授权语境。若要更严，应把「会话建立」本身作为审批对象（K 已有 `(run_id, 参数指纹, cwd)`），而不是给每次写入加一个问题。
- **把工具结果直接产物化**：`read` 的 20 000 字符分页已经限制了上下文成本；工具结果层原有的产物化仍按原样工作。
- **并发写 stdin 的公平性**：同一 run 的进程工具是串行的（`requires_host_execution`），不存在两个 `write` 竞争同一条管道。

### 12.6 验收

| 类别 | 结果 |
|---|---|
| `long` 场景（45 秒命令） | 真实供应商下成功；分两次读回输出，退出码 0，结果文件生成 |
| 取消回收 | 取消后进程组不存在，孙进程也不写残留文件 |
| 活动进程上限 | 第二个会话进程被拒，错误提示 `process(action='stop')` |
| 一次性语义不变 | 无 `yield_time_ms` 时不进进程表，超时仍 `killpg`，`outcome_unknown` 仍为真 |
| 归属隔离 | 其它 run 读/停该 id 得到 `LookupError`，且提示里不含该 id |
| 输出窗口 | 窗口收窄后 `dropped > 0`，内容为尾部，并带 gap 说明 |

## 13. 出网边界：`web_search` 与 `web_fetch`（W 批）

状态：2026-10-29 已实施，全量 410 项测试（新增 27 项）；实现与实测见[实施记录](实施记录.md)第 21 节。

### 13.1 为什么它是一条独立的边界

S 批的沙箱约束的是 `exec_command` 派生的**子进程**：写不出工作区、连不上网。`web_search`／`web_fetch` 是 agent 进程内的 async 函数，不发子进程，所以 **seatbelt 对它们不生效**。这不是实现疏漏，而是能力本身的要求——要联网就必须有一个不受「断网」约束的通道。

因此出网必须有**自己的闸门**，且默认关闭：

```text
CHAGENT_WEB_ACCESS=off      默认。工具面 12 个，没有任何出网工具
CHAGENT_WEB_ACCESS=tavily   注册 web_search + web_fetch；缺 key 时启动即失败
```

一个开关管两个工具，因为「这次运行能不能上网」是一个决定，不是两个。开启但缺 key 在 `Settings.__post_init__` 里直接报错，而不是注册一个首次调用才失败的工具：配置错误应该在启动时暴露。

### 13.2 契约

| 契约 | 本版落地 |
|---|---|
| 闸门 | `CHAGENT_WEB_ACCESS`（`off`／`tavily`），默认 `off`；`Behavior:` 行与 `config show` 都显示实际值，key 只显示 `set`／`missing` |
| 凭据 | `CHAGENT_TAVILY_API_KEY`，字段 `repr=False`；只用于构造 `Authorization` 头，不进日志、不进事件、不进工具结果 |
| 搜索 | `GET`／`POST` 单次请求，`max_results ≤ 8`，单次渲染 ≤ 8 000 字符；超出截断并标注 |
| 抓取 | 单页 `GET`，响应体 ≤ 2 MB（流上截停），返回文本 ≤ 20 000 字符 |
| 重定向 | **不跟随**：3xx 返回目标地址，由模型决定是否再取，因此每次连接都重新过地址检查 |
| 地址 | loopback／RFC1918／link-local／ULA／multicast 一律拒绝；域名先 `getaddrinfo` 再判断，防 DNS 指向内网 |
| 协议 | 仅 `http`／`https`；带 `user:pass@` 的 URL 拒绝 |
| 内容类型 | 仅文本类（html／text／json／xml／csv）；图片、PDF 等直接报错 |
| 脚本 | 不执行 JS，不点任何东西。客户端渲染的页面会接近空——这是能力边界，不是缺陷 |
| 数据/指令 | 两份 description 都写明返回内容是数据而非指令；每条结果带来源 URL |
| 缓存 | 同一 run 内相同请求 5 分钟、最多 16 条；重复查询不再消耗额度，也让 I 批的重复调用判定更少误伤 |

### 13.3 四条边界（README 里不能写成「能上网了」）

1. **只读，不能登录。** 没有 cookie、没有会话、没有表单提交，付费墙与登录墙之后的页面拿不到。
2. **没有浏览器。** 不执行 JS、不渲染、不截图。SPA、无限滚动、`<canvas>` 内容基本取不到；要「看效果」需要截图能力，本批不含。
3. **搜索依赖第三方。** 换供应商要改 `WebSearchTool._post` 与响应解析；本版只实现 Tavily，因为它是唯一「一次调用就返回可读正文片段」的常见方案（省一轮）。额度用尽时返回 429 的可操作错误，不会静默降级到抓 HTML 搜索结果页。
4. **不是沙箱内行为。** 出网发生在 agent 进程，权限等同启动 Chagent 的那个用户；沙箱开着也无法阻止它——只能靠这个开关。

### 13.4 能力表

| 能力 | 现状 |
|---|---|
| 主动检索当前信息 | 可以：`web_search`，8 条结果＋摘录＋答案摘要 |
| 读取指定页面正文 | 可以：`web_fetch`，HTML 转文本，实体解码 |
| 时间敏感查询 | 可以：`recency` 取 `day`／`week`／`month`／`year` |
| 登录态页面 | **不可以** |
| JS 渲染 / 截图 | **不可以** |
| PDF / 图片内容 | **不可以**（明确报「不是文本」）。本地文件是另一条路：`read_file` 直接解析 PDF／Word／Excel，见[基础工具设计](基础工具设计.md) |
| 内网 / 本机地址 | **拒绝**（含 DNS 解析后落在私有段） |
| 关键词结果合并去重 | 不做：一次一个 query，模型自己改写 |
| 出网审批 | 不做：开关是进程级决定；若需逐次确认，应把 `requires_host_execution` 那套审批复用到 `web_*`，本批不含 |

## 14. Shell 可用性与约束强化方案（下一批）

J 批给出了「能跑超过 30 秒的命令」的形状，S 批给出了「写不出去」的形状，K 批给出了「停下来问人」的形状。三块都在，但拼起来仍然不是一个能用的 shell：任务会被 35 秒的调用超时截断，交互式程序因为拿不到 tty 直接不可用，装依赖因为断网必然失败。本方案不新增第四套机制，只把这三块补成一条完整的链路，并且把「约束」从审批挪回内核。

### 14.1 「可用」的定义

先给判据，否则容易做成「参数变多了」：

1. 能装依赖：`pip install` / `npm install` / `go mod download` 在不关闭沙箱的前提下完成。
2. 能跑长任务：一次测试或构建跑满 5 分钟，不返回 `Tool execution timed out`。
3. 能跑交互程序：`python` REPL、`psql`、`git rebase -i`、`ssh` 能启动、能输入、能 `Ctrl-C`。
4. 能开服务：`npm run dev` 起得来，下一次工具调用还能读到它的日志，能显式停掉。
5. 以上每一条都在沙箱里，不是靠用户点「同意」换来的。

### 14.2 实测缺口

| 缺口 | 证据 | 后果 |
|---|---|---|
| 调用超时 35 s | `tools/executor.py:16` 默认 `timeout=35`，`bootstrap.py:96` 构造时未传；`asyncio.timeout` 包住整次调用 | `run_tests` 的 120 s／300 s、`exec_command` 的 30 s 全部被截断，返回 `outcome_unknown` |
| `process` 不在审批面 | `tools/policy.py` 的 `HOST_TOOLS = {"exec_command", "run_tests"}` | `exec_command(cmd="sh", yield_time_ms=100)` 批准一次后，`process write` 可送任意命令，不再过 policy |
| 一次性输出留头 | `tools/command.py` 的 `capture()` 写满 `limit` 后丢弃后续块 | 构建／测试的报错在尾部，恰好被丢掉 |
| 无 PTY | `command.py`／`processes.py` 只用 `stdin=PIPE` | `isatty` 为假的程序退化或拒绝；无 `Ctrl-C`、无窗口尺寸 |
| 环境全继承 | spawn 未传 `env=` | `CHAGENT_DATABASE_URL`、供应商 key 对任意命令可见 |
| 沙箱是黑名单 | `sandbox.py::profile` 以 `(allow default)` 开头 | 能读 `/etc`、读别的项目、给同用户其他进程发信号；只有写和出站网络被限制 |
| 网络二元 | `CHAGENT_SANDBOX_NETWORK` 是 bool | 装依赖只有「关沙箱」一条路 |
| 审批单次消费 | `approvals.py` 消费即失效 | 反复跑测试会逼用户直接 `never` |
| 仅 macOS | `sandbox.py` 只实现 `SeatbeltBackend` | Linux 上 `workspace-write` fail-closed，等于不可用 |

### 14.3 设计原则

1. **约束下沉，分类器保持小。** 能被内核 profile 拦住的（写、读、信号、出网）一律不写进审批逻辑。审批只处理沙箱管不了的三件事：出网、远端不可逆操作（`git push`、`gh`、`ssh`）、后端不可用时的显式降级。
2. **默认姿态与能力同向。** 开启宿主命令时默认带沙箱；不开命令的用户不受影响。不允许「开了 shell、但沙箱和审批都还是默认关」这种组合被静默接受。
3. **能力必须可回收。** 每一个长活进程都要有归属（run 或 session）、上限和显式停止路径；没有 reattach 之前不做跨进程存活。
4. **数字要说真话。** 声明的时间上限、输出上限必须等于生效值；做不到就不写进 description。

### 14.4 目标形态：三档预设

不再让用户自由组合 `sandbox` 与 `approval`，改为一个 `preset` 推导出两者：

| 预设 | 文件写 | 读 | 网络 | 审批 | 用途 |
|---|---|---|---|---|---|
| `read-only` | 禁止（`/dev/null` 除外） | 系统区 + 工作区 | 断 | 越界才问 | 只读探索、review |
| `workspace`（默认） | 工作区 + 合成 HOME + TMPDIR | 系统区 + 工作区 + 合成 HOME | 断，按需授权 | 出网、越界、`write` 才问 | 日常开发 |
| `full` | 不限制 | 不限制 | 通 | 不问 | 显式 opt-in，UI 常驻警示 |

组合规则（在 `Settings.__post_init__` 里校验，不满足直接启动失败）：

- `allow_host_commands=true` 且 `preset` 未显式设置 → 取 `workspace`。
- `preset=full` 必须同时显式设置 `CHAGENT_SHELL_ALLOW_FULL=true`，否则启动报错。
- 沙箱后端不可用（Linux 无 bwrap、macOS 无 `sandbox-exec`）→ 不允许 `workspace`／`read-only`，只能显式 `full`，且 `approval` 强制 `untrusted`。

### 14.5 分批

四批，严格按依赖顺序；每批独立可回退、独立可验收。

#### 14.5.1 第一批：说真话（0.5–1 人日）

范围：只修数值与审批面，不动沙箱、不加能力。

1. `AgentTool` 增加 `timeout_seconds: float | None`，默认 `None`。`ToolExecutor.execute` 取 `tool.timeout_seconds or self.timeout` 作为上限。
   - `exec_command`：`30 + 5` 秒（一次性）／`35` 秒（yield 路径，`yield_time_ms ≤ 30 000`）。
   - `run_tests`：`305` 秒。
   - `process`：`35` 秒。
2. `HOST_TOOLS` 增加 `process`，但按参数细分：`covers()` 改为对 `process` 只在 `action == "write"` 时返回真；`subject()` 返回 `process write <id>`。`list`／`read`／`stop` 不需要审批——它们只能作用于本 run 自己起的进程，且 stop 是收敛动作。
3. 一次性输出改为**保留尾部**：`capture()` 用 `bytearray` 追加、超限时从头部丢弃并累计 `dropped` 字节，结果里报告 `Truncated: dropped N bytes from the front`。
4. `max_output_chars` 默认改 `64_000`，schema `maximum` 改 `1_048_576`，两侧一致。

验收：`run_tests` 能跑满 120 秒；`process write` 触发审批；`exec_command` 输出 100k 行时保留最后 64k 并报告丢弃量。

回退：单点改动，直接 revert 本批提交。

#### 14.5.2 第二批：沙箱成为边界（2–3 人日）

范围：把 `profile()` 从黑名单改成白名单，并解决「白名单下 HOME 写不进去」的连锁问题。

1. **profile 重写**。`(deny default)` 起步，白名单分四组：

```scheme
(deny default)
(allow process-exec) (allow process-fork)
(allow signal (target same-sandbox))
; 系统运行时：直接 vendor Codex 的 seatbelt_read_only_platform_defaults.sbpl
; （Apache-2.0，保留归属声明），含 dyld、sysctl、mach-lookup、/dev 基础设备
(allow file-read*   (subpath <workspace>) (subpath <home>) (subpath <tmpdir>))
(allow file-write*  (subpath <workspace>) (subpath <home>) (subpath <tmpdir>)
                    (literal "/dev/null") (regex "^/dev/fd/(1|2)$"))
(allow file-read* file-write* (literal "/dev/tty") (literal "/dev/ptmx")
                              (regex "^/dev/ttys[0-9]+$"))
(allow file-ioctl (regex "^/dev/ttys[0-9]+$"))
; 非 grant 时不出现 network-outbound
```

   注意：`(allow default)` 下「全局 deny 读会导致动态链接失败」的结论不成立，失败原因是系统区白名单不全。Codex 的默认文件已经把这些路径列全，直接复用比自建可靠。
2. **合成 HOME**。每次运行前创建 `<workspace>/.chagent/home`（或 `TMPDIR` 下，按 `CHAGENT_SANDBOX_HOME`），设置 `HOME`、`XDG_CACHE_HOME`、`XDG_CONFIG_HOME`、`npm_config_cache`、`PIP_CACHE_DIR`。生成最小 `~/.gitconfig`（`user.name`／`user.email` 从宿主 `git config` 读取，**不带 credential helper**）。这样 `~/.ssh`、`~/.aws`、`~/.npmrc` 不是被黑名单挡住，而是根本不可见；`npm install` 也不会因为写不了宿主缓存而失败。
3. **env 白名单**。只透传 `PATH`、`LANG`、`LC_*`、`TERM`、`TZ`、`SHELL` 与 `CHAGENT_ENV_PASSTHROUGH` 列出的名字；其余全部剔除。`CHAGENT_*` 一律不传（除了 `CHAGENT_SANDBOX_HOME` 这类无凭据的）。
4. **`BwrapBackend`**（Linux）：

```text
bwrap --ro-bind / / --dev /dev --proc /proc --tmpfs /tmp \
      --bind <workspace> <workspace> --bind <home> <home> \
      --unshare-net --die-with-parent --new-session -- /bin/sh -c <cmd>
```

   `--unshare-net` 在 `network=grant` 时去掉。可用性用 `bwrap --ro-bind / / true` 探测，失败即 fail-closed。
5. **探测扩到九项**：现有六项（`starts`、`workspace_writable`、`outside_denied`、`read_denied`、`no_residue`、`network_denied`）之外，增加 `read_outside_denied`（读工作区外非黑名单文件应失败）、`pty_opens`（`/dev/ptmx` 可打开）、`signal_confined`（向沙箱外进程发信号应失败）。
6. **预设接入**：`CHAGENT_SHELL_PRESET` 推导 `sandbox` 与 `approval`，`Behavior:` 行与 `config show` 显示实际生效值。

验收：沙箱内 `cat ~/.ssh/id_rsa`、`cat <别的项目>/x`、`curl example.com`、`kill -9 <外部 pid>` 全部失败；`git status`、`pytest`、`python -m venv`、`npm install --offline` 全部成功；`test_sandbox` 从 10 skip 变为真实执行。

回退：`CHAGENT_SANDBOX_PROFILE=legacy|strict`，默认 `legacy` 一个版本，下一版转 `strict` 为默认。

#### 14.5.3 第三批：交互与生命周期（3–4 人日）

范围：PTY、信号、可回收的长活进程。

1. **`exec_command` 增加 `tty: bool`**（默认 `false`）。实现：

```python
master, slave = os.openpty()
proc = await asyncio.create_subprocess_exec(
    *argv, stdin=slave, stdout=slave, stderr=slave,
    cwd=cwd, start_new_session=True,
    preexec_fn=lambda: fcntl.ioctl(0, termios.TIOCSCTTY, 0),
)
os.close(slave)
loop.add_reader(master, drain_master)
```

   输出需过滤 ANSI 序列与 `\r`，否则模型看到的是转义垃圾；`tty=true` 时 `description` 明说「输出已做最小清理，光标控制类程序不可用」。
2. **`process` 增加 `signal`（`INT`／`TERM`／`KILL`）与 `resize`（`rows`／`cols`，`TIOCSWINSZ`）**。这两个是 `Ctrl-C` 和 `vim` 的前提。
3. **生命周期分两类**：`ephemeral`（默认，run 结束回收，保持 J 批语义）与 `service`（`background=true` 启动，活到 session 结束或显式 `stop`）。`service` 上限 4，列表在网页运行面板可见，session 结束统一回收。
4. **墙钟与上限可配**：`CHAGENT_PROCESS_TIMEOUT` 默认 1800 s（原 600），`CHAGENT_PROCESS_MAX` 默认 4。
5. `run_tests` 复用同一套 spawn 与捕获，不再单独维护一份超时逻辑。

验收：`python -c "import pty; pty.spawn(['/bin/sh'])"` 可用；`npm run dev` 起服务后 `process read` 能持续拿到日志、`signal TERM` 能停；REPL 输入 `1+1` 能回显 `2`。

回退：`CHAGENT_SHELL_TTY=false` 关闭 PTY，退回管道；`service` 用 `CHAGENT_PROCESS_SERVICE=false` 关闭。

#### 14.5.4 第四批：网络与审批记忆（3–5 人日）

范围：让「装依赖」不需要关沙箱，让「反复跑测试」不需要反复点同意。

1. **网络三态**：`CHAGENT_SANDBOX_NETWORK=off|grant|on`。
   - `off`（默认）：profile 不含 `network-outbound`。
   - `grant`：命令需要出网时走审批，批准后该进程不带断网规则，授权绑定参数指纹、session 内有效。审批文案必须写清「这条命令将获得完整出网能力」。
   - `on`：等同 `preset=workspace` 下的常开，仅 `full` 或显式配置可用。
   - 二期（本批不做）：本地代理 + 域名规则。seatbelt 的 `network-outbound` 是二元的，按域名管控只能靠代理；等真的有「只允许 pypi」的需求再做。
2. **审批作用域**：`ApprovalStore` 的 key 从当前 `(run_id, 指纹, cwd)` 扩展为 `(作用域, 指纹, cwd)`，作用域取 `run | session`。默认 `run`；用户选「本会话内都允许」时写 `session`。TTL 与显式撤销在网页端可见。
3. **规则沉淀**：批准时可选「以后同类命令不再问」，落地为 `approval_allowlist` 的一条前缀；生成前用现有的 `SHELL_CONTROL` 判定拒绝，防止把 `pytest; curl …` 沉成规则。
4. **危险命令识别收窄**：只保留三类——出网、远端不可逆（`git push`／`gh`／`ssh`／`scp`／`rsync` 到远端）、`sudo`（沙箱内必然失败，提前给明确错误）。`rm -rf` 不再单独判断：沙箱决定了它只能删工作区。

验收：`pip install requests` 在 `workspace` 预设下完成（一次授权）；同一 `pytest` 第二次不再弹审批；`git push` 在未授权时被拒并给出原因；`sudo` 返回「沙箱内不可用」而不是超时。

回退：`CHAGENT_SANDBOX_NETWORK` 保持 `off|on` 两态即可退回；审批作用域用 `CHAGENT_APPROVAL_SCOPE=run` 固定。

### 14.8 风险与回退

| 风险 | 处理 |
|---|---|
| 白名单缺路径导致正常命令失败（`python -m venv`、`npm`、`git`） | 探针在合成树上跑，不放宽到真实工作区；上线前用 5 个真实项目各跑一遍 |
| 合成 HOME 让 `git commit` 缺少身份 | 生成最小 `gitconfig`，只含 `user.name`／`user.email` |
| bwrap 在部分发行版禁用 user namespace | 探针失败即 fail-closed，日志指向 `CHAGENT_SHELL_PRESET` |
| PTY 输出污染上下文（ANSI、密码回显） | 过滤 ANSI 与 `\r`；`tty=true` 的 description 明确说明 |
| 默认改沙箱打断现有用户 | 只在 `host_commands=true` 时改默认；`CHAGENT_SANDBOX_PROFILE=legacy` 可回退一个版本 |
| `service` 进程泄漏 | session 结束统一回收 + UI 可见 + 上限 4 |

### 14.9 明确不做

- **不做命令解析器**。`bash -lc` 套 `env` 套 `sudo`，解析永远是漏的；沙箱能兜住的就不判断。
- **不做跨进程 reattach**。需要持久化进程表、孤儿回收与断线重连，成本高于收益；`service` 在 session 内可见已经够用。
- **不做按域名网络代理**。二期再看；本批只保证「出网必须被看见」。
- **不做 `on-failure` 自动升级重试**。审批失败后由模型重新发起，比自动放宽权限更可控。
- **不改 `apply_patch` 的路径判定**。它已经走工作区检查，与本方案正交。
