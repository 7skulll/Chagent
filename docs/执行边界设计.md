# 执行边界设计：策略、沙箱与审批

状态：修订后的待实施设计。本文与[下一阶段实施方案](下一阶段实施方案.md)合并使用：后者规定统一交付顺序，本文规定执行边界的技术契约。两份文档均不代表功能已经实现。

## 1. 评审结论与合并决策

原方案的核心方向可用：策略由 Executor 收口、沙箱与审批分离、沙箱不可用时明确降级、审批持久化、关键事件先提交后通知。原示例存在下列实现风险，本版以修订规则替换，不能继续按旧伪代码实施。

| 原设计 | 问题 | 合并后采用 |
|---|---|---|
| 工作区内写入一律 allow | read-only 仍可写，违反配置含义 | 先判断写权限，再判断路径与授权 |
| full 下 untrusted 等同 on-request | 本来要逐次审批的操作被放行 | approval 策略独立于沙箱模式 |
| 三档 sandbox 同时当默认权限和绝对上限 | 审批“越过上限”语义矛盾 | 默认权限、宿主允许授予的最大权限分别定义 |
| S1 把区外写变成可读拒绝作为主要收益 | 现有 Executor 已把路径异常转为可读错误；真正缺少的是统一权限规则 | S1 验收只读与有效权限，不把已有错误转换算作新增能力 |
| 工作区外写批准后执行原文件工具 | `WorkspaceFS.parts()` 仍会拒绝；改 root 又可能扩大授权 | 第一版文件工具保持工作区边界，不支持批准后任意区外写 |
| 只按 `(workspace, mode)` 缓存 profile | 不同网络、临时目录或读取权限可能误用旧 profile | 按完整有效权限与后端版本缓存 |
| 审批等待后才延长 timeout | 等待期间原 deadline 已可触发，补时间太晚 | 等待前暂停活动预算，返回后恢复剩余预算 |
| 在现有 execute 内直接等待审批 | Scheduler 外层已持有额度与工作区门控；可能长时间阻塞其他会话 | prepare/审批先完成，再获取执行资源 |
| future 创建晚于审批入库 | 快速批准可能发生在 waiter 注册之前 | 先订阅通知，再查库与等待，数据库为准 |
| 每个 run 一个事件队列 | 多连接会竞争消费，或慢连接反压发布；补历史后再订阅也有窗口 | 提交后版本通知 + 持久游标追赶 |
| 按启动时间终结所有旧运行 | 无法证明其他进程已死亡 | 所有权 token、租约到期与事务内收敛 |
| 任意执行失败后无沙箱重试 | 命令可能先修改文件再失败，重试重复副作用 | 第一版关闭 on-failure；未来按尝试审计、显式确认重试 |
| deny profile 的 true 退出 0 即可宣称支持 | 只能证明能启动，不能证明限制确实生效 | 探测实际允许／拒绝行为，并单独验收目标平台 |
| full + never 等价于所有旧配置 | 还取决于命令注册、网络、路径及环境规则 | 使用明确兼容配置；不宣称单个组合复现全部旧行为 |

原文记录了本机限制性 sandbox-exec profile 失败。本轮没有重新探测系统，只把它视为“该环境尚未验证可用”的证据，不推断整个 macOS 平台都不可用。

## 2. 目标与威胁边界

目标是限制模型发起的工具调用，并让超出默认权限的动作有可审计的人工授权。不是隔离恶意 Python 插件，也不把审批当作 OS 沙箱。

- 文件工具在 Python 进程中执行，使用路径与权限检查；命令子进程由平台沙箱约束，两条路径必须遵守同一个有效权限模型。
- 默认不把“能读整个用户目录”当作必须功能。读取范围包含工作区与命令所需的运行时路径；扩展读取范围要明确列出并测试。若兼容模式允许广泛读取，必须明确不提供宿主文件保密性保证。
- 凭证目录、应用自身配置／状态和仓库控制路径需要单独规定读写权限。workspace-write 不自动意味着可以改写所有 `.git`、配置或凭证文件。
- 子进程采用经过筛选的环境，不默认继承模型 API Key、数据库凭证和代理凭证；正常任务需要哪些环境变量由宿主配置。
- 默认关闭命令网络权限。模型请求的是权限，最终执行权限由宿主配置与有效授权决定。
- `full` 或 unsandboxed 表示没有相应内核限制；若无法落实“网络关闭”，结果里必须如实标注，不能只靠配置文字宣称已经隔离。

## 3. 配置与第一版范围

### 3.1 三层权限

1. **默认权限**：`read-only`／`workspace-write`／`full` 是一次调用未经额外授权时的权限配置名称。
2. **可申请范围**：宿主决定能否申请工作区写、网络、受保护路径或无沙箱执行。禁止申请的能力，即使用户对某张审批卡点批准，也不能授予。
3. **本次授权**：绑定一个规范化调用与有限权限增量，不永久修改默认配置，也不赋予任意后续调用同样权限。

网络授权与文件写权限分别表达，不能用“安装依赖需联网”直接请求 full。工具参数中的理由不参与信任判断，只用于向用户说明。

### 3.2 配置建议

| 配置 | 第一版约定 |
|---|---|
| `CHAGENT_SANDBOX` | read-only／workspace-write／full；建议默认 workspace-write |
| `CHAGENT_APPROVAL` | 先实现 never、on-request、untrusted；on-failure 明确拒绝配置，不能悄悄映射到其他模式 |
| `CHAGENT_SANDBOX_NETWORK` | 默认 false，独立于文件写模式 |
| `CHAGENT_ALLOW_HOST_COMMANDS` | 保留已有显式开关，默认仍 false；不因探测通过自动改变用户权限 |
| `CHAGENT_ALLOW_UNSANDBOXED` | 默认 false，表示宿主是否允许无沙箱执行；不等于自动批准某次执行 |
| 审批等待上限 | 初始 300 秒，独立于活动执行时间 |

可以在后续经平台实测后设计“受限命令默认启用”，本批不把沙箱探测结果与默认授权混在一起。

### 3.3 判定原则

| 动作 | never | on-request | untrusted |
|---|---|---|---|
| 在默认读取范围内读取 | allow | allow | allow |
| 默认 workspace-write 下普通工作区写入 | allow | allow | 每次 ask |
| 默认 read-only 下工作区写入 | deny | 显式申请且宿主允许时 ask | 宿主允许时 ask |
| 默认权限内 exec | allow，仍需注册与后端可用 | allow | 每次 ask |
| 超出默认权限但在宿主可申请范围内 | deny | 显式申请、说明理由后 ask | ask |
| 超过宿主硬性范围／无实现支持 | deny | deny | deny |

full 不跳过 untrusted 审批；never 不自动允许越界。普通工作区写入的权限检查要先于放行。

第一版 `read_file/list_dir/write_file/edit_file` 继续限制在会话工作区，路径检查沿用目录描述符与 no-follow 操作。工作区外文件工具请求直接拒绝并说明不支持，不展示“批准后可写”按钮。以后需要区外写入时，再实现限定到具体路径的文件访问能力，不能把 root 改成 `/`。

未知工具默认使用保守策略，不能因为名字像 read 就直接放行。能力类别由宿主注册的工具定义提供，模型不能修改。

## 4. 调用路径与最少新增对象

```text
Runner / Scheduler 到达一个可执行分组
  → Executor.prepare：参数、上下文、宿主开关、策略检查
      → allow：生成 PreparedInvocation
      → deny：生成未执行的错误结果
      → ask：持久化审批并等待（不持有执行槽或工作区门控）
  → Scheduler 获取额度与工作区门控
  → Executor.execute_prepared：重新校验所有权、授权有效期、参数及路径
  → 提交 tool_started，真正执行工具
  → 保存真实结果／产物，按原模型调用顺序推进 RunState
```

新增职责：

| 对象 | 职责 |
|---|---|
| `ExecutionPolicy` | 纯判定，输出 allow／deny／ask，以及请求的精确能力 |
| `PreparedInvocation` | 冻结规范化参数、调用指纹、有效权限与本次 grant 引用 |
| `SandboxBackend` | 能力探测与实际命令包装，报告可落实的限制 |
| `ApprovalBroker` | 创建／读取／决策审批，等待通知；不执行工具 |
| `RunBudget` | Runner 持有，管理活动预算及审批等待暂停 |

第一版可以把相关小数据类型放在 `domain/execution.py`，不需要每个对象拆成多层接口。

策略拒绝和用户拒绝是可交给模型的未执行结果；Broker／存储故障、所有权丢失与协议错误必须传播给 Runner 收敛，不能被 Executor 现有的兜底 except Exception 全部吞成普通工具错误。只有确认没有开始执行时，才能声称“未修改文件”；执行后失败继续沿用未知副作用语义。

### 4.1 与并发调度的关系

- 可能 ask 的调用按原调用次序独立分组；快速分类可保守返回“可能需要审批”，不做 I/O，也不解析 shell 字符串来证明安全。
- 只有实际到达该组时才发起审批，前组先执行并提交；不能提前批准整个批次中尚未到达的修改。
- 同一 run 等待审批时不再派发后面的组。不同 run 的审批分别管理，不能用一个全局审批锁阻塞整个服务。
- 等待不占并发槽、不持有工作区锁、不占数据库连接。lease 心跳与取消继续运行。
- 获批后重新获取资源并复核条件。审批展示写入时应绑定目标的现存版本或“不存在”状态；即使模型没提供 expected_sha256，也不能忽略等待期间的变化。版本冲突返回冲突并重新准备，不能套用旧批准覆盖新内容。文件检查在 Executor 准备阶段完成，纯策略分类本身不做 I/O。
- 工具只有真正开始执行才记 tool_started；等待审批期间保持 queued，并通过审批行解释等待。拒绝可从 queued 直接保存未执行错误结果，结果必须标明 execution_started=false。

现有 Scheduler 在外层获取 gate、worker 在 slot 内调用 Executor，因此不能只给 `_groups()` 加一条 may_ask 就算完成审批支持。

## 5. 沙箱后端与降级

### 5.1 后端契约

后端接收实际 argv、cwd、有效权限、临时目录与环境，输出包装命令及可审计的执行配置。策略只决定允许的能力，不能把任意模型参数直接拼成受信任 profile。

macOS 的 seatbelt、Linux 的 bwrap 是候选后端，本文不提供可直接宣称安全的通用 profile。实现时要按目标系统验证运行所需的读取、进程和网络权限。

探测至少使用合成工作目录与独立的区外临时文件验证：

1. 普通命令能够启动。
2. workspace-write 可以写允许目录，不能写指定禁止路径。
3. read-only 对工作区写入确实拒绝。
4. 需要网络关闭时，用受控本地测试服务验证访问被拒绝，不依赖公网服务。
5. 配置要求的读取与受保护路径限制确实生效。

启动探测要有超时，记录耗时；不能预先承诺“只有 10ms”。探测结果按后端和权限能力记录，而不是一个适用于所有模式的 available 布尔值。

profile／命令模板缓存必须包含实际根路径、模式、读取范围、写入范围、受保护路径、网络、临时目录和后端策略版本；SBPL 与 argv 分别使用正确的编码规则。

### 5.2 不可用时

- 受限后端不可用且不允许 unsandboxed：拒绝命令或不注册命令，文件工具继续按自身策略运行，网页明确显示命令能力不可用。
- 允许 unsandboxed：仍需匹配宿主配置和审批策略；不把用户选择 workspace-write 悄悄变成 full。
- 每次执行记录 backend、实际限制、网络状态、是否无沙箱、批准来源。请求的权限与实际执行的权限分别保留。
- 不回退整个服务，不修改用户全局配置。能力不足的路径要明确报“不支持”，不能用 mock 通过作为平台支持证据。

主进程工具、子进程和未来 ProcessManager 必须复用这些策略；不能让新命令入口绕过 Executor。

## 6. 审批持久化、唤醒与授权消费

### 6.1 记录内容

`approval_requests` 保存 run、tool record、执行 attempt、调用指纹、规范化 cwd／路径、请求权限、理由、策略版本、owner token、期限与决策信息。

第一版状态为 pending／approved／denied／expired／cancelled；增加授权消费时间或等价的消费记录。一个工具尝试最多一个 pending 请求，并对重复创建设置唯一约束。将来若支持重试，通过新的 attempt 区分，不以“允许问两次”为理由移除所有去重约束。

原工具参数的审计沿用 tool_calls；审批展示和普通日志应脱敏，优先引用原记录，避免重复扩散凭证。

### 6.2 无竞争窗口的等待

1. 注册审批通知订阅，再创建审批请求及 approval_requested 事件，提交后通知。
2. 读取持久化状态；pending 才等待版本变化或短周期兜底查询。
3. 批准／拒绝使用条件更新：只允许未到期 pending、匹配的活动 owner；决策与事件同事务，提交后唤醒。
4. Broker 被唤醒后重新读库，不把 future 的 bool 当作最终授权。
5. 过期与批准竞争依靠数据库条件更新决定，不能由两套内存计时器分别覆盖。
6. 执行前按调用指纹、owner、策略版本、grant 期限校验并消费 grant；参数改变、所有权改变或授权失效均不得执行。

重复决策返回冲突；取消后的批准不复活运行。数据库消费 grant 与外部执行不是同一事务：崩溃后可能需要标 unknown，不能因此宣称严格 exactly-once，也不能重放已消费授权。

审批 API 必须确认属于当前本地用户界面与正确工作区，检查 Origin／本地会话令牌等必要的请求来源约束；模型和工具没有自行批准接口。卡片展示实际命令／路径、有效权限差异与风险信息，理由只是说明，不是授权依据。

### 6.3 运行态

第一版保留 `runs.status=running`，API 根据 pending 审批投影 `waiting_for=approval` 与审批 ID，网页显示“等待确认”。这样活动会话索引、终态 CHECK 和现有取消逻辑无需为一个等待原因全部扩展。

不采用原文的 awaiting_approval 状态迁移。如果将来需要多种持久等待态，再统一设计，而不是每增加一种等待就改 RunStatus。

### 6.4 活动预算

审批是在当前 run 已排空前组且无其他本批执行的边界等待，暂停的是整个 run 的活动执行预算。

- 进入等待前记录单调时钟下的剩余预算，并禁用该活动 deadline（使用 reschedule(None) 或等价预算机制）。已过期的预算不能被暂停复活。
- 审批受独立等待期限约束。返回后以“当前时间 + 剩余预算”恢复，不能到 finally 才补已经触发的旧 deadline。
- tool timeout 仅覆盖实际工具执行，不覆盖人工审批、额度和门控等待。模型请求 timeout 保持独立。
- 用户取消、服务关闭与 owner 丢失不被暂停；心跳持续进行。
- 可配置总墙钟上限，防止通过反复审批无限延长运行；墙钟上限不因审批暂停。

### 6.5 重启与失败

审批上线依赖主运行所有权／租约。只清理 owner 已失效的运行及其 pending 审批；禁止按 started_at 或“服务刚启动”批量终结其他进程的运行。

审批拒绝／到期返回未执行的错误结果，模型可选择其他方案。取消或失联则取消 pending 审批并结束运行。第一版不从崩溃前的 pending 审批直接恢复执行，用户新运行重新请求。

## 7. on-failure 与扩大权限重试

第一版不实现 on-failure，配置时明确报暂不支持。

后续只有沙箱包装器能证明“目标命令尚未启动”的失败，才可能作为无副作用的重新发起；普通非零退出码、超时、无网络错误都不足以证明未修改文件。

如果允许用户主动重试已执行命令，必须展示前次结果及可能副作用，创建新的执行 attempt 与授权，保留两次审计；网络授权只增加网络权限，不默认移除文件限制。工具成功与已产生副作用的调用都不能自动重跑。

## 8. 事件通道与迁移

事件合并、首片提交、有界 writer、版本通知与 SSE 等待协议已按 A 批交付，实现与实测见[实施记录 第 2 节](实施记录.md)。不再实现每个 run 一个竞争消费队列。

合并窗口先用 20ms／4KiB，64KiB 缓冲；首片优先，定时刷新独立于新片段。60ms 仅作为性能实验候选，不同时维护两套默认规则。count 可以作为统计元数据，但正文正确性按 delta 拼接验收。

旧文 128 增量的 256 条语句仅描述两条事件 SQL × 128，不代表整条运行总 SQL；未来报告必须区分事件事务、事件 SQL、完整运行 SQL 与 SSE 查询次数。

迁移只追加，不预先固定 0010 的职责。按实际落地顺序先增加 owner／租约，再增加审批表及相关约束。审批第一版不增加 RunStatus，因而不需要重建 runs 状态 CHECK／活动索引。旧版本代码遇到审批表前，必须已停止新授权并清理活动等待，不能只靠批量 UPDATE 声称安全回退。

## 9. 验收矩阵

| 类别 | 核心通过条件 |
|---|---|
| 策略 | 只读拒写；full 不绕过 untrusted；never 不隐式提权；网络与文件权限独立 |
| 路径 | 区外、父路径、符号链接、受保护目录行为明确；审批不扩大 WorkspaceFS 根 |
| 后端 | 真正验证允许与拒绝；后端不可用时 fail closed；未验证平台不标为支持 |
| 配置 | 保留命令显式开关；无沙箱行为可见；拒绝暂未实现的 on-failure |
| 审批 | 刚创建即批准不丢信号；批准／过期竞争；重复 POST；取消后批准；参数改变后不执行 |
| 预算 | 活动预算 0.5 秒、审批等待 2 秒仍可继续；工具预算不消耗在等待上；用户取消立即生效 |
| 资源 | 等待时不占 slot、gate 或数据库连接；另一会话可访问同工作区；授予后重验文件版本 |
| 所有权 | 双进程共享库时不误清理；旧 owner、过期 grant 不可执行或回写 |
| 审计 | 请求、决策、消费和实际执行可追溯；失败不重试未知副作用 |
| 入口 | CLI、Web 和直接工具入口使用同一策略；审批接口不能由非受信请求来源批准 |

CLI 交互模式可以本地询问；非交互模式遇到 ask 应明确返回无法取得批准，不无限等待，也不自动允许。真实链路使用合成临时工作区验证命令受限与模型收到拒绝后的处理；OS 测试与模型语义测试分开报告。

实施切片、统一顺序及性能验收见[下一阶段实施方案](下一阶段实施方案.md)。本轮只修订设计，没有执行沙箱探测、数据库迁移、代码实现或新的供应商请求。
