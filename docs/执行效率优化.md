# 执行效率评估与写入路径优化

日期：2026-10-28。状态：评估已完成，方案待实施。本文回答两个问题：这套设计是不是太重；如果重，重在哪、怎么减。实测都在本机 `chagent` 库、单进程、`synchronous_commit=on` 下取得，脚本见第 2 节。

## 1. 结论

**不是代码量重，是写路径重。** 一次普通运行要 57 条 SQL、11 个事务；一次 1.6 秒的流式回答要 260 条 SQL、81 个事务，其中 76 个事务只写一条文本增量。上下文构建反而不是瓶颈：400 条历史每轮重建 7.5ms。

在本机 localhost 下，一次普通运行多出约 10ms 的数据库时间，相对模型数秒的响应只占 1–2%，**性能不是当前瓶颈**。真正的代价有三处：提交次数带来的 fsync 与 WAL 放大；每轮把完整请求体落库带来的存储膨胀；以及为"多写入者"设计的每写必校验，把一个单用户单进程应用锁进了多进程协议。E 批（审批、沙箱）会继续往同一条写路径上加表、加事件，所以这笔账应当先还。

## 2. 实测

`scripts/bench_write_path.py`，临时 schema、离线模型、每组 3 次取中位数：

| 场景 | 显式 SQL | 事务 | 事件 | WAL | 墙钟 |
|---|---:|---:|---:|---:|---:|
| 两轮模型 + 一次工具（`tool_turn`） | 57 | 11 | 10 | 20KB | 10.4ms |
| 1.6 秒流式回答（150 片，10ms 间隔，`stream`） | 260 | **81** | 80（`text_delta` 76） | 38KB | 1666ms |
| 上下文构建 100／200／400 条（带投影缓存） | — | — | — | — | 1.9／3.8／7.5ms 每轮 |

几个直接读数：

- **94% 的事务在写文本增量。** 每次 20ms 刷新就是一个事务、三条 SQL（`check_owner` → `SELECT ... FOR UPDATE` → `INSERT`），并触发一次 fsync。
- **每个事件固定 3.2 条 SQL。** 序号用 `MAX(sequence)+1` 分配，所以每条事件都要先锁 `runs` 行，再插入。
- **请求体全量落库。** `model_calls.request` 存的是整份消息数组：100 条历史 80KB、200 条 160KB、400 条 320KB，另加 16–62KB 的上下文快照。一个 10 轮的会话在第 200 条历史附近，光请求审计就写入约 2MB，远超上面两个场景。
- **上下文不是瓶颈。** 投影缓存后每轮 7.5ms（400 条），且不随模型轮次线性叠加。上一版"200 条历史 10,602 条消息序列化、48.4ms"的记录是加缓存之前的状态。

复现：

```sh
PYTHONPATH=src uv run --env-file .env python scripts/bench_write_path.py --repeats 5
```

## 3. 与 Pi、Codex 的对照

| 维度 | Chagent | Pi `packages/agent` | Codex `codex-rs` |
|---|---|---|---|
| 循环内状态 | 每轮从库重读历史并重建 `ModelRequest` | `currentContext.messages` 原地追加，只在 LLM 边界转换 | 线程内 history 持有，事件推给订阅者 |
| 持久化时机 | 每个状态变化各自一个事务，前台等待 | `appendFileSync` 一行 JSONL，无事务、无锁 | `mpsc::channel(256)` + writer task，入队即返回 |
| 事件 | 逐条落 `run_events`，带序号与所有权校验 | 直接 emit 给订阅者，不落库 | `EventMsg` 走通道，客户端订阅；rollout 记完整条目 |
| 所有权 | 每次写入 `SELECT ... FOR UPDATE` 校验 | 无（单进程） | 进程内 actor，无 DB |
| 上下文 | 每轮重建 + 预算选择 + 投影缓存 | 原地追加 + 压缩回调 | 内存 + 压缩 |

共同点值得注意：**三者的"真相"都在内存，磁盘是旁路。** Pi 和 Codex 的持久化都是"追加、可批量、失败最多丢尾部"，不是"每条日志一个事务"。Chagent 反过来：数据库是真相，内存是视图，于是每次状态推进都要一次提交。

Chagent 的审计要求决定了不能照搬 JSONL，但**"追加 + 批量 + 旁路 commit"** 这个形态可以保留：语义上仍然是 PostgreSQL 唯一真相，只是把 N 次提交压成一次。

## 4. 方案

四步，前两步收益最大且不动语义。每步独立提交、独立验收。

### 4.1 F0：基线护栏（已落地）

`scripts/bench_write_path.py` 已提交：临时 schema、离线模型、统计显式 SQL、事务、事件、WAL 增量与墙钟，覆盖"两轮 + 一次工具"和"慢速流式回答"两个场景，输出 JSON 可归档到 `docs/diagnostics/`。

没有这条基线，后面无法判断"减少 60%"是对谁而言，也会重演 A 批那种"只改进了突发、没改慢速流"的偏差——A 批把 128 片突发从 128 个事务压到 2 个，但 10ms 间隔的慢速流仍然是每 20ms 一个事务。

### 4.2 F1：事件批量提交（收益最大）

目标：把"每条事件一个事务"改成"每批事件一个事务"，行与序号都不变，仍可逐条回放。

| 项 | 改动 |
|---|---|
| 新增 `storage/event_writer.py` | 每 run 一个有界队列 + 单写任务；`interval=100ms`、`batch=64` 条触发提交，容量不足时对生产方背压 |
| `RunRepository.event()` | 只入队并返回；所有权校验从每条一次改为每批一次 |
| 批量 SQL | 一次事务内：`SELECT ... FOR UPDATE` 锁 run → `WITH base AS (SELECT COALESCE(MAX(sequence),0) ...) INSERT ... SELECT base.n + row_number() ... FROM unnest(...)` |
| `finish()` | 先 `flush()`，再在同一事务写终态行与终态事件；缓冲区已空，序号不冲突 |
| 崩溃与取消 | 取消时最多再给 100ms 排空；超过则丢弃未提交事件并记录。强杀最多丢 100ms 事件 |

必须守住的四条：

1. **序号仍由数据库分配**，批量语句里用 `row_number()`，不留空洞也不假设单写者。记忆 worker 的审计事件与主运行并发时依然安全。
2. **终态事件不与状态行分离。** `run_completed` / `run_failed` 仍在 `finish()` 的同一个事务里，这是现有契约，不能被批量队列打破。
3. **顺序按入队顺序**，同一 run 内 FIFO；`tool_started` 不能晚于 `tool_result`。
4. **写失败要传播**，与 `TextStreamWriter` 一样让模型消费停止，不能静默丢。

预期：流式回答 260 → 约 45 条 SQL、81 → 约 20 个事务（1.6 秒 ÷ 100ms 窗口）；普通运行 57 → 约 30 条、11 → 约 4 个。把窗口放宽到 250ms 可再少一半事务，但断线回放的粒度变粗，默认取 100ms。

### 4.3 F2：所有权校验降频

现在 `check_owner` 是独立的一次 `SELECT ... FOR UPDATE`，每条事件、每次写入都做一次。B1 的目标是"旧 owner 不能回写"，这可以由三条更便宜的手段满足：

- 事件批量事务里校验一次（随 F1 落地）。
- 业务写入改成条件更新：`UPDATE ... WHERE id = %s AND status = 'running' AND owner_token = %s`，受影响 0 行才判定失联。省掉前置 SELECT，语义不变。
- 心跳继续保留（5 秒一次），租约仍是 30 秒。

不动的部分：`begin`／`finish`／工具结果提交仍要求 owner 匹配；"租约过期不等于旧进程已死"的边界不变。

预期：每次运行再省约 10 次 SELECT，每条写入从 3 条 SQL 降到 2 条。

### 4.4 F3：请求审计瘦身

`model_calls.request` 存整份消息数组，是当前最大的单笔写入。

推荐做法：`request` 只存 `{model, max_tokens, message_ids[]}`，正文由 `messages` 表按 ID 还原。`messages` 只追加是既有契约，所以 ID 列表永远可还原，不会出现"审计时拼不回请求"。同时把 `context_snapshot.selections`（400 条时 62KB）改成只记录**未选中**的消息与原因——选中是默认值，没必要逐条存。

备选是把整个 `request` 用 zstd 压成 `bytea`：改动最小（约 320KB → 60KB），但仍是重复存储，只是把浪费压缩了。

预期：第 200 条历史附近，每轮写入从约 222KB 降到 10KB 以内。

### 4.5 暂不实施

| 想法 | 判断 |
|---|---|
| 上下文改成内存增量维护（学 Pi 的 `currentContext`） | 实测每轮 7.5ms，收益低于破坏"每轮都从库重建"带来的正确性风险。触发条件：单 run 超过 20 个模型轮次且历史超过 800 条 |
| 文本增量不落库、只在终态落最终消息 | 会削弱断线回放。当前 100ms 批量已经把提交降到每秒 10 次以内，不值得再换语义 |
| 事件表分区／保留策略 | 属运维，不属效率。等 `run_events` 超过千万行再谈 |
| 换掉 PostgreSQL 或引入消息队列 | 与"审计事实落库"的定位冲突，不讨论 |

## 5. 边界

- 审计语义不变：PostgreSQL 仍是唯一真相，`messages` 仍只追加，`RunState` 仍是活动视图。
- 允许的退化只有一条：强杀时最多丢失 100ms 内未提交的事件行。业务状态（消息、工具结果、终态）不受影响。
- 不承诺与 Pi／Codex 的同机速度对比；三者的问题域不同。
- F1 会增加一个后台任务，必须纳入现有的取消与关闭流程，不能留下悬挂 writer。

## 6. 验收

| 项 | 通过条件 |
|---|---|
| 正确性 | 全量回归通过；新增"批量顺序与序号连续""终态前强制排空""取消时排空上限""写失败传播""并发审计事件不撞号" |
| 回放 | 断线重连按游标补齐，无缺片、无重复；`text_delta` 拼接仍等于最终正文 |
| 性能 | 流式回答的事务数下降 ≥ 80%；普通运行 SQL 下降 ≥ 40%；提交到 SSE 生成的 P95 不明显回退 |
| 存储 | 第 200 条历史附近，每轮写入体积下降 ≥ 90% |

基准沿用 A 批的口径：同机、同文本、同节奏、30 次取中位数与 P95，改动前后各跑一次。

## 7. 排期位置

建议插在 E1 之前，理由：E2 的审批会增加新表与新事件（`approval_requested`／`approval_resolved`），如果仍按"每条事件一个事务"落地，等待审批期间的心跳、事件与审批状态会叠加在同一条写路径上，之后返工成本更高。

顺序调整为：**F0 → F1 → F2 → F3 → E1 → E2 → C → D**。F0 已随本次评估落地；F1／F2 不改表结构，可合成一次交付；F3 涉及 `model_calls` 的语义，单独一次更安全。
