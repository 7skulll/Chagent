# 主链路诊断与优化方案

日期：2026-10-28（北京时间）  
状态：完成基线诊断；A、E、F 已实施（见[关键路径优化](关键路径优化.md)），B、C、D、G、H 尚未实施。

后续真实 DeepSeek 链路已测试，见[真实链路测试与 Claude 参考设计](真实链路测试与Claude参考设计.md)。真实样本新增 P0：显式 /remember 必须先经本地命令路由，不能让模型额外创建记忆文件；候选与已生效状态应由程序准确展示。其余阶段按本文推进。

## 1. 结论与范围

当前核心问题是执行循环把数据库访问、重复上下文计算和记忆提取串在同一关键路径上；失败后的上下文与运行所有权规则也不完整。保留现有 Python、PostgreSQL、消息类型和模型适配器，先调整执行边界，不进行整体重写。

本轮实际运行了：

- 包含真实 PostgreSQL 集成测试的现有测试集：103 项全部通过。
- 9 组主链路场景，每组 5 次，记录阶段耗时、显式 SQL execute 次数、模型调用数和事件完整性。
- 40／200／400 条消息的上下文构建微测，每组 5 次。
- 4 组故障探针：记忆收尾超时、失败后的文件副作用、失去执行者的运行、同步文件操作超时。
- 5 种供应商配置的实际 HTTP 请求体检查，使用 MockTransport，无外网调用。

基线文件：[原始 JSON](diagnostics/main-path-baseline-2026-10-28.json)。脚本：[diagnose_main_path.py](../scripts/diagnose_main_path.py)。JSON 保存 Python／数据库版本、关键源码 SHA256 和每次样本。

测量使用无网络的确定性模型，主链路数据不是实际模型回答时间。没有进行浏览器可见首字、并发负载、真实断电／kill、网络重试或 Pi/Codex 同任务速度测量，因此不据此宣称端到端提速比例。

## 2. 复现方式与统计口径

```sh
CHAGENT_TEST_DATABASE_URL=postgresql:///chagent \
  uv run python scripts/diagnose_main_path.py \
  --output docs/diagnostics/main-path-baseline-local.json --repeats 5

CHAGENT_TEST_DATABASE_URL=postgresql:///chagent \
  uv run python -m unittest discover -s tests
```

脚本要求显式设置测试数据库环境变量，不加载 .env、不读取 API Key。每次创建随机 `chagent_diag_` schema，关闭连接池后在 finally 中删除；文件副作用只发生在临时目录。进程被强制终止可能绕过 finally，需按该次 schema 名清理，不能批量删除其他运行的 schema。

本次环境：macOS、Python 3.13.9、PostgreSQL 16.15（Homebrew）。连接池预热和场景初始化不计时。SQL 数量指包装后的 `connection.execute` 调用，不包含隐式 BEGIN／COMMIT、fetch、连接池内部维护及验证查询；不能解释为全部网络往返数。

阶段 span 是包含子调用的时间，存在重叠，不能相加。`first_text_committed_ms` 是首个文本增量完成数据库提交的时间，不是浏览器首字。单次任务的 `model_stream` 也包含 Runner 等待增量落库的时间，不能全部归为供应商延迟。

时长包含诊断包装器开销；5 次样本只用于局部基线，不能代表生产 p95。不同场景按固定顺序执行，系统负载和缓存状态会引入波动。后续对比同时检查操作次数与时长，并交错运行 A/B 场景。

## 3. 主链路基线

下表为本次保存的 5 次耗时中位数。文本场景均输出 1,024 个字符，只改变分片数量。

| 场景 | 耗时中位数 | 显式 SQL 次数 | 观察 |
|---|---:|---:|---|
| 1 次 Echo 工具循环 | 9.12ms | 44 | 含 2 次模型调用、工具意图与结果提交 |
| 文本 1 个增量 | 4.87ms | 27 | 无工具、关闭记忆 |
| 文本 32 个增量 | 10.89ms | 89 | 同样的正文产生更多事务与事件 |
| 文本 128 个增量 | 32.37ms | 281 | 增量阶段执行 256 次显式 SQL |
| 32 个增量，每次持久化前注入 5ms 等待 | 208.33ms | 89 | 等待被串入模型流消费路径 |
| 同批 3 个各等待 20ms 的工具 | 82.32ms | 58 | 工具等待顺序相加 |
| 8 轮工具／9 次模型调用 | 35.86ms | 163 | 每轮重新读取与构建 |
| 同上，开启空记忆库检索，关闭自动提取 | 39.03ms | 191 | 9 次检索共 27 条 SQL，收尾额外读取 1 次历史 |
| 开启记忆，提取模型注入 50ms 等待 | 87.63ms | 35 | 模型最终输出后的收尾中位数为 81.76ms |

最后一行的 50ms 是注入的 sleep 参数，并非测得的全部记忆耗时；调度和其他阶段使实际收尾更长。空记忆库结果也不能代表真实记忆规模下的检索成本。

### 3.1 增量落库

`AgentRunner._response()` 对每个 `text_delta` 等待 `RunRepository.event()`；后者开启事务，锁定运行行，再计算序号并插入事件。每个增量增加两次显式 SQL execute 及相应事务成本。本次分片数量变化时，总 SQL 满足 `25 + 2 × 增量数`。

注入等待的场景保留真实 SQL，只在增量事件入口附加 5ms 延迟，用于验证依赖关系。它证明事件接收端的等待会反向阻塞模型流，不能用来估计生产数据库恰好增加多少延迟。

网页 SSE 当前按 150ms 周期查运行和事件。空闲时单连接理论上约 13.3 次查询／秒；这是代码推导，未做多连接实测。

### 3.2 上下文重复计算

| 输入消息数 | count 调用次数 | 累计序列化消息数 | 构建中位数 |
|---:|---:|---:|---:|
| 40 | 22 | 522 | 2.73ms |
| 200 | 102 | 10,602 | 48.96ms |
| 400 | 202 | 41,202 | 185.14ms |

每轮包含一条用户消息与一条助手消息，各有 200 字符正文。为了观察增长，使用 1,000 条历史上限和足够大的上下文窗口；默认历史上限为 200，不能把 400 条全部保留的结果当成默认配置耗时。

根因：Builder 为每个候选轮次重新 render 和 count；默认计数器每次执行 asdict 与 JSON 编码。历史选择范围内出现近似二次的重复工作。压缩二分试探又会多次调用 Builder。数据库历史读取没有利用摘要边界限制原始消息加载范围。

## 4. 故障复现与误判更正

### F1：回答已保存，记忆提取却使整个运行失败

固定模型先完成回答；记忆模型等待 2 秒；主运行总超时设为 0.5 秒。结果：最终助手回答已经保存，记忆请求已开始，但运行终态为 failed。

原因：`prepare_completed()` 与任务循环共享总超时，并且在 `runs.finish(completed)` 前执行。普通记忆错误虽会被捕获，运行总超时引发的取消仍会传到 Runner。

### F2：实际副作用仍在，下一轮上下文排除了操作记录

先通过真实 write_file 写入临时目录，再让后续模型调用失败。结果：文件存在；失败运行有 3 条可检查消息；新运行的模型历史中，这次失败运行的消息数为 0。

当前过滤规则整体排除 failed／cancelled／interrupted 运行，既排除了不完整批次，也一起排除了已经完成的操作事实。不能简单恢复整段原始记录，否则会重新引入孤立调用和失效摘要。

### F3：失去所有者的 running 记录阻塞继续

在数据库创建 running 记录，但不登记任何活动 asyncio Task，随后创建新 Runner。结果：新运行被 RunBusyError 拒绝；新 Runner.cancel 返回 false；数据库仍是 running。

这是所有者缺失状态的确定性模拟，没有真的杀进程。仍需在实施恢复机制后增加子进程 kill／重启验证。

### F4：同步文件操作越过异步超时

在真实 read_file 的同步 handle 边界注入 50ms 阻塞，ToolExecutor 超时设为 10ms。结果：约 55.55ms 后正常返回，is_error=false。

原因：同步调用期间事件循环不能推进取消，asyncio.timeout 不能抢占同步工作。这是事件循环阻塞验证，不是磁盘速度测量。

### C1：撤回“输出预算没有发送”的上一轮结论

上一轮只检查了 `transcript.openai_payload()`，漏看外层 `OpenAIChatClient.payload()` 的补充逻辑。这是审查遗漏，当前完整发送路径已传递预算。

本轮用 MockTransport 检查实际 HTTP request body，指定 17：OpenAI 预设请求包含 max_completion_tokens=17；DeepSeek、Qwen、Anthropic 和 custom 包含 max_tokens=17。5 种配置均完成解析，无外部网络。

因此不把“补传输出预算”列为修复项。后续仍需要能力矩阵覆盖不同模型配置，但这与本次错误判断是两件事。

## 5. 修改方案与顺序

### 第一阶段：完成语义与恢复边界（P0）

**A. 分离任务完成和记忆提取。**（已实施：`memory_jobs` 队列 + `MemoryWorker`，见[关键路径优化](关键路径优化.md)）

- 改动入口：agent/runner.py、memory/service.py、storage/repositories.py、网页 lifespan；增加记忆任务表迁移。
- 显式 /remember 保留现有确定性保存与冲突校验。
- 自动提取仅在主运行完成事务内写入记忆 job，包含 run_id、源消息 ID、提取策略／提示词版本；唯一键防重复。
- 有界后台 worker 处理 job，使用独立超时、重试计数和租约。候选审核和证据检查保留。
- job 与运行完成在同一事务提交，避免“运行完成后、入队前崩溃”丢任务。不能只 create_task 后不追踪。
- 记忆故障只影响 job 状态；用户取消已完成任务不能把原运行改成 cancelled。关闭与重启可重新处理未完成 job。

验收：将提取耗时从 50ms 改为 2 秒，主运行完成耗时不随其增加；最终回答状态保持 completed；job 能在重启后重试；同一输入不重复生成候选；记忆可用时间允许晚于主任务完成。

**B. 引入最小运行所有权和失联修复。**

- 增加 owner_id、lease_expires_at／心跳；活动 Runner 管理心跳任务。
- 所有状态修改校验当前所有权。后台扫描只处理租约到期的运行，不在启动时无条件中断所有 running。
- 将失联运行和未完成调用转换为明确终态，工具副作用标记 unknown；保存对应事件，再允许新输入。
- 单进程场景也使用明确的所有者规则，避免以后多进程时错误接管。

验收：子进程 kill 后在限定租约时间内解除占用；仍有心跳的运行不被接管；两个恢复者只允许一个胜出；已确认的工具结果不丢失；不自动重放写入和命令。

**C. 保存失败运行中的已确认事实。**

- 原始消息和失败状态保留，摘要有效性规则不放宽。
- 构建恢复上下文时，识别完整工具批次、已提交的操作结果和 unknown 操作。
- 用宿主生成的恢复观察记录表达状态、来源、文件或产物引用；工具正文仍按不可信数据处理。
- 不把未完成的 assistant/tool 序列直接混回正常历史，不把原始失败摘要直接激活。
- unknown 操作提示核验当前状态；重复执行前仍遵守工具的副作用规则。

验收：F2 的下一轮可以看到“写入已经成功”的带来源事实；协议配对校验通过；未闭合调用不进入请求；失败摘要仍不激活；取消发生在结果提交前后两种情况均有正确表示。

### 第二阶段：缩短稳定执行路径（P1）

**D. 先合并文本增量，再分离实时订阅。**

- 第一小步保留可靠事件序号与事务：在有界时间／字节阈值内合并文本增量，例如先试验 20ms／4KiB，而非逐供应商分片提交。
- 到达阈值、流结束、错误、取消和阶段切换时处理剩余缓冲；低速流也必须由计时器触发刷新。
- 内存队列有容量上限；数据库变慢时施加明确背压，不能无限增长。
- 第二小步加入进程内订阅：已提交事件直接通知 SSE，历史回放仍查询 PostgreSQL；必要时以低频查询检查其他实例写入。
- 对浏览器承诺的持久化游标只能对应已提交事件。若以后支持未提交的即时预览，必须另行定义其无持久 ID 的语义及最终替换规则。

验收：固定 1KiB、128 增量的突发样本，文本事件相关 SQL 降到不超过 8 次（可调整的本地验收目标）；正文逐字相同；终态和最后一段文本无乱序；断线游标回放无缺漏；取消／失败及时刷新或明确终结；不因缓存造成无界内存。

20ms 是待验证配置，不是性能承诺；低速流中保存频率由时间阈值决定，不能只看突发样本的 SQL 数量。

**E. 优化上下文投影与计数。**（已实施：投影缓存 + 可加计数，见[关键路径优化](关键路径优化.md)；供应商校准仍未做）

- 先消除一次 build 内重复序列化：只对消息的模型可见投影计算一次成本，以轮次累计值选择候选。
- 可替换 TokenCounter 未必可加；为可加计数器定义明确能力，未知实现保留精确回退，不能强行求和。
- 不以可变 dataclass 的对象身份作为缓存键；使用持久消息 ID、投影版本和计数器版本。
- 压缩试探复用已准备的投影和累计量，最后一次对实际请求完整校验。
- 正常上下文查询加载摘要后保留的尾部、必要系统消息和当前输入；审计／摘要源读取保持独立。
- 再增加 run-scoped 活动状态，每轮追加已提交消息。任务状态、记忆和工具集合按版本失效。同会话单写者和租约提供一致性边界。
- 按实际供应商可见内容估算 token；逐步增加供应商校准，不把时间戳、usage 等内部 JSON 开销当成正文 token。

验收：同样 200 条消息，计数序列化量从 10,602 降到接近线性量级；本机微测目标先设为至少减少 70%，以分配／调用次数和多次交错 A/B 复核；工具配对、最新输入和任务约束仍完整；原始消息不被修改；摘要边界后的读取量有上限。

**F. 同一运行内复用记忆查询。**（已实施：run 级召回复用；首轮预算预留仍未做）

- 当前输入、workspace_id 和已选记忆引用放进 run-scoped 状态；同一输入不在每个工具循环重复读取。
- 记忆有明确 revision／epoch；编辑、删除、审核和注入预算变化时重新计算。
- 首轮预算必须给记忆预留空间，避免每次都在最后剩余预算里碰运气。

验收：9 次模型调用不会产生 9 次相同检索；至少消除重复用户输入与会话查询；中途编辑／删除的可见时机有明确约定；每次请求仍记录实际注入的版本。

### 第三阶段：工具与交互能力（P2）

**G. 工具有界并发和阻塞隔离。**

- 从纯读取工具开始，用并发上限和明确资源互斥调度；写入同一文件和有依赖的命令保留顺序。
- 将同步文件操作放入有界工作线程或可管理执行器，先定义取消后的结果归属。线程取消不能撤销已经开始的文件修改。
- 并行结果可以按完成顺序记录事件，但给模型的批次结果顺序与调用 ID 必须确定。

验收：3 个独立 20ms 异步工具的执行等待接近一轮而非三轮；并发上限可观测；同文件编辑不竞争；事件循环心跳在慢文件操作时继续推进；取消后未确认完成的写操作不能被误记为没有发生。

**H. 进程会话、输入队列和模型重试。**

- ProcessManager 提供启动、等待、读取、stdin、终止与资源清理，长命令不绑定单次模型请求。
- 输入队列区分运行中纠正与排队后续输入，在工具／模型边界消费，避免覆盖正在运行的请求。
- 模型重试区分永久失败、可重试失败、部分输出和已完成工具；保存尝试 ID，避免重放工具副作用。

验收：长命令可继续读取、可取消、无孤儿进程；运行中纠正有明确确认事件；重试不会重复执行已提交工具；模型重试、任务和后台记忆具有各自的预算。

## 6. 目标结构与复杂度控制

```text
SessionRuntime（运行所有权、活动状态、输入队列）
  → AgentLoop（模型／工具推进）
      → ContextManager（投影、预算、压缩）
      → ModelClient
      → ToolScheduler → ToolExecutor／ProcessManager
      → 已提交事件 → 实时订阅
      → Repository（关键提交、审计、恢复）
  → 主任务完成事务 → MemoryJob → 有界 worker
```

以上是职责边界，不要求立即为每个名字建立新类。先采用 run-scoped 状态，证明收益后再扩展为驻留 SessionRuntime。保留现有 dataclass、模型协议、工具协议和 SQL Repository；避免引入新消息中间件或通用插件框架。

Pi 参考点：packages/agent/src/agent-loop.ts 的内存上下文、直接事件流、steering／follow-up 和顺序／并行批次。Codex 参考点：core/src/state/session.rs、session/input_queue.rs、tools/parallel.rs、unified_exec 和 responses_retry.rs 的状态所有权、输入控制、独占／并行调度、进程及重试。两者均参考本地源码，不假定当前外部版本行为一致，也不复制其全部功能。

## 7. 交付与验证顺序

1. 当前交付：诊断脚本、原始 JSON、本方案；业务源码未改。
2. 首批实施 A／B／C，先建立故障回归用例，修正完成与恢复语义。
3. D／E／F 分开实施，每项保存 before／after 数据；不能只以总耗时下降作为正确性证明。
4. G／H 按任务需要逐步实施，保留小型调度核心。
5. 每批运行相关回归、现有集成测试与同版本诊断；比较实际请求、正文、工具副作用和数据库状态。
