**问题不是功能缺失，是边界放错了位置。**

Chagent 用 seatbelt 在**进程内**给自己上锁：策略写在自己的 Python 代码里，白名单要穷举每个运行时，探针要证明策略真的生效。这条路在「只跑预置依赖的 Python 测试」时成立，一旦目标变成「配置并启动 Spring Boot」就断了——不是漏配，是结构性的。

**方案一句话：把边界从「进程内的策略」换成「进程所在的位置」。**

**效果一句话：从「只能跑预置好依赖的 Python 小程序」变成「缺什么装什么，能编译、能起服务」。**

## 2. 诊断：三个病

**病一：白名单随生态线性增长。**
`deny default` 要求把每个运行时的每个路径都写进去。Python → Node → Go → Rust → JDK → Gradle → Kotlin，每加一个：`runtime_roots()` 加路径、`isolated_environment()` 加 PATH、探针加一条、验收加一轮。这是曲线，不是常数。

**病二：能力与门禁错位。**
审批 970 行、只读档、`workspace-write`、stdin、模式切换——实现完整，但守卫条件永不成立，所以永远走不到。模式是「先实现、再上锁，锁加上后没回收解锁条件」。

**病三：一个词表达三件事。**
改造前 `execution_profile=trusted-development` 同时表示「跑在哪」「能不能执行」「要不要人批」，配置与网页准入存在重复判定。`/api/info` 与 `/api/config` 的 `code_mode: false` 是统一工具面下“不能选择旧 code 标签”的兼容值，不是执行能力标志；现已新增 `boundary`，并继续使用 `programmable` 表示网页可编程能力。

## 3. 决策

| # | 决策 | 理由 | 被否决的替代 |
|---|---|---|---|
| D1 | 边界放**进程外**：整个 Chagent 跑在容器里 | 白名单曲线换成常数：加工具链＝改镜像一行 | 继续扩 seatbelt 白名单（曲线无解） |
| D2 | 保留 `WorkspaceFS` | inode 校验、不跟随符号链接，容器里同样需要，防止符号链接把写入引出挂载点 | 交给容器（挂载点内仍可被符号链接击穿） |
| D3 | **不做**工具级隔离（不学 gondolin） | Chagent 是常驻 web 服务，整进程容器天然可行；工具级要重写 317 行保护逻辑换更窄的边界；且 `tools/web.py` 联网工具在进程内，只路由 bash 等于边界开洞 | 把 read/write/edit/bash 路由进 micro-VM |
| D4 | 三轴拆开，只留 3 个合法组合 | 每个组合一句话能说清；增加的是语义不是分支 | 保留 4 档边界（组合爆炸） |
| D5 | 目标形态不做应用内沙箱与 14 项启动探针 | 容器标记与显式声明可阻止普通误配，但声明本身可伪造，不构成强安全证明 | 继续以旧探针作为唯一执行边界 |
| D6 | 审批保留为 `gate=approval`，但**不是**代码执行的前置 | 位置解决了边界，不需要逐次批准；审批留给不可逆的高危动作 | 让审批承担边界职责（当前的做法） |
| D7 | 先建新路径，再拆旧实现 | P2 纯删除可单独 revert；先删会让中间态无法验证 | 边删边改 |

## 4. 目标形态

三轴，各自回答一个问题：

| 轴 | 取值 | 回答 |
|---|---|---|
| `boundary` | `container` / `none` | 进程跑在哪 |
| `capability` | `full` / `read-only` | 能不能执行命令 |
| `gate` | `none` / `approval` | 高危动作要不要人批 |

只保留 3 个合法组合：

| 组合 | boundary | capability | gate | 用途 |
|---|---|---|---|---|
| A | `container` | `full` | `none` | **唯一能执行代码的生产形态** |
| B | `container` | `read-only` | `none` | 只读会话 |
| C | `none` | `read-only` | `none` | 没装 Docker 时的降级：能读写文件、能联网查资料，**不能执行命令** |

当前只有 **`container + full` 提供代码执行**。旧 `trusted-development + isolated` 已在第 6 步删除。本机 `configured` 仍可用于诊断，但生产网页只开放组合 A；B/C 的独立网页入口尚未交付。

三轴已经实现：`src/chagent/execution.py` 的 `resolve()` 是唯一推导与校验入口，`Settings.axes` 提供结果，`SandboxSettings.allows_execution` 是同一判定的运行侧一半。`container + full + approval` 记为 `RESERVED`：审批 broker 仍在，但没有入口接线，所以不向模型开放；其余组合在启动时拒绝。

组合 C 是刻意的降级：没 Docker 仍能读代码、改文件、写文档、查资料，只是不能跑程序。想在本机执行，用 Podman / Colima / OrbStack，都是 Docker 兼容运行时，不是例外路径。

一次代码执行的路径（改造后）：

```
模型调用 process → 容器内 bash（工作区挂载在 /workspaces） → 无白名单、可联网
                ↘ 审计写 tool_calls.details.boundary = {boundary, network, workspace_writable, image}
```

**第 4 步不能省，也不能用合成 fixture 代替**——项目自己的纪律是「合成 fixture 不计真实项目」。第 4 步跑通之前，1–3 都只是「代码写完了」。

### 5.1 第 2 步必须连带改的四处（已实施）

它们原来硬要求 `sandbox == "isolated"`，不改则容器根本起不来；现在四处都读同一份结果：

| 位置 | 原状 | 现状 |
|---|---|---|
| `config/__init__.py` | `trusted_development` 要求 isolated | `__post_init__` 调 `resolve()`，条件只写一处 |
| `web/policy.py` | 逐字符重复上一条 | 只判断 `axes.programmable` + 实际容器标记 |
| `bootstrap.py`、`builtin.py` | `unified` 要求 `sandbox.mode == "isolated"` | `sandbox.settings.allows_execution` 一个谓词 |

### 5.2 第 3 步的镜像与挂载

实际镜像与挂载配置见项目根目录的 [Dockerfile](../Dockerfile) 和 [compose.yaml](../compose.yaml)。镜像用 Python 基础镜像、Node 多阶段复制和 Java 21/Maven；Compose 只挂载显式指定的工作区，另有 PostgreSQL 与 Maven 缓存卷。

`execution_profile=containerized` 要求 `sandbox=off`、显式声明、工作区可写、网络开启、命令开启和 `approval=never`，并检查容器标记。旧 `trusted-development` 和进程内沙箱档已拒绝。

Compose 不挂 `~/.ssh`、`~/.aws`、`~/.gitconfig` 或宿主 `~/.m2`。模型 key 可由项目 `.env` 注入 Agent 进程；工具子进程使用筛选后的环境，不继承 key 与数据库连接串。

`web/__main__.py:30` 的 `HOST = "127.0.0.1"` 必须改成 `--host` 参数（默认仍 127.0.0.1），这是容器化**唯一**绕不开的代码改动。`boundaries.py:18` 的 `validate_workspace` 额外要求工作区落在 `CHAGENT_WORKSPACE_ROOT` 内，否则容器里读写「成功」但文件消失。

### 5.3 第 6 步保留什么

- `WorkspaceFS`（inode 校验、不跟随符号链接、版本哈希）
- `Sandbox.wrap(argv)` 接口本身——退化为恒等函数，**保留调用点**，将来换执行后端不用改工具
- `tool_calls.details.sandbox` → 改名 `details.boundary`，记录 `{boundary, network, workspace_writable, image}`

## 7. 预期效果

| 指标 | 现在 | 之后 |
|---|---|---|
| 可执行语言 | 4 种，依赖必须预置 | 任意，缺什么装什么 |
| 依赖安装 | 不可能 | 可以 |
| 平台 | macOS only | 任意（Docker） |
| 隔离代码 | ~1,150 行（含 398 测试）+ 508 行脚本 | ~120 行 |
| 合法组合 | 1（7 条件布尔断言写两遍） | 3（每格一句话） |
| 新工具链成本 | 改 3 处 + 重跑 14 项探针 + 一轮验收 | 改 Dockerfile 一行 |
| 启动自证 | 14 项探针，任一失败 503 | 1 条声明，不存在「探针被骗过」 |
| 模型撞墙重试 | 3 次后终止 run | 提示写明边界，第一次就绕开 |

**四项代价，必须写清楚**

1. **隔离强度实际下降**。容器不是安全边界：daemon 以 root 运行、默认共享内核。强隔离要 rootless + userns-remap + seccomp，本方案不含。
2. **macOS 上 bind mount 慢**。virtiofs 下小文件 IO 比原生慢 2–10 倍，`mvn` 编译可感知。
3. **容器内起服务要额外暴露端口**。用户说「跑起来」时 8080 在容器内，宿主需 `-p` 映射。这是行为变更。
4. **失去「本机直跑」**。没有 Docker 就不能执行代码（组合 C 仍可读写文件）。

## 8. 明确做不到

- **不是零信任**：能联网就能外泄；模型 key 在进程内存里。
- **不防容器逃逸**：内核漏洞、`--privileged`、挂载 `docker.sock` 都会击穿。
- **不回滚**：取消 run 后文件改动仍在。
- **无 PTY**：`process_stdin` 仍禁用，交互式命令跑不了。
- **不跨项目读文件**：工作区外仍不可达。

最后一条要说明：这不是退步。现在「读不到工作区外」靠 seatbelt 白名单，之后靠「没挂载进来」。**保证来源变了，结论没变**——而且更硬，白名单会配错，没挂载不会。

## 10. 验收口径

**第 1–2 步（声明）**
- `CHAGENT_BOUNDARY=none` 且 `allow_host_commands=true` → 拒绝启动
- `/api/info`、`/api/config` 返回 `boundary`，与启动横幅一致
- `/api/info` 的 `code_mode=false` 保留为旧标签兼容语义，`programmable` 与 `boundary` 分别报告网页执行能力和边界

**第 3 步（容器）**
- `docker compose up` 后 `curl localhost:8765/api/info` 返回 `boundary=container`
- 容器内 `java -version`、`mvn -v`、`node -v` 均有输出
- 浏览器能对话，能读写 `/workspaces` 下文件，宿主能看到改动

**第 4 步（真实链路）**
- 真实模型从空目录创建 Spring Boot 项目并生成 jar，服务启动，宿主 `curl` 返回 HTTP 200、`pong`
- 当前验收跨两次 run：首次遇到 NUL 入库故障，修复后续跑；没有人工补写项目文件或补执行命令。单次 run 完成仍属后续回归目标

**第 5 步（能力）**
- `pom.xml` 工作区 `run_tests` 返回 `suite=maven`
- run 的系统消息里能读出 `Boundary:` 段

**第 6 步（删除）**
- `grep -r "sandbox-exec" src/` 无结果
- 全量回归绿，跳过 0；删除后为 548 项通过、0 跳过，P3 收敛后为 563 项通过、0 跳过
