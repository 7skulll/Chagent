## 1. 初衷与当前定位

原始目标是借鉴 pi 的简洁工具循环，尽快让 Chagent 具备创建、修改、执行和验证代码的能力，同时把现有权限与逐次授权系统从编码主线中解耦。只读实现提供了有效的阶段性隔离验证，但不能完成可写编码闭环。

因此只读档保留为代码审查与分析配置，不再承担编码主线终点。编码主线现已交付显式启用的可信开发配置：复用现有工具与 Runner，在工作区边界内允许写入和执行，无需逐项审批；现有审批策略继续保留为另一条路径。具体顺序与验收统一见[实施计划](实施计划.md)。该配置的标准库项目编码闭环已完成真实模型网页验收，详见[开发验收](代码开发验收-2026-11-03.md)；真实项目与更多工具链仍在后续计划中。

借鉴 pi 的直接执行方式不等于复制其宿主权限范围，也不要求重写 Chagent。保留已有 isolated、工作区检查、运行记录、超时与进程回收；逐次审批与编码能力分别装配。

## 2. 只读档的实际契约

目标是让模型读取代码、执行适用命令，同时由内核禁止命令修改工作区。scratch、数据库、上传等仍可能写入，不承诺零副作用或完整资源隔离。只读不替代可写编码，也不替代需要审批的配置。

网页只在以下条件全部满足时开放只读 code：

```sh
CHAGENT_SANDBOX=isolated
CHAGENT_SANDBOX_WRITABLE=false
CHAGENT_SANDBOX_NETWORK=false
CHAGENT_CODE_MODE=on
CHAGENT_ALLOW_HOST_COMMANDS=true
```

审批配置沿用用户现有设置，不要求设成 never。沙箱只限制命令进程；模型 API、数据库和独立网页工具有各自的行为与配置。

## 3. 实现机制

改造前，两种启用的沙箱 profile 都授予工作区写权限。当前 `writable_workspace` 决定是否发出工作区写授权，Settings、SandboxSettings 和 SandboxPolicy 显式透传；配置默认 true 以保持既有底层行为，网页只读准入要求 false。

| 层 | 手段 | 效果 |
|---|---|---|
| 工具注册 | code 按实际沙箱禁写设置裁掉 write_file/edit_file/apply_patch；网页同时收回工作区写工具 | 工具面与能力一致，点名写工具返回未知工具 |
| 内核 | isolated profile 不授予工作区写权限 | Shell/Python/Git 等命令的工作区写操作被拒绝 |
| 网页门禁 | 配置与实际 runner、注册工具、沙箱探针共同检查 | 不因仅隐藏按钮或配置字段而放行 |
| 进程 | process 仅 read/stop，schema 与执行层都拒绝 write/EOF | 不提供交互 stdin |

isolated 采用默认拒绝与读取白名单，保留私有 scratch 的写权限。HOME/tmp 按 run 分配，进程回收后释放，不与工作区或运行时重叠。命令、测试与长进程使用公共环境，只读档设置 GIT_OPTIONAL_LOCKS=0 和 PYTHONDONTWRITEBYTECODE=1。

旧 workspace-write 以 allow default 为基础，读取和进程权限较宽；即使工作区禁写且命令断网，也不能据此认为它等同 isolated。其只读 profile 仅供显式诊断，共享临时目录授权与工作区重叠时拒绝。

## 4. 支持范围

| 操作 | 当前只读档 |
|---|---|
| 读代码、grep、glob、文档解析 | 工作区与文件身份检查通过后可用 |
| Git log/diff/show/status | 已验证常见流程；特殊配置/依赖可能失败 |
| Python、ruff、mypy 等 | 依赖和运行时可访问时可用；缓存需显式关闭或定位 scratch，不承诺自动降级 |
| pytest/unittest | 适用测试可运行；pytest 工具关闭缓存插件，但用例自身的工作区写入、外部读取或联网仍会失败 |
| 构建与安装 | 首版不承诺；是否可执行取决于写入位置、依赖、运行时和网络，不按命令名称推断安全性 |
| 工作区写工具与命令写入 | 写工具未注册；命令写入由内核拒绝 |
| create_file 下载 | 仍只属于 work，不扩展到 code |

当前范围是 macOS、本机已声明运行时与有限真实项目。只读不是 CPU、内存、进程数和 scratch 磁盘配额；已有超时与进程回收不等于完整资源隔离。

## 6. 与可写开发配置及恢复的关系

只读档、可信开发配置和审批配置分别有自己的能力与验证要求。已完成只读验收，不能仅将 writable 改为 true 就宣布可写网页交付；必须经过统一装配、门禁、写工具、真实模型编码闭环及对应回归。本轮可信开发配置已完成这些限定范围验收，详细证据与限制见开发验收。

Git checkpoint 可作为未来修改恢复辅助，但不替代隔离或授权，也不能承诺恢复数据库、外部服务、进程及任意未跟踪/忽略文件。它不作为首个可写闭环的前置条件；既有用户改动不得自动 stash/reset 或覆盖。

只读能力故障时关闭 code 并重启，保留配置与证据，不以恢复写权限或降级到 off 回退。后续开发配置也必须单独可关闭，保留用户文件与历史；不承诺回滚已发生的副作用。

当前实现契约见[执行边界设计](执行边界设计.md)，未来批次、顺序与完成条件只在[实施计划](实施计划.md)维护。
