# 只读 code 模式方案

状态：**R1–R5 已实施并完成本机只读验收；可写 code 未开放**。本文描述一种先于 C3 审批开放的 code 形态，目标是让模型能读代码、跑只读命令，但无法写入工作区。实施顺序与批次依赖只在[实施计划](实施计划.md)维护；当前实现见[执行边界契约](执行边界设计.md)。本文只对应已开放的只读形态；可写/交互审批批次仍保留。

## 1. 目标与非目标

目标：在**不做 C3 审批**的前提下，让 code 面可用，同时把「不可逆的文件副作用」从能力集合里整体移除，而不是靠提示词或工具裁剪来约束。

非目标：

- 不是 coding agent。不能改代码、不能提交、不能装依赖，见 §6。
- 不替代 C3。C3 仍要做，只是不再阻塞「读 + 只读执行」这一档。
- 不改变 work 的任何行为。

## 2. 为什么禁写必须落在沙箱层

这是本方案的全部前提。

工具层裁掉 `write_file` / `edit_file` / `apply_patch` 只让模型**看不见**写工具。`exec_command` 仍在时，`echo > x`、`sed -i`、`tee`、`python -c "open('x','w')"`、`git checkout -- .` 都能写。因此：

> 「禁止写」如果只做在注册层，等于没有做。

现有三种档位没有一种能禁止工作区写：

| 档位 | 工作区写 |
|---|---|
| `off` | 宿主权限 |
| `workspace-write` | profile 显式授予 `(subpath workspace)` |
| `isolated` | `isolated_profile()` 同样显式授予 `(subpath workspace)` 与 scratch |

两处授权分别在 `tools/sandbox.py` 的 `profile()` 与 `isolated_profile()`。要让「禁止写」成立，必须把工作区从 allow 列表里去掉，让内核返回 `EPERM`。

## 3. 方案

### 3.1 配置

```sh
CHAGENT_SANDBOX=isolated
CHAGENT_SANDBOX_WRITABLE=false     # 新增，默认 true；只接受 true/false
CHAGENT_SANDBOX_NETWORK=false
CHAGENT_CODE_MODE=on
CHAGENT_ALLOW_HOST_COMMANDS=true
CHAGENT_APPROVAL=never             # 保持现状，不改
```

选独立开关而不是新增第四个 `CHAGENT_SANDBOX` 枚举值，理由：

- 正交。「离线 + 禁写」需要 `isolated` 与禁写同时成立，枚举表达不了；`isolated` + `WRITABLE=false` 才是最强档。
- 改动面小。`MODES` 校验、`apply_policy` 分支、既有沙箱测试都不必改语义。
- 默认 `true`，不改变任何现有装配的行为。

### 3.2 profile 形状

`SandboxPolicy` 增加 `writable_workspace: bool = True`，`SandboxSettings` 与 `Settings` 透传。两个 profile 各自按它决定是否发出工作区写授权。示意（非完整语法）：

```scheme
(deny file-write*)
(allow file-write*
  (literal "/dev/null") (literal "/dev/stdout") (literal "/dev/stderr")
  (subpath "<用户 TMPDIR>"))          ; 工作区不在其中
```

**私有 TMPDIR 必须保留可写**。否则 Python 临时文件、pytest 的 `tmp_path`、构建工具的中间产物全部失败，只读档会退化成「什么都跑不起来」。

`isolated_profile()` 同理：去掉 `(subpath workspace)` 的写授权，保留 scratch。scratch 仍可写是刻意的——它按 run 私有分配，进程清理后释放，不属于用户工作区。旧 workspace-write 档的共享临时目录授权若包含只读工作区，则拒绝该组合。

### 3.3 两层同时生效

| 层 | 手段 | 效果 |
|---|---|---|
| 注册层 | `allow_workspace_writes=False`（已存在） | 模型看不到三个写工具，点名得到 `Unknown tool` |
| 内核层 | `writable_workspace=False` | 任何命令写工作区得到 `EPERM` |

两层都要。注册层负责让工具面诚实，内核层负责让绕过不成立。

## 4. 改动清单

| 文件 | 改动 |
|---|---|
| `tools/sandbox.py` | `SandboxPolicy` / `SandboxSettings` 增 `writable_workspace`；`profile()` 与 `isolated_profile()` 条件发出工作区写授权；`record()` 增 `workspace_writable` |
| `config/__init__.py` | 新字段与 `CHAGENT_SANDBOX_WRITABLE` 解析（默认 `true`），非法值在启动时报错而非静默取默认 |
| `bootstrap.py` `_tool_faces` | 保留生产 code 命令必须 isolated；只读 code 同时裁掉工作区写工具 |
| `tools/command.py` | 公共环境在只读档注入 `GIT_OPTIONAL_LOCKS=0` / `PYTHONDONTWRITEBYTECODE=1`，覆盖命令/测试/长进程 |
| `tools/tests_runner.py` | 已有 pytest `-p no:cacheprovider` 保持；统一只读环境，禁写 pycache、Git 可选锁 |
| `diagnostics/behavior.py` | `sandbox=` 后附只读标记，例如 `sandbox=isolated(ro)`；网页 `/api/config` 同源显示 |
| `web/__main__.py`、`web/app.py`（两处） | 三处 `raise ValueError("网页暂不支持 code 模式")` 改为：只读档放行，其余仍拒 |
| `web/app.py` 装配 | 保留 `allow_workspace_writes=False`（与只读档一致，网页不提供写入口） |

## 5. 能力边界

| 操作 | 只读档 |
|---|---|
| 读代码、grep、glob、文档解析 | 可以 |
| `git log` / `diff` / `show` / `status` | 可以（依赖 §4 的 `GIT_OPTIONAL_LOCKS`） |
| `python -c`、`ruff check`、`mypy` | 可以；缓存写失败时降级为不缓存 |
| `pytest` | 可以；用例内 `tmp_path` 正常，仓库缓存不写 |
| `cargo build`、`npm install`、`go build` | 不可以，需要写 `target/`、`node_modules/`、构建缓存 |
| `write_file` / `edit_file` / `apply_patch` | 未注册 |
| 工作区内的文件写入 | 内核拒绝；私有 scratch 仍可写 |
| `create_file`（写数据库、生成下载） | 仍只属于 work，首版不扩展到 code |

结论：这一档的实际定位是**代码审查与分析**，不是修改。若目标是「能改但可回滚」，应做 §9 的 git checkpoint，而不是本方案。

## 6. 安全性发生了什么变化

对比 `isolated`，只读档在三点上更弱：

1. **可读范围**。`workspace-write` 底子是 `(allow default)`，只定向遮挡 9 条凭据路径（`~/.ssh`、`~/.aws`、`~/.npmrc` 等）。它能读用户 home 下其他一切——包括源码、笔记、其他项目。
2. **可联网**。若 `CHAGENT_SANDBOX_NETWORK=true`，命令可以出网。写入被拒不等于数据出不去：`curl -d @file` 是读操作 + 网络发送，profile 拦不住。
3. **进程权限**。可以 exec 任意二进制、向其他进程发信号。文件系统不可逆副作用被消除，进程层面的不可逆动作（杀进程、发通知、调系统服务）没有被消除。

因此，**只读 + 断网不足以证明 workspace-write 可以跳过 C3**。该档仍允许较宽的宿主读取、进程信号和系统交互，不能称为“命令只剩读取和本地计算”。

首版网页只开放 `isolated + writable_workspace=false + network=false`，保留现有生产命令的 isolated 门槛。workspace-write 的只读 profile 可用于显式诊断，不作为网页开放条件。隔离只约束命令进程，不约束 Agent 自身的模型请求、数据库写入或独立网页工具；不得承诺零副作用或绝对防外泄。

首版 `process` 仅开放 read/stop，schema 与执行层都拒绝 write/EOF；后续交互输入由 C3 处理。已有 exec/test 审批配置继续生效，不强制覆盖为 never。具体落地与真实探针门槛见[实施计划](实施计划.md)。

## 7. 探针与验收

正向（必须成功）：

- `cat README.md`、`grep -r def src`、`git log --oneline -5`、`git diff`
- `python -c "print(1)"`
- `python -c "import tempfile; tempfile.NamedTemporaryFile().write(b'x')"`

反向（必须失败，且是 `EPERM` 而不是命令不存在）：

- `echo x > probe.txt`
- `touch probe.txt`
- `python -c "open('probe.txt','w').write('x')"`
- `sh -c 'printf x | tee probe.txt'`
- `git checkout -- .`（准备有实际差异的受跟踪文件，核对写入被拒且内容不变）
- `sed -i '' s/a/b/ README.md`
- 点名 `write_file` / `edit_file` / `apply_patch` → `Unknown tool`

回归要求：

- `scripts/start.command` 启动后 `/api/config` 的 `behavior` 显示只读标记。
- 工作区前后文件清单、内容哈希及相关元数据一致；`git status` 仅作辅助，不能漏过被忽略文件。
- 全量测试通过，`workspace-write` 与 `isolated` 的既有探针不得因新字段改变行为。
- 依赖真实 seatbelt 的用例（`test_sandbox`、`test_readonly`、`test_web` 两条只读 API 用例）在机制不可用时按 `SEATBELT_READY` 跳过，不报成回归；跳过不等于通过，本机“0 跳过”的数字不能外推到 CI。
- 只读门禁本身的拒绝行为必须有一条不依赖 seatbelt 的用例：`test_readonly_missing_backend_refuses_api_before_model_call` 在缺少后端时返回 503 且不调用模型。

只测正向等于没测：本方案的价值全在反向那七条。

## 8. 回退

关闭 code 并重启服务，保留只读配置和诊断；不以恢复工作区写权限、关闭沙箱或降级档位作为运行期回退。代码按实施批次逆序回退，无数据库迁移。详见实施计划。

## 9. 与 git checkpoint 的关系

只读档用「不能改」换取安全。另一条路是「能改但可回滚」：每个 turn 前 `git stash create` 存一个 shadow ref，出问题可恢复到 turn 边界。

| 取舍 | 只读档 | checkpoint |
|---|---|---|
| 能改代码 | 不能 | 能 |
| 不可逆风险 | 工作区写入被拒；scratch 仍可写 | 降到「一个 turn 内的改动」 |
| 依赖 | 无 | 工作区必须是 git 仓库且干净 |
| 适合 | 审查、分析、只读执行 | 真实修改 |

两者不冲突，可先后实施。若用户的目标是「让模型干活」，checkpoint 更接近；若目标是「先让 code 面在网页上跑通且工作区不可写」，本方案更直接。

## 10. 首版已确定的取舍

- 会话创建后保持 mode 固定，不新增中途切换；服务级只读设置改变后重启。
- process 仅开放 read/stop，write/EOF 在 schema 和执行层均拒绝。
- 已有审批配置继续生效；无需 C3 不等于取消 exec/test 审批。
- 首版只使用 isolated；work 工具面保持既有语义，code 不新增 create_file。
- 文件边界统一、scratch 会话隔离及正反向探针是开放依赖，不由只读开关替代。

具体 R1–R5 步骤、文件范围与完成条件统一维护于[实施计划](实施计划.md)。
