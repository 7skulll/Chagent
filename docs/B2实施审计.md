# B2 实施与审计：失败运行的事实恢复

状态：已实施。失败、取消与中断运行中已提交的副作用进入下一次上下文，原始消息仍不回放。

## 为什么不能直接放开历史

`ConversationRepository.messages()` 只为模型加载 `completed` 运行与当前运行的消息。失败运行可能停在半个工具批次里：助手消息带着 tool call、结果没提交，或者反过来。原样放回历史会让 `ContextBuilder._validate` 的配对检查失败，供应商协议也不接受孤立的 tool result。

所以恢复走另一条路：只读结构化记录，历史一行不改。

## 实现

| 位置 | 改动 |
|---|---|
| `domain/recovery.py` | `RecoveryFact`、`RecoveryNote`、`build_recovery_note()`：渲染宿主注记，按（工具，目标）取最新，上限 12 条／2000 字符 |
| `storage/repositories.py` | `RunRepository.recovery_facts()`：只读查询，不写任何行 |
| `agent/runner.py` | 每次运行加载一次事实，有事实时写 `recovery_projected` 审计事件 |
| `agent/types.py` | `RunState.recovery`，同一运行的所有轮次复用一份注记，不重复查询 |
| `context/builder.py` | 作为固定系统开销的一部分注入，计入上下文预算 |
| `domain/context.py` | `ContextSnapshot` 增加 `recovery_fact_count` 与 `recovery_source_runs` |

注记永远不是消息：没有 message id、没有 sequence，不会被回放、压缩，也不会被当作 tool_call 的配对结果。

## 采集与措辞

- 只采信 `tool_calls.status = 'completed'`（模型已经看到的确定结果）与 `'unknown'`（已开始但无结果）。`'failed'` 表示工具返回了错误结果、没有留下持久副作用，不投影。
- 只收集有外部副作用的工具：`write_file`、`edit_file`、`exec_command`。读操作不产生事实。
- 每条事实带源运行、工具名、目标、提交状态；有产物时附 artifact 短 id。
- `unknown` 的措辞固定为 "no result was committed, verify before retrying"，不写"已完成"。
- 注记正文声明自己是参考数据，重复执行必须重新确认；它不构成授权，也不写入 task_state。

## 恢复边界（去重）

只读**最近一次 completed 运行之后**的失败。会话一旦有运行正常结束，更早的失败就属于历史——否则每次续聊都会重新注入同一批旧事实。更早的失败仍留在数据库与诊断脚本里可查。

同一条失败链里反复修改同一文件，按（工具，目标）只保留最后一次；这是"状态快照"而不是"操作日志"。

## 验收

192 项测试通过（B2 新增 9 项）：

| 用例 | 覆盖 |
|---|---|
| 已确认写入进入下一轮 | 文件真实存在；下一轮 system 含路径、committed、源运行 id；历史里仍只有新输入 |
| unknown 不写成成功 | 手工把工具置 `unknown` 后，注记措辞为未知 |
| 完成运行之后不再注入 | 失败 → 正常结束 → 再续聊，注记消失 |
| 同目标只保留最新 | 两次失败写同一文件，注记只有一行且是后一次 |
| 只读工具不算事实 | `list_dir` 失败后没有注记 |
| 渲染规则 | 空集合返回 None；按目标去重；上限 12 条且保留最新的 |

实测确认 F2 的形态已经反转：`write_file` 落盘 → 模型请求失败 → 下一轮的 system 指令里出现"`write_file notes.txt` — committed"，而 `messages` 仍只有 `["system", "user"]`。

## 未覆盖的边界

- 注记不持久化，因此没有 message id：可在 `model_calls.request` 与 `context_snapshot` 中审计，但不能回放。
- 若下一次运行正常结束却完全没碰那些文件，再下一次不会知道这些事实。放宽这条要按目标跟踪"最近一次成功写入"，属于后续工作。
- 恢复注记不改变授权：看到 `exec_command` 曾经执行过，不代表现在可以执行。
- `exec_command` 的 `unknown` 只说明结果没落库，不能证明子进程已停止——B1 的同一限制在这里依然成立。
