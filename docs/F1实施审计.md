# F1 实施与审计：事件批量提交

状态：已实施。文本增量的写入从"每条一个事务"变成"每批一个事务"，事件行、序号与回放语义不变。

## 问题

一次 1.6 秒的流式回答产生 76 条 `text_delta`，每条都走同一条路径：开事务 → `check_owner`（`SELECT ... FOR UPDATE`）→ 锁 `runs` 行分配序号 → `INSERT` → 提交。也就是 76 次 fsync、76 个事务、约 245 条 SQL，全部压在模型流上。

A 批的文本合并只解决了突发（128 片压成 2 个事件），但真实供应商是慢速流：一次刷新只产生一条事件，合并窗口无从发挥。

## 实现

| 位置 | 改动 |
|---|---|
| `storage/event_queue.py`（新） | `EventStream`：每 run 一个有界缓冲（256 条）、一个 `asyncio.Lock` 保证顺序、一个刷盘任务（100ms 或 64 条触发） |
| `storage/repositories.py` | `emit()` 只入队；`flush_events()` 排空；`close_events()` 收尾；`event_failure()` 供模型流等待；`_insert_events()` 支持一次插入多行 |
| `agent/runner.py` | 文本增量改走 `emit()`；`_response()` 与模型流、文本 writer 一起等待刷盘失败；每个响应结束前排空一次；`finally` 里关闭流 |
| `tests/test_event_batch.py`（新） | 8 项：缓冲、后台提交、顺序、终态、拒绝、失权、关闭、上限 |

批量插入仍由数据库分配序号：

```sql
INSERT INTO run_events (run_id, sequence, type, payload)
SELECT %s,
       (SELECT COALESCE(MAX(sequence), 0) FROM run_events WHERE run_id = %s)
         + row_number() OVER (ORDER BY t.ord),
       t.kind, t.payload::jsonb
FROM unnest(%s::text[], %s::text[]) WITH ORDINALITY AS t(kind, payload, ord)
```

`MAX(sequence)` 读到的是语句开始前的快照，所以一条语句可以给整批编号；批量事务仍然先 `check_owner` 锁住运行行，别的写入者不会插进来。

## 三个必须守住的点

**顺序靠"写前排空"，不靠内存排序。** 任何业务写入（`save_response`、`queue_tool_calls`、`tool_completed`、`finish`、直写 `event`）在开事务前都先调用 `flush_events()`。缓冲里的增量永远以更小的序号先落库，因此 `sequence` 顺序就是入队顺序，不需要第二套序号分配。

**终态事件仍在 `finish()` 的同一事务里。** 排空发生在终态事务之前，而不是之后：状态行、`run_failed`/`run_completed` 与它们前面所有增量一次性提交，回放不会看到"终态之后还有文字"。

**刷盘失败必须中断模型流。** 只把错误存在缓冲里是不够的：供应商阻塞时没有下一次 `append` 来暴露它，运行会一直挂着。`_response()` 因此同时等待三件事——消费者、文本 writer、事件流失败——任一先完成就按它处理。

## 失败与退化的边界

- 批量被数据库拒绝（例如触发器报错）：`flush` 记下错误并抛出；`finish()` 捕获后丢弃这一批并照常写终态。**终态优先**——事件已经丢了，让运行卡在 `running` 只会更糟。
- 所有权丢失：`finish()` 不吞这个错误，`RunOwnershipLost` 继续上传，由 runner 归类为 `storage_error`，运行留给扫描器收敛。
- 取消：`close_events()` 排空一次再停任务；排不空就丢。强杀最多丢 100ms 内未提交的增量，消息与工具结果不受影响。
- 缓冲满（256 条）：`emit()` 直接 `flush()`，把"数据库慢"变成对生产方的背压，而不是无界内存。

## 实测

`scripts/bench_write_path.py --repeats 3`，同一临时 schema、同一模拟供应商：

| 场景 | SQL | 事务 | 事件 | WAL |
|---|---:|---:|---:|---:|
| 两轮模型 + 一次工具（改前 → 改后） | 57 → 56 | 11 → 11 | 10 | 20KB |
| 1.6 秒流式回答（改前 → 改后） | 260 → **64** | 81 → **21** | 80（增量 76） | 38KB → 32KB |

21 个事务 = 建运行、开始模型调用、17 个增量批次、保存响应、收尾。

**没到方案里的"约 45 条 SQL"**：每批仍要 `check_owner`（2 条：校验 + 插入）。再往下压就得把所有权校验降到"每 N 批一次"，那会削弱 B1 的边界，不做。F2 会通过条件更新把校验并进业务语句，那才是剩下的降幅。

**墙钟没有变快**（1666ms → 1690ms，噪声内）。这符合预期：1.6 秒由模拟供应商的 150×10ms 决定，F1 的作用是让提交不再串在流上，而不是让模型变快。

## 验收

全量 200 项通过（F1 新增 8 项）：

| 用例 | 覆盖 |
|---|---|
| 增量缓冲不落库 | `emit` 两次后库里只有 `run_started`；`flush` 后两条按序出现 |
| 后台自动提交 | 不调用 `flush` 也能在窗口内看到事件 |
| 直写与缓冲混排 | 两条增量 + 一条 `tool_queued`，序号 1..4，拼接正文正确 |
| 终态最后写 | 有未排空的尾部时，`run_cancelled` 仍是最后一条 |
| 批次被拒绝 | 触发器拒绝 `text_delta`，终态仍写成 `failed`，事件表无增量 |
| 失权不被吞 | 令牌不匹配时 `finish` 抛 `RunOwnershipLost`，运行仍是 `running` |
| 关闭收尾 | `close_events` 后无 `run-event-flush-*` 任务残留，尾部已提交 |
| 缓冲上限 | 超过容量时 `emit` 等待一次提交，缓冲不超界 |

事件链路原有的 21 项（SSE 回放、慢读、断线、并发订阅、提交失败中断供应商）全部保持通过，其中三项把打桩点从 `event()` 换到 `emit()`，因为文本增量不再走直写路径。

## 未覆盖的边界

- 刷盘任务在进程内，跨进程的审计事件（记忆 worker 的 `memory_saved`）仍走直写路径，与批量事务靠 `runs` 行锁互斥。
- 100ms 是我们选的回放粒度：放宽到 250ms 能再少一半事务，但断线重连时一次补的块更大。
- 批量写失败目前只能整体丢弃，没有"重试一次"的策略。数据库短暂不可用时会丢一个窗口的增量；正文仍在 `messages` 里，不影响回答本身。
