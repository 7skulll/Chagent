## 1. 目的与范围

三个目标分开建设，**不合并成一个"打分系统"**。合并的后果是得到一个既不能诊断也不能门禁的排行榜。

| 编号 | 系统 | 回答的问题 | 交付物 |
|---|---|---|---|
| **T** | 链路追踪 trace | 一次运行发生了什么，时间和钱花在哪 | 统一 Span 视图 + 单次运行诊断卡 |
| **A** | 失败归因 attribution | 坏在哪一层，该改哪个文件 | F1–F10 标签 + 频率分布表 |
| **L** | 闭环自迭代 loop | 改了什么，是否真的变好 | 提案 → 门禁 → 指标曲线 |

**顺序固定为 T → A → L。** A 未做扎实就做 L，等于按指标盲改：能观测到"分变了"，但无法区分是能力变了还是判据漂了。

## 2. 现状盘点

### 2.1 已有资产（不需要新埋点）

| 资产 | 位置 | 对本方案的用途 |
|---|---|---|
| 每次模型请求与响应 | `model_calls.request` / `response` / `context_snapshot`（jsonb） | 回放、上下文差异、时延与用量 |

| 事件时间线 | `run_events`（26 类） | 阶段耗时、压缩与审批时点 |
| 审批记录 | `approval_requests` | 人工介入率、审批摩擦（F9） |
| 失败分类 | `tools/retry.py` 八类结局 + `retryable` | 现成的失败标签，不需 LLM 判定 |
| 路径投影 | `models/outbound.py` | 让回放产物跨机器可比（绝对路径不进 fixture） |
| 无头装配 | `bootstrap.create_runner` / `create_demo_runner` | 执行器入口，含确定性自检面 |
| 工作区隔离 | 每工作区独立容器 | 用例沙箱，可弃置 |

### 2.2 实测基线（2026-11-09，本机 `chagent` 库）

| 状态 | 数量 | 平均工具调用 | 平均轮次 | 平均耗时 | 最大耗时 |
|---|---|---|---|---|---|
| completed | 142 | **1.8** | 2.5 | 4 s | 64 s |
| failed | 17 | **6.6** | **5.9** | 16 s | 166 s |
| cancelled | 1 | 20.0 | 13.0 | 15 s | 15 s |

三条读数，全部影响后续设计：

1. **失败的特征是挣扎，不是偷懒。** 失败 run 的工具调用是成功的 3.7 倍、轮次 2.4 倍、耗时 4 倍。因此改进信号不必等到失败：库里存在"成功但用了 23 次工具、18 轮、64 秒"的 run，它本身就是工单。**改进 backlog 主要在"成功的烂 run"里。**
2. **历史语料主要是闲聊，不能当能力测评集。** 142 个成功 run 中 42 个零工具（纯对话）、85 个仅 1–3 次工具，超过 10 次的只有 5 个。历史数据可用于建归因器，但能力测评必须另建用例集。
3. **时延与成本已经入库。** `model_calls.response` 含 `duration_ms`、`usage`、`stop_reason`。记账缺的是聚合层，不是采集点。

停滞规则的实测：按 `(run_id, name, arguments)` 分组，重复 ≥3 次的组合为 **0**。F7 在现有语料上零命中——规则要写，但不能靠它撑起归因覆盖率。

## 3. 三个系统的设计

### 3.1 T · 链路追踪

**统一 Span。** 把五张表规约成同一形状，只读、不改写路径：

```
Span(span_id, run_id, parent_id, kind, started_at, ended_at,
     wait_ms, tokens_in, tokens_out, cost, status, payload_ref)

kind ∈ {run, model, tool, approval, compaction, memory, site}
```

**时延分解。** 这是最容易做错的一处：**工具耗时必须扣掉审批等待**，否则"工具很慢"实际是"人在想"。

```
端到端 wall
├── 模型时间     Σ(model.ended − model.started)
│   └── 首 token  model_started → 第一个 text_delta
├── 工具时间     Σ(tool.ended − tool.started) − Σ(审批等待)
├── 审批等待     Σ(approval_decided − approval_requested)
├── 压缩时间     compaction_calls
└── 空闲/调度    wall − 以上之和      ← 这个数大 = 框架问题，不是模型问题
```

**上下文差异。** `context_snapshot` 是本方案里价值最高、目前完全未开采的资产：

- 上下文水位曲线：每轮 token 数，压缩在第几轮触发
- 轮间 diff：第 N 轮有的消息在第 N+1 轮消失
- 压缩因果：`compaction_calls` 前后各丢了哪几条工具结果
- 注入审计：记忆与环境注入了什么

"为什么这次回答不对"，多数答案在上下文差异里，不在最终输出里。

**完成判据**：一条命令打印任一次 run 的完整时间线；一个屏幕（时间瀑布 + 工具序列 + 上下文水位 + 失败标签 + 成本）能回答"这次哪里坏了"。

### 3.2 A · 失败归因

**先给结论：多数归因可以机械判定，不需要 LLM judge。**

| 标签 | 含义 | 判据来源 | 可机械判定 | 改动位置 |
|---|---|---|---|---|
| F1 | 规格误解 | 需人判定或用例期望 | ✗ | 提示 |
| F2 | 上下文丢失 | `context_snapshot` 轮间 diff | **✓ 强** | 压缩策略 / fresh window |
| F3 | 工具选错 | 工具序列 vs 用例期望 | ✓ 半 | 工具描述 / 延迟加载 |
| F4 | 参数错误 | schema 校验 / 执行期报错类型 | ✓ | 工具 schema / 校验 |
| F5 | 执行失败 | `tools/retry.py` 八类 | **✓ 现成** | 工具实现 / 环境 |
| F6 | 结果误读 | 下一步 `arguments` 与上一步 `result` 矛盾 | ✓ 半 | 结果格式 / 事实放置 |
| F7 | 循环停滞 | 同 `name + arguments` 重复 | ✓ | 停滞检测 + 提示注入 |
| F8 | 预算耗尽 | 计数器 + run 终态 | ✓ | 预算配置 |
| F9 | 审批摩擦 | `approval_requests` 拒绝 / 超时 | **✓ 独有** | 审批粒度 / 分级 |
| F10 | 环境漂移 | 工作区清单哈希变化 | ✓ | 用例夹具 |

F2、F5、F9 依赖本项目独有数据，是这个方案相对通用 agent 测评的主要差异化点。

**规则形态**：一条标签一个纯函数 `Span[] → label | None`，代价零模型调用，可对历史 160 个 run 直接跑。

**完成判据**：对 17 个 failed run 逐条出标签并人工核对；规则命中率与误报率可复算；输出失败频率分布表（"F5 ×N、F8 ×N"），而不是只有 `failed` 一个词。

### 3.3 L · 闭环自迭代

**核心原则：判据必须比改进者活得更久。**

若被测系统可以修改判据、用例或门禁，它会（不是恶意，而是朝指标梯度下降）。届时所有数字失去含义，且无法区分"变好"与"判据漂移"。因此闭环是**单向门**：

```
历史 run + 用例
  → 归因器出失败分布
  → agent 生成提案（补丁 + 假设 + 预期指标变化 + 复现命令）
  → 人审 / CI
  → 门禁复测
  → 指标曲线入库
```

| 护栏 | 做法 | 防的是 |
|---|---|---|
| 判据冻结 | `eval/cases/`、`graders/` 只由人改，agent 只读 | 奖励黑客 |
| 提案不落地 | agent 只写 `proposals/*.patch`，不改源码 | 静默破坏 |
| 三绿门禁 | (a) 冻结用例集 (b) 现有全量单测 (c) 历史工具回放 | 回归 |
| 翻转清单必填 | 任何用例翻绿 / 翻红都写清取舍 | 悄悄牺牲 A 换 B |
| 目标是最多频的失败类 | 不打分；消掉一个 F6 类无法被刷 | 指标游戏 |
| 成本帽 | 每轮迭代的模型预算上限 | 评测本身烧钱 |

**工具级回放是这个方案里性价比最高的一步**：库里已有 390 条历史 `tool_calls.arguments` 与 `result`。把历史入参灌进新实现、diff 结果 —— **完全确定性、零模型成本、秒级完成**，能挡住多数工具语义的静默回归。它比全量模型回放便宜一个数量级，应早于全量回放先做。

**完成判据**：一条提案从生成到合并全程可追溯（补丁、复现命令、改动前后的指标与翻转清单同时存在）；三绿门禁任一红时禁止合并；历史工具回放能定位到具体受影响的调用。

## 4. 落地形态

```
eval/
  spans.py        # 五表规约成统一 Span 树（只读）
  attribute.py    # F1–F10 规则，纯函数
  cases/          # 冻结用例：case.yaml + fixture.tar.zst(sha256) + graders/
  record.py       # 从 model_calls 录 cassette
  replay.py       # 工具回放（必然）与模型回放（P4）
  gate.py         # 三绿门禁
  report.py       # 聚合、区间、翻转清单
  proposals/      # agent 产出，人合并
```

四条硬规矩：

1. **独立 schema 或独立库。** 业务库已到 `0028`，评测表混入会让迁移互相打架；坏用例也不该污染业务数据。
2. **判据只读数据库事实与磁盘快照，绝不读模型回答正文。** C5 的教训（审批生效而模型自述未提示）在测评里会以"模型宣称测试通过"的形式重现，且更难发现。
3. **fixture 用 `tar + sha256`，不 pin git ref。** ref 会随仓库演进漂移，历史数字将不可解释。
4. **确定性判据优先；LLM judge 只能补充，不能单独否决。**

## 5. 阶段与完成判据

| 阶段 | 内容 | 排序理由 | 完成判据 |
|---|---|---|---|
| **P0** | `spans.py` 统一视图（只读） | 后续一切的前提 | 一条命令打印任一次 run 的完整时间线 |
| **P1** | `attribute.py`，先跑历史 160 个 run | **零模型成本**，两周可用 | 失败分布表；17 个 failed 有人工核对记录 |
| **P2** | 工具级回放（390 条历史入参） | 零成本、挡静默回归 | 改工具实现后能 diff 出受影响的历史调用 |
| **P3** | 冻结用例集 20–30 个（建站 / 修项目 / 边界 / 负向） | 历史语料不是硬任务，能力测评必须有专门用例 | 同一用例重跑两次结论可比 |
| **P4** | 模型 cassette 回放 | 开始能不花钱复现整条轨迹 | 固定模型响应下工具链行为可复现 |
| **P5** | Trace UI：时间瀑布 + 上下文 diff | 人的诊断效率是循环里最贵的一环 | 一屏回答"这次哪里坏了" |
| **P6** | 提案流水线与三绿门禁 | 最后才闭环 | 见 3.3 完成判据 |

阶段之间不跳。P1 的价值在于**在没有任何用例集的情况下就能产出可用结论**，这是排序的关键理由。

## 6. 明确不做或不测

| 项 | 原因 |
|---|---|
| 回答质量自动评分 | 无可靠判据，只能人工抽检；不假装可自动化 |
| 真实浏览器点按路径 | 需独立自动化子工程；当前本就未重跑 |
| 交互式长任务的确定性复现 | `process` 流式交互与跨 run 恢复难复现 |
| 多轮追问的连贯性 | 需要多轮用例，成本高，留待 P6 之后 |
| 在指标上做跨模型大排行 | 用例须模型无关，pin 的是 fixture 哈希 |

宁可写清"未覆盖"，也不为凑齐报表去测。
