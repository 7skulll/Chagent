# 本地 Agent 三版开发设计

状态：讨论稿  
更新日期：2026-10-27

| 版本 | 开发重点 | 完成后的能力 |
|---|---|---|
| V1 | 跑通本地网页 Agent，建立基础上下文与显式记忆 | 能通过网页完成本地任务，保存对话，继续长对话 |
| V2 | 完善记忆生命周期，建立评测系统 | 能跨会话找回、纠正和管理记忆，比较不同策略的效果 |
| V3 | 根据评测优化上下文、记忆和长任务续接 | 对已知失败持续改进，并能解释收益与成本 |

## V1：跑通本地网页 Agent

### 1. 本版目标

先交付一个可以日常试用的版本：用户在网页发起任务，Agent 调用模型和本地工具完成工作；对话较长时可以压缩上下文；明确要求记住的信息能在之后的会话中使用。

本版优先采用固定规则，记录足够的运行信息，为 V2 的评测和改进提供依据。

### 2. 开发内容

| 开发项 | 本版实现 |
|---|---|
| 网页对话 | 会话列表、工作区选择、发送消息、流式回答、取消运行 |
| 执行循环 | 模型请求、工具执行、结果回填、继续或结束 |
| 基础工具 | 读取、编辑、写入文件与执行 Shell 命令 |
| 上下文 | token 预算、近期完整历史、任务状态、阶段摘要 |
| 显式记忆 | 用户要求保存时写入，支持检索、查看、编辑和删除 |
| 运行记录 | 请求上下文、工具结果、状态、token 与耗时 |
| 本地存储 | PostgreSQL 保存结构化数据，本地文件保存附件和长输出 |

### 3. 实现顺序

#### 3.1 跑通最小执行链路

```text
网页提交消息
  → 保存消息并创建运行
  → 构建上下文
  → 请求模型
  → 执行工具并保存结果
  → 构建下一次请求，直到完成
  → 保存最终回答与任务状态
```

先接入一个实际使用的模型供应商，保留模型适配接口。执行循环和工具注册借鉴 nanobot、Pi；运行状态和事件组织借鉴 Codex。

网页通过 HTTP 提交、查询与取消任务，通过 SSE 接收文本和工具进度。后端持有运行状态，页面刷新后重新读取历史和当前状态，不重新发起任务。

默认仅监听本机地址，先支持单用户。单会话最多一个活动运行，全局默认同时运行一个任务。忙碌时新请求得到明确提示，用户可取消后重发。

#### 3.2 建立上下文构建模块

将 ContextBuilder 与 Runner 分开。前者决定本次提供哪些信息，后者负责执行模型和工具循环。

每次请求按以下优先级选择信息，再按模型协议组织消息：

1. 必要指令、项目规则与当前用户输入。
2. 当前任务的目标、约束和未完成事项。
3. 最近的完整交互单元。
4. 覆盖更早历史的阶段摘要。
5. 在剩余预算内补入匹配记忆和必要工具片段。

```text
可用输入预算 = 模型上下文上限 - 输出预留 - 安全余量
```

预算包含指令、工具定义、消息、记忆和附件。优先使用兼容模型的 token 计数；无法精确计算时保守估算并记录。

以完整交互单元裁剪历史，保留工具调用与结果的配对。长工具输出完整保存到文件，模型只接收必要片段和查阅入口。必要信息本身超预算时，明确报告限制。

为每次请求保存 ContextSnapshot：选入信息、来源、估算 token、裁剪原因，以及最终请求引用。首版用简单数据结构表达，不引入复杂评分器。

#### 3.3 增加任务状态与阶段摘要

先按会话维护一个 TaskState：

```text
目标、用户约束、已完成事项、当前决定、未完成事项、来源引用
```

用户明确提出的约束保留原文引用；模型归纳的进度和决定标注为派生内容。

接近预算时，将较早的完整历史压缩成阶段摘要。摘要至少保留目标、约束、决定、待办和关键证据位置，并记录覆盖范围，避免与原文重复注入。

压缩后仍保留原始历史。摘要失败时保留较小的合法历史窗口；若因此缺少继续任务的必要信息，则停止并报告。

#### 3.4 增加显式长期记忆

只处理用户明确要求保存的信息，例如“记住这个项目使用 pnpm”。保存后在网页展示结果，用户可以编辑和删除。

记忆最小字段：

```text
id, content, kind, scope, scope_id
source_refs, status, created_at, updated_at
```

- kind 先支持偏好和事实。
- scope 支持全局与工作区，默认写入当前工作区。
- status 先支持 active 和 deleted。
- 临时任务进度保存到 TaskState，不写入长期记忆。

检索先过滤范围和状态，再做 PostgreSQL 文本匹配，限制返回条数和 token。中文先提供子串或字符片段匹配回退，验证实际召回效果。V1 不引入 embedding 或独立检索服务。

当前明确指令优先于旧记忆。用户编辑或删除后，旧内容立即退出检索。记忆删除与会话历史删除分别处理，在界面说明其影响。

#### 3.5 接入网页并完成本地持久化

模块随开发建立：

```text
网页 → API → Runner
               ├── ContextBuilder
               ├── MemoryStore
               ├── 模型与工具适配
               └── TraceRecorder
                        │
                   PostgreSQL + 本地文件
```

模块放在同一代码仓库、同一后端服务中。通过简单函数或接口连接，不提前拆分多个独立包。

PostgreSQL 先保存以下数据：

| 数据 | 用途 |
|---|---|
| 工作区、会话、消息 | 恢复对话及隔离项目数据 |
| 运行、模型调用、工具调用 | 记录执行状态、用量和结果 |
| 任务状态、摘要、记忆 | 构建后续请求 |
| 上下文快照、运行事件 | 检查请求与恢复网页展示 |

附件、完整长输出和请求正文可保存在本地文件，由数据库引用。文件采用临时写入后原子替换，结构化状态通过事务更新。

网页第一版只做聊天、最小记忆列表和运行详情。运行详情能够回答“这次模型看到了什么”。

### 4. 本版必要约束

- 工具有参数校验、输出上限、超时与明确错误结果，默认串行执行。
- 文件工具限制在授权工作区。Shell 采用隔离后端或用户明确启用的宿主执行模式；工作目录检查不等同于进程沙箱。
- 密钥由后端持有，不写入记忆或普通日志。
- 完整上下文快照保存在本机，提供保留期限和清理入口。
- 本地运行可以调用云端或本地模型；选择云端时，所选上下文会发送给模型服务。

### 5. 交付物与验收

交付可启动的本地服务、网页聊天界面、数据库初始化与迁移、基础上下文和记忆模块，以及运行检查视图。

验收场景：

- 通过网页完成“读取文件 → 修改内容 → 执行验证 → 汇报结果”。
- 刷新页面后可查看原有会话和活动运行。
- 对话压缩后能继续任务，保留用户约束和未完成事项。
- 明确保存的项目事实可以在同工作区新会话中找回。
- 其他工作区的专属记忆不混入，删除的记忆不再使用。
- 重启后保留历史，并明确标记中断任务。
- 每次模型调用均可检查上下文组成、来源和用量。

本版采用人工验收与必要的功能检查，保留可用于后续评测的固定样例和轨迹。正式 EvalRunner、策略对比和评测报告在 V2 开发。

### 6. 本版暂不开发

自动记忆抽取、后台整理、语义向量检索、运行中追加指令、自动续跑、会话分支，以及多 Agent 编排。

## V2：完善记忆，建立评测系统

### 1. 本版目标

在 V1 可以实际使用后，补齐跨会话记忆的写入、召回、纠错与失效机制，同时建立评测系统，能够判断一种策略是否比另一种更有效、成本是否合理。

先建立 V1 的评测基线，再修改记忆策略，保留前后对照。

### 2. 开发内容

| 开发项 | 本版新增 |
|---|---|
| 评测执行器 | 隔离运行用例，复用真实 Agent 内核 |
| 评测数据 | 基础任务、长上下文、记忆召回、纠正与隔离场景 |
| 结果比较 | 固定配置、分组指标、成本、失败轨迹 |
| 检索流程 | 查询构建、候选排序、去重与预算选择 |
| 记忆生命周期 | 候选、激活、替代、过期和删除 |
| 输入控制 | 当前运行追加指令与后续任务排队 |
| 网页 | 候选记忆处理、修订记录和评测结果查看 |

### 3. 实现顺序

#### 3.1 先建立评测执行器

EvalRunner 使用独立命令行入口，复用 Runner、ContextBuilder、MemoryStore，不另写一套简化执行循环。

```text
加载用例与实验配置
  → 创建隔离数据库或 schema、临时工作区
  → 写入初始历史、记忆和文件
  → 顺序提交多轮输入
  → 保存上下文快照与工具轨迹
  → 检查回答、文件和记忆状态
  → 输出报告并清理环境
```

禁止访问日常工作区与个人生产记忆，不使用真实发送账号。样例数据、工具环境和后台整理任务均限定在当次实验中。

第一版执行器先支持 YAML/JSON 用例、规则评分与本地报告。网页先读取报告，暂不实现网页任务调度器。

用例格式示意：

```yaml
id: memory-correction-001
category: memory_correction
workspace_fixture: fixtures/project-a
initial_memories:
  - content: "项目使用 npm 管理依赖"
    scope: workspace
steps:
  - new_session: true
  - user: "项目已改用 pnpm，请更新这条记忆。"
  - new_session: true
  - user: "这个项目安装依赖应该用哪个命令？"
checks:
  answer_contains: ["pnpm install"]
  forbidden_commands: ["npm install"]
  memory_expectations:
    active_contains: ["pnpm"]
    superseded_contains: ["npm"]
```

答案关键词仅作基础断言。关键任务同时检查实际工具行为、文件结果和数据库状态，避免回答正确但行为错误仍被判定成功。

#### 3.2 建立数据集与 V1 基线

先整理不少于 30 个手工审阅用例，覆盖：

| 场景 | 需要检验的行为 |
|---|---|
| 基础本地任务 | 文件操作与验证能够完成 |
| 早期约束 | 长对话后仍遵守最初要求 |
| 摘要续接 | 压缩后能继续待办，不重复已完成操作 |
| 显式记忆召回 | 新会话找回相关事实，支持中文不同表达 |
| 记忆纠正与失效 | 采用新要求，排除旧记录 |
| 项目隔离 | 排除其他工作区的记忆 |
| 干扰与错误材料 | 无关信息不挤占必要内容，材料中的指令不升级为用户要求 |

对 V1 的上下文模块提供三组策略配置：

- B0：只使用近期合法历史窗口。
- B1：近期历史加阶段摘要。
- B2：B1 加显式记忆检索。

使用同一模型、工具设置与输出预算，比较实际效果和输入成本。分别报告短任务、长任务和跨会话任务，保留逐例结果。

#### 3.3 定义指标和实验记录

| 指标 | 检查方式 |
|---|---|
| 任务成功率 | 必需检查项全部通过 |
| 约束遵守率 | 对照预先标注的要求逐项检查 |
| 记忆召回 | 相关记录 Recall@k，适用时补充 Precision@k |
| 错误记忆使用率 | 含错误、过期或越界记忆时，是否在输出或操作中采用 |
| 摘要完整性 | 必需事实是否正确保留 |
| 成本 | 前台、摘要、记忆整理的总 token 与调用次数 |
| 延迟 | 检索、上下文构建、首段输出、任务完成耗时 |

先采用规则评分，主观质量再补充模型评分与人工抽查。模型评分使用明确标准，并将被测回答作为数据处理。

保存代码与用例版本、策略配置、模型标识、生成参数和工具环境。数据集分开发集与冻结验收集，后者不参与调参或记忆学习。关键对比重复运行，报告样本量和波动。

组件测试、模拟工具任务和真实本地任务分开报告，不合并为单一分数。

#### 3.4 改进检索与上下文选择

在基线完成后，新增以下流程：

```text
当前输入 + TaskState
  → 构建检索查询
  → 过滤工作区、状态与时效
  → 候选召回
  → 简单排序与去重
  → 按 token 预算选入
```

查询先使用规则拼接，排序先使用匹配程度、范围和时效等少量可解释信号。ContextSnapshot 增加选入、排除和截断原因。

摘要信息不足时，可以按来源查阅原始片段。保留文本检索；只有评测表明语义召回是主要瓶颈时，才增加本地 embedding 索引，并单独验证收益。

#### 3.5 增加记忆生命周期

```text
原始证据 → 候选记忆 → 去重与冲突检查 → 激活
                                      ├── 修订并替代旧版本
                                      ├── 过期或失效
                                      └── 删除并禁止同源重新提取
```

扩展记忆字段：

```text
origin, revision, supersedes_id, expires_at
status: candidate / active / superseded / expired / deleted
```

- 任务结束后可以异步抽取候选，避免每轮对话额外调用模型。
- 模型推断的事实和经验默认待审，用户确认后激活。
- 用户明确保存或纠正的信息可以直接更新，保留来源与修订关系。
- 同义重复可以合并；不同条件和范围的事实分别保留。
- 不以“更新时间较新”作为所有冲突的解决方式；无法判断时呈现冲突，必要时澄清。
- 删除时记录禁止同源重新提取的标记，避免后台抽取重新生成。

#### 3.6 补充运行交互和网页检查

- 支持 steer：将追加指令在当前完整工具批次后的安全边界纳入下一次请求。
- 支持 follow-up：当前运行完成后再启动后续请求。
- 明确当前请求与排队请求，取消时分别处理。
- 记忆页展示来源、范围、状态和修订记录，支持处理候选。
- 评测页对比配置、分组指标和失败轨迹，能够定位到某次请求的上下文。

### 4. 交付物与验收

交付 EvalRunner、首批数据集、B0/B1/B2 基线报告、记忆生命周期模块，以及网页记忆与评测视图。

验收条件：

- 一条命令可运行评测，并生成可追溯的配置和结果报告。
- 每个失败能定位到具体步骤、上下文、记忆与工具结果。
- 跨会话能够找回相关项目知识，排除其他工作区的专属记忆。
- 用户纠正后旧记录退出检索；删除后不会被同源抽取重新激活。
- 候选推断不会未经规则允许升级为长期事实。
- 在冻结验收集上确认目标场景的收益，基础任务和关键约束无未解释的退化。
- 新机制是否默认启用，依据重复实验与成本预算决定，不预设任意提升比例。

### 5. 本版暂不开发

通用动态策略 Agent、无限后台反思、完整任务图、自动恢复所有工具、多 Agent 协作，以及分布式评测调度。

## V3：按评测结果优化与增强续接

### 1. 本版目标

从 V2 已经记录的失败中选择问题，逐项改善上下文选择、长期记忆和长任务续接。每次改进都要有明确的失败案例、对照实验与成本记录。

本版列出的机制是候选开发项。只有对应问题在使用或评测中成立时才实现。

### 2. 开发内容

| 观察到的问题 | 对应开发项 |
|---|---|
| 关键约束被摘要遗漏 | 约束保留规则与摘要回归用例 |
| 摘要缺少可验证细节 | 按需查阅原文与来源有效性检查 |
| 记忆增多后无关信息干扰 | 排序、预算、时效与停用规则 |
| 不同任务需要的信息比例不同 | 少量任务类型的上下文配额 |
| 长任务中断后难以继续 | 阶段检查点与有限恢复 |
| 优化效果难以归因 | 消融实验、失败回放与持续回归 |

### 3. 实现顺序

#### 3.1 建立失败到改进的闭环

```text
收集真实失败轨迹
  → 人工审阅与脱敏
  → 转成可复现用例
  → 定位信息选择或记忆问题
  → 修改单个策略
  → 对照运行与消融实验
  → 达标后启用，否则回退
```

真实使用数据默认保留在本机，加入回归集前需要审阅。固定模型和工具条件比较上下文策略，模型变化单独作为实验变量。

#### 3.2 优化上下文分配

先支持少量可解释策略，例如短问答、文件任务、长任务续接，分别设置历史、原文、摘要和记忆配额。

- 约束丢失时加强原文约束保留。
- 证据不足时按需取回原始片段。
- 记忆干扰时减少候选或调整排序。
- 保持稳定指令与工具定义顺序，缓存收益以实际用量验证。

增加上下文选择回放：同一份候选信息分别交给不同策略，比较选入内容、遗漏信息和预算。此模式用于定位组件问题，不能代替端到端任务重跑。

#### 3.3 增加经过验证的经验记忆

- 从重复成功的任务中提取 procedure 候选，保存适用条件和验证证据。
- 先通过回归任务，再决定是否激活。
- 排序结合范围、时效、来源与反馈，不仅依赖使用次数。
- 项目文件派生知识记录源文件版本或内容摘要，变化后标记待更新。
- 低价值记忆先停止自动注入，保留手动查阅；不因低频自动删除用户明确保存的信息。

后台整理按空闲或阈值触发，设置单次与每日预算。先处理有限候选，评测中统计整理成本和错误写入。

#### 3.4 增加长任务检查点与有限恢复

阶段检查点保存：

```text
目标、约束、关键证据、已完成操作、待办、结果未知的操作
```

恢复前分别判断：

| 操作状态 | 处理方式 |
|---|---|
| 已确认完成 | 使用已有结果，避免重复执行 |
| 尚未执行 | 重新调度前检查当前任务和权限 |
| 失败 | 按有限重试策略处理 |
| 结果未知 | 先查询或验证，不能直接假设未执行 |

只读或可证明幂等的工具可以自动恢复。文件修改或外部副作用需要验证执行结果、使用幂等键，或由用户确认后继续。保存检查点本身不保证操作只发生一次。

自动重试有次数与预算上限，重复失败进入可检查的暂停状态。恢复任务状态与回滚工作区文件分别设计。

#### 3.5 建立持续回归

- 日常运行快速、无真实外部副作用的用例集，完整任务集按需执行。
- 对摘要、检索、重排和后台整理分别做消融，避免同时改动造成归因困难。
- 模型评分保留人工抽查，并报告重复运行波动。
- 增加中断恢复、记忆规模增长、源文件变化等场景。
- 分别观察检索延迟、上下文 token、任务成功率和后台成本。

### 4. 交付物与验收

交付经实验验证的策略改进、经验记忆候选流程、长任务检查点、有限恢复，以及持续回归报告。

验收条件：

- 每项默认启用的优化都有明确目标用例、对照结果和新增成本。
- 能解释一条记忆的来源、修订过程、适用范围及选入原因。
- 长任务中断后可恢复必要状态，对结果未知的操作不会盲目重试。
- 记忆与历史规模增长时，各项延迟和用量处于已经测量的预算内。
- 无收益或存在退化的策略可关闭，能够回退至 V1/V2 路径。

### 5. 本版暂不预设

不提前承诺具体压缩率、召回提升或 token 降幅；不为尚未出现的问题增加通用规划器、复杂多级记忆或新的基础设施。下一步开发由评测中最重要的失败决定。
