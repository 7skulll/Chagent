# 本地网页 Agent 设计文档

状态：讨论稿，等待产品与架构审阅  
日期：2026-10-27  
项目暂称：Chagent

## 1. 产品定位

Chagent 是一个运行在用户电脑上、通过浏览器对话的个人 Agent。它能够围绕本地工作目录理解任务、调用工具、生成结果，并在较长任务和多次会话中保留必要的信息。

核心投入放在两个方面：

1. **上下文与记忆**：在有限 token 预算内，为模型提供准确、相关、及时的信息；持续保留值得复用的事实、偏好和经验。
2. **评测系统**：用可复现的任务验证上下文与记忆设计，衡量任务效果、成本以及失败原因。

执行循环、模型接入、工具和网页通信采用成熟的可借鉴的实现。系统先服务单用户、单机使用。

本文将产品分成三个递进版本：V1 建立可用闭环和评测基线，V2 改善跨会话记忆，V3 根据评测优化信息选择和长任务能力。每一版应可以独立使用；后续机制通过评测后再纳入默认行为。

## 2. 设计原则

| 原则 | 对实现的要求 |
|---|---|
| 简单优先 | 单后端进程、一个postgresql数据库、本地文件目录 |
| 上下文可检查 | 能查看一次模型请求实际使用的信息及其来源 |
| 原始记录可追溯 | 摘要和记忆保留来源引用；压缩不删除原始记录 |
| 记忆可以纠正 | 支持查看、更新、失效和删除；旧记忆不能覆盖当前明确要求 |
| 评测伴随开发 | 从 V2建立数据集、基线和失败案例，策略变化必须能够比较 |
| 成本必须可见 | 同时报告效果、token、耗时和工具调用，避免通过无限增加上下文提高得分 |
| 边界明确 | 用户指令、项目规则、检索材料、工具输出和推断性记忆标注来源与用途 |

### 2.1 三个版本共用的范围

- 浏览器聊天、本地文件访问、受控的命令执行。
- 多个会话，每个会话同一时间最多一个活动运行。
- 会话绑定一个工作区；不同工作区的项目记忆默认隔离。
- 核心服务和数据存储位于本机，模型可以使用云端 API 或本地服务。
- 默认仅监听本机地址。云端模型调用会发送所选上下文，本地部署不等于推理数据完全不出机。

### 2.2 暂缓的功能

多用户、团队权限、远程公开访问、多渠道消息入口、插件市场、复杂多 Agent 编排，以及分布式任务调度均不在本轮目标中。

## 3. 总体架构

```text
浏览器
  ├── 聊天与会话
  ├── 运行详情与上下文检查
  ├── 记忆管理
  └── 评测结果（V1 可先通过本地报告查看）
       │ HTTP：提交、查询、取消
       │ SSE：文本增量、工具进度、状态变化
       ▼
本地后端
  ├── API：网页接口与事件订阅
  ├── Runner：运行状态、模型调用、工具循环
  ├── ContextBuilder：选择、组装和裁剪上下文
  ├── MemoryStore：检索、写入、更新和失效
  ├── TraceRecorder：请求快照、事件与用量
  └── Adapters：模型、文件、Shell、Skills
       │
       ├── 会话、消息、记忆、运行和评测元数据
       └── 本地文件：附件、长工具输出、请求快照与评测报告

EvalRunner（独立命令行入口）
  └── 复用 Runner、ContextBuilder、MemoryStore
      使用隔离数据库、工作目录、工具环境和模型配置
```

模块表示职责边界，初期均放在同一代码仓库，不拆微服务。评测入口可以启动独立进程执行用例。

建议初期使用 Python 后端与浏览器前端，便于处理数据、工具和评测；网页是否引入 React 以实际交互复杂度决定。该技术选型属于提案，不是三个版本的前置约束，不以框架数量作为进度目标。

### 3.1 核心对象

| 对象 | 含义 |
|---|---|
| Workspace | 本地工作区与项目记忆边界 |
| Session | 一个持续对话，属于一个工作区 |
| Run | 一次用户请求及其引发的多轮模型、工具活动 |
| ModelCall | 一次实际模型请求，包含上下文快照和用量 |
| ToolCall | 一次工具请求与结果，关联模型请求与运行 |
| TaskState | 当前会话的目标、约束、决定、进度和未完成事项 |
| Memory | 可跨运行使用的信息，包含范围、来源与生命周期 |
| ContextSnapshot | 某次模型请求的信息选择结果及预算记录 |
| EvalCase / EvalRun | 评测用例与某一配置下的执行结果 |

TaskState 在 V1 按会话维护，允许一个会话内连续推进同一任务。切换到无关目标时创建新会话，暂不实现通用任务图。



## 4. 上下文与记忆的统一模型

### 4.1 三类信息分别保存

| 类型 | 解决的问题 | 保存方式 |
|---|---|---|
| 原始记录 | 实际说过什么、执行过什么 | 消息、模型请求、工具调用及原始结果 |
| 任务状态与摘要 | 当前任务如何继续 | 结构化 TaskState 和关联来源的阶段摘要 |
| 长期记忆 | 未来任务可能需要知道什么 | 带作用范围和来源的独立 Memory |

摘要压缩过去的过程；任务状态描述现在的任务；长期记忆供未来按需使用。三者可以引用同一条证据，但分别拥有自己的更新规则。

### 4.2 上下文条目

每个候选条目使用轻量的 ContextItem 表示：

```text
id, kind, content_or_artifact_ref
source_refs, scope, trust_origin
estimated_tokens, priority, selection_reason
```

kind 可取 instruction、task_state、recent_message、summary、memory、tool_result。trust_origin 标识用户输入、受信配置、外部材料或模型推断；它是数据来源标识，不是模型自报的可信分数。

ContextBuilder 的输出包含有序消息和选择清单。选入、截断、未选入的信息应有可解释的原因，例如“当前任务必需”“超出预算”“属于其他项目”。

### 4.3 token 预算

```text
可用输入预算 = 模型上下文上限 - 输出预留 - 安全余量
```

预算计算同时包含系统指令、工具定义、消息、记忆与附件开销。优先使用供应商兼容的计数方式；无法精确计算时使用保守估算并标注。

优先保留当前输入、必要指令、当前约束及合法的工具调用/结果配对。按相关性和优先级填充其他内容。长输出先保存完整文件，再返回有边界的片段和查阅入口。

不按单条消息机械截断历史，以免留下孤立的工具结果或不完整的调用。必要信息本身超预算时，要求缩小输入或明确报告限制；不静默删除用户约束。

### 4.4 记忆记录

```text
id, kind, scope, scope_id
content, source_refs, origin
status, revision, supersedes_id
created_at, updated_at, expires_at
```

- kind：preference、fact、procedure。
- scope：global 或 workspace；具体任务的临时信息留在 TaskState。
- origin：explicit_user 或 inferred。
- status：candidate、active、superseded、expired、deleted。
- source_refs：消息、工具结果或文件位置；来源变化后不能假定内容仍然成立。

V1 只要求实现当版用到的字段和状态，其余随版本演进迁移。

### 4.5 冲突与删除

当前明确指令优先于检索到的旧记忆；用户明确纠正优先于旧的模型推断。不同范围或条件下的事实可以共存，不能仅根据更新时间强行合并。

删除后，记忆不再被检索。删除某条记忆不会自动抹除原始会话；界面必须说明差异。V2 增加基于来源的禁止重新提取标记，避免被删除的记忆在后台整理时重新出现。

## 5. V1：建立可用闭环与可靠基线

### 5.1 目标

用户可以通过网页操作本地 Agent，完成需要读取、修改文件和执行命令的任务；长对话可以通过摘要继续；明确要求保存的信息能跨会话找回。每次请求均可检查，并能运行第一批评测。

### 5.2 网页与基础能力

- 会话列表、工作区选择、消息发送、流式回答、取消运行。
- 文件读取、编辑、写入与 Shell 工具；每个工具有参数校验、输出上限和超时。
- 展示工具调用及完成、失败、取消状态。
- 刷新后通过历史和运行状态恢复页面。SSE 事件携带序号，重新订阅可补取保留范围内的事件；超出范围时重新读取快照。
- 最小记忆列表：查看、编辑、删除。
- 运行详情：查看上下文组成、来源、估算 token 与实际用量（如供应商返回）。

服务端持有密钥，网页不接收明文密钥。文件工具限定在会话授权工作区。Shell 必须有明确的执行模式：提供隔离后端，或让用户在设置中明确启用宿主执行并展示访问范围；工作目录检查不被描述为进程沙箱。

### 5.3 上下文策略

采用固定规则构建：

1. 基础指令与必要项目规则。
2. 当前用户输入与任务状态。
3. 最近完整交互单元。
4. 必要的历史阶段摘要。
5. 在剩余预算内加入匹配记忆与相关工具片段。

上述列表描述优先级，最终按模型协议组织消息。摘要覆盖哪些历史必须有边界标识，避免摘要和原文重复注入。

接近输入预算时，对较早的完整交互生成结构化摘要，至少包含目标、约束、决定、已完成事项、未完成事项、关键路径和证据引用。原始记录保留。摘要失败时采用更小的合法历史窗口；若这样会丢失关键任务信息，则停止并报告。

TaskState 中用户明确提出的约束保留原文引用；模型生成的进度和决定标注为派生内容。压缩时不能悄悄改写这些约束。

### 5.4 记忆策略

- 只在用户明确要求“记住”时写入长期记忆；用户可在界面确认和修订内容。
- 默认写入当前工作区；全局偏好需要明确范围。
- 使用 SQLite 全文索引与简单文本匹配。为中文提供基础字符片段或子串匹配回退，用中文用例验证实际召回能力。
- 检索先按范围和状态过滤，再匹配内容，返回少量结果，并受 token 预算约束。
- 凭证与密钥不进入记忆；提供“本次内容不写入长期记忆”的控制。

V1 不自动抽取长期记忆，不引入 embedding，不实现后台 Dream。

### 5.5 评测范围

建立建议不少于 30 个手工审阅用例，覆盖基础工具任务、早期约束保留、摘要续接、显式记忆召回、项目隔离及用户纠正。

为上下文策略提供统一配置入口，对比：

- B0：只使用近期合法历史窗口。
- B1：近期历史加阶段摘要。
- B2：B1 加显式长期记忆检索。

三组使用同一模型、输出预算和工具设置，同时记录实际输入成本。短任务和长任务分别报告，避免总体均值掩盖退化。

### 5.6 验收

- 网页可完成“读取文件 → 修改内容 → 执行验证 → 汇报结果”的完整任务。
- 重启后会话和记忆可恢复；中断运行可识别，不自动重复执行结果未知的工具调用。
- 每次模型请求能定位到上下文快照和来源。
- 工具配对、工作区隔离、已删除记忆排除等确定性检查全部通过。
- 可通过一条命令运行评测并生成配置、分组结果、成本与失败案例报告。
- 获得 B0/B1/B2 的真实基线，尚不承诺任意提升比例。

## 6. V2：改善跨会话记忆和信息召回

### 6.1 目标

减少用户重复交代背景的次数，改善长对话和跨会话任务，同时让记忆写入、冲突和失效可控。

### 6.2 上下文改进

- 根据当前输入、TaskState 和尚未解决的问题构建检索查询。
- 查询生成先使用规则拼接，只有评测证明有收益时才增加模型改写。
- 采用“范围过滤 → 候选召回 → 简单排序 → 去重 → 预算选择”的流程。
- 支持按来源引用取回原始片段，避免摘要信息不足时继续猜测。
- 记录记忆被选入与对应执行结果，但不把一次任务成功直接归因为该条记忆有效。
- 支持运行中追加指令和后续任务队列；在完整工具批次后的安全边界纳入新输入。

### 6.3 记忆生命周期

```text
原始证据 → 候选记忆 → 去重与冲突检查 → 激活
                                      ├── 更新并替代旧版本
                                      ├── 到期或失效
                                      └── 删除并禁止同源重新提取
```

- 任务结束后可异步抽取候选，避免每轮对话调用额外模型。
- 模型推断的事实和经验默认进入待审列表；用户确认后激活。
- 明确的用户偏好与纠正可直接更新，但必须保留来源和修订记录。
- 同义重复可合并；条件不同的记录分别保留。
- 遇到冲突时优先采用可验证的直接证据。无法消解时呈现冲突，必要时向用户澄清。
- 全局偏好和工作区知识分别检索，跨工作区读取需要明确选择。

全文检索仍然保留。仅当语义召回失败在评测中成为主要问题时，增加本地 embedding 索引，并与原方案做消融比较。

### 6.4 评测与界面

- 用例扩展到跨会话序列：学习信息、结束会话、再次提问、纠正、过期和删除。
- 增加中文同义表达、无关干扰、错误候选和来源冲突场景。
- 提供网页评测页，对比实验配置、分组分数、成本与执行轨迹。
- 支持对单个失败案例重跑，固定其初始记忆与工作区。
- 在相同上下文预算下比较召回策略；另外报告效果与成本的折中。

### 6.5 验收

- 新会话可找回同工作区的相关记忆，其他工作区的专属知识不会混入。
- 用户纠正后旧记录停止参与检索；删除后后台整理不会从同一来源重新生成。
- 候选推断不会未经规则允许直接升级为长期事实。
- 在冻结评测集上，相比 V1 改善目标场景；基础任务与关键约束场景无未解释的退化。
- 只有提升被重复运行支持、成本处于约定预算内的机制才默认启用。

## 7. V3：用评测驱动上下文优化与长任务能力

### 7.1 目标

针对已经观察到的失败，优化信息选择与长任务续接，使系统在任务变长、记忆增多时仍然有效且成本可控。

### 7.2 上下文优化

- 从固定预算分配升级为少量可解释策略：短问答、文件操作、长任务续接分别采用不同配额。
- 根据实际失败类型调整摘要和原文比例，例如约束丢失时加强约束保留，证据不足时增加原文查阅。
- 对长任务保存阶段检查点：目标、约束、证据、已完成操作、待办和结果未知的操作。
- 保留稳定的指令与工具定义顺序，减少无谓的上下文变化；缓存收益以实际模型用量为准。
- 提供上下文选择回放，比较“为何旧策略遗漏、为何新策略选入”，无需先真实重跑所有工具。

“动态”不代表再加入一个通用决策 Agent。优先使用少量规则、阈值和配置，机制数量由评测收益约束。

### 7.3 长期记忆改进

- 只有经过验证的重复成功流程才能进入 procedure 候选，记录适用条件与验证依据。
- 采用范围、时效、来源与使用反馈排序；不单纯以调用次数强化记忆。
- 对项目文件派生知识记录文件版本或内容摘要，源文件变化后标记待更新。
- 后台整理按空闲或阈值触发，设置单次与每日预算；只处理有限候选，不做无限递归反思。
- 对低价值记忆先停止自动注入，保留用户可查阅记录；不因低频而自动删除用户明确保存的信息。

### 7.4 有限的执行恢复

- 对只读或能够证明幂等的工具，允许从检查点恢复。
- 对修改文件或外部副作用，必须验证执行结果、使用幂等键，或交由用户确认后继续。
- 明确表示“未执行、已完成、失败、结果未知”，不把 checkpoint 等同于 exactly-once 保证。
- 自动重试有次数与预算上限，重复失败进入可检查的暂停状态。

### 7.5 持续评测

- 将人工审阅过的真实失败轨迹脱敏后转换为回归用例；默认不直接上传个人使用数据。
- 固定模型与工具条件比较上下文策略；模型变化单独作为实验变量。
- 使用消融实验判断摘要、记忆检索、重排和后台整理分别贡献了什么。
- 对模型评分校准并保留人工抽查，报告重复运行的波动。
- 只对快速、无真实外部副作用的用例执行日常回归；完整任务集按需运行。

### 7.6 验收

- 新增策略对明确失败类型产生可重复收益，报告新增成本。
- 可以说明一条长期记忆的证据、修订过程、适用范围和检索依据。
- 长任务中断后能恢复任务状态，对结果未知的操作不会盲目重试。
- 数据和记忆增长时，检索延迟、上下文 token 与后台整理成本仍处于已测量的预算内。
- 缺乏收益的策略可以关闭，回退到 V1/V2 的简单路径。

## 8. 评测系统详细设计

### 8.1 评测对象

| 层级 | 验证问题 | 主要方法 |
|---|---|---|
| 上下文构建 | 必需信息是否入选、预算是否超限、工具配对是否合法 | 固定输入、检查 ContextSnapshot |
| 摘要 | 是否遗漏或扭曲目标、约束、待办与来源 | 结构检查、事实断言、人工抽查 |
| 记忆写入 | 是否记错、记多、范围错误、漏掉明确保存要求 | 对照预期数据库状态 |
| 记忆检索 | 相关记忆是否召回、无关及过期记录是否排除 | 标注集合、排名与干扰检查 |
| 任务效果 | 最终结果是否满足要求、是否采用最新事实 | 文件断言、工具状态、答案规则 |
| 效率与稳定性 | 收益需要多少 token、时间、重试和整理成本 | 用量、耗时与重复运行统计 |

### 8.2 用例格式

用例由 YAML/JSON 描述，文件夹包含所需的工作区样本和期望结果：

```yaml
id: memory-correction-001
category: memory_correction
workspace_fixture: fixtures/project-a
initial_memories:
  - content: "项目使用 npm 管理依赖"
    scope: workspace
    status: active
steps:
  - new_session: true
  - user: "项目已改用 pnpm，请更新这条记忆。"
  - new_session: true
  - user: "这个项目安装依赖应该用哪个命令？"
checks:
  answer_contains: ["pnpm install"]
  forbidden_commands: ["npm install"]
  memory_expectations:
    active_contains: ["pnpm"]
    superseded_contains: ["npm"]
```

以上为目标格式示意，实际执行器随版本逐步支持字段。答案包含判断仅是基础断言；关键场景同时检查真实工具行为和最终文件状态，避免只凭一句正确表述判定成功。

### 8.3 运行方式

```text
加载用例与策略配置
  → 创建独立数据目录与工作区
  → 写入初始历史、记忆和文件
  → 按顺序提交多轮输入
  → 收集请求快照、工具轨迹与最终状态
  → 运行规则检查与必要的模型评分
  → 输出分组指标和失败报告
```

三种运行模式分开报告：

1. **组件模式**：使用固定消息和工具结果，验证选择、压缩、检索等组件。
2. **模拟工具任务模式**：真实模型配合确定性工具环境，比较 Agent 行为。
3. **真实本地任务模式**：在临时工作区运行工具，验证文件和进程结果。

禁止在评测中使用个人生产记忆、真实发送账号或日常工作区。模拟工具与真实工具的分数不得混为同一结果。

### 8.4 指标

- 任务成功率：通过该用例所有必需检查的比例。
- 约束遵守率：逐项检查早期约束和最新纠正。
- 记忆召回：相关记录的 Recall@k；数据适用时补充 Precision@k。
- 错误记忆使用率：在含过期、错误或越界记忆的用例中，输出或动作采用这些信息的比例。
- 摘要完整性：预先标注的必要事实被正确保留的比例。
- 成本：前台与后台总 token、模型调用、工具调用；供应商有可靠价格时再计算费用。
- 延迟：上下文构建、检索、首段输出和任务完成分别测量；样本充分时报告中位数与 P95。
- 恢复正确性：中断后状态是否一致，是否重复执行副作用。

不将所有指标压成单一总分。先检查隔离、约束等必要条件，再比较成功率与成本。

### 8.5 可复现与评分规则

- 保存代码版本、用例版本、策略配置、模型标识、生成参数和工具环境；无法锁定的模型后端变化需要注明。
- 数据集分开发集与冻结验收集；验收集不参与策略调参或记忆写入。
- 固定输入不保证云端模型完全确定，关键比较进行多次运行并报告样本量与波动。
- 规则评分优先；模型评分使用明确 rubric，不向评分器暴露实验名称，且被测回答作为数据处理。
- 记忆学习、摘要生成和后台整理的成本均计入对应方案，避免隐藏成本。
- 每个失败可定位到用例步骤、选入上下文、记忆记录和工具结果。

## 9. 存储、接口与记录

### 9.1 建议数据表

| 表 | 内容 |
|---|---|
| workspaces / sessions | 工作区、会话与关联配置 |
| messages | 原始消息与来源信息 |
| runs / model_calls / tool_calls | 状态、输入输出引用、用量与错误 |
| task_states / summaries | 任务状态及有来源边界的摘要 |
| memories / memory_revisions | 活跃记录与修订关系，V2 补全生命周期 |
| context_snapshots | 选择清单、预算及最终请求引用 |
| run_events | 网页重连所需的有序事件 |
| eval_runs / eval_case_results | 配置、结果及报告引用 |

完整附件、长输出和请求正文可以文件存储，由数据库引用。结构化状态和引用在事务内更新。文件先写临时文件再原子替换，避免记录指向半写入内容；定期清理孤立文件。

诊断日志不默认打印完整 prompt、密钥或工具正文。完整请求快照按会话设置保存在本机，并提供保留期限与清理入口。评测用例必须允许完整追踪，以保证可检查性。

### 9.2 最小 API

```text
POST   /api/sessions
GET    /api/sessions/{id}
POST   /api/sessions/{id}/runs
POST   /api/runs/{id}/cancel
GET    /api/runs/{id}
GET    /api/runs/{id}/events        # SSE，按序号恢复
GET    /api/model-calls/{id}/context
GET    /api/memories
PATCH  /api/memories/{id}
DELETE /api/memories/{id}
```

V2 增加 steer、follow-up、候选记忆处理与评测结果查询接口。V1 评测从命令行运行，避免提前实现网页调度器。

Run 状态建议采用 queued、running、waiting_user、completed、failed、cancelled、interrupted。工具状态单独记录，并允许 unknown，表示副作用是否完成无法确认。

## 11. 开发顺序与审阅重点

### 11.1 开发顺序

1. 定义消息、运行、工具结果和 ContextSnapshot 数据结构，同时写第一批评测样本。
2. 跑通最小 Runner 与工具循环，支持保存、取消及错误报告。
3. 接入网页聊天和 SSE，验证刷新恢复与工作区选择。
4. 实现 V1 上下文预算、阶段摘要、显式记忆和检查视图。
5. 运行 B0/B1/B2，对照失败案例完成 V1 验收。
6. 根据实际失败选择 V2 的下一项改进，每次仅改变少量变量。
7. V2 稳定后，才决定 V3 中哪些机制有必要实现。

### 11.2 当前需要审阅的决定

- 三版的范围是否符合预期，尤其是 V1 是否接受仅显式写入长期记忆。
- 产品主要服务编程任务、通用本地工作，还是两者并重；这将决定第一批工具与评测任务的比例。
- 是否接受 V1 的中断处理：保存状态，由用户发起继续，不自动重放工具。
- 是否采用 Python 后端；若更希望复用 Pi 的 TypeScript 组件，可整体换用 TypeScript，保持本文模块边界。
- 云端模型和本地模型的优先顺序，以及首批实际使用的模型。

这些决定影响实现与用例配比，不阻止先审阅上下文、记忆和评测的主体设计。
